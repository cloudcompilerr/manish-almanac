🔑 The Async Boundary — Most Important Design Decision

The Event Service writes to Kafka and immediately returns HTTP 200 to the client. The counting logic never touches the user's request path. Kafka absorbs the load spike during viral events (10x traffic) and the downstream processors catch up at their own pace.

03 · The Engine Room

Stream Processing: Apache Flink

Flink is where all the intelligence lives. Each Flink worker handles one Kafka partition, meaning it sees all events for a specific subset of entities. No coordination needed.

What Each Flink Worker Does (per 30-second window)

t=0 … t=30s
Step 1 — Deduplication via Bloom Filter
For each incoming event, check Bloom filter keyed by user_id + entity_id + window_id. If present → discard (duplicate view). If absent → add to filter and proceed. Bloom filter uses ~1GB of memory per worker for 100M unique pairs. Accepts 0.1% false positive rate (slight undercounting, never overcounting).
Concurrent
Step 2 — Count-Min Sketch Increment
For each valid event, increment the CMS: hash entity_id with 5 hash functions → increment 5 cells in the local 5×272 grid. Memory: ~6KB regardless of how many entities are seen. This tracks approximate counts without storing a counter per entity.
Concurrent
Step 3 — Local Min-Heap Update
Maintain a min-heap of size K (e.g., K=1000 to be safe). When a count is incremented, query CMS for that entity's current estimate. If estimate > heap root → replace root, re-heapify in O(log K). Heap always holds the local top-1000 entities.
t=30s
Step 4 — Window Flush
Flush the local heap's K items to: (1) Redis ZINCRBY for the sorted set, (2) Cassandra for durable aggregation, (3) Kafka output topic for ClickHouse ingestion. The flush ships at most K=1000 items regardless of how many total events were processed. This is the scalability trick.
Fault recovery
Step 5 — Checkpoint to S3
Flink checkpoints its full state (CMS grid, heap, Bloom filter, Kafka offset) to S3 every 60 seconds. On crash, it resumes from last checkpoint, re-reads from Kafka from the saved offset. "At-least-once" semantics: some events may be double-counted across the checkpoint boundary. Acceptable for Top-K.
# Flink pseudo-logic per window class TopKWindowFunction: def __init__(self, k=1000, epsilon=0.01, delta=0.01): self.cms = CountMinSketch(epsilon, delta) # ~6 KB fixed memory self.heap = MinHeap(k) # O(K) memory self.bloom = BloomFilter(capacity=100_000_000, fp_rate=0.001) self.window_id = current_window() def process(self, event): dedup_key = f"{event.user_id}:{event.entity_id}:{self.window_id}" if self.bloom.contains(dedup_key): return # duplicate, skip self.bloom.add(dedup_key) self.cms.increment(event.entity_id) # O(d) — 5 hash ops estimated_count = self.cms.query(event.entity_id) if self.heap.size < self.heap.k or estimated_count > self.heap.peek_min(): self.heap.upsert(event.entity_id, estimated_count) # O(log K) def on_window_close(self): top_k_items = self.heap.get_all() # max K=1000 items self.flush_to_redis(top_k_items) # ZINCRBY for each self.flush_to_cassandra(top_k_items) # upsert aggregation self.flush_to_kafka_output(top_k_items) # → ClickHouse ingestion self.reset()

05 · Warm Tier · Durable Counts

Cassandra: The Warm Store

Redis is volatile — TTL expires and the data is gone. Cassandra is the durable, queryable store of aggregated counts. It holds 30–90 days of hourly aggregations per entity. It's used to: backfill Redis on restart, power longer-window Top-K queries, and feed ClickHouse for OLAP.

Why Cassandra (not PostgreSQL)?

Architecture Rationale

Write pattern: Flink writes ~50K rows/sec (one row per entity per window flush). Cassandra handles millions of writes/sec with linear horizontal scaling. PostgreSQL would be write-bottlenecked.

Read pattern: "Give me all hourly counts for entity X over the last 30 days" — a partition-local range scan in Cassandra. Very fast when data is co-located by partition key.

No joins needed: Counts are pre-aggregated. No complex relational queries. Cassandra's limited query model is not a constraint here.

06 · Analytics Layer · The OLAP Power

ClickHouse: OLAP for Deep Analytics

Redis answers "what is Top-K right now?" Cassandra answers "what was the count for X in window Y?" ClickHouse answers everything else — historical Top-K, breakdowns by region+device+time, trend analysis, anomaly detection, and business intelligence. This is what turns raw counts into insights.

Why ClickHouse, not Redshift or BigQuery?

ClickHouse is the OLAP choice for high-frequency aggregation workloads. Its columnar MergeTree engine can ingest 500K rows/sec and answer GROUP BY COUNT queries on billions of rows in under 2 seconds. It compresses count columns by 10–20x (integers compress very well column-wise). BigQuery/Redshift are managed and easier to operate but have higher query latency for sub-second needs. For Twitter/YouTube scale, ClickHouse is the answer.

How Data Gets Into ClickHouse

Path 1 — Streaming (preferred)
Kafka → ClickHouse Kafka Engine
ClickHouse has a native Kafka table engine. It consumes from the Flink output topic (topk.aggregated) directly. As Flink flushes every 30s, ClickHouse ingests those aggregated rows in near-real-time. No separate ETL pipeline needed. Latency: 30–60 seconds behind live.
Path 2 — Batch (for raw events)
S3 → ClickHouse S3 Table Function
The raw event Parquet files in S3 can be queried directly via SELECT … FROM s3('s3://bucket/events/…', 'Parquet') or imported nightly for full historical analysis. Used for ML feature extraction, audit reports, and backfilling.

11 · Follow-up Playbook

Every Hard Follow-up, Answered

How does OLAP (ClickHouse) fit with the real-time path — isn't there overlap?+
They serve completely different consumers and query contracts — there is no overlap.

Redis answers: "What are the top 10 videos right now?" — called by the API on every user page load. Latency <1ms. Data freshness: 30–60 seconds. Data depth: only current window, only top-K items. Real-time product feature.

ClickHouse answers: "What was the hourly breakdown of #WorldCup trending by region and device over the past 7 days?" — called by dashboards, analysts, ML pipelines. Latency: 300ms–2s. Data depth: every entity, every hour, every dimension, for years. Analytics and intelligence layer.

The same event stream (Kafka) feeds both. Flink writes aggregated rows to a Kafka output topic. ClickHouse consumes this topic via its Kafka engine. Redis receives ZINCRBY calls. Both are updated within 30–60 seconds, but used for entirely different purposes.
If Redis crashes and restarts, how do you recover the sorted sets?+
Three-layer recovery strategy:

1. Redis persistence (AOF/RDB): Redis can be configured to write an AOF (Append-Only File) or periodic RDB snapshot to disk. On restart, it replays the log or loads the snapshot. Trade-off: AOF adds ~10% write overhead. RDB loses data since last snapshot. For Top-K, RDB every 5 minutes is acceptable.

2. Cassandra backfill: If Redis starts cold (no AOF), the Read API detects a miss and triggers a Cassandra query to rehydrate the sorted set. This is the Cassandra fallback in the read path. Takes 30–60 seconds to warm up fully.

3. Flink re-flush: Flink flushes every 30 seconds anyway. Even without any recovery mechanism, Redis will be fully repopulated within 30 seconds of restarting, as Flink's next window close will write all top-K items. The 30-second gap is acceptable for a trending feature.

In practice: Redis Cluster with replicas (3 primaries + 3 replicas) means a single node failure has zero downtime — the replica is promoted immediately. Only a full cluster failure requires backfill.
How do you handle the "hot key" problem — one viral video getting 100x traffic?+
This is a hot partition problem at both Kafka and Redis levels.

Kafka hot partition: All events for vid_viral land on one partition → one Flink worker is overwhelmed.
Solution: Key salting. Append a random suffix: vid_viral#0 through vid_viral#7. Events are spread across 8 partitions. The Flink aggregator receives 8 partial counts and sums them: final_count = SUM(count_0..7). This requires a second-stage aggregation step (another Flink job or the flush aggregator handles the merge).

Redis hot key: Millions of ZINCRBY calls on topk:video:GLOBAL:1h all hitting one Redis shard.
Solution: Write sharding. Flink writes to topk:video:GLOBAL:1h:shard_{0..7}. A background job (or Lua script) merges these into the canonical topk:video:GLOBAL:1h every 10 seconds. Reads always hit the merged key.

Proactive detection: Monitor Flink worker lag and Redis key write rate. If one key exceeds 50K writes/sec, automatically enable sharding for that key. This is a configuration flag, not a code change.
Why use both Cassandra AND ClickHouse? Isn't that redundant?+
They are optimised for opposite access patterns and cannot substitute each other.

ClickHouse is an analytical database optimised for reading lots of data to answer complex questions. In the simplest terms: Cassandra keeps your system running; ClickHouse makes your data useful.
How would you implement "Top K in sliding window" (not tumbling)?+
Sliding windows are more accurate for "trending now" but costlier.

Flink approach: Define a sliding window of size 1 hour, sliding every 5 minutes. Flink maintains multiple overlapping window states simultaneously. Memory = (window_size / slide_interval) × state_per_window = 12 × heap_memory. CPU cost also 12x compared to tumbling.

Approximate sliding window with weighted decay: Instead of a true sliding window, apply exponential decay to counts:
score = α × new_count + (1 - α) × previous_score
where α is tuned to the desired half-life (e.g., α=0.1 for 1-hour effective window). Flink applies this formula on every flush. The Redis sorted set holds the decayed scores. New content rises fast; old content fades naturally.

ClickHouse complement: For historical sliding windows, ClickHouse's windowFunnel and runningDifference functions can compute sliding window aggregations on demand over historical data — giving you the precise sliding window answer with a few seconds of compute time.
How do you use ClickHouse snapshots to power a "rank history" feature?+
The topk_snapshots table is specifically designed for this.

A background job runs every 30 minutes and reads Redis's ZREVRANGE → inserts the full ranked list into ClickHouse's topk_snapshots table with a timestamp. This creates a time-series of Top-K rankings.

Now you can answer: "When did #WorldCup first enter the Top-10?" → SELECT MIN(snapshot_time) WHERE entity_id='#WorldCup' AND rank <= 10
"How long did vid_abc hold the #1 position?" → Sum the duration of consecutive snapshots where rank=1.
"What was the rank trajectory of vid_abc over the last 7 days?" → SELECT snapshot_time, rank WHERE entity_id='vid_abc' ORDER BY snapshot_time — returns a time series you can graph.

This is a feature that makes the product genuinely useful for content creators ("your video peaked at #3 for 4 hours on Tuesday") and is impossible to derive from Redis alone since Redis only holds current state.
12 · Core Concepts Deep Dive

The mechanics every FAANG interviewer expects you to know

01 Why CMS + Min-Heap Together
What it is
CMS tracks frequency estimates for all items. Min-heap tracks only the top-K candidates — they serve different purposes.

/p>

CMS alone: can answer "how often did item X appear?" but cannot enumerate which items are in the top K — it doesn't store item identities.

Min-heap alone: would require storing exact counts for all items — O(N) memory for N distinct items.

Together: CMS provides O(1) count estimate for any item in O(w×d) memory. Min-heap of size K holds only the K candidates. Total memory: O(w×d + K) — independent of item cardinality.

02 Time Window Strategy
What it is
Top-K is time-sensitive — "trending now" ≠ "most popular ever." Three windowing strategies:

/p>

Tumbling window: fixed 5-minute buckets. Top-K resets every 5 minutes. Simple, but the moment before reset and the moment after give very different results.

Sliding window: rolling last 60 minutes. More accurate sense of "now" but requires maintaining multiple CMS buckets and merging them.

Exponential decay: multiply counts by a decay factor on each time step. Recent events count more than old events. Most accurate "trending now" signal. Used by Twitter/TikTok for trending topics.

03 Partition Strategy for Scale
What it is
At billions of events/sec, a single CMS/heap is a bottleneck. Shard the problem.

/p>

Approach: N parallel Flink tasks, each maintaining a local CMS + min-heap for its partition of the input stream. Kafka partitioning by entity key ensures each item always goes to the same partition (consistent counts).

Merge step: every 5 minutes, merge all N local CMS sketches (O(w×d) per merge) and merge all N min-heaps (O(K×N log K)) to produce the global Top-K.

✓✓ Linear horizontal scaling. 10 partitions → 10x throughput. Merge overhead is negligible because K and w×d are small constants.
04 Hot Item Problem
What it is
In a Top-K system, the top items get disproportionate traffic — the very thing you are measuring causes a feedback loop.

/p>

Showing a trending item → more clicks → increases its count → stays trending → more clicks. The Matthew effect: the rich get richer.

Mitigation: time-decay (older trend scores decay), diversity constraints (cap any one category at 20% of top-K), freshness boost (newer items get a multiplier to break into the top-K even without full momentum).

→These are business logic layered on top of the pure CMS/heap mechanism. The interview answer is to acknowledge the feedback loop and propose a mitigation strategy.
05 Read Path: Tiered Lookup
What it is
Serving the Top-K result requires a tiered lookup strategy for different time horizons.

/p>

Real-time (last 5 min): Redis ZSET pre-populated by Flink every 30 seconds. Single ZREVRANGE command, <1ms.

Recent (last 24h): ClickHouse query on 1-minute pre-aggregated rollup table. <100ms.

Historical (last 30 days): ClickHouse on daily rollup table or Cassandra wide-column store. <500ms.

The API blends these tiers: real-time result for the top strip, historical context for each item's trend line.

06 Exactly-Once Counting
What it is
In a distributed system, events can be processed more than once — duplicate counts corrupt the Top-K.

/p>

Flink checkpointing with Kafka source: Flink checkpoints its consumer offset + CMS state atomically. On recovery from failure, Flink replays from the last checkpoint offset. With Kafka exactly-once transactions, each event is counted exactly once even after restarts.

✓✓ Flink's two-phase commit checkpoint + Kafka transactions = exactly-once semantics end-to-end. The only way to guarantee exact counts in a distributed streaming system.
07 Space Savings vs HashMap
What it is
At what scale does CMS beat a HashMap? Let's calculate.

/p>

1 billion distinct items (all URLs ever visited): HashMap = 1B keys × ~50 bytes avg = 50GB RAM.

CMS at ε=0.001, δ=0.01: w=2718, d=5 → 13,590 cells × 8 bytes = 108KB.

Ratio: 50GB / 108KB ≈ 500,000× more memory for exact counting.

✓✓ This is why CMS is non-negotiable at internet scale. No machine has 50GB of RAM dedicated to a single counter table. CMS solves this with 108KB and a bounded, predictable error.
08 Cassandra Wide-Column for Top-K History
What it is
Storing Top-K results for historical queries: partition by (date, granularity), cluster by rank.

/p>

Schema: CREATE TABLE topk_results (date DATE, granularity TEXT, rank INT, item_id TEXT, score DOUBLE, PRIMARY KEY((date, granularity), rank))

Write: Flink emits the top-100 for each 1-minute window → 100 Cassandra writes per minute.

Read: "Top 10 trending last Tuesday at 3pm" → single partition read → <5ms.

→This is the warm store layer in the Top-K architecture. Redis holds real-time (last 5 min), Cassandra holds recent (last 90 days), ClickHouse holds long-term analytics (all time).

BILLION-SCALE · REAL-TIME
INGESTION
Every video play event → Kafka topic (partitioned by video_id → consistent CMS per video). 2 billion plays/day = ~23K events/sec. 100 Kafka partitions handle this trivially (230 events/sec/partition).
PROCESSING
Flink job: 100 parallel tasks (one per Kafka partition). Each maintains local CMS (ε=0.001, δ=0.01) + min-heap(K=200). Every 1 minute: emit local top-200 with CMS-estimated counts to a merge topic.
MERGE
Single Flink merge task: receives top-200 from all 100 partitions → merges 100 CMS sketches → recomputes global top-200 from merged counts → writes to Redis ZSET (key: trending:global:1min) with ZADD.
SERVE
Trending API: ZREVRANGE trending:global:1min 0 9 → top 10 video IDs → enrich with metadata from cache → return in <5ms. 99.9th percentile latency: <10ms. Zero ClickHouse queries in the hot path.
DECAY
Exponential decay applied at merge: each video's score = current_hour_views × 1.0 + prev_hour_views × 0.5 + 2hr_ago × 0.25. A video trending NOW ranks higher than one that went viral yesterday. Avoids zombie trending items.
TikTok — For You Page Top-K
PERSONALISED · REAL-TIME
TWO TOP-K
TikTok runs two parallel Top-K systems: global trending (same for all users) and personalised (per-user signal). Global: CMS + min-heap on raw play events, 5-minute windows. Personalised: ML model scores on top of global candidates, re-ranked per user interest graph.
DECAY

FRESHNESS
For You Page must reflect events from the last 30 seconds. Redis ZSET updated every 15 seconds by a dedicated Flink job. API: ZREVRANGE → enrich with video metadata from Redis Hash → return. P99 latency: <8ms including enrichment.
🎯Top-K System Design — Key Decisions
01
What is the required freshness of the Top-K result?
<30 seconds →Flink streaming → Redis ZSET. Flink updates Redis every 15–30 seconds. Real-time trending. Redis ZREVRANGE serves in <1ms. Required for: live event trending, real-time gaming leaderboards.
Minutes →Flink micro-batch → ClickHouse. Flink batches every 1–5 minutes. ClickHouse stores the aggregated result. API queries ClickHouse directly. Simpler than Redis ZSET, good for: hourly trending, daily top charts.
Hours/daily →Spark batch → Cassandra or ClickHouse. Run a Spark job every hour/day on the full event log in S3. No streaming infrastructure needed. Cheapest, simplest, most reliable.
02
Do you need exact counts or approximate?
Approximate OK →CMS + min-heap. O(w×d) memory. Handles unlimited distinct items. 0.1% error rate at billions of events is imperceptible for ranking. The production choice for Top-K at scale.
Exact required →Exact aggregation in ClickHouse or Cassandra. Store (item, window, count) tuples exactly. For moderate cardinality (<1M distinct items/window), exact counting in ClickHouse is fast and practical. Only use CMS when exact counting exceeds memory bounds.
