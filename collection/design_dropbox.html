00 · Requirements

Scope and scale

Functional
Upload files from any device. Download on any device. Sync: changes on one device appear on all devices. Share files/folders with other users. Version history (last 30 versions). Offline access (cached locally).
Non-Functional
700M users, 500M files synced/day. File size: up to 5GB. Upload reliability: resume on failure. Sync latency: <30 seconds from upload to visible on other devices. Conflict resolution: two devices edit same file simultaneously.
Estimation
500M file operations/day = 5,787 ops/sec. Average file: 1MB. Total storage: 700M users × 5GB avg = 3.5 PB. Delta sync: only changed chunks uploaded → avg 10% of file changed = 100KB upload per "modified file." Storage growth: ~5PB/year.
01 · Architecture

The complete file sync system

01Chunked Storage & Deduplication
What it is
Files split into 4MB content-addressed chunks. Identical chunks stored once. Upload: client splits file into 4MB chunks. SHA-256 hash each chunk. Check with server: "Do you have chunks [hash1, hash2, hash3, ...]?" Server returns which hashes are missing. Client uploads only missing chunks to S3 (pre-signed URLs). Server assembles file metadata: file_id → [chunk_hash1, chunk_hash2, ...]. Deduplication: if two users upload the same 1GB video, their chunks have identical hashes. Server stores only one copy in S3. Both users' file metadata points to the same chunk hashes. Dropbox saved 2+ PB via deduplication. The technique works because files like "office2023_installer.exe" are identical across millions of users.
02Delta Sync
What it is
Only upload changed chunks — not the entire file. User edits a 1GB presentation, changes one slide (100KB). Without delta sync: upload 1GB on every save. With delta sync: client re-chunks the modified file → 2 chunks changed out of 256 → upload 8MB (2 × 4MB chunks) → 99% less bandwidth. Algorithm: client maintains local chunk hash list. On change: re-chunk → compare new hashes to cached hashes → identify changed chunks → upload only those. Server reconstructs latest version from existing chunks + new chunks.
03Sync Engine
What it is
Change notifications → long-poll / WebSocket → sync clients across devices. Device A uploads a file → server stores metadata → publishes ChangeEvent to a notification service → other devices (B, C) are notified → download delta. Notification delivery: Delta notification service maintains a long-poll connection per device (or WebSocket for modern clients). Device registers: "I'm at cursor position 12345 for user X." On change: push "new events from cursor 12345." Device downloads new chunk hashes → downloads new chunks from S3 → updates local file. Cursor-based sync: each device has a "sync cursor" (logical timestamp). Only events after the cursor are delivered. If device was offline for 1 week: fetch all events since its cursor, apply in order, fully caught up.
04Conflict Resolution
What it is
Two devices edit the same file offline → both upload → conflict on merge. Detection: each file version has a vector clock (Dropbox uses a simpler "edit counter"). If device A's edit counter and device B's edit counter both diverge from the common base: conflict detected. Resolution: Dropbox's simple strategy — keep BOTH versions. "report.docx" becomes "report.docx" (winner — usually the later timestamp) and "report (Alice's conflicted copy 2026-03-21).docx." Users see both, manually merge. This is safe (no data loss) even if not elegant. Google Docs does better with CRDT-based operational transforms — concurrent edits merged automatically. For Dropbox (arbitrary binary files, not just text), CRDTs aren't applicable — conflicted copies is the right approach.
05Version History
What it is
Each version is stored as a list of chunk hashes. No data duplication for unchanged chunks. Version V1: [chunk_A, chunk_B, chunk_C]. Version V2: [chunk_A, chunk_B_new, chunk_C]. Storage cost of V2: only chunk_B_new is new (4MB). chunk_A and chunk_C are shared with V1. Maintaining 30 versions of a 1GB file that has small edits: near-zero additional storage cost (only changed chunks are new). Restore: select version → server reconstructs file from that version's chunk list → client downloads chunks (most already in local cache).
02 · Follow-ups

The questions your interviewer will ask

How do you handle file encryption so Dropbox employees can't read user files?+
Two models: encryption at rest (Dropbox manages keys) vs end-to-end encryption (user manages keys).

Standard Dropbox: files encrypted in S3 with AES-256. Dropbox manages the encryption keys in their KMS. Dropbox employees with sufficient access COULD decrypt files. This is why Dropbox is not suitable for top-secret data.

Dropbox Paper (E2EE): user generates a key on their device, derived from their password using PBKDF2. Files encrypted client-side before upload. Server stores only ciphertext. Dropbox cannot decrypt. If user forgets password: data lost forever (no recovery). Key is never sent to the server.

Sharing with E2EE: when sharing with another user, the file key is encrypted with the recipient's public key (RSA-2048). The encrypted key is stored on Dropbox's server. Recipient decrypts the file key with their private key (on device), then decrypts the file. Dropbox never has the plaintext key.

The trade-off: with client-side E2EE, Dropbox loses: deduplication (can't check if encrypted ciphertext is identical — same plaintext encrypted differently produces different ciphertext), virus scanning (can't scan encrypted content), server-side search. These are real feature losses for security. Dropbox offers both models — standard for most users, E2EE for enterprise/sensitive use cases.
How do you handle 1 million users concurrently syncing large files?+
The key insight: bandwidth is the constraint, not compute. S3 + pre-signed URLs means your servers never handle the bytes.

Upload flow: client → your API server (metadata only: "I'm uploading file X with these chunk hashes") → API server generates pre-signed S3 URL → client uploads directly to S3. Your server never receives the file bytes.

With 1M concurrent uploads at 10MB/s each: total bandwidth = 10 TB/s. This is handled by S3's distributed infrastructure, not your servers. S3 is designed for this. Your API servers handle only metadata operations (kilobytes, not gigabytes).

Throttling: per-user upload rate limiting (don't let one user saturate S3 bandwidth allocation). Dropbox throttles to 10 parallel chunk uploads per user. Total bandwidth per user: 40MB/s (10 chunks × 4MB). Rate limiting applied at the API layer (token bucket per user_id).

Sync queue backpressure: 1M events/second from sync engine is manageable. The notification service uses long-poll with server-sent events — each connection is lightweight (HTTP keepalive, no WebSocket overhead). 1M long-poll connections ≈ 100 servers at 10K connections each.
How does Dropbox's "Smart Sync" (online-only files) work?+
Virtual filesystem with on-demand download: files appear as placeholders locally until accessed.

Smart Sync uses OS-level virtual filesystem drivers. On macOS: kernel extension intercepts file system calls. On Windows: Cloud Files API (built-in since Windows 10). On Linux: FUSE (Filesystem in Userspace).

How it works: file "report.pdf" appears in Finder/Explorer with a cloud icon. Size shows as 50MB but no local data exists. User double-clicks: OS file open call is intercepted by Dropbox's filesystem driver → driver downloads the file from S3 → buffers to local disk → returns the file handle to the OS → application opens it normally.

The illusion: from the application's perspective, the file was always there. Applications don't need to know about Smart Sync — it works transparently.

Pinning: users can "pin" files to always keep offline. Driver marks them for permanent local storage. Eviction: LRU policy removes unpinned files that haven't been accessed recently when local disk is full. The eviction is transparent — the file still "exists" in the filesystem, just as a cloud placeholder again.
