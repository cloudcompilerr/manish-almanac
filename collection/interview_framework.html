00 · The Framework

The 45-minute system design interview — minute by minute

The interviewer's scorecard

FAANG interviewers score on four dimensions: (1) Problem clarification — did you ask the right questions before designing? (2) Scale reasoning — do your design choices match the actual scale? (3) Technical depth — can you go deep when probed? (4) Trade-off awareness — do you acknowledge limitations of your choices?

The biggest mistake: jumping into the architecture without clarifying requirements. Interviewers give negative marks for this.

Phase 1 (0–5 min)
Requirements
Never start designing. Start asking.

Functional requirements: "What are the core features? What should the system do?" For "Design Twitter": post tweets, follow users, see a feed, search. Agree on scope — you cannot design everything in 45 minutes.

Non-functional requirements: "What are the scale expectations? What latency is acceptable? Is consistency or availability more important for this use case?"

Out of scope: explicitly state what you're NOT designing. "I'll focus on the feed generation and tweet storage — not ads, not direct messages, not trending." This shows maturity. Template: "Before I start designing, let me clarify a few things. [Ask 3-5 targeted questions]. Based on your answers, here's what I'll focus on: [summarise scope]."

Phase 2 (5–10 min)
Estimation
Estimate the scale. The numbers drive every subsequent design decision.
State your assumptions: "Let me assume 100M DAU, each user reads their feed 5 times/day and posts once/week."
Calculate: QPS (reads + writes), storage per year, bandwidth.
Derive implications: "At 50K read QPS, a single DB won't handle this — I'll need read replicas and caching. At 100TB/year, I'll need distributed storage." ✓ The estimation isn't tested for precision — it's tested for reasoning. Show how the numbers inform your design. "Because reads are 10× writes, I'll optimise heavily for the read path."
Phase 3 (10–25 min)
High-Level Design
Draw the architecture. Start simple, then add components as needed.
Start with: clients → API gateway → [core services] → [data stores]. Label every arrow with the protocol (REST/gRPC/Kafka). Label every box with its role.
Walk through the main flows: "For a tweet post: client → API gateway → Tweet Service → [DB write + Kafka event]. For feed read: client → API gateway → Feed Service → Redis cache [cache hit] OR PostgreSQL [cache miss]." Speak while drawing. Interviewers follow your thought process. Silence while drawing is a red flag — they can't assess reasoning they can't hear.
Phase 4 (25–40 min)
Deep Dive
The interviewer picks the hardest component. Justify every choice.
Common deep dives: "How does the feed generation work at scale?" / "How does search work?" / "How do you handle a hot user with 50M followers?"
Structure your answer: "Here's the problem, here's my approach, here's why I chose X over Y, here are the trade-offs." ✓ Depth is what separates L5 from L6 at Google. Having an answer is table stakes. Having a better answer AND knowing why it's better is what gets you the senior hire.
Phase 5 (40–45 min)
Trade-offs & Wrap-up
Proactively identify weaknesses in your design before the interviewer does.
"My design uses eventual consistency for the feed — users might see a tweet from someone they follow 200ms after it's posted. For most use cases this is acceptable, but if we needed strong consistency here's how I'd approach it..."
"The bottleneck in my design is the feed fan-out for celebrity users. Here's how I'd handle the hot key problem..." ✓ Self-aware trade-off discussion is a strong positive signal. It shows you understand the design holistically, not just the happy path.
01 · The 10 Questions to Ask

The clarifying questions that make or break the interview

Scale Questions
Ask these first — they determine the entire architecture:
"How many daily active users do we expect?" (1K vs 1B changes everything)
"What is the read:write ratio?" (feeds are 100:1, databases are 1:1)
"What is the expected QPS?" (helps size the fleet and cache)
"How much data do we expect to store?" (small = single DB, large = distributed storage)
"Is this a greenfield system or are we scaling an existing one?"
Consistency Questions
Ask these to understand the consistency requirements:
"Does the user need to see their own writes immediately?" (read-your-own-writes)
"Is it acceptable for different users to see slightly different states briefly?" (eventual consistency OK?)
"What happens if the system is unavailable for a few minutes — is that acceptable?" (CA vs CP trade-off)
"Are there any financial or compliance implications that require strong consistency?" (payments, healthcare)
Latency Questions
Ask to understand where latency matters most:
"What is the acceptable p99 latency for the main user-facing operations?"
"Are there batch operations where latency doesn't matter (just throughput)?"
"Is this globally distributed — do we need low latency in multiple regions?"
02 · Common Mistakes

What kills good candidates — and how to avoid each

Starting with
a Solution
"I'll use Kafka, Redis, Cassandra, Kubernetes, and a microservices architecture." Said before understanding the problem. This is the #1 negative signal.
Why it hurts: you're pattern-matching, not problem-solving. A system for 1,000 users that uses Kafka and Cassandra is over-engineered. An interviewer sees you don't understand trade-offs.
Fix: start with requirements. Let the scale drive the technology choices. "At 50K QPS, a single PostgreSQL won't suffice — I'd add Redis for caching." Not: "I'll use Redis because Redis is good."
Designing in Silence
Drawing a diagram for 5 minutes without speaking.
The interviewer is assessing your reasoning. Silent drawing gives them nothing to evaluate. They cannot probe your thought process. You cannot demonstrate depth.
Fix: narrate continuously. "I'm adding a load balancer here because we have multiple app servers. I'm choosing to put Redis in front of the DB because our read:write ratio is 10:1 and most reads are for the same hot data..."
Not Defending
Choices
Saying "I'll use MySQL" and moving on without explanation.
Interviewers probe: "Why MySQL and not PostgreSQL?" "Why not NoSQL?" If you don't have answers, it signals the choice was arbitrary.
Fix: for every major component, state why you chose it over the obvious alternatives. "I chose PostgreSQL over MySQL because we need JSONB columns and advanced indexing. I chose it over Cassandra because our access patterns are relational and we need ACID transactions."
Ignoring
Failure Modes
Designing only the happy path.
Real systems fail. Redis goes down. A DB replica falls behind. A service crashes. An interviewer who sees no failure handling in your design infers you haven't operated production systems.
Fix: proactively address failure modes. "What happens if Redis is unavailable? I'd fail open — requests fall through to the DB with higher latency. An alert fires if Redis is down for >30 seconds." One failure mode addressed unprompted is worth more than ten features explained.
03 · Estimation Cheatsheet

The numbers to compute in every interview

Design Twitter — Full Estimation Example
WORKED EXAMPLE
GIVEN
300M DAU. Users read feed 5×/day. 0.1% of users post daily (300K posts/day). Average tweet = 300 bytes. Each tweet has 2 images on average (200KB each).
READ QPS
300M × 5 reads/day ÷ 86,400 sec/day = 17,360 reads/sec. Peak (3× avg) = 52,000 reads/sec. This tells us: we need multiple app servers and aggressive caching.
WRITE QPS
300K posts/day ÷ 86,400 = 3.5 writes/sec. Peak = 10 writes/sec. Small! A single PostgreSQL handles this easily. Media uploads are different: 300K × 2 images = 600K image uploads/day = 7 image uploads/sec.
STORAGE
Text: 3.5 writes/sec × 300 bytes × 31M sec/year = ~33 GB/year (tiny — PostgreSQL is fine). Images: 7 uploads/sec × 200KB × 31M sec = ~43 TB/year → S3 + CDN, not the DB.
IMPLICATIONS
Read:write = 5000:1 → optimise heavily for reads. Redis cache for hot tweets + user timelines. Image storage in S3 + CloudFront. Text storage in PostgreSQL (33GB/year is tiny). Fan-out is the hard problem: 300K posts/day to followers who follow 1K people avg = 300M feed updates/day.
04 · Follow-ups

Every hard meta-question, answered

How do you handle it when you don't know the answer to a follow-up question?+
Honesty + structured reasoning > bluffing. Interviewers respect "I'm not sure, but here's how I'd think about it."

When you don't know: "I haven't used X in production, but based on what I know about it, I'd expect [reasoning]. The trade-off I'd worry about is [concern]. Could you tell me if my intuition is on the right track?"

What to never do: make up numbers or fabricate facts. Interviewers know the real numbers. Getting caught making up "Kafka can handle 10 million messages per second on a single broker" (it can't — it's about 1M with optimal tuning) destroys your credibility for the rest of the interview.

What to do instead: use first principles. "I don't know Kafka's exact throughput limit. But I know it's an append-only log with sequential disk writes, which is the fastest possible disk operation. So I'd estimate high throughput — probably hundreds of thousands per second per broker, maybe more. I'd size the cluster conservatively and monitor actual throughput."

This is actually a positive signal: it shows you can reason under uncertainty rather than needing to memorise facts.
Should you always start with a simple design and then scale, or start with the scaled design?+
Always start simple. Then add complexity where the scale demands it.

The interviewer is evaluating whether you can identify what the actual bottlenecks are. If you jump to a fully distributed microservices design immediately, you skip the reasoning step that shows you understand trade-offs.

The approach that impresses: "Let's start with the simplest possible design that works: a single server with a database. [Draw it]. Now let's apply our scale numbers: at 50K read QPS, this single DB becomes the bottleneck. So I'd add caching here [draw Redis]. Our write QPS is only 10/sec — the single DB handles that fine. Now the API server becomes the bottleneck at this scale — I'd horizontally scale app servers behind a load balancer [draw it]."

This shows: you know what the simple baseline looks like, you know where it fails, and you add complexity only where justified. Far more impressive than "I'll use Kubernetes, Kafka, and 15 microservices" — which shows pattern-matching, not reasoning.
How specific should your technology choices be? Should you name specific databases and tools?+
Name specific technologies, but justify them. Vague answers ("I'll use a NoSQL database") show less depth than specific ones ("I'll use Cassandra because its wide-column model fits our time-series access pattern and it handles write-heavy workloads well").

Good specificity: "I'd use PostgreSQL for the user table because it needs ACID transactions and the access pattern is simple key lookups. I'd use Cassandra for the activity feed because it's append-heavy and we need time-ordered data partitioned by user."

Bad specificity: "I'll use MongoDB because it's flexible" — this shows you chose MongoDB without understanding the trade-offs against other options for this specific use case.

The pattern: Technology choice + Why this choice + Why not the obvious alternative. "PostgreSQL because ACID + relational. Not Cassandra because we need JOINs. Not DynamoDB because we don't know our access patterns yet and want flexibility."

On uncertainty: "I'd use a time-series database here — either InfluxDB or TimescaleDB. I haven't used both at scale, but TimescaleDB's PostgreSQL compatibility would let us use our existing tooling. I'd prototype both and benchmark for our specific access patterns."
How do you handle it when the interviewer pushes back on your design?+
Pushback is part of the interview. It tests whether you can defend your choices AND update your view when given new information.

Two types of pushback:

Testing a valid concern: "What happens when your Redis cache goes down?" The interviewer has a real concern. Acknowledge it: "That's a great point — I should address this. If Redis fails, I'd [fall open to DB / fail with degraded performance / return cached data from a local fallback]. The trade-off is [latency vs availability]."

Playing devil's advocate: "Why not just use a flat file for this?" The interviewer is testing whether you'll abandon a good design under pressure. Hold your ground, with reasoning: "I considered that. A flat file would work for the initial scale, but at 50K QPS concurrent reads on the same file would require locking that kills throughput. The DB gives us concurrent access and indexed lookup which we need here."

The failure mode: immediately abandoning your position at the first pushback without reasoning. This signals you don't actually understand your own design — you were pattern-matching, not reasoning. It's fine to say "you're right, I hadn't considered that" when the pushback reveals a genuine flaw. But capitulate with reasoning: "You're right — that would be a problem because X. I'd address it by Y."
How do you structure the answer for "Design a URL shortener" end-to-end?+
A complete URL shortener answer in 5 minutes:

Requirements (1 min): shorten long URLs, redirect short URLs to original. Scale: 100M URLs, 1B redirects/day. Latency: redirect must be <10ms. Durability: URLs must not expire (unless specified).

Estimation (1 min): 1B redirects/day = 11,574 reads/sec. 100M URLs × 500 bytes each = 50GB (fits in one PostgreSQL). 11,574 reads/sec → we need a cache (Redis) to avoid hitting the DB on every redirect.

Core design (2 min): POST /shorten → generate a 7-character Base62 ID (62^7 = 3.5T unique IDs) → store (short_id → long_url) in PostgreSQL → return short URL. GET /{short_id} → Redis lookup → cache miss: PostgreSQL lookup, populate Redis with TTL 24h → cache hit: return 301 redirect. Why 301 (permanent) vs 302 (temporary)? 301: browsers cache the redirect client-side, reduces server load. 302: every redirect hits your server, allows analytics tracking. Use 302 if you need click analytics.

ID generation (1 min): auto-increment integer is simple but predictable. Random 7-char Base62 is unpredictable. Collision probability: 3.5T IDs, 100M used = 0.003% collision rate. Check for collision on insert (retry on conflict). At scale: pre-generate ID ranges per server to avoid DB lookup on every generate.

Trade-offs: this design has a single PostgreSQL primary — bottleneck at extreme write scale. Mitigation: shard by short_id prefix if needed. Redis is a single point of failure — Redis Sentinel for HA. Custom domain support: just add domain column and index on (domain, path).
