00 · The Foundation

What is OLAP and why is it different?

OLAP stands for Online Analytical Processing. It's the class of databases built for reading a lot of data to answer complex questions, as opposed to OLTP (Online Transaction Processing) databases which are built for many small reads and writes.

OLTP vs OLAP — the supermarket analogy
OLTP (PostgreSQL, MySQL, DynamoDB): The cash register. Each transaction is tiny — scan item, charge card, update inventory. Thousands happening simultaneously. Each one must be fast and correct.

OLAP (ClickHouse, BigQuery, Druid): The quarterly business review. The manager asks "which products sold most in the North last Tuesday compared to the same Tuesday last year, broken down by hour?" This query needs to scan millions of rows. No one expects it in 10ms — but they want it in under 2 seconds, not 2 hours.

The core difference: OLTP is optimised for row access (get me order #12345). OLAP is optimised for column scans (sum all sales values in column X across 10 billion rows). This is why OLAP databases store data column-by-column instead of row-by-row.

Why Columnar Storage Changes Everything

The Key Insight

Row storage (PostgreSQL): Each row is stored together on disk. To compute SUM(revenue) across 1 billion rows, you read ALL columns of ALL rows — most of which you don't need.

Column storage (ClickHouse/BigQuery): Each column is stored together. To compute SUM(revenue), you only read the revenue column. 10x–100x less data read. And integers in the same column compress 10–20x better than mixed row data.

Real impact: A query that takes 10 minutes in PostgreSQL takes 300ms in ClickHouse — on the same data.

The Four OLAP Engines

ClickHouse
Columnar OLAP · Self-Hosted
The speed demon. Built by Yandex for web analytics. Ingests 500K rows/sec, answers GROUP BY on 100B rows in under 2 seconds. Battle-tested at Cloudflare, Uber, eBay. Self-host or ClickHouse Cloud.
Born 2016 · Yandex → Apache · MergeTree engine

Real-Time OLAP · Self-Hosted
The sub-second explorer. Designed for interactive dashboards with <1s query response. Pre-aggregates data at ingest time (rollup). Used by Lyft, Twitter, Netflix for operational analytics.
Born 2011 · Metamarkets → Apache · Segment-based
🔷
BigQuery
Serverless OLAP · Managed GCP
The serverless giant. No clusters to manage. Pay per query. Scales to petabytes automatically. Perfect for data warehouses, data science teams, and ad-hoc exploration. Google's backbone for internal analytics.
Born 2010 · Google · Dremel paper lineage
🟠
Amazon Redshift
MPP Data Warehouse · Managed AWS
The AWS native warehouse. Massive Parallel Processing (MPP), deep S3 integration (Redshift Spectrum), familiar SQL. Best for structured warehouse queries in the AWS ecosystem.
Born 2012 · Amazon AWS · ParAccel / PostgreSQL lineage

How They Fundamentally Differ in Architecture

The Critical Architectural Distinction

ClickHouse & Druid: Shared-nothing architecture. Each node stores data and computes. Data is co-located with compute. Extremely fast for co-located queries. Hard to scale compute independently of storage.

BigQuery & Redshift Spectrum: Separate storage from compute. Data lives in object storage (GCS/S3). Compute scales independently. Slower for hot data but infinitely scalable and cheaper for cold data.

02 · Under the Hood

How Each One Actually Works

ClickHouse — MergeTree Engine

-- ClickHouse's secret: the MergeTree family -- Data is stored in "parts" — immutable sorted chunks written at ingest. -- Background merge process combines small parts into larger ones (like LSM tree). -- Primary key determines sort order within a part → fast range scans. -- Sparse primary index: one entry per 8192 rows → tiny index, full scan avoided. CREATE TABLE entity_events_agg ( event_date Date, -- PARTITION KEY: one part per date event_hour DateTime, entity_type LowCardinality(String), -- Stored as dict-encoded integers entity_id String, region LowCardinality(String), view_count UInt64 ) ENGINE = MergeTree() PARTITION BY toYYYYMM(event_date) ORDER BY (entity_type, region, entity_id, event_hour); -- ORDER BY = physical sort order = primary key for sparse index -- Query: WHERE entity_type='video' AND region='IN' skips 99% of data

Apache Druid — Pre-Aggregation at Ingest (Rollup)

-- Druid's killer feature: it pre-aggregates data as it ingests -- Called "rollup" — reduces data volume before storing -- Raw events (100M rows): user_id=123, video_id=456, timestamp=2026-03-20T14:23:45, region=IN -- After Druid rollup (grouped by minute + entity + region): video_id=456, minute=2026-03-20T14:23, region=IN, count=847 -- Result: 100M raw events → 2M aggregated rows → 50x storage reduction -- Trade-off: you lose individual user_id — can't answer "how many unique users?" -- Unless you include a HyperLogLog sketch for approximate cardinality -- This is why Druid queries are sub-second — much of the work is already done

BigQuery — Dremel's Columnar Tree

-- BigQuery uses a tree of execution nodes (Dremel architecture) -- Your query is broken into a tree: root distributes, leaves read columns -- Thousands of workers read in parallel from Google's Colossus storage -- Cost model: you pay for data scanned, not compute time -- SELECT * FROM table → scans ALL columns → expensive -- SELECT revenue FROM table → scans 1 column → cheap -- Optimisation: partition + cluster your tables CREATE TABLE events PARTITION BY DATE(event_time) CLUSTER BY entity_type, region; -- Partition pruning: only scan today's partition -- Cluster pruning: only scan video+IN blocks within partition -- Combined: query that scans 100TB now scans 50GB → 2000x cheaper

Cost at Scale — Real Numbers

BigQuery vs ClickHouse at Top-K Scale

Assume: 500K events/sec → 43B events/day → 100 bytes per row after aggregation → ~4.3TB of aggregated data written per day. Analytical queries run 1,000 times/day each scanning ~500GB.

BigQuery: 1,000 queries × 500GB × $5/TB = $2,500/day in query costs alone. Plus storage: 4.3TB × 30 days × $0.02 = $2,580/month.

ClickHouse (10 nodes, 16-core, 64GB each, AWS r6i.4xlarge): 10 × $1.00/hr × 24hr = $240/day. Handles all 1,000 queries easily. Same queries, same data, ~10x cheaper at this scale.

BigQuery wins for: Unpredictable, bursty, data-science workloads where you'd otherwise pay for idle cluster capacity.

04 · Applied to Real Systems

Which OLAP Engine for Which System?

Top-K Trending (YouTube / Twitter)
HIGH FREQUENCY · 500K EVENTS/SEC
WINNER
ClickHouse ✓ Flink flushes aggregated rows every 30s directly into ClickHouse via its Kafka engine. AggregatingMergeTree + columnar storage = "top 10 videos in India last hour" in 300ms on 100B rows. Streaming ingest is native — no extra pipeline.
WHY NOT DRUID
Druid ⚠ Druid's rollup would actually work well here — but the operational complexity (ZooKeeper, Historical nodes, Broker nodes, Coordinator, Overlord) is far higher than ClickHouse. For Top-K specifically, ClickHouse's window functions and GROUP BY are cleaner.
WHY NOT BIGQUERY
BigQuery ✗ At 43B writes/day, BigQuery Storage Write API costs would be significant. And the 2–5s query latency makes "what's trending right now" feel slow. ClickHouse is 10x cheaper and 10x faster for this specific workload.
QUERIES ENABLED
Historical Top-K ("what was #1 last Tuesday?") · Trend analysis hour-over-hour · Breakdown by device/region · Rank history for a specific entity — all in <2s.
Ride-Sharing Analytics (Uber)
OPERATIONAL DASHBOARDS
REAL-TIME OPS
Druid ✓ Uber uses Druid for operational dashboards: "How many rides completed in the last 5 minutes by city?" Sub-second queries on streaming data let operations teams react in real time. Druid's rollup pre-aggregates by city+minute, making this near-instant.
LONG-TERM ANALYTICS
BigQuery ✓ Historical analysis: "Compare Q4 ride completion rates by city 2024 vs 2025." Petabytes of historical data, ad-hoc exploration by data scientists, no need for sub-second latency. BigQuery's serverless model is perfect — data scientists don't need to manage clusters.
Ad Analytics Platform
HIGH CARDINALITY · REAL-TIME BILLING
WINNER
ClickHouse ✓ Ad click aggregation: entity_id, campaign_id, impression counts, CTR — high write throughput, complex GROUP BY queries, need accurate counts for billing. ClickHouse's exactly-once semantics via Kafka + ReplacingMergeTree prevents double-counting.
WHY NOT DRUID
Druid ✗ Druid's rollup loses individual event detail. For billing, you need exact click counts per ad per user. Rollup would lose the granularity needed for fraud detection and accurate billing.
Data Warehouse / Business Intelligence
AD-HOC · DATA SCIENCE
WINNER
BigQuery ✓ For a BI team running diverse queries across petabytes of historical data with unpredictable patterns, BigQuery's serverless model wins. No cluster to right-size, pay only for what you query. Connects natively to Looker, Tableau, dbt.
AWS EQUIVALENT
Redshift ✓ Same use case but in the AWS ecosystem. Redshift Spectrum lets you query data directly in S3 without loading it. Deep integration with Glue, EMR, QuickSight. If you're all-in on AWS, Redshift + Spectrum is the natural choice.

06 · Interview Follow-up Playbook

Every Hard Follow-up, Answered

Why can't I just use PostgreSQL for analytics? It has window functions and GROUP BY.+
You can — until you can't. PostgreSQL is fine for analytics up to ~100GB and simple aggregations. But at billions of rows, a single GROUP BY on PostgreSQL requires a full sequential scan reading every column. ClickHouse on the same data reads only the columns you reference, compresses integers 10–20x, and parallelises across all CPU cores.

Benchmark: SELECT entity_type, SUM(view_count) FROM events WHERE event_date = today() GROUP BY entity_type — PostgreSQL on 1B rows: ~8 minutes. ClickHouse: ~400ms. Same query, same data. That's why OLAP exists.
ClickHouse says it can ingest 500K rows/sec. How does that work with Kafka?+
ClickHouse has a native Kafka engine — you define a Kafka table and ClickHouse becomes a consumer.

CREATE TABLE kafka_events ENGINE = Kafka SETTINGS kafka_broker_list = 'kafka:9092', kafka_topic_list = 'events', kafka_format = 'JSONEachRow';

Then a Materialized View continuously reads from the Kafka table and inserts into your main MergeTree table. ClickHouse batches these inserts internally — it doesn't write each message individually. Batches of thousands of rows are written as a single "part" to disk, keeping write amplification low. The result: Kafka → ClickHouse pipeline with 30-60 second latency and 500K rows/sec throughput.
What's the difference between Druid's rollup and ClickHouse's AggregatingMergeTree?+
Both pre-aggregate — but at different points in the pipeline and with different flexibility.

Druid rollup happens at ingest time. Raw events with the same dimensions within the same time granularity are collapsed into a single aggregate row. You define rollup at table creation. If you didn't include a dimension at ingest, you can never query by it. This achieves 50–100x storage reduction but is irreversible.

ClickHouse AggregatingMergeTree aggregates during background merge. Raw data is initially stored, then merged and aggregated in the background. You keep the full resolution until merged. More flexible, but storage reduction comes later and is less extreme than Druid's rollup.

The choice: Known, fixed query patterns with approximate counts OK → Druid rollup. Need full granularity or exact counts → ClickHouse AggregatingMergeTree.
BigQuery charges per TB scanned. How do you control costs in a large team?+
Four cost control techniques used at production scale:

1. Partition pruning: Always filter on the partition column (usually date). WHERE event_date = '2026-03-20' scans only one day's partition instead of all-time data. Mandatory in every query policy.

2. Column selection: Never SELECT *. Each column selected costs proportional to its size. SELECT event_type, COUNT(*) is 10x cheaper than SELECT * on the same rows.

3. Clustering: Cluster tables by high-cardinality filter columns. BigQuery skips irrelevant blocks within a partition when the filter matches a clustered column.

4. Materialized Views / cached results: Common dashboard queries are cached for 24 hours. BigQuery caches identical queries automatically at no cost. Materialised Views pre-compute and store expensive aggregations.

5. Reservations: Buy BigQuery slots (fixed compute) for predictable workloads instead of paying per query.
In the Top-K system, why is ClickHouse used instead of Cassandra for analytics?+
Cassandra and ClickHouse serve fundamentally different query profiles.

Cassandra (warm store in Top-K): "Give me all hourly counts for entity X in region IN over the last 30 days" — a narrow range scan within one partition. Fast because it reads very little data. Good for: backfilling Redis, known entity lookups.

ClickHouse (OLAP layer in Top-K): "Give me the top 10 entities globally across all regions for the last 7 days, broken down by device, with hour-over-hour change" — a full table scan across billions of rows with complex aggregation. Cassandra would do a full cluster scan for this query — every node would need to respond. ClickHouse scans only relevant columns and returns the answer in 500ms.

Rule of thumb: Cassandra is for "fetch a specific partition." ClickHouse is for "aggregate across many partitions." They're complementary, not competitive.
