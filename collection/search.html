00 · Core Intuition

Why a database cannot do what a search engine does

A SQL database index finds exact values fast: WHERE user_id = 123. But WHERE body LIKE '%distributed systems%' requires a full table scan — every row, every time. At 1 billion documents, that takes minutes. A search engine can answer this in milliseconds because it inverts the problem entirely.

The book index analogy
A database is a book read cover-to-cover to find a word. Slow.

A search engine is a book with an index at the back: "distributed systems → pages 12, 47, 203, 891." You go directly to those pages. That back-of-book index is an inverted index — and it is the entire secret of how search works.
01 · Inverted Index

The data structure that powers every search engine

How It Works
An inverted index maps each unique term to the list of documents containing it.
Documents: Doc1="Redis is fast", Doc2="Redis scales well", Doc3="Kafka is fast"
Inverted index:
redis → [Doc1, Doc2]
fast → [Doc1, Doc3]
is → [Doc1, Doc3]
scales → [Doc2]
Query "redis fast" → intersection of [Doc1,Doc2] and [Doc1,Doc3] → Doc1 (contains both terms)
Posting List
For each term, the index stores not just document IDs but positions and frequencies.
redis → [(Doc1, freq:1, pos:[0]), (Doc2, freq:1, pos:[0])]
Position enables phrase queries: "redis cluster" requires "redis" and "cluster" to be adjacent.
Frequency enables relevance scoring — a document mentioning "redis" 20 times ranks higher than one mentioning it once.
Text Analysis Pipeline
Before indexing, text passes through an analysis pipeline that normalises it.
1. Tokenization: "Redis is Fast!" → ["Redis", "is", "Fast"]
2. Lowercasing: → ["redis", "is", "fast"]
3. Stop word removal: → ["redis", "fast"] (removes "is")
4. Stemming/Lemmatization: "running" → "run", "faster" → "fast"
The same pipeline must run at query time. "Running Redis" → ["run", "redis"] → matches documents containing "run" or "redis" in any form.
TF-IDF / BM25
Relevance scoring: not all matches are equal.
TF (Term Frequency): how often does the term appear in this document? More occurrences = more relevant.
IDF (Inverse Document Frequency): how rare is the term across all documents? "the" appears everywhere — low IDF, low importance. "Kafka" appears rarely — high IDF, high importance.
BM25: modern improvement over TF-IDF used by Elasticsearch. Prevents very long documents from dominating just because they mention a term more times.
Elasticsearch uses BM25 by default. You can boost specific fields (title matches worth 3x body matches).
02 · Elasticsearch Architecture

How ES scales to billions of documents

Index → Shards
An Elasticsearch index is split into N primary shards. Each shard is a complete, independent Lucene index.
Index "tweets" with 5 shards: each shard holds ~20% of documents. Queries fan out to all 5 shards in parallel, results merged by the coordinator.
⚠ Shard count is set at creation and cannot be changed (except via reindex). Over-sharding (too many small shards) is as harmful as under-sharding (too few large ones). Rule of thumb: aim for 10–50GB per shard.
Replication
Each primary shard has N replica shards on different nodes.
Writes: go to primary, primary replicates to replicas.
Reads: can be served by primary or any replica — distributes read load.
Node failure: replica promoted to primary automatically.
✓ Replicas both provide HA and increase read throughput. 5 shards × 2 replicas = 15 Lucene indexes total across the cluster.
Near Real-Time
(NRT) Search
Newly indexed documents are searchable within ~1 second, not immediately.
Lucene writes to an in-memory buffer → every 1 second, refreshed to a new segment (searchable) → eventually merged into larger segments.
This is why Elasticsearch is "near real-time" not "real-time." To force immediate visibility: ?refresh=true on indexing — forces a refresh but hurts write throughput. Only use for critical flows.
Lucene Segments
Lucene (the underlying library) writes data in immutable segments.
New documents → write buffer → periodic flush → new immutable segment. Background merges combine small segments into larger ones (like Cassandra SSTables, like ClickHouse parts).
Deletes are soft-deletes (marked, not removed) until a merge happens. This is why delete-heavy workloads require periodic forced merges to reclaim space.
03 · Typeahead / Autocomplete

Design: search-as-you-type at FAANG scale

Prefix Trie
A tree where each node is a character. Every path from root to leaf is a word. O(L) lookup for a prefix of length L — regardless of vocabulary size.
To find all words starting with "redis": traverse to node 'r'→'e'→'d'→'i'→'s', return all words in subtree.
✓ Fast prefix lookup. Memory-efficient with shared prefixes. Used by: Google Suggest backend, IDE autocomplete.
⚠ Storing popularity scores in a trie and returning top-K results requires augmenting each node with a max-heap — complex. Sharding a trie across machines is non-trivial.
Elasticsearch
Completion Suggester
Built-in completion suggester using an in-memory FST (Finite State Transducer) — more memory-efficient than a trie.
Index time: store completion field with weight (popularity score).
Query: suggest: {prefix: "red", field: "title.completion", size: 5}
Returns top-5 completions by weight instantly.
✓ Easy to implement on top of existing ES infrastructure. Handles millions of suggestions in milliseconds.
Redis ZSET Approach
Store all prefixes as ZSET members scored by popularity. For "redis", store "r", "re", "red", "redi", "redis" all pointing to the suggestion with its popularity score.
ZRANGEBYLEX suggestions "[redis" "[redisÿ" LIMIT 0 5
✓ Extremely fast (sub-ms). Works well for known vocabulary (hashtags, product names). Easy to update popularity in real time with ZINCRBY.
⚠ Storage: O(L × V) where L is avg word length and V is vocabulary size. For a 10M-word vocabulary, this becomes large.
04 · System Design Examples

Search in real systems

Twitter Search
500M TWEETS/DAY
WRITE PATH
New tweet → Kafka → Indexing Service → Elasticsearch. The Kafka buffer decouples tweet volume from ES indexing rate. ES indexes ~6K tweets/sec sustained. NRT lag: ~1 second before searchable.
SEARCH
Elasticsearch ✓ Full-text BM25 scoring + recency boost + engagement boost. Query rewriting: "from:elonmusk" → field-specific filter. Hashtag search: exact term match on the hashtag field (no tokenization).
TRENDING
Trending hashtags NOT from ES — from a streaming Count-Min Sketch pipeline (Kafka + Flink + Redis ZSET). ES is too slow for trending (requires aggregation queries). The two systems complement each other.
WHY NOT SQL
LIKE '%distributed%' on 500M tweets = full table scan = minutes. Elasticsearch full-text search on same data = milliseconds. Not even close.
05 · Follow-ups

Every hard follow-up, answered

How do you keep Elasticsearch in sync with your primary database?+
Two patterns, with very different trade-offs:

1. Dual write: Application writes to DB AND ES in the same request. Simple but dangerous — if ES write fails, you have inconsistency with no way to detect it. Acceptable only for non-critical search.

2. Change Data Capture (CDC): Debezium (or similar) reads the PostgreSQL WAL (Write-Ahead Log) and publishes every change to Kafka. An ES indexing consumer reads from Kafka and keeps ES in sync. This is the production approach:
— Source of truth is always the DB
— ES is an eventually consistent read replica
— On ES failure, reindex from DB
— Typical lag: 100ms–2s

Tools: Debezium + Kafka + Elasticsearch Kafka Connector. Used by: LinkedIn, Airbnb, Shopify.
What is vector search and when do you need it?+
Vector search finds documents semantically similar to a query, not just exact keyword matches.

Classic inverted index search for "fast database" would not return a document about "high-performance data store" — different words, even if same meaning. Vector search uses ML embeddings (e.g., OpenAI text-embedding-ada-002) to convert both query and documents to dense vectors in the same semantic space. Documents near the query vector in that space are semantically similar.

Implementation: index document embeddings in a vector database (Pinecone, Weaviate, Milvus, or Elasticsearch with kNN). Query: embed the query text → find K nearest neighbours using approximate nearest neighbour (HNSW algorithm).

When to use: semantic search ("show me articles about making databases fast"), recommendation ("more content like this"), Q&A (RAG — Retrieval Augmented Generation for LLMs).

Hybrid search: combine keyword BM25 + vector KNN scores (Reciprocal Rank Fusion). Best of both worlds — used by production AI search systems.
