00 · Why Rate Limiting

What collapses without it — the three failure modes

A single misbehaving client, a buggy retry loop, or a credential-stuffing bot can send 100,000 requests per second to your API. Without rate limiting, your database absorbs all of it until it falls over — and every other user is impacted. Rate limiting is the contract between your API and the outside world.

Three failure modes you are actually defending against
1. Accidental overload: A customer's backend has a bug — their retry loop goes infinite. They go from 10 req/sec to 100,000 req/sec. Without rate limiting: your API goes down for all customers. With it: their requests get 429s, your other customers are unaffected.

2. Abuse / scraping: A competitor scrapes your entire product catalogue. Without limits: they steal your data and you pay the egress bill. With it: they hit limits at 1,000 requests/minute and give up.

3. Brute force: An attacker tries 10M password combinations against your login endpoint. Without limits: they eventually succeed. With per-IP limits (5 attempts/minute → 7,200 attempts/day): trying all 10M combinations takes roughly 3.8 years — and a per-account lockout after a handful of failures makes it far worse for the attacker than that.
⚠ The interview trap that catches most candidates

"I'll rate limit by IP address" is the answer that gets a candidate cut off fast. IP is the weakest possible identity to rate limit on: NAT means thousands of legitimate users (an entire corporate office, a university, a mobile carrier's CGNAT pool) can share one IP, so a per-IP limit either starves them collectively or has to be set so loose it stops nothing. It's also trivially evaded — an attacker with a botnet or a residential proxy pool rotates IPs faster than any reasonable window resets. The strong answer rate-limits on authenticated identity (user ID from a validated token) as the primary key, with IP-based limiting layered on top only for unauthenticated endpoints (login, signup) where no user ID exists yet.

01 · The Five Algorithms

Token bucket, leaky bucket, fixed window, sliding window log, sliding window counter

Token Bucket
Industry Standard
A bucket holds up to N tokens. Tokens refill at rate R per second. Each request consumes 1 token. Empty bucket = rejected request.
Example: capacity=100 tokens, refill=10/sec. A burst of 100 requests is served immediately (empties the bucket). Then max 10/sec sustained.
Implementation: store (token_count, last_refill_time). On each request: tokens = min(capacity, stored_tokens + (now - last_refill) × rate). If tokens ≥ 1: decrement and allow. Else: reject. ✓ Allows legitimate burst traffic. O(1) memory per user. Smooth average enforcement. AWS API Gateway's throttling and Stripe's rate limiter are both explicitly documented as token bucket implementations — it's the default answer for "which algorithm" in an interview unless a specific requirement argues otherwise. ⚠ Two users can both exhaust their buckets at the same moment and both immediately refill — two full bursts back-to-back at window boundaries.
Leaky Bucket
Requests enter a fixed-size queue (the bucket). They drain at a fixed rate (the leak). Queue full = requests dropped.
Enforces exactly R requests/second regardless of arrival rate. A burst of 100 arrives — 100 enter the queue, they drain at 10/sec, all served over 10 seconds. ✓ Perfectly smooth outbound rate. Protects downstream services that can only handle a fixed rate (DB connection pool, third-party API with strict QPS). No traffic spikes ever reach the downstream. ⚠ Burst requests experience queuing latency, not fast rejection. A slow legitimate request queues behind a burst attacker's requests. If queue fills, the most recent requests (possibly legitimate) are dropped.
Fixed Window
Count requests per fixed time window. Reset counter at the boundary.
Example: 100 req/minute. Counter for window "14:03" resets at "14:04:00.000".
Redis: INCR ratelimit:user:123:14:03 → EXPIRE key 60 → check count ≤ 100. ✓ Simplest implementation. Single Redis INCR per request. Minimal memory. ⚠ Boundary attack: 100 requests at 14:03:59 + 100 requests at 14:04:01 = 200 requests in 2 seconds — both within their respective windows. Set your limit 50% conservatively to compensate, or use sliding window.
Sliding Window Log
Store a timestamp for every request in a sorted set. Count entries in the last N seconds. Reject if over limit.
Redis: ZADD log:user:123 {now_ms} {now_ms} → ZREMRANGEBYSCORE log 0 {now_ms - window_ms} → ZCARD log → compare to limit. ✓ Perfectly accurate. No boundary attack possible. True rolling window at all times. ⚠ Memory: O(requests per window) per user. At 1,000 req/min and 1M users: 1 billion sorted set entries. Only viable for low-rate, high-value endpoints: login, payment, account creation.
Sliding Window Counter
Production Choice
Interpolate between current and previous fixed window counts to approximate a rolling window. O(1) memory, ~0.003% error rate.
count = prev_window_count × (1 - elapsed/window_size) + curr_window_count
Example: window=1min, 40% through current minute. prev_window had 80 requests, current has 30.
Estimated rolling count: 80 × 0.6 + 30 = 78. Compare to limit. ✓ O(1) memory (two counters per user). Accurate enough: Cloudflare's own published analysis of this algorithm found a 0.003% wrongly-allowed/rate-limited rate across roughly 400 million sampled requests. The practical production algorithm at scale.

02 · Distributed Rate Limiting

Distributed Enforcement — Across Servers & Layers

The core problem

Each app server sees only 1/100th of total traffic. If you rate-limit locally at 100 req/min per server with 100 servers, your effective global limit is 10,000 req/min — 100x too permissive. You need a shared counter that all servers update atomically.

Redis INCR
with Lua Script
Atomic increment + check in a single Redis round trip using Lua.
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local current = redis.call('INCR', key)
if current == 1 then
  redis.call('EXPIRE', key, window)
end
if current > limit then
  return 0  -- rejected
else
  return 1  -- allowed
end
✓ Lua executes atomically in Redis — no race between check and increment. One network round trip. Works correctly under any concurrency.
Token Bucket in Redis
Atomic token bucket using Lua: refill tokens based on elapsed time, check, consume.
Key stores [token_count, last_refill_timestamp] as a hash.
Lua script: (1) read current tokens and last refill time, (2) compute new tokens = min(capacity, stored + elapsed × rate), (3) if tokens ≥ 1: set tokens−1, allow; else: reject.
All in one atomic operation. Libraries: redis-rate-limiter, redis-cell (native Redis module). ✓ Handles burst correctly in distributed context. Two servers both try to consume simultaneously → Lua serialises them → correct token count maintained.
Local Approximation
+ Async Sync
Each server maintains a local counter. Sync to Redis every 100ms. Reduces Redis calls by 100x.
Each server allows up to limit / server_count requests locally before checking Redis. Every 100ms, flush local count to Redis, refresh local quota. ✓ Reduces Redis round trips 100x at cost of slight inaccuracy. Burst of 200ms can exceed limit by up to limit × (100ms / window). Acceptable for most APIs. ⚠ Not suitable for strict financial or security rate limiting where brief overages could be exploited.

04 · System Design Examples

Rate limiting in production systems

Stripe — Multi-Dimensional API Rate Limiting
PAYMENTS · TIERED
DIMENSIONS
Stripe enforces rate limits on 3 independent dimensions simultaneously: per API key (100 req/sec), per endpoint (POST /charges: 25/sec separate from GET /customers), and per live/test mode (separate limits for test keys so testing doesn't consume production quota).
ALGORITHM
Token Bucket ✓ Allows burst traffic from legitimate API integrations (a customer's batch job), while enforcing sustained average limits. Idempotency keys work with rate limiting — duplicate requests use the cached response without consuming a new token.
HEADERS
Ratelimit-Limit: 100, Ratelimit-Remaining: 73, Ratelimit-Reset: 1742383260. On 429: Retry-After: 1 (seconds until next token available). Clients use these to implement exponential backoff + jitter before retrying.
TIERED LIMITS
API key's plan tier stored in JWT or Redis hash. Free: 25/sec, Pro: 100/sec, Enterprise: custom. Tier checked once per request from JWT claim — zero extra Redis lookup for tier. Only limit counter needs Redis.
Login Endpoint — Security Rate Limiting
BRUTE FORCE · AUTH
LAYERED DEFENCE
3 independent limits: (1) per-IP: 10 login attempts / 10 minutes — stops distributed credential stuffing from one location. (2) per-username: 5 attempts / 15 minutes — stops password spraying on one account from many IPs. (3) global: 10K login attempts / minute — circuit breaker for the entire auth service.
ALGORITHM
Sliding Window Log ✓ Exactly the right choice here. Login endpoint handles 10K/sec globally but the per-user limit is 5/15min — very small cardinality of allowed requests per user. Memory cost is acceptable. Accuracy matters — an attacker cannot exploit boundary timing.
PROGRESSIVE DELAYS
After 3 failed attempts: add 1-second delay. After 5: add 5-second delay. After 10: lock account, require email verification. This is orthogonal to rate limiting — slows automated tools even within rate limits.
Notification Service — Outbound Rate Limiting
THIRD-PARTY API · QUOTA
PROVIDER LIMITS
SendGrid allows 100K emails/hour. Twilio allows 1 SMS/sec per phone number. These are outbound limits — you rate-limit your own send rate to avoid hitting provider quotas that result in drops, not 429s you can handle.
ALGORITHM
Leaky Bucket ✓ Queue all outbound notifications. Drain at exactly provider-allowed rate. Excess is buffered (queue), not dropped. For SendGrid: fill 100K tokens/hour (27 tokens/sec), drain 1 token per email sent. If queue grows: auto-scale workers within token availability.
USER ANTI-SPAM
Separate per-user limits: max 2 SMS per user per 10 minutes, max 5 emails per user per hour. Prevents notification spam to individual users from rogue internal services. Independent from the global send-rate limits.
05 · Decision Framework

Choose the right algorithm for your use case

🎯Rate Limiting Algorithm Selection
01
Do you need to allow legitimate burst traffic?
YES (bursts OK) →Token Bucket. Accumulates tokens during quiet periods. Allows burst up to bucket capacity. Standard choice for REST APIs, SDKs, and developer-facing APIs.
NO (strict smooth rate) →Leaky Bucket. Enforces exactly R/sec regardless of arrival pattern. Use when protecting a downstream that cannot handle any spike: DB connection pool, third-party API, CPU-bound service.
02
How important is boundary-attack resistance?
Critical (auth/payment) →Sliding Window Log. Perfectly accurate. Immune to boundary timing attacks. Acceptable because rate limits are small (5 logins/15min) so memory cost is low.
High scale, OK with ~0.003% error →Sliding Window Counter. Cloudflare's production choice. O(1) memory. Handles billions of requests. Not perfectly accurate but close enough for all practical purposes.
Low stakes, simplicity first →Fixed Window. Single Redis INCR. Set limit 50% conservatively to compensate for boundary doubling. Simple to implement, debug, and monitor.
03
What is the enforcement layer?
External API traffic →API Gateway layer. Kong, AWS API Gateway, or Nginx. Centralised enforcement before any application code runs. Language and framework agnostic.
Business logic limits (plan tiers) →Application middleware. Redis-backed. Access to business context (user plan, feature flags). Apply different limits per tier.
Service-to-service internal →Service mesh (Istio/Envoy). Circuit breaking + local rate limiting per sidecar. Prevents a runaway microservice from overwhelming its dependencies.
06 · Follow-ups

Every hard follow-up, answered

How do you implement tiered rate limits for free/pro/enterprise plans?+
Embed the tier in the JWT, map to limits in config, use tier in the Redis key.

JWT payload includes "plan": "pro" — decoded at the rate limit middleware with zero extra lookups. A config map translates plan to limit: {"free": 25, "pro": 100, "enterprise": 10000}. The Redis key includes the plan: ratelimit:pro:user:123:minute.

Why include plan in the key: if a user upgrades from free to pro mid-window, their free-plan counter simply stops being checked. The pro counter starts fresh. No need to invalidate or reset anything.

For enterprise customers with custom limits: store the custom limit in Redis itself (ratelimit:config:user:123 = 50000) with fallback to the plan default if not set. Check this config key on each request (cached in-process for 60 seconds to avoid per-request Redis lookups).
What happens if your Redis rate limit store goes down?+
You must decide: fail open (allow all traffic) or fail closed (reject all traffic). There is no free lunch.

Fail open: if Redis is unreachable, allow all requests. Users see no degradation. Abuse is possible during the outage window. Acceptable for: consumer APIs where rate limits are about fairness, not security. Google's approach for most rate limiting.

Fail closed: if Redis is unreachable, return 429 or 503. Zero abuse possible. Legitimate users are blocked. Acceptable for: payment APIs, authentication endpoints, anything where abuse has direct financial or security cost.

Hybrid (recommended): fall back to local in-process counters. Each app server tracks its own count. If Redis is down, enforce limit / server_count locally. This is slightly over-permissive (multiple servers don't coordinate) but functional. As soon as Redis recovers, switch back to shared counters. Redis Sentinel or Cluster ensures Redis outages are brief (<30 seconds for automatic failover).
How do you rate-limit on distributed clients — a user calling from multiple IPs or devices?+
Rate limit on authenticated user identity, not on IP. IP-based limiting is supplementary only.

The user's user_id extracted from their JWT is the primary rate limit key: ratelimit:user:{user_id}:{window}. This accumulates across all their devices, IPs, and sessions. A user signing in from phone + laptop + tablet all share the same quota. Prevents circumventing limits by rotating devices.

IP-based limiting runs in parallel as a separate independent limit — specifically for unauthenticated endpoints (login, signup, password reset) where you don't yet have a user_id. For these: ratelimit:ip:{hashed_ip}:{window}. Hash the IP (SHA-256 first 8 bytes) — prevents storing raw PII, harder to reverse than plain IP storage.

Never use IP as the sole mechanism for authenticated APIs — enterprise customers may have thousands of users behind a single NAT IP (corporate proxy, VPN). A per-IP limit of 1,000/min would mean 1 request per user per minute for a 1,000-person company behind one IP.
How do you handle the circuit breaker pattern as it relates to rate limiting?+
Rate limiting and circuit breaking are complementary but solve different problems.

Rate limiting: "You are sending too many requests — slow down." Applied at the entry point to protect your service from external or internal overload. Proactive.

Circuit breaking: "The downstream service is failing — stop sending requests to protect it and yourself." Applied at the exit point (your outbound calls to dependencies). Reactive to failure.

Circuit breaker states: Closed (normal, all requests pass through) → Open (downstream is failing, immediately return error without calling downstream) → Half-Open (probe with one request — if success, close; if failure, stay open).

They work together: rate limiting prevents your service from being overwhelmed. Circuit breaking prevents your service from overwhelming a failing dependency. In Envoy/Istio: configure both — rate limiting on the ingress side, circuit breaking on the egress side for each service call.
07 · Redis Implementation — Atomicity & Lua Scripts

How to implement rate limiting correctly in Redis without race conditions

01 Sliding Window with Lua Script
What it is
Lua scripts in Redis execute atomically — multiple Redis commands as one atomic operation.

The race condition without Lua: (1) GET count (2) if count < limit → INCR (3) SET expiry. Between steps 1 and 2, another request can GET the same count and both increment — exceeding the limit.

The Lua solution (runs as a single atomic transaction):

local key = KEYS[1]

local limit = tonumber(ARGV[1])

local window = tonumber(ARGV[2])

local current = redis.call('INCR', key)

if current == 1 then redis.call('EXPIRE', key, window) end

if current > limit then return 0 else return 1 end

Redis executes this Lua script as one atomic unit — no other commands can interleave. No race condition possible.

02 Token Bucket with Redis
What it is
Precise token bucket using Redis MULTI/EXEC or Lua for atomicity:

Key: ratelimit:{user_id} → Hash with fields: tokens (current bucket level), last_refill (timestamp).

On each request: calculate tokens to add since last_refill (rate × elapsed seconds). Cap at bucket capacity. Check if tokens ≥ 1. If yes: decrement tokens, allow request. If no: reject with 429.

All of the above in a single Lua script to ensure atomicity. Returns: allowed (1) or rejected (0) + current token count + time until next token.

Retry-After header: include X-RateLimit-Reset: {unix_timestamp} in 429 responses. Client knows exactly when to retry. Prevents exponential backoff pileup — all clients retry at the same informed time instead of random exponential times.

03 Distributed Rate Limiting Without Redis
What it is
When Redis is unavailable: fail open vs fail closed — a critical production decision.

Fail open: if Redis is unavailable, allow requests through. Rate limiting is a best-effort feature. Service stays available. Risk: unprotected during Redis outage — a DDoS during a Redis outage can overwhelm the service.

Fail closed: if Redis is unavailable, reject all requests (or allow only a local-cache-based limit). Service is protected but unavailable. For authentication endpoints (brute force protection): fail closed is correct. For API quota limiting: fail open is usually correct.

Local fallback: each app server maintains a local rate limiter (Guava RateLimiter) as a fallback. Less accurate (doesn't coordinate across servers) but better than either extreme.

→Circuit breaker on the rate limiter itself: if Redis is returning errors, switch to local limiter automatically. When Redis recovers, switch back. The rate limiter protecting your service must itself be resilient.
⚠ · Failure Modes

What actually breaks in production — real incident patterns

01The Global Limit That Isn't Global
What breaks & how
A team sets "100 req/min per user" but implements it as an in-process counter on each app server instead of a shared store. With 50 app servers behind the load balancer, the effective limit becomes 5,000 req/min per user — 50x too permissive — and nobody notices until a single account's traffic spike takes down a downstream dependency the rate limit was supposed to protect.
⚠Fix: enforce on a shared store (Redis) with an atomic script, not per-process counters. If you must tolerate Redis outages, fail over to limit / server_count locally — over-permissive but bounded, not unbounded.
02Thundering Herd at the Reset Boundary
What breaks & how
Fixed-window rate limiting resets every client's counter at the same wall-clock boundary. A large fleet of clients that all got throttled near the end of one window retry the instant the next window opens — a self-synchronized burst that looks identical to an attack, aimed squarely at the moment your system is least prepared for it (right after a quiet, throttled period).
⚠Fix: sliding window (log or counter) instead of fixed window removes the hard reset boundary entirely. If fixed window is unavoidable, add jittered retry-after guidance in the 429 response so clients don't all retry at exactly :00.
03The Rate Limiter Becomes the Outage
What breaks & how
Redis — now in the critical path of every single request — has a brief network blip. A rate limiter configured fail-closed rejects 100% of traffic during the blip, turning a 10-second infrastructure hiccup into a full outage for every customer, which is a strictly worse outcome than the abuse scenario the rate limiter exists to prevent.
⚠Fix: fail-closed only where the cost of under-protection (brute force on auth) clearly exceeds the cost of an outage. Everywhere else, fail open or fall back to a local approximate limiter, and alert loudly on the fallback so the degraded accuracy window is short and visible.
📋 · Requirements & Scale

Requirements & Non-Functional Constraints

Functional Requirements

FR1The system must limit how many requests a single identity (user, API key) can make in a given window, using an algorithm chosen for the traffic pattern — bursty-but-bounded (token bucket) vs. strictly smooth (leaky bucket) vs. exact accounting (sliding window).
FR2Limits must be enforceable on more than one dimension simultaneously (user, IP, endpoint) so that a well-behaved user isn't penalised for another identity's abuse on a shared resource, and so no single endpoint can be starved by traffic aimed at another.
FR3Different customer tiers (free, pro, enterprise) must be able to have different quotas enforced from the same rate-limiting infrastructure, without a code change per tier.
FR4Every response — allowed or rejected — must tell the client how much quota remains and, on rejection, when it's safe to retry, so well-behaved clients can back off correctly instead of hammering the endpoint.
FR5The limit must be enforced correctly across the whole fleet of app servers, not per-server — a shared, atomically-updated counter, not independent local counters that silently multiply the effective limit by the server count.
FR6The system must have a defined, deliberate behavior for when its own enforcement store (Redis) is unavailable — either fail open (stay available, temporarily unprotected) or fail closed (stay protected, temporarily unavailable) — chosen per endpoint based on which failure mode is cheaper.

Non-Functional Requirements

NFR1Rate limit check overhead: a target to defend, commonly sub-millisecond to low-single-digit milliseconds for one Redis round trip on the same network — measure it on your own infrastructure rather than citing a fixed number.
NFR2Accuracy: a design choice per endpoint class, not a universal constant — exact enforcement (sliding window log) for low-volume, high-stakes endpoints (auth, payment); an approximation with a small, known error rate (sliding window counter) is an acceptable and common trade-off at high volume.
NFR3Redis throughput: published benchmarks show roughly 100K–200K simple GET/SET/INCR ops/sec per core without pipelining on typical hardware, climbing past 1M ops/sec only with request pipelining — since a rate-limit check is a single unpipelined round trip, budget from the lower figure, not the pipelined one.
NFR4Distributed consistency: not a number — a correctness property. Atomic Lua scripts (or an equivalent single round-trip primitive) are what actually prevents the check-then-increment race, not "using Redis" by itself.
NFR5Retry-After precision: a design goal, not a fixed number — token-bucket implementations can compute time-to-next-token exactly, which is why Stripe and similar APIs can return a precise retry hint instead of a generic backoff suggestion.
NFR6Observability: a requirement to define concretely for your system (which metrics, what alert thresholds) rather than a number — at minimum, rate-limit-hit rate per endpoint and per identity, so you can distinguish "one abusive client" from "the limit is miscalibrated for everyone."
