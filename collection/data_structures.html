00 · Bloom Filter

Probabilistic membership testing — "definitely not" or "probably yes"

The club bouncer analogy
A Bloom filter is like a bouncer who checks a blacklist. If the blacklist says someone is banned, they might actually be banned — OR it might be a false positive (wrong person). But if the blacklist says someone is NOT banned, they are definitely not banned. No false negatives.

This asymmetry — perfect recall, imperfect precision — is exactly what makes Bloom filters useful. "Is this item in the set?" → "Definitely not" (perfect) or "Probably yes" (with a known false positive rate).
⚠ The interview trap that catches most candidates

"I'll use a Bloom filter to store the set of banned users, then check it before letting someone log in." This is backwards from what a Bloom filter can safely guarantee. A Bloom filter can tell you "definitely not banned" with certainty, but "probably banned" always carries a false-positive risk — some fraction of legitimate users will be wrongly flagged as banned and locked out. The correct answer names the asymmetry explicitly: use a Bloom filter as a fast pre-filter before an expensive, authoritative check (skip a disk read, skip a network call) — never as the final source of truth for anything where a false positive has a real cost (security denials, billing, exact deduplication). If false positives are unacceptable, that's a signal you need an exact structure (hash set, or a Cuckoo filter if you also need deletion), not a Bloom filter.

01How It Works
What it is
A bit array of size m, with k independent hash functions. Insert "redis": hash1("redis")=42, hash2("redis")=891, hash3("redis")=3042 → set bits 42, 891, 3042 to 1. Query "redis": hash all 3 positions → if ALL bits are 1 → "probably in set." If ANY bit is 0 → "definitely not in set." False positive: "kafka" happens to hash to positions where all bits are 1 (set by other items) → reports "probably yes" even though "kafka" was never inserted. False negative: impossible — inserted items always set their bits. Those bits stay 1 forever.
02Space Math
What it is
For n items with false positive rate p: m = -n × ln(p) / (ln2)² bits. Optimal k = m/n × ln2 hash functions. 1 billion URLs, 1% false positive rate: m = -1B × ln(0.01) / 0.48 ≈ 9.6 bits/item = 1.2 GB. Compare: storing 1B URLs as SHA-256 hashes = 1B × 32 bytes = 32 GB. Bloom filter is 26× more compact. For 0.1% false positive: 1.8GB (50% more space, 10× less false positives).
03Production Uses
What it is

Everywhere a "probably not" check avoids an expensive lookup:

Cassandra/HBase: before reading an SSTable from disk (expensive), check a Bloom filter. If "definitely not in this SSTable" → skip the disk read entirely, avoiding an unnecessary disk I/O for every SSTable the filter correctly rules out. The exact fraction of reads saved depends on your workload and false-positive rate, not a fixed industry percentage.

Chrome Safe Browsing: Chromium's own design keeps the client-side Bloom filter's serialized size under roughly 2MB — a size budget, not a fixed item count — checked locally before falling back to a network round trip to Google's servers for anything that isn't a definite "not present."

Redis: native BF.ADD / BF.EXISTS commands. Used for: seen-URLs deduplication in crawlers, unique event deduplication in streaming pipelines.

04When NOT to Use
What it is
Bloom filters cannot delete items. Once a bit is set, it stays set. If you need deletion: use a Counting Bloom Filter (each "bit" is a counter, decrement on delete) at 4× the memory cost. Or use Cuckoo Filter (supports deletion, better practical performance at low false positive rates).
⚠⚠ Don't use Bloom filter when false positives are unacceptable (security checks where a false positive lets a malicious URL through). Don't use when you need exact set membership (financial deduplication).
01 · Trie

Prefix tree — the data structure behind autocomplete

The dictionary-by-spelling analogy
Imagine sorting words not alphabetically in a list, but by building a physical structure: a box labelled "C", inside it a box labelled "A" (for words starting "CA"), inside that a fork — one path labelled "T" (for "cat"), another labelled "R" (for "car", and inside that, one more box "D" for "card").

To find every word starting with "ca", you don't scan every word in the dictionary — you walk straight to the "C" → "A" box and grab everything inside it. The shared prefix "ca" is stored exactly once, as a location in the structure, not repeated in every word. That's a trie: a tree where the path from the root spells out a prefix, and everything below a given node shares that prefix.
01How It Works
What it is
A tree where each node represents one character. Every path from root to a leaf node represents a word. Words "cat", "car", "card": root→c→a→t (end), root→c→a→r (end)→d (end). The prefix "ca" is shared — stored once. Prefix search: traverse to the node for the last char of your prefix ("ca") → return all words in the subtree below it. O(L + R) where L is prefix length and R is result count.
✓✓ O(L) lookup regardless of vocabulary size. Memory-efficient for shared prefixes. Every IP routing table in routers uses a trie variant (Patricia trie). DNS resolution uses tries for domain suffix matching.
02Autocomplete Design
What it is
Trie + frequency scores = autocomplete system. Each end-of-word node stores a popularity score. Query "redis" → traverse to 's' node → return top-K words in subtree by score (use a min-heap of size K during traversal). At FAANG scale (1M+ vocabulary): store trie in memory on dedicated autocomplete servers. Update scores in background from click-through logs. Shard by first letter if needed (26 shards, each holds 1/26 of vocabulary). Alternative at scale: Elasticsearch Completion Suggester (FST in memory), or Redis ZSET prefix trick for simpler cases.
03IP Routing
What it is
Routers use Patricia Tries (compressed tries) to match IP prefixes in nanoseconds. IP 192.168.1.100: look up in the trie bit by bit. The longest matching prefix determines the next hop. With millions of routing table entries, a trie provides O(32) lookup (32 bits in IPv4, 128 in IPv6).
→CIDR blocks in AWS security groups use trie-based matching. Firewall rules use trie prefix matching. Every packet routing decision in the internet uses this data structure.
02 · Merkle Tree

Cryptographic data integrity — the tree behind Bitcoin and Cassandra repair

01How It Works
What it is

A tree where every leaf node contains the hash of a data block. Every internal node contains the hash of its children's hashes. Root hash = hash(hash(hash(data1)+hash(data2)) + hash(hash(data3)+hash(data4))) If data3 changes → its leaf hash changes → its parent hash changes → the root hash changes.

Key property: to verify that data3 is correct, you only need: hash(data3) + hash(data4) + left subtree root hash. You verify 3 values to prove 1 item in a tree of N items. O(log N) proof.

02Cassandra Anti-Entropy
What it is
Cassandra uses Merkle trees to efficiently find which data diverges between two replicas. Each replica builds a Merkle tree of its data. Exchange only the root hashes (cheap). If different: compare child hashes, recursively narrowing down until you find exactly which token ranges have divergent data. Repair only those ranges.
✓✓ Without Merkle trees: comparing two replicas requires comparing every single row (petabytes). With Merkle trees: O(log N) exchanges to find divergent segments — then repair only the divergent data. nodetool repair uses this internally.
03Blockchain / Git
What it is
Bitcoin blocks use Merkle trees for transaction verification. Git uses Merkle DAGs. Bitcoin: a block contains thousands of transactions in a Merkle tree. To prove transaction X is in a block, provide the Merkle proof (O(log N) hashes). Light nodes verify without downloading all transactions. Git: every commit is a Merkle DAG snapshot. Two commits differ → traverse the tree to find which files changed. git diff uses Merkle comparison. Identical files across commits share hash nodes — this is why git is space-efficient.
03 · Quadtree & Geospatial Indexing

Finding things near a location — Uber's core data structure

01Quadtree
What it is
A tree that recursively divides 2D space into four quadrants. Each node covers a geographic region. Start: root covers the entire world. If a region has too many points (e.g., >4 drivers), split into 4 sub-regions. Recurse until each leaf has ≤4 points. Query "find drivers within 2km of 12.9716°N, 77.5946°E": traverse the quadtree, finding all leaf nodes that overlap with the 2km circle. Return all points in those leaves. O(log N + result size).
✓✓ Dense urban areas (Mumbai, New York) get many small cells. Sparse rural areas get large cells. Automatically adapts to data density. Used for: Uber driver proximity, Yelp nearby restaurants, Twitter geosearch.
02Geohash / S2 Cells
What it is
Encode geographic coordinates into a string or cell ID. Nearby locations share a common prefix. Geohash: "tdr1w" covers a ~5km × 5km area in Bangalore. "tdr1wx" is a sub-cell. All geohashes starting with "tdr1w" are within that bounding box. Nearby query: find all geohashes within 1 level of precision of the target. S2 cells (Google): hierarchical cell decomposition of the sphere (not a flat map). Level 0 = whole Earth. Level 30 = ~1cm². Each cell has a 64-bit integer ID. Used by: Google Maps, Uber (S2 library open-sourced by Google).
→Geohash is simpler and widely supported. S2 is more accurate (handles sphere curvature) and better for large-radius queries near poles. Redis GEORADIUS uses geohash internally.
03Proximity System Design
What it is
The standard architecture for "find N nearest entities" at FAANG scale: Driver locations → update Redis GEOADD every 4 seconds → GEORADIUS pickup_location 2 km ASC COUNT 10 → nearest 10 drivers, sorted by distance, in <1ms. At very high scale: shard by geohash prefix (all drivers in "tdr" geohash shard → same Redis instance). Prevents hotspots in dense cities. Historical data: S2-indexed Cassandra for trip history and analytics. Redis for live positions only.
04 · Skip List

Redis ZSET's secret — why it beats a balanced BST

The express-train analogy
A subway line has a local train that stops at every station, and an express train that only stops at every 4th station. To get from station 1 to station 19, you don't ride the local the whole way — you take the express to the station nearest your destination, then switch to the local for the last few stops.

A skip list is a sorted linked list with several of these "express lines" stacked on top of the base list, each skipping more stations than the one below it. Searching starts on the fastest express line and drops down a level every time it overshoots — reaching any element in roughly logarithmic time without ever needing to rebalance a tree.
01How It Works
What it is
A sorted linked list with multiple "express lanes" that skip over elements for faster traversal. Level 0: every element → [1] → [3] → [7] → [12] → [19] → [25] Level 1: every 2nd element → [1] → [7] → [19] → [25] Level 2: every 4th element → [1] → [19] Find 12: start at highest level, jump to 19 (too big), drop to level 1, jump to 7, drop to level 0, walk to 12. O(log N) expected.
✓✓ Same O(log N) as a balanced BST. But skip list is lock-free for concurrent access (CAS on pointers). Simpler to implement correctly. Cache-friendlier (linked list, not tree nodes scattered in memory). Redis chose skip list for ZSET for exactly these reasons.
02Redis ZSET Internals
What it is
Redis Sorted Sets use a skip list + hash table hybrid. Hash table: O(1) score lookup by member ("what is user:123's score?"). Skip list: O(log N) rank queries ("what rank is user:123?") and range queries ("return members with score 100–200"). ZADD: O(log N). ZRANK: O(log N). ZRANGEBYSCORE: O(log N + result size). ZSCORE: O(1).
→The skip list is why ZREVRANGE (return top-K by score) is efficient. A simple sorted array would be O(1) read but O(N) insert. The skip list gives O(log N) for both — the right trade-off for a leaderboard that's constantly updated and queried.

05 · System Design Examples

Data structures in production

Web Crawler — Bloom Filter for URL Deduplication
1 BILLION URLs · 1.2GB RAM
PROBLEM
A web crawler must not visit the same URL twice. With 1 billion URLs in the visited set, a HashSet requires 32GB (SHA-256 hashes). The crawler runs on a single machine with 16GB RAM.
SOLUTION
Bloom filter: m = 9.6 bits/URL × 1B = 1.2GB. False positive rate = 1% (1% of new URLs incorrectly marked as "already visited" → skipped). Acceptable trade-off: a crawler that misses 1% of new pages is far better than one that crashes from OOM.
DISTRIBUTED
Distributed Bloom filter: 10 crawlers share a Redis Bloom filter (Redis BF.ADD/BF.EXISTS). All crawlers coordinate via the shared filter. Each add/check is a single Redis command — ~0.1ms. No distributed locking needed (Bloom filter operations are commutative).
Uber — Real-Time Driver Proximity
GEOHASH · REDIS GEO
DATA MODEL
Redis GEO key per city: GEOADD drivers:bangalore 77.5946 12.9716 driver:123. Each driver update (every 4 seconds): GEOADD drivers:bangalore {lng} {lat} {driver_id} — updates position in the geo index.
QUERY
GEORADIUS drivers:bangalore 77.5946 12.9716 2 km ASC COUNT 10 → 10 nearest drivers sorted by distance. Returns in <1ms. Redis GEO uses a geohash-based sorted set internally — Geohash encoded as ZSET score.
SHARDING
One Redis key per city holds all drivers in that city. At 50,000 drivers per city, the ZSET has 50K members — trivially fast. Cities are natural shards: Bangalore drivers never need to be co-located with Mumbai drivers.

🎯Which Structure for This Problem?
1
Do you need an exact answer, or is a bounded error acceptable in exchange for far less memory?
Approximate is fine →Probabilistic structure. Bloom filter for membership, Count-Min Sketch for frequency, HyperLogLog for cardinality — all trade a small, tunable error rate for orders-of-magnitude less memory than an exact structure.
Must be exact →Go to Step 2 — pick among the exact structures based on the query shape you actually need.
2
Is the query "give me everything sharing this prefix"?
Yes →Trie. Autocomplete, IP routing, any domain where keys naturally share prefixes and you want O(L) lookup regardless of vocabulary size.
No →Go to Step 3.
3
Do you need to detect exactly which records diverged between two large replicas or datasets?
Yes →Merkle tree. Anti-entropy repair, content-addressed storage, any "prove/find the difference without comparing everything" problem.
No →Go to Step 4.
4
Is the query fundamentally spatial ("what's near this point") or ordinal ("what's ranked near this value")?
Spatial →Quadtree or geohash/S2. Proximity search, geospatial indexing — pick geohash for simplicity and library support, S2 when sphere accuracy near poles or at large radius matters.
Ordinal / ranked →Skip list. Sorted sets, leaderboards, range queries with concurrent access — this is exactly why Redis chose it for ZSET over a balanced BST.
06 · Follow-ups

Every hard follow-up, answered

When would you use a Bloom filter vs a Count-Min Sketch?+
Different questions → different data structures.

Bloom filter: "Is item X in the set?" → YES/NO with bounded false positive rate. Binary membership. Insert, query. No counting. Used for: URL deduplication, Cassandra SSTable filtering, Chrome malicious URL check.

Count-Min Sketch: "How many times has item X appeared?" → approximate count with bounded error. Frequency counting. Insert, increment, query count. Used for: Top-K trending, frequency estimation, network traffic analysis.

The analogy: Bloom filter = bouncer checking a blacklist (in/out). Count-Min Sketch = tallying how many times each voter voted. Completely different operations, similar space efficiency principles.
How does a consistent hash ring relate to a trie in terms of prefix routing?+
Both use prefix matching for routing, but in completely different spaces.

A trie routes by string prefix: "what node handles all keys starting with 'user:1'?" Deterministic, hierarchical. Used for: DNS routing, IP routing, autocomplete.

A consistent hash ring routes by hash value prefix/range: "what node handles all keys whose hash falls in range [0x3000, 0x6000]?" Pseudo-random distribution (hash function destroys original prefix). Used for: distributed cache sharding, Cassandra token ring.

The practical distinction: tries work on the semantic structure of keys (natural prefixes matter). Consistent hashing deliberately destroys key structure to achieve uniform distribution. Use a trie when you want keys with similar prefixes to co-locate (range queries). Use consistent hashing when you want uniform distribution across nodes.
How would you implement a "users near me" feature for a social app with 100M users?+
Three layers: live location (Redis GEO), privacy controls (opt-in + fuzzing), search index (geohash-sharded).

Data model: users who opt into location sharing update their position periodically (once per hour is sufficient for "users near me" — not a real-time driver tracker). Store in Redis: GEOADD users:geo {lng} {lat} user:{id} with TTL (if not updated in 24h, consider offline).

Privacy: never store or transmit exact coordinates. Apply a random offset (±500m) before storing — "near me" doesn't need precision. User sets privacy: exact neighborhood, city only, or hidden. Store the fuzzed version only.

Query: GEORADIUS users:geo {my_lng} {my_lat} 5 km COUNT 50. Filter by privacy settings and mutual connection status. Limit result set to prevent information harvesting.

Scale: 100M users, ~10% share location = 10M active entries. One Redis GEO key with 10M members is manageable (~800MB). Or shard by geohash prefix (4-char geohash = ~40km × 40km cells, ~500 cells for India — 500 Redis keys).

The hard part: GDPR/privacy regulations require explicit consent, right to deletion, and data minimisation. "Delete my location" must purge from Redis immediately. Audit logs of who queried your location. This is more important than the technical implementation in a real interview.
How does Git use Merkle trees and why does that matter for system design?+
Git's entire efficiency comes from content-addressable storage using SHA-1/SHA-256 hashes — a Merkle DAG.

Every blob (file), tree (directory), commit in git has a hash based on its content. A commit's hash depends on: the tree hash (all files), the parent commit hash, author, timestamp, message. Changing any file changes the tree hash → changes the commit hash → changes all descendant commit hashes. This is why commit SHAs provide tamper detection.

Deduplication: if two commits contain the same file, they share the same blob hash — stored once. This is how git repos stay small even with thousands of commits.

System design application: the same principles apply to distributed storage systems. Docker image layers use content-addressable storage (each layer is a hash of its content). Sharing layers across images = storage deduplication. IPFS (InterPlanetary File System) uses Merkle DAGs for distributed content-addressable storage. The pattern: hash the content → use the hash as the address → automatic deduplication + integrity verification.
📋 · Requirements & Scale

Requirements & Non-Functional Constraints

Functional Requirements

FR1The system must be able to answer "have I definitely never seen this item?" in a way that never produces a false negative, using far less memory than storing every item exactly — trading a small, tunable false-positive rate for that space saving (Bloom filter).
FR2The system must return every stored item sharing a given prefix in time proportional to the prefix length, not the size of the whole vocabulary — the basis for autocomplete and longest-prefix-match routing (Trie).
FR3The system must be able to prove two large replicas of the same dataset are identical, or pinpoint exactly which pieces diverged, without transferring or comparing every record between them (Merkle tree).
FR4The system must support fast insert, delete, and ordered range queries on a frequently-changing sorted collection, under concurrent access, without the rebalancing complexity of a balanced tree (Skip list).
FR5The system must be able to find all entities within a given radius of a location efficiently, adapting automatically to uneven data density (many points in a city, few in open country) (Quadtree / Geohash).
FR6The system must estimate how many times each of a very large or unbounded number of distinct items has occurred, using a fixed memory budget that does not grow with the number of distinct items seen (Count-Min Sketch).

Non-Functional Requirements

NFR1Bloom filter space: ~9.6 bits per item is the mathematically-derived requirement for a 1% false-positive rate (from the standard formula m = −n·ln(p)/(ln 2)²) — this is a formula output you can recompute for your own target error rate, not a number to cite as a vendor fact.
NFR2Trie lookup is O(L) where L is the prefix length, independent of vocabulary size — an algorithmic property of the data structure, not a benchmark figure.
NFR3Merkle-tree comparison requires O(log N) hash exchanges to localize a divergence in a tree of N leaves — an algorithmic property, not a measured target.
NFR4Skip list operations are O(log N) in expectation (not worst-case guaranteed, since the structure is probabilistic) for insert, delete, and search — state this as an expected-case property when discussing it, not an absolute bound.
NFR5Geohash precision by string length (standard, verifiable table): 6 characters ≈ ±0.61km cell size; 9 characters ≈ ±2.4m; 12 characters ≈ ±1.9cm — precision improves by roughly one order of magnitude every ~3.3 characters. Pick the length that matches the precision your use case actually needs (city-block-scale ride matching doesn't need centimeter geohashes).
NFR6Count-Min Sketch update and query are O(d) (the number of hash rows), commonly described as O(1) since d is a small constant chosen at design time; total memory is O(w×d) — algorithmic properties, not vendor-specific numbers.
⚠ · Failure Modes

When data structures fail in production

01Bloom Filter False Positive AvalancheFAILURE MODE
What breaks & how
The filter was sized for N items but keeps taking inserts past that — every additional item sets more bits to 1, and the false-positive rate climbs, potentially far past its designed target. In Cassandra, an under-sized bloom filter means far more reads incorrectly fail to skip the SSTable that doesn't contain the key — you don't lose data, but you pay the disk read the filter was supposed to save you, and read latency degrades cluster-wide.
⚠Monitor the filter's observed false-positive rate against its design target (Cassandra exposes bloom filter false-positive ratio per table via nodetool tablestats/cfstats). Size the filter for expected item count with headroom, and re-run compaction/upgradesstables if the table has grown well past the original sizing assumption.
02Skip List Memory Explosion — Redis OOMFAILURE MODE
What breaks & how
A Redis ZSET leaderboard with no cap on membership (every user who ever scored, never trimmed) grows unbounded. Once it approaches the instance's maxmemory, Redis either evicts keys (if a maxmemory-policy is set) or starts rejecting writes with OOM errors (if it isn't) — and if Redis crashes or is killed by the OS OOM killer, every other key on that instance goes down with it, not just the oversized ZSET.
⚠Always set maxmemory and an explicit maxmemory-policy. Cap leaderboard size at write time with ZADD followed by ZREMRANGEBYRANK 0 -(K+1) to keep only the top K. Monitor memory via INFO memory in production, not just at deploy time — organic growth is the usual culprit, not a single bad deploy.
03Geohash Boundary Problem — Missing Nearby PointsFAILURE MODE
What breaks & how
A driver sits just across a geohash cell boundary from the rider — geographically 50 metres away, but in a cell whose string prefix shares nothing with the rider's cell. A naive "search this cell only" implementation misses them entirely, even though they're the closest driver available.
⚠Always search the cell plus its 8 neighbours (9 cells total) for proximity queries, then merge and deduplicate by driver id. Redis's own GEORADIUS/GEOSEARCH commands handle this correctly internally — the failure mode shows up specifically in hand-rolled geohash-prefix lookups that skip this step.
04Merkle Tree Repair StormsFAILURE MODE
What breaks & how
Anti-entropy repair (Cassandra's nodetool repair) walks Merkle trees across replicas and streams every divergent range it finds. If repair has been skipped for too long, or a node was down for an extended window, the divergent range can be large — the resulting repair streams heavy data and consumes significant CPU/network on every replica involved, degrading read/write latency for unrelated queries hitting the same nodes during the repair window.
⚠Run repair on a predictable schedule (before gc_grace_seconds elapses — 10 days by default) rather than reactively. Use incremental or subrange repair to bound the blast radius of any single repair run, and schedule repairs to avoid overlapping with peak traffic windows.
