00 · Start Here

Before picking a database, answer one question

Most candidates jump straight to "I'll use PostgreSQL" or "I'll use Cassandra" without justifying the choice. The interviewer doesn't care which database you pick — they care whether you understand what each is optimised for and why it matches your access pattern.

The filing cabinet analogy — for a complete layman
Imagine you're running a law firm with four types of filing systems:

PostgreSQL is a meticulous paralegal with a master index. Ask anything — "all cases involving John AND contract law from 2022" — and they find it. But they can only work so fast, and adding more paralegals requires careful coordination.

MongoDB is a flexible folder system. Each folder can hold anything — a mix of documents, photos, notes. Great when your documents have varying shapes and you're still figuring out what you need to ask.

DynamoDB is a warehouse with perfectly labelled shelves. If you know the shelf number, retrieval is instant and the warehouse grows infinitely. But you can only ask "what's on shelf 7B" — not "show me everything red."

Cassandra is a warehouse distributed across 10 cities. Every city holds a copy of relevant files. Writes go to all 10 simultaneously. No city going down stops you. But reorganising the filing system later is painful.
The only three questions that matter

1. What is your write pattern? Low-volume transactional writes (PostgreSQL/MongoDB) vs high-throughput append-heavy writes (Cassandra/DynamoDB)?

2. What is your read pattern? Flexible ad-hoc queries (PostgreSQL) vs known key-based lookups (DynamoDB/Cassandra)?

3. Do you need ACID transactions? If yes: PostgreSQL. If no: the others can offer far more scale.

03 · The Hard Part

Sharding — How Each Database Splits Data Across Machines

Sharding is splitting your data across multiple machines so no single machine holds everything. This is the most-tested topic in FAANG interviews because it forces you to confront real trade-offs.

Sharding explained with a phone book
You have a phone book with 1 billion entries. It's too heavy for one shelf. You split it:

Range sharding — A–F on shelf 1, G–M on shelf 2, N–Z on shelf 3. Simple, but "S" names might dominate (hot shard).

Hash sharding — Run the name through a hash function, result tells you which shelf. Perfectly balanced, but you can't look up "everyone between Adams and Brown" anymore.

Consistent hashing — Like hash sharding but when you add a new shelf, you only move a fraction of entries, not half of everything.
PostgreSQL
Manual / Citus
Postgres doesn't shard natively. You either shard at the application layer or use the Citus extension. Both are complex to operate. Cross-shard joins require careful design. Great for read replicas; write sharding is painful.
HARD — DIY or Citus
MongoDB
Built-in Sharding
Native range and hash sharding via a mongos router. Shard key choice is the most critical decision. Bad shard key (low cardinality or monotonically increasing) causes hot spots and is very hard to fix after the fact.
MEDIUM — Built-in but tricky
DynamoDB
Invisible Partitioning
AWS handles all partitioning automatically based on your partition key using consistent hashing. You just define a good partition key (high cardinality, evenly distributed). Hot partitions are still your problem if keys are skewed.
EASY — AWS managed
Cassandra
Token Ring
Uses a consistent hash token ring. Each node owns a range of tokens. Data is hashed to a token, written to that node + N replicas. Adding nodes redistributes tokens automatically. No downtime for scaling.
EASY — Native, automatic

The Hot Partition Problem — All Four Face It

⚠️ The problem interviewers always probe

What it is: One shard/partition gets disproportionately more traffic. Example: a celebrity user — all writes for their posts hit the same shard.

The fix (universal): Add a random suffix — write user_123#0 through user_123#7. This distributes across 8 shards. A scatter-gather read merges results. Or use write-time fan-out.

Cassandra-specific: Time-based keys cause one partition per time window to become hot during peak. Use bucketing: entity_type + date_bucket as partition key to distribute load.

DynamoDB-specific: Adaptive Capacity auto-absorbs bursts, but consistent hot keys still cause throttling. Write sharding with a #bucket suffix is the right fix.

04 · CAP Theorem in Practice

Consistency, Availability, Partition Tolerance

CAP theorem: in a distributed system, you can guarantee only two of: Consistency (every read gets the latest write), Availability (every request gets a response), Partition Tolerance (system works even if network splits). Since network partitions always happen, the real choice is CP vs AP.

Plain English

CP (Consistency + Partition Tolerance): "I'd rather return an error than return stale data." A bank is CP — you never want a wrong balance.

AP (Availability + Partition Tolerance): "I'd rather return slightly old data than nothing." Twitter's trending list is AP — seeing a hashtag ranked #3 vs #4 is fine.

Cassandra Consistency Levels — Understand This Deeply

-- Cassandra consistency levels (replication factor RF = 3) ONE → Write/Read confirmed by 1 replica. Fastest. Lowest consistency. Best for: metrics, logs — stale reads acceptable. QUORUM → Write/Read confirmed by majority: (RF/2)+1 = 2 of 3. Best for: user data — good balance of speed and correctness. ALL → Write/Read confirmed by ALL replicas. Strongest. Best for: financial. One node down = total failure. -- The golden rule: -- write_CL + read_CL > RF → guaranteed to read your own writes -- QUORUM(2) + QUORUM(2) = 4 > 3 ✓ Strong consistency -- ONE(1) + ONE(1) = 2 < 3 ✗ May read stale data
05 · Applied to Real Systems

Which Database Wins in Which System?

Top-K Trending (YouTube / Twitter)
500K EVENTS/SEC
HOT STORE
Redis ZSET Not one of the four — Redis wins for real-time sorted sets. ZINCRBY + ZREVRANGE at sub-ms. None of the four match this for live ranking.
WARM STORE
Cassandra ✓ 50K rows/sec from Flink flush. Partition by entity_type+region, cluster by window_bucket. Range queries by time are Cassandra's home ground. PostgreSQL would be bottlenecked at this write rate.
Why NOT Postgres
PostgreSQL ✗ Sustained 50K writes/sec saturates a single node. Sharding Postgres is operationally complex. And we don't need joins — pre-aggregated counts need no relational features.
Why NOT DynamoDB
DynamoDB ⚠ Could work technically but cost is prohibitive. At $1.25 per million writes × 4.3B writes/day ≈ $5,400/day. Cassandra on 10 nodes ≈ $200/day at the same scale.
Ride-Sharing App (Uber)
MIXED WORKLOAD
RIDE ENTITY
PostgreSQL ✓ Ride lifecycle: create → assign driver → update status → charge payment → close. You need ACID transactions across tables. PostgreSQL prevents double-assignment and double-charging atomically.
DRIVER LOCATION
Cassandra ✓ Location history: partition by driver_id, cluster by timestamp DESC. For real-time queries use Redis GEOADD. Cassandra stores the durable time-series history.
USER PROFILES
MongoDB ✓ Profiles vary: saved addresses, payment methods, preferences, ratings. Document model is natural. No joins needed — just fetch the user document by user_id.
SESSION TOKENS
DynamoDB ✓ Token → user_id + expiry. DynamoDB TTL auto-expires sessions. Millions of sessions, single-key lookups, zero ops. Perfect fit.
E-Commerce (Amazon-style)
MULTI-MODEL
ORDERS / PAYMENTS
PostgreSQL ✓ Money moves. "Deduct inventory AND create order AND charge payment" must be atomic. PostgreSQL's ACID guarantees this in a single transaction. Nothing else on this list does it reliably.
PRODUCT CATALOG
MongoDB ✓ A T-shirt has size/color. A laptop has RAM/CPU. A book has ISBN. Product attributes vary wildly — flexible schema is perfect. Add new product types without migration.
SHOPPING CART
DynamoDB ✓ Cart = user_id → [items]. Single-key access. TTL to expire abandoned carts. Millions of concurrent sessions. Zero ops burden.
ORDER HISTORY
Cassandra ✓ "All orders for user X sorted by date" — perfect Cassandra query. Partition by user_id, cluster by order_date DESC. Append-only, high write throughput during sale events.
06 · The Decision Framework

How to Pick in an Interview — in 60 Seconds

// Ask these questions in order: Step 1: Do you need ACID transactions across multiple entities? YES → PostgreSQL. Full stop. NO → Continue. Step 2: What is your write volume? <10K writes/sec → PostgreSQL or MongoDB. 10K–100K/sec → MongoDB (sharded) or DynamoDB. >100K writes/sec → Cassandra or DynamoDB. Step 3: What is your read pattern? Flexible ad-hoc (joins, filters, aggregations): → PostgreSQL or MongoDB Known key lookups (always by user_id, entity_id): → DynamoDB or Cassandra Range queries on time within a known partition: → Cassandra (ideal partition + clustering key) Step 4: Do you control your infrastructure? YES — self-hosted, cost matters → PostgreSQL / Cassandra / MongoDB NO — managed, AWS shop → DynamoDB Step 5: Does schema change frequently? YES, still evolving → MongoDB NO, stable → PostgreSQL or Cassandra

The Rules You Must Know

🐘 Never use PostgreSQL for…
  • Write-heavy workloads >50K TPS
  • Multi-region active-active writes
  • Flexible evolving schemas
  • IoT sensor streams (millions of tiny writes)
🍃 Never use MongoDB for…
  • Strict ACID transactions at high volume
  • Write throughput >100K/sec reliably
  • Inherently relational data with complex joins
  • When you need Cassandra-style time partitioning
⚡ Never use DynamoDB for…
  • Ad-hoc queries (pay for full table scans)
  • Complex joins or aggregations
  • High-volume cross-item ACID transactions
  • Non-AWS deployments
💎 Never use Cassandra for…
  • ACID transactions or financial data
  • Ad-hoc queries
  • Small teams without ops expertise
  • Frequently changing query patterns
07 · Interview Follow-up Playbook

Every Hard Follow-up, Answered

Why not just use PostgreSQL for everything?+
This is right for 80% of startups. With proper indexing and read replicas, Postgres handles tens of thousands of TPS and terabytes of data. Instagram ran on PostgreSQL until billions of photos — they added sharding only when forced.

The threshold: when you need multi-region active-active writes, >50K sustained writes/sec, or petabyte-scale storage. Below those thresholds, Postgres with read replicas is correct and introduces less complexity.
Cassandra says "no joins" — how does a social app do "get tweets liked by users I follow"?+
Denormalise and pre-compute. Design tables for your queries, not your entities.

Store user_liked_tweets(user_id, tweet_id, liked_at) for "show me what I liked." Store tweet_liked_by(tweet_id, user_id) for "show me who liked this tweet." Same data, two tables, two access patterns. Write fan-out handles both. Storage is cheap; compute is expensive.
DynamoDB vs Cassandra — they seem to do the same thing?+
They share a heritage (Dynamo paper) but differ in practice:

DynamoDB: Fully managed, AWS-only, pay per request, zero ops. Expensive at massive scale, AWS lock-in.

Cassandra: Self-hosted or Astra, any cloud, pay for machines. Requires ops expertise. Dramatically cheaper at extreme scale — Netflix uses it because at their scale (trillions of rows) savings justify the ops investment.

Decision: team size and cloud commitment. Small team on AWS → DynamoDB. Large team, predictable massive load → Cassandra.
How does Cassandra handle a node going down mid-write?+
Hinted Handoff + Read Repair.

Hinted Handoff: Write to 3 nodes; node 2 is down. Coordinator stores a hint — "send this write to node 2 when it recovers." Node 2 receives all missed writes on restart.

Read Repair: On a QUORUM read, if replicas return different values, Cassandra detects inconsistency and repairs the stale replica in the background.

Anti-Entropy Repair: Weekly background process comparing replicas via Merkle trees. Skipping this causes data loss over time.
When would you choose MongoDB over PostgreSQL?+
MongoDB wins when:

1. Schema is genuinely unknown or rapidly evolving — CMS, product catalog with 50 different product types, configuration system. Each document legitimately has different fields.

2. Data is hierarchically structured — blog post with embedded comments, tags, and author info as one document. Faster than 4 JOINed tables.

3. Prototyping fast without a DBA — no migrations, no ALTER TABLE.

MongoDB loses when: You need transactions, your "flexible" schema has become inconsistent garbage no one understands, or your aggregation pipeline is 200 lines of nested JSON.
What's the difference between a secondary index in DynamoDB vs Cassandra?+
DynamoDB: Two types — Local Secondary Index (same partition key, different sort key, created at table creation, can't be deleted) and Global Secondary Index (different partition key entirely, created any time, has its own read/write capacity). GSIs are eventually consistent and cost additional write capacity units for every write to the base table.

Cassandra: Secondary indexes are a trap. They scatter queries across all nodes (each node checks its local data), creating latency spikes and hot spots. The correct Cassandra approach is to create a new table denormalised for the access pattern, not add a secondary index. Materialized Views are an alternative but have their own consistency trade-offs.
