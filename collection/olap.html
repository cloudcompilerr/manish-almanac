01 · What Is OLAP and Why Does It Exist

OLAP vs OLTP — the fundamental split

Most databases are built for OLTP (Online Transaction Processing) — fast individual row reads and writes that power the live product. A user signs up, an order is placed, a message is sent — these are OLTP queries. They affect a few rows at a time and need to be fast (sub-millisecond).

OLAP (Online Analytical Processing) is the opposite. Queries read millions or billions of rows, scan entire columns, compute aggregations: "total revenue per country last quarter," "top 1000 videos in the last hour," "average session duration by device type over 30 days." These queries are slow on OLTP databases but fast on OLAP engines — because they're built completely differently.

🏪 The Supermarket Analogy

OLTP = The checkout register. Processes one transaction at a time, extremely fast. Does not care about sales trends across all 10,000 products.

OLAP = The weekly inventory report. Reads all 10,000 products across all 50 stores, computes which products sold most, what was the average price per category. No individual transaction is urgent. You need the full picture fast.

You would never use the checkout register to produce the inventory report. You need a separate system designed for scanning everything at once.

💬 Say This in Your Interview

"Our OLTP database (Postgres/DynamoDB/Cassandra) handles the live product. But analytical queries — GROUP BY, window functions, aggregations across billions of events — would kill OLTP p99 latency if run directly. We push data to an OLAP engine via CDC or a stream, and run analytics there. The two systems have completely different read/write contracts."

02 · Columnar Storage — The Core Insight

Why columnar storage makes analytics 100× faster

Every OLAP engine is columnar. Understanding this is the key to understanding everything else about them.

Row storage (OLTP) vs columnar storage (OLAP)

📦 The Filing Cabinet vs Spreadsheet Analogy

Row storage: All data for one customer is stored together — name, email, age, city, purchase_count, revenue. Like a filing cabinet where each folder contains everything about one person. Fast to get all info for one person. Slow to answer "what is the average age of all customers" — you must open every folder and extract just the age field.

Columnar storage: All ages for all customers are stored together, all cities together, all revenues together. Like a spreadsheet where each column is stored as one contiguous block on disk. To compute average age, you read only the age column — 10× less data to scan. To compute revenue by city, you read only revenue and city — everything else is untouched.

Step-by-step: how columnar query execution works

  1. Parse the query and identify columns needed
    For SELECT city, SUM(revenue) FROM orders WHERE date > '2026-01-01' GROUP BY city:
    • Columns needed: only city, revenue, date — 3 of potentially 50 columns
    • All other columns (customer_name, email, phone, address…) are not touched at all
    • I/O savings: if table has 50 columns and you need 3, you read 6% of the data
  2. Read column files from disk with compression
    Each column is stored as a separate compressed file on disk.
    • Because all values in a column have the same type, compression is extremely effective
    • A column of integers like revenue compresses 10–20× (run-length encoding, delta encoding)
    • A column of low-cardinality strings like city compresses 30–50× (dictionary encoding: map "Bangalore"→1, "London"→2, store integers)
    • ClickHouse achieves 5–20× compression vs PostgreSQL on the same data
  3. Apply vectorised execution (SIMD)
    Modern CPUs have SIMD instructions (Single Instruction Multiple Data) that process multiple values in a single clock cycle.
    • Row stores process one row at a time: read name, read email, read age, move to next row
    • Column stores process 16 or 32 integers simultaneously: compute 32 revenue additions in one CPU instruction
    • ClickHouse processes 8–32 values per CPU instruction via AVX2/AVX-512 — this is the real reason ClickHouse query throughput is extraordinary
  4. Aggregate and return results
    GROUP BY, SUM, COUNT, window functions operate on dense arrays of same-typed data — no pointer chasing, no row parsing.
    • ClickHouse: GROUP BY on 100M rows in 200–500ms
    • PostgreSQL row store: same query in 30–120 seconds (sequential scan + per-row processing)
    • The columnar advantage is not just I/O — it's CPU cache efficiency: dense arrays fit in CPU L1/L2 cache, enabling near-memory-speed processing

04 · How They Actually Work Inside

Internals that interviewers probe

ClickHouse — MergeTree Engine

ClickHouse's core storage engine. Understanding MergeTree is what separates a good answer from a great one.

  1. Writes go to a MemTable (in-memory buffer)
    Incoming rows accumulate in memory. ClickHouse periodically flushes them to disk as a data part — a sorted, compressed block of rows.
    • Each data part is immutable once written — no in-place updates
    • This is why ClickHouse can ingest 500K rows/sec: writes are sequential appends, never random
    • Updates in ClickHouse are actually: mark old rows as deleted + insert new rows. Mutations run asynchronously.
  2. Background compaction — MergeTree's magic
    Over time, many small data parts accumulate. Background merge process combines small parts into larger ones, sorting and re-compressing.
    • Queries during merge: read from both old parts and new merged part — transparent to the query
    • Merge reduces number of files to scan on query, improving query speed over time
    • This is the same LSM-tree concept as Cassandra but optimised for reads (column-oriented) rather than just writes
  3. Primary index (sparse) enables fast range scans
    ClickHouse stores a sparse index — one index entry per 8192 rows (configurable). Tiny index, fits in RAM.
    • For WHERE event_date = '2026-03-20': index skips to the right range in milliseconds
    • Not row-level index — ClickHouse skips 8192 rows at a time. Within the range, it scans linearly.
    • Order by matters: if you ORDER BY (tenant_id, event_date), queries filtering by tenant_id are fast. Queries filtering only by event_date must scan everything.
  4. AggregatingMergeTree — for pre-aggregated counts
    Specialised MergeTree variant that merges rows with the same key, combining their aggregate state.
    • Example: two rows (ad_id=123, count=500) and (ad_id=123, count=300) merge to (ad_id=123, count=800)
    • ClickHouse does this merging in background without any explicit trigger
    • This is how the Top-K system works: Flink writes partial counts to ClickHouse, ClickHouse merges them continuously

Apache Druid — Pre-aggregation at ingest (Rollup)

  1. Ingest-time rollup — aggregate before storing
    Druid's key differentiator: it aggregates data as it ingests.
    • Raw event: {user_id: "u1", video_id: "v42", region: "IN", timestamp: 14:32:47, count: 1}
    • Druid rolls up to 1-minute granularity: {video_id: "v42", region: "IN", minute: "14:32", count: 547}
    • Many individual events collapse into one row — potentially 100–1000× data reduction
    • Trade-off: you lose individual event detail. You cannot answer "did user u1 watch video v42?" after rollup.
  2. Segments — immutable, pre-sorted, pre-compressed time slices
    Druid divides data into time-based segments (e.g., one segment per hour per datasource).
    • Each segment is immutable — like ClickHouse parts
    • Segments are distributed across Historical nodes, with deep storage (S3) as source of truth
    • Query: Broker routes to relevant Historical nodes, merges results
  3. Bitmap indexes enable sub-second filter performance
    Druid automatically creates bitmap indexes on all dimensions (region, device, etc.).
    • Bitmap index: for each value of "region" (IN, US, UK…), store a bitset of which rows match
    • Filtering "region = IN" = bitwise AND of the IN bitmap with other filters — extremely fast
    • This is why Druid excels at dashboard queries with many filters: each filter is a bitwise operation

BigQuery — Dremel columnar tree

  1. Dremel execution model — distributed tree of workers
    BigQuery uses Google's Dremel engine. A query fans out to thousands of workers in milliseconds.
    • Root server receives query, distributes to intermediate servers, which distribute to leaf servers
    • Leaf servers read Colossus (Google's distributed file system) directly — no data movement
    • Results aggregate back up the tree
    • A query that scans 1 TB can use 2,000 workers simultaneously — each worker reads 0.5 GB
  2. Slots — units of compute
    BigQuery measures compute in "slots" — a virtual CPU.
    • On-demand pricing: you don't manage slots — BigQuery allocates automatically, charges per TB scanned
    • Reservations pricing: buy a fixed number of slots (e.g., 500 slots) — predictable cost, consistent performance
    • A complex query might use 2,000 slots for 3 seconds — that's 6,000 slot-seconds of compute
  3. Partitioned and clustered tables for cost control
    Critical for production BigQuery usage:
    • Partition by date: Query WHERE date = '2026-03-20' reads only that date's partition — 1/365 of the data
    • Cluster by column: Within a partition, data is co-located by cluster column. Filter on cluster column skips most blocks.
    • Without partitioning: a query always scans the entire table. At $5/TB, a 1 PB table = $5,000 per query. Always partition.

06 · When to Use Each

Real system design examples

ClickHouse — high-frequency writes + fast aggregation

  • Top-K trending (our system): Flink writes 50K aggregated count rows/sec. ClickHouse ingests via Kafka engine natively. Query "top 10 videos in India last hour" = 200ms on 100B rows. No other OLAP engine matches this ingest+query combination.
  • Ad click analytics: 10K clicks/sec, each click is one row event. ClickHouse ingests via Kafka, aggregates by ad_id and time window. Advertisers query "my ad performance last 24 hours" — sub-second response.
  • Observability / APM: Cloudflare processes 30M DNS queries/sec — all logged to ClickHouse. Engineers query "how many 5xx errors from IP range X in last 5 minutes" — answers in <1 second.
  • User behaviour analytics: ByteDance (TikTok) uses ClickHouse for product analytics. Every user action (swipe, play, like, skip) is one row. A/B test analysis, funnel queries, retention cohorts — all ClickHouse.

Apache Druid — sub-second interactive dashboards

  • Business intelligence dashboards: Operations team needs a dashboard that responds in <500ms to every filter change (date range, region, device type). Druid pre-aggregates at ingest — filter changes just flip bitmap indexes. No other OLAP engine is this fast for interactive exploration.
  • Real-time anomaly detection: Data is visible in Druid in <1 second. Dashboard shows "current minute revenue vs expected" — Druid handles both the real-time ingest and the historical baseline query in the same system.
  • Pinterest Ads analytics: Advertisers need to see their campaign performance update in real time as users interact with pins. Druid's streaming ingestion + rollup makes this possible at Pinterest's scale.
  • When NOT to use Druid: Complex multi-join queries across large datasets; when you need to retain raw event granularity; when ops complexity is a concern (Druid clusters are hard to manage).

BigQuery — ad-hoc exploration, ML, no-ops

  • Data science exploration: A data scientist needs to run 20 different exploratory queries on last year's data. They don't know the queries in advance. BigQuery: spin up, run queries, pay only for what you scan. No infrastructure to manage, no index to design.
  • ML training data: BigQuery ML (BQML) lets you train models directly in SQL without moving data. Spotify uses BigQuery to train their recommendation models on listening history — petabytes of data, no data pipeline needed.
  • Cross-team analytics at Google scale: Multiple teams query the same data. BigQuery handles concurrency automatically — 2,000 concurrent queries with automatic slot allocation.
  • When NOT to use BigQuery: When you need <1 second query latency consistently; when you have very high-frequency streaming ingest; when you're not on GCP and don't want cloud vendor lock-in.

Redshift — AWS-native data warehouse

  • AWS-native workloads: You're already heavily on AWS (S3, Kinesis, Glue). Redshift Spectrum can query S3 directly without loading. Glue automatically catalogs your data. The ecosystem integration is seamless.
  • Traditional BI with standard SQL: Teams familiar with PostgreSQL SQL, using Tableau or Looker. Redshift's PostgreSQL-compatible SQL and JDBC/ODBC connectors work with every BI tool out of the box.
  • When NOT to use Redshift: High-frequency writes (Redshift is batch-oriented); when you need Druid-style sub-second interactive queries; when you're on GCP (BigQuery is the obvious choice).

08 · Every Hard Follow-up

Questions interviewers always ask

Why not use PostgreSQL for analytics? It has window functions and GROUP BY.+

PostgreSQL can handle analytics on small datasets. The problem emerges at scale:

  • Row storage is fundamentally wrong for column scans: SELECT COUNT(*) FROM events WHERE date = today() on 100M rows — PostgreSQL reads every column of every row (even unused ones) due to row-oriented storage. ClickHouse reads only the date column — 50× less I/O on a table with 50 columns.
  • MVCC overhead on analytical queries: PostgreSQL must check visibility for every row it scans (is this row visible to my transaction?). On 100M rows, this adds 10–30% CPU overhead. ClickHouse has no MVCC.
  • No vectorised execution: PostgreSQL processes one row at a time through a tree of plan nodes. ClickHouse processes 8,192 rows per batch using SIMD instructions — 50–100× more CPU-efficient for aggregations.
  • Competing with live workload: Running a long analytical query on the OLTP PostgreSQL blocks autovacuum, consumes I/O, and spikes p99 latency for real users. Always separate OLAP from OLTP.
ClickHouse claims 500K rows/sec ingest. How does that work with Kafka?+

ClickHouse has a native Kafka Table Engine that acts as a built-in Kafka consumer.

  1. You create a Kafka table pointing at your Kafka topic (broker address, topic name, consumer group, format).
  2. You create a destination MergeTree table where data will be stored.
  3. You create a Materialised View that connects the Kafka table to the MergeTree table — this is the insert trigger.
  4. ClickHouse continuously polls Kafka, batches messages (default: 65,536 rows or 1 second, whichever comes first), and inserts into MergeTree atomically.

Why this is fast: Batched inserts write entire sorted data parts to disk sequentially — no random I/O. Each batch is one atomic disk write per column. With 500K rows/sec at ~100 bytes per row = 50 MB/sec sequential write — well within NVMe SSD capacity.

Exactly-once guarantee: ClickHouse commits the Kafka offset only after the insert succeeds. If ClickHouse crashes mid-insert, it re-reads from the last committed offset — at-least-once semantics. Use ReplacingMergeTree with deduplication key to handle duplicate inserts.

What is Druid rollup and how is it different from ClickHouse AggregatingMergeTree?+

Both pre-aggregate data, but at different stages and with different trade-offs:

  • Druid rollup — at ingest time: Data is aggregated as it enters Druid. Raw events are combined into coarser time buckets (e.g., 1-minute granularity) before being stored. You configure rollup granularity upfront — you lose raw event detail permanently. 1B raw clicks become 10M rolled-up rows. Storage is 100× smaller, queries are 100× faster. But you can never answer "what did user_id X do at 14:32:47" after rollup.
  • ClickHouse AggregatingMergeTree — at background merge time: Raw data is stored initially. Background merge process combines rows with identical keys, merging their aggregate state (SUM, MAX, HyperLogLog sketch). Raw data exists temporarily — row-level queries work until merged. After merge, rows with same key are combined. More flexible than Druid rollup — you can always query raw data before it's merged.

Which to choose: Druid rollup is more aggressive — better for when you know your query granularity in advance and want maximum compression. ClickHouse AggregatingMergeTree is more flexible — data is stored raw initially, merged asynchronously, and you can query at different granularities.

BigQuery charges per TB scanned. How do you control costs in production?+

BigQuery cost control is a real engineering concern. The four levers:

  • Partition pruning: Always add WHERE _PARTITIONDATE = '2026-03-20' or use partition columns in filters. Without this, every query scans the entire table. A 1 PB table with daily partitions: filtering one day = 1/365 of cost.
  • Clustering: CLUSTER BY user_id co-locates rows with the same user_id in the same blocks. A query filtering by user_id skips 90%+ of blocks. Combined with partitioning, you can reduce scan to <1% of total data.
  • BI Engine / materialised views: Pre-compute common aggregations as materialised views. Dashboard queries hit the view (tiny) not the raw table (huge). BI Engine caches frequently-run query results in RAM — subsequent identical queries cost nothing.
  • Reservations: Switch from on-demand to flat-rate reservations once you have predictable query volume. $1,800–$2,400/slot/month with 500 slots is predictable vs unpredictable per-TB charges. Break-even is roughly when you scan 400+ TB/month.

Common interview answer: "In production, all BigQuery tables are partitioned by date and clustered by the most common filter dimension. We use materialised views for dashboard queries. Monthly cost monitoring with alerts when a query scans >10 TB unexpectedly."

In the Top-K system, why use ClickHouse instead of Cassandra for analytics?+

They serve completely different query contracts — this is a crucial distinction:

  • Cassandra serves the operational read path: "Give me all hourly counts for entity X in region IN over the last 7 days" = partition key lookup + range scan on clustering key. Fast, pre-defined access pattern. Cannot do GROUP BY, cannot scan all entities to find top ones, cannot do complex aggregations.
  • ClickHouse serves the analytical read path: "What were the top 10 videos in India last Tuesday between 6–8pm, broken down by device type, and how does that compare to the same period last week?" — this requires full columnar scan + GROUP BY + window functions + join across time periods. ClickHouse handles this in 2–3 seconds on 100B rows. Cassandra would timeout or require 10+ minutes of scatter-gather across all partitions.

The same event stream (Kafka) feeds both. Flink writes to Cassandra (for operational real-time reads) AND to a Kafka output topic that ClickHouse consumes (for analytics). They receive the same data but answer different questions at different time horizons.

Summary: Cassandra = fast, narrow, pre-planned queries on current data. ClickHouse = flexible, deep, analytical queries on historical data. Both necessary; neither can replace the other.

ClickHouse vs Druid — when does Druid's sub-second speed matter more than ClickHouse's ingest speed?+

The decision comes down to the latency requirement and whether you need raw events:

  • Choose Druid when: You need <500ms guaranteed for interactive dashboards with arbitrary filter combinations. A business user changes the date range slider and expects the chart to update instantly. Druid's bitmap indexes on every dimension make this possible. ClickHouse's <1s is often good enough, but not always.
  • Choose ClickHouse when: You have high-frequency ingest (>100K rows/sec), need to retain raw event granularity (user-level queries), need flexible ad-hoc SQL, or want simpler operational management. ClickHouse's single binary vs Druid's 5-node-type cluster is a significant ops advantage.
  • The Druid tax: Druid's rollup destroys raw event granularity. If you ever need "did this specific user see this specific ad?", Druid after rollup cannot answer this. ClickHouse retains raw events until they're merged.

Real-world trend: Many teams that previously used Druid are migrating to ClickHouse + pre-aggregated materialised views — they get 95% of Druid's query speed with ClickHouse's simpler ops and better SQL support.

The one rule to remember
"ClickHouse: extreme ingest + fast aggregation, self-hosted. Druid: sub-second interactive dashboards, pre-aggregates at ingest. BigQuery: serverless analytics, pay per TB, zero ops. Redshift: AWS-native data warehouse. All four are columnar — the difference is when they aggregate, how they manage ops, and what they cost."
