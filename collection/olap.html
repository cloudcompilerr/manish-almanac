01 · What Is OLAP and Why Does It Exist

OLAP vs OLTP — the fundamental split

The librarian vs. the index card analogy
A row-oriented database (OLTP) is like a librarian who retrieves one book at a time — perfect for reading the full contents of a specific book.

A columnar database (OLAP) is like having a separate index for every attribute: one index for all book publication years, one for all authors, one for all genres. To answer "how many science books were published in the 1980s?" — you only touch the genre index and the year index. You never open a single book.

This is why ClickHouse can scan 1 billion rows/second — it only reads the two columns you asked about, skipping the other 50 columns entirely. Row storage would read all 50 columns for every row.

Most databases are built for OLTP (Online Transaction Processing) — fast individual row reads and writes that power the live product. A user signs up, an order is placed, a message is sent — these are OLTP queries. They affect a few rows at a time and need to be fast (sub-millisecond).

OLAP (Online Analytical Processing) is the opposite. Queries read millions or billions of rows, scan entire columns, compute aggregations: "total revenue per country last quarter," "top 1000 videos in the last hour," "average session duration by device type over 30 days." These queries are slow on OLTP databases but fast on OLAP engines — because they're built completely differently.

🏪 The Supermarket Analogy

OLTP = The checkout register. Processes one transaction at a time, extremely fast. Does not care about sales trends across all 10,000 products.

OLAP = The weekly inventory report. Reads all 10,000 products across all 50 stores, computes which products sold most, what was the average price per category. No individual transaction is urgent. You need the full picture fast.

You would never use the checkout register to produce the inventory report. You need a separate system designed for scanning everything at once.

💬 Say This in Your Interview

"Our OLTP database (Postgres/DynamoDB/Cassandra) handles the live product. But analytical queries — GROUP BY, window functions, aggregations across billions of events — would kill OLTP p99 latency if run directly. We push data to an OLAP engine via CDC or a stream, and run analytics there. The two systems have completely different read/write contracts."

02 · Columnar Storage — The Core Insight

Why columnar storage makes analytics 100× faster

Every OLAP engine is columnar. Understanding this is the key to understanding everything else about them.

Row storage (OLTP) vs columnar storage (OLAP)

📦 The Filing Cabinet vs Spreadsheet Analogy

Row storage: All data for one customer is stored together — name, email, age, city, purchase_count, revenue. Like a filing cabinet where each folder contains everything about one person. Fast to get all info for one person. Slow to answer "what is the average age of all customers" — you must open every folder and extract just the age field.

Columnar storage: All ages for all customers are stored together, all cities together, all revenues together. Like a spreadsheet where each column is stored as one contiguous block on disk. To compute average age, you read only the age column — 10× less data to scan. To compute revenue by city, you read only revenue and city — everything else is untouched.

⚠ The interview trap that catches most candidates

"ClickHouse/BigQuery is so fast, why not use it for everything, including the live product?" is the trap. Columnar engines are fast at exactly one shape of query — scan many rows, touch few columns, aggregate — and slow at the opposite shape. A point lookup ("give me order #48213") or a single-row update ("mark this order shipped") is what row-oriented OLTP stores are built for: columnar formats must locate and rewrite fragments across every column file the row touches, and most OLAP engines (ClickHouse, Druid) treat updates as expensive async mutations, not first-class fast operations. A strong candidate names both directions of the trade-off — "OLAP for scan-heavy analytical reads, OLTP for row-level transactional reads and writes" — rather than treating one engine as a universal upgrade.

Step-by-step: how columnar query execution works

  1. Parse the query and identify columns needed
    For SELECT city, SUM(revenue) FROM orders WHERE date > '2026-01-01' GROUP BY city:
    • Columns needed: only city, revenue, date — 3 of potentially 50 columns
    • All other columns (customer_name, email, phone, address…) are not touched at all
    • I/O savings: if table has 50 columns and you need 3, you read 6% of the data
  2. Read column files from disk with compression
    Each column is stored as a separate compressed file on disk.
    • Because all values in a column have the same type, compression is extremely effective
    • A column of integers like revenue compresses 10–20× (run-length encoding, delta encoding)
    • A column of low-cardinality strings like city compresses 30–50× (dictionary encoding: map "Bangalore"→1, "London"→2, store integers)
    • ClickHouse achieves 5–20× compression vs PostgreSQL on the same data
  3. Apply vectorised execution (SIMD)
    Modern CPUs have SIMD instructions (Single Instruction Multiple Data) that process multiple values in a single clock cycle.
    • Row stores process one row at a time: read name, read email, read age, move to next row
    • Column stores process 16 or 32 integers simultaneously: compute 32 revenue additions in one CPU instruction
    • ClickHouse processes 8–32 values per CPU instruction via AVX2/AVX-512 — this is the real reason ClickHouse query throughput is extraordinary
  4. Aggregate and return results
    GROUP BY, SUM, COUNT, window functions operate on dense arrays of same-typed data — no pointer chasing, no row parsing.
    • ClickHouse: GROUP BY on 100M rows in 200–500ms
    • PostgreSQL row store: same query in 30–120 seconds (sequential scan + per-row processing)
    • The columnar advantage is not just I/O — it's CPU cache efficiency: dense arrays fit in CPU L1/L2 cache, enabling near-memory-speed processing

04 · How They Actually Work Inside

Internals that interviewers probe

ClickHouse — MergeTree Engine

ClickHouse's core storage engine. Understanding MergeTree is what separates a good answer from a great one.

  1. Writes go to a MemTable (in-memory buffer)
    Incoming rows accumulate in memory. ClickHouse periodically flushes them to disk as a data part — a sorted, compressed block of rows.
    • Each data part is immutable once written — no in-place updates
    • This is why ClickHouse can ingest 500K rows/sec: writes are sequential appends, never random
    • Updates in ClickHouse are actually: mark old rows as deleted + insert new rows. Mutations run asynchronously.
  2. Background compaction — MergeTree's magic
    Over time, many small data parts accumulate. Background merge process combines small parts into larger ones, sorting and re-compressing.
    • Queries during merge: read from both old parts and new merged part — transparent to the query
    • Merge reduces number of files to scan on query, improving query speed over time
    • This is the same LSM-tree concept as Cassandra but optimised for reads (column-oriented) rather than just writes
  3. Primary index (sparse) enables fast range scans
    ClickHouse stores a sparse index — one index entry per 8192 rows (configurable). Tiny index, fits in RAM.
    • For WHERE event_date = '2026-03-20': index skips to the right range in milliseconds
    • Not row-level index — ClickHouse skips 8192 rows at a time. Within the range, it scans linearly.
    • Order by matters: if you ORDER BY (tenant_id, event_date), queries filtering by tenant_id are fast. Queries filtering only by event_date must scan everything.
  4. AggregatingMergeTree — for pre-aggregated counts
    Specialised MergeTree variant that merges rows with the same key, combining their aggregate state.
    • Example: two rows (ad_id=123, count=500) and (ad_id=123, count=300) merge to (ad_id=123, count=800)
    • ClickHouse does this merging in background without any explicit trigger
    • This is how the Top-K system works: Flink writes partial counts to ClickHouse, ClickHouse merges them continuously

Apache Druid — Pre-aggregation at ingest (Rollup)

  1. Ingest-time rollup — aggregate before storing
    Druid's key differentiator: it aggregates data as it ingests.
    • Raw event: {user_id: "u1", video_id: "v42", region: "IN", timestamp: 14:32:47, count: 1}
    • Druid rolls up to 1-minute granularity: {video_id: "v42", region: "IN", minute: "14:32", count: 547}
    • Many individual events collapse into one row — potentially 100–1000× data reduction
    • Trade-off: you lose individual event detail. You cannot answer "did user u1 watch video v42?" after rollup.
  2. Segments — immutable, pre-sorted, pre-compressed time slices
    Druid divides data into time-based segments (e.g., one segment per hour per datasource).
    • Each segment is immutable — like ClickHouse parts
    • Segments are distributed across Historical nodes, with deep storage (S3) as source of truth
    • Query: Broker routes to relevant Historical nodes, merges results
  3. Bitmap indexes enable sub-second filter performance
    Druid automatically creates bitmap indexes on all dimensions (region, device, etc.).
    • Bitmap index: for each value of "region" (IN, US, UK…), store a bitset of which rows match
    • Filtering "region = IN" = bitwise AND of the IN bitmap with other filters — extremely fast
    • This is why Druid excels at dashboard queries with many filters: each filter is a bitwise operation

BigQuery — Dremel columnar tree

  1. Dremel execution model — distributed tree of workers
    BigQuery uses Google's Dremel engine. A query fans out to thousands of workers in milliseconds.
    • Root server receives query, distributes to intermediate servers, which distribute to leaf servers
    • Leaf servers read Colossus (Google's distributed file system) directly — no data movement
    • Results aggregate back up the tree
    • A query that scans 1 TB can use 2,000 workers simultaneously — each worker reads 0.5 GB
  2. Slots — units of compute
    BigQuery measures compute in "slots" — a virtual CPU.
    • On-demand pricing: you don't manage slots — BigQuery allocates automatically, charges per TB (technically TiB) scanned
    • Capacity-based pricing (BigQuery's current "Editions" model — Standard/Enterprise/Enterprise Plus, which replaced the older flat-rate reservation model in 2023): buy autoscaling slots billed per slot-hour, with discounts for 1- or 3-year commitments — predictable cost, consistent performance for steady query volume
    • A complex query might use thousands of slots for a few seconds — slot-seconds is the underlying unit of compute either way
  3. Partitioned and clustered tables for cost control
    Critical for production BigQuery usage:
    • Partition by date: Query WHERE date = '2026-03-20' reads only that date's partition — 1/365 of the data
    • Cluster by column: Within a partition, data is co-located by cluster column. Filter on cluster column skips most blocks.
    • Without partitioning: a query always scans the entire table. At BigQuery's current on-demand rate (~$6.25/TiB), a 1 PB table scanned in full runs into the thousands of dollars for a single query — the exact number moves with pricing, the lesson (always partition) doesn't.

06 · When to Use Each

Real system design examples

ClickHouse — high-frequency writes + fast aggregation

  • Top-K trending (our system): Flink writes 50K aggregated count rows/sec. ClickHouse ingests via Kafka engine natively. Query "top 10 videos in India last hour" = 200ms on 100B rows. No other OLAP engine matches this ingest+query combination.
  • Ad click analytics: 10K clicks/sec, each click is one row event. ClickHouse ingests via Kafka, aggregates by ad_id and time window. Advertisers query "my ad performance last 24 hours" — sub-second response.
  • Observability / APM: Cloudflare processes 30M DNS queries/sec — all logged to ClickHouse. Engineers query "how many 5xx errors from IP range X in last 5 minutes" — answers in <1 second.
  • User behaviour analytics: ByteDance (TikTok) uses ClickHouse for product analytics. Every user action (swipe, play, like, skip) is one row. A/B test analysis, funnel queries, retention cohorts — all ClickHouse.

Apache Druid — sub-second interactive dashboards

  • Business intelligence dashboards: Operations team needs a dashboard that responds in <500ms to every filter change (date range, region, device type). Druid pre-aggregates at ingest — filter changes just flip bitmap indexes. No other OLAP engine is this fast for interactive exploration.
  • Real-time anomaly detection: Data is visible in Druid in <1 second. Dashboard shows "current minute revenue vs expected" — Druid handles both the real-time ingest and the historical baseline query in the same system.
  • Pinterest Ads analytics: Advertisers need to see their campaign performance update in real time as users interact with pins. Druid's streaming ingestion + rollup makes this possible at Pinterest's scale.
  • When NOT to use Druid: Complex multi-join queries across large datasets; when you need to retain raw event granularity; when ops complexity is a concern (Druid clusters are hard to manage).

BigQuery — ad-hoc exploration, ML, no-ops

  • Data science exploration: A data scientist needs to run 20 different exploratory queries on last year's data. They don't know the queries in advance. BigQuery: spin up, run queries, pay only for what you scan. No infrastructure to manage, no index to design.
  • ML training data: BigQuery ML (BQML) lets you train models directly in SQL without moving data. Spotify uses BigQuery to train their recommendation models on listening history — petabytes of data, no data pipeline needed.
  • Cross-team analytics at Google scale: Multiple teams query the same data. BigQuery handles concurrency automatically — 2,000 concurrent queries with automatic slot allocation.
  • When NOT to use BigQuery: When you need <1 second query latency consistently; when you have very high-frequency streaming ingest; when you're not on GCP and don't want cloud vendor lock-in.

Redshift — AWS-native data warehouse

  • AWS-native workloads: You're already heavily on AWS (S3, Kinesis, Glue). Redshift Spectrum can query S3 directly without loading. Glue automatically catalogs your data. The ecosystem integration is seamless.
  • Traditional BI with standard SQL: Teams familiar with PostgreSQL SQL, using Tableau or Looker. Redshift's PostgreSQL-compatible SQL and JDBC/ODBC connectors work with every BI tool out of the box.
  • When NOT to use Redshift: High-frequency writes (Redshift is batch-oriented); when you need Druid-style sub-second interactive queries; when you're on GCP (BigQuery is the obvious choice).
08 · Every Hard Follow-up

Every Hard Follow-up, Answered

Why not use PostgreSQL for analytics? It has window functions and GROUP BY.+

PostgreSQL can handle analytics on small datasets. The problem emerges at scale:

  • Row storage is fundamentally wrong for column scans: SELECT COUNT(*) FROM events WHERE date = today() on 100M rows — PostgreSQL reads every column of every row (even unused ones) due to row-oriented storage. ClickHouse reads only the date column — 50× less I/O on a table with 50 columns.
  • MVCC overhead on analytical queries: PostgreSQL must check visibility for every row it scans (is this row visible to my transaction?). On 100M rows, this adds 10–30% CPU overhead. ClickHouse has no MVCC.
  • No vectorised execution: PostgreSQL processes one row at a time through a tree of plan nodes. ClickHouse processes 8,192 rows per batch using SIMD instructions — 50–100× more CPU-efficient for aggregations.
  • Competing with live workload: Running a long analytical query on the OLTP PostgreSQL blocks autovacuum, consumes I/O, and spikes p99 latency for real users. Always separate OLAP from OLTP.
ClickHouse claims 500K rows/sec ingest. How does that work with Kafka?+

ClickHouse has a native Kafka Table Engine that acts as a built-in Kafka consumer.

  1. You create a Kafka table pointing at your Kafka topic (broker address, topic name, consumer group, format).
  2. You create a destination MergeTree table where data will be stored.
  3. You create a Materialised View that connects the Kafka table to the MergeTree table — this is the insert trigger.
  4. ClickHouse continuously polls Kafka, batches messages (default: 65,536 rows or 1 second, whichever comes first), and inserts into MergeTree atomically.

Why this is fast: Batched inserts write entire sorted data parts to disk sequentially — no random I/O. Each batch is one atomic disk write per column. With 500K rows/sec at ~100 bytes per row = 50 MB/sec sequential write — well within NVMe SSD capacity.

Exactly-once guarantee: ClickHouse commits the Kafka offset only after the insert succeeds. If ClickHouse crashes mid-insert, it re-reads from the last committed offset — at-least-once semantics. Use ReplacingMergeTree with deduplication key to handle duplicate inserts.

What is Druid rollup and how is it different from ClickHouse AggregatingMergeTree?+

Both pre-aggregate data, but at different stages and with different trade-offs:

  • Druid rollup — at ingest time: Data is aggregated as it enters Druid. Raw events are combined into coarser time buckets (e.g., 1-minute granularity) before being stored. You configure rollup granularity upfront — you lose raw event detail permanently. 1B raw clicks become 10M rolled-up rows. Storage is 100× smaller, queries are 100× faster. But you can never answer "what did user_id X do at 14:32:47" after rollup.
  • ClickHouse AggregatingMergeTree — at background merge time: Raw data is stored initially. Background merge process combines rows with identical keys, merging their aggregate state (SUM, MAX, HyperLogLog sketch). Raw data exists temporarily — row-level queries work until merged. After merge, rows with same key are combined. More flexible than Druid rollup — you can always query raw data before it's merged.

Which to choose: Druid rollup is more aggressive — better for when you know your query granularity in advance and want maximum compression. ClickHouse AggregatingMergeTree is more flexible — data is stored raw initially, merged asynchronously, and you can query at different granularities.

BigQuery charges per TB scanned. How do you control costs in production?+

BigQuery cost control is a real engineering concern. The four levers:

  • Partition pruning: Always add WHERE _PARTITIONDATE = '2026-03-20' or use partition columns in filters. Without this, every query scans the entire table. A 1 PB table with daily partitions: filtering one day = 1/365 of cost.
  • Clustering: CLUSTER BY user_id co-locates rows with the same user_id in the same blocks. A query filtering by user_id skips 90%+ of blocks. Combined with partitioning, you can reduce scan to <1% of total data.
  • BI Engine / materialised views: Pre-compute common aggregations as materialised views. Dashboard queries hit the view (tiny) not the raw table (huge). BI Engine caches frequently-run query results in RAM — subsequent identical queries cost nothing.
  • Capacity commitments: Switch from on-demand to a capacity-based BigQuery Editions commitment (Enterprise/Enterprise Plus, billed per slot-hour with 1- or 3-year discounts) once you have predictable, high query volume — this replaced the older flat-rate reservation model in 2023. It's predictable vs unpredictable per-TB charges; the break-even point depends on current on-demand and slot pricing, so model it against your own volume rather than assuming a fixed threshold.

Common interview answer: "In production, all BigQuery tables are partitioned by date and clustered by the most common filter dimension. We use materialised views for dashboard queries. Monthly cost monitoring with alerts when a query scans >10 TB unexpectedly."

In the Top-K system, why use ClickHouse instead of Cassandra for analytics?+

They serve completely different query contracts — this is a crucial distinction:

  • Cassandra serves the operational read path: "Give me all hourly counts for entity X in region IN over the last 7 days" = partition key lookup + range scan on clustering key. Fast, pre-defined access pattern. Cannot do GROUP BY, cannot scan all entities to find top ones, cannot do complex aggregations.
  • ClickHouse serves the analytical read path: "What were the top 10 videos in India last Tuesday between 6–8pm, broken down by device type, and how does that compare to the same period last week?" — this requires full columnar scan + GROUP BY + window functions + join across time periods. ClickHouse handles this in 2–3 seconds on 100B rows. Cassandra would timeout or require 10+ minutes of scatter-gather across all partitions.

The same event stream (Kafka) feeds both. Flink writes to Cassandra (for operational real-time reads) AND to a Kafka output topic that ClickHouse consumes (for analytics). They receive the same data but answer different questions at different time horizons.

Summary: Cassandra = fast, narrow, pre-planned queries on current data. ClickHouse = flexible, deep, analytical queries on historical data. Both necessary; neither can replace the other.

ClickHouse vs Druid — when does Druid's sub-second speed matter more than ClickHouse's ingest speed?+

The decision comes down to the latency requirement and whether you need raw events:

  • Choose Druid when: You need <500ms guaranteed for interactive dashboards with arbitrary filter combinations. A business user changes the date range slider and expects the chart to update instantly. Druid's bitmap indexes on every dimension make this possible. ClickHouse's <1s is often good enough, but not always.
  • Choose ClickHouse when: You have high-frequency ingest (>100K rows/sec), need to retain raw event granularity (user-level queries), need flexible ad-hoc SQL, or want simpler operational management. ClickHouse's single binary vs Druid's 5-node-type cluster is a significant ops advantage.
  • The Druid tax: Druid's rollup destroys raw event granularity. If you ever need "did this specific user see this specific ad?", Druid after rollup cannot answer this. ClickHouse retains raw events until they're merged.

Real-world trend: Many teams that previously used Druid are migrating to ClickHouse + pre-aggregated materialised views — they get 95% of Druid's query speed with ClickHouse's simpler ops and better SQL support.

09 · Follow-ups

Every hard follow-up, answered

When should you use ClickHouse instead of Redshift or BigQuery?+
ClickHouse wins on raw query speed and cost at high query volume. Cloud DWs win on zero ops and ecosystem integration.

Choose ClickHouse when: (1) Query latency matters at millisecond level (dashboards updating every few seconds). (2) You run high query volume — BigQuery/Redshift charge per byte scanned, which gets expensive. (3) You want to self-host and have ops capacity. (4) You need real-time ingestion with seconds-fresh query results. Uber, Cloudflare, ByteDance all use ClickHouse for exactly these reasons.

Stay with BigQuery/Redshift when: (1) You prioritise zero infrastructure management. (2) Your queries are infrequent and ad-hoc — BigQuery's serverless model is perfect. (3) You need tight integration with the cloud provider's ecosystem (Redshift + S3 + Glue + QuickSight). (4) Your team lacks the expertise to tune ClickHouse (MergeTree configuration, shard keys, tiered storage).
How do you handle schema changes in a live OLAP system?+
Schema evolution in OLAP is harder than OLTP because of partitioned, compressed, column-oriented storage.

Adding a new column: safe in ClickHouse (ALTER TABLE ADD COLUMN — metadata change only, new column is NULL/default for existing rows). Safe in BigQuery (ADD COLUMN via schema update). Safe in Redshift (ALTER TABLE ADD COLUMN — fast metadata operation).

Changing column type or removing a column: dangerous. Options: (1) Add new column with new type, backfill from old column, update application to use new column, eventually drop old column. (2) Create a new table with correct schema, backfill from old, swap via view or DNS change. Never modify column types in place on petabyte tables — it requires a full rewrite.

Changing partition key: requires full reingestion. There is no shortcut. Plan partition keys carefully before launch — they are permanent.

Druid: schema changes require re-ingesting affected time intervals from the source (Kafka or S3). Druid's immutable segment model means in-place schema migration is not possible.
How do you design a real-time dashboard showing metrics with sub-second freshness?+
Three-layer architecture: streaming ingestion → real-time OLAP → query cache.

Layer 1 — Ingestion: events from your application → Kafka topic → Flink aggregation (1-minute tumbling windows) → ClickHouse or Druid sink. Flink reduces event volume by 100x before hitting OLAP (10K events/sec → 100 pre-aggregated rows/sec per dimension).

Layer 2 — OLAP: ClickHouse table partitioned by hour, clustered by (date, metric_name, dimensions). Pre-computed rollups for common queries. Queries return in <50ms even at billions of rows because they hit pre-aggregated data.

Layer 3 — Query cache: dashboard queries for the same time range and dimensions are cached in Redis for 10 seconds. 100 concurrent users viewing the same dashboard = 1 ClickHouse query per 10 seconds (not 100). Cache-aside with short TTL matches the sub-second freshness requirement.

The trap to avoid: querying raw events in ClickHouse from a dashboard with 100 concurrent users. Even fast OLAP becomes slow under that load. Pre-aggregate + cache is always the answer for dashboard use cases.
What is the difference between a data warehouse and a data lake?+
Schema-on-write (warehouse) vs schema-on-read (lake) — and the modern "lakehouse" that combines both.

Data Warehouse (Redshift, BigQuery, Snowflake): structured, schema defined before loading, data cleaned and transformed at ingest (ETL). Fast queries because structure is known. Cannot store unstructured data (images, raw logs, JSON blobs).

Data Lake (S3 + Parquet): store raw data in any format first, define schema when reading (schema-on-read). Flexible, cheap, can store anything. Slow queries without proper partitioning and file format discipline.

Data Lakehouse (Databricks Delta Lake, Apache Iceberg on S3): combine both. S3/GCS storage cost + columnar Parquet performance + ACID transactions from Delta/Iceberg metadata layer. Query directly from S3 with warehouse-like performance. This is the modern standard — most new data platform designs use the lakehouse pattern.

Interview answer: "I'd start with a data lake on S3 using Parquet + Delta Lake for ACID. Query with Athena for ad-hoc, Spark for batch processing, and ClickHouse for dashboard queries. This gives warehouse performance at lake economics."
08 · Core Concepts

OLAP Internals Every Interviewer Tests

Columnar Storage
OLAP stores data column-by-column, not row-by-row. This is the single most important architectural difference from OLTP.
Row store: [id=1, name=Alice, age=30, country=IN] | [id=2, ...] — all columns for one row are adjacent.
Column store: [age: 30,25,41,28...] [country: IN,US,IN,UK...] — all values for one column are adjacent. ✓ Analytics queries read 2–3 columns from 100M rows. Column store reads only those 2–3 columns from disk. Row store must read all columns even if only 2 are needed — 50x more I/O. Compression ratio also dramatically better: a column of country codes compresses 100:1 (dict encoding).
Vectorised Execution
ClickHouse processes data in vectors (batches of 1,024 values) rather than row-by-row.
Traditional row-by-row: per-row function call overhead, poor CPU cache utilisation. Vectorised: load 1,024 values into SIMD registers, apply operation to all 1,024 simultaneously using CPU vector instructions. ✓ 10–100x faster for aggregations (SUM, AVG, COUNT) compared to row-by-row execution. ClickHouse benchmarks: 1 billion row aggregation in <1 second on a single node. DuckDB also uses vectorised execution for embedded analytics.
Pre-Aggregation
(Rollup / Materialization)
Pre-compute aggregations at ingest time so queries read pre-rolled-up data instead of raw events.
Apache Druid: at ingest, rolls up (timestamp, country, device) → count. If 10,000 events have the same (minute, country, device) tuple, they become 1 row. Query on pre-aggregated data is 10,000x smaller. ✓ Dramatic query speedup and storage reduction. Perfect for: dashboard metrics (DAU, event counts, revenue). Trade-off: cannot reconstruct individual events — only aggregated data is stored. ⚠ Must define aggregation dimensions at ingest time. Changing dimensions later requires full reingestion.
Partitioning &
Pruning
Partition data by time (day/month). Queries with time filters only scan relevant partitions.
ClickHouse: PARTITION BY toYYYYMM(timestamp). Query for March 2026: reads only the March partition. Other months never touched.
BigQuery: partition by date column. A query for last 7 days scans only 7 partitions regardless of total table size. Billing is based on bytes scanned — partitioning directly reduces query cost. ✓ Always partition OLAP tables by time. Most analytics queries have a time filter — partition pruning turns full-table scans into partition scans. 100x reduction in data scanned is typical.
Dremel / BigQuery
Execution Model
BigQuery uses a distributed execution engine (Dremel) that dynamically allocates thousands of workers for a single query.
A query on 10TB of data: BigQuery spins up 10,000 workers, each reading 1GB of Parquet from Colossus (Google's distributed filesystem). Workers aggregate in a shuffle step. Result returned in seconds.
No indexes — BigQuery relies entirely on columnar scan parallelism. Works because: fast network (100Gbps), columnar compression (read only needed columns), massive parallelism. You pay per query (bytes scanned). Use partitioning + column selection to minimise scan cost. Clustering (sorting by commonly filtered columns) further reduces bytes scanned.

Uber — Real-Time Surge Pricing Analytics
REAL-TIME OLAP · DRUID
PROBLEM
Surge pricing requires knowing demand (ride requests) vs supply (available drivers) per geo-cell, per minute, globally. Must be fresh (<30s), queryable by city/zone/time, and handle millions of events per second.
ARCHITECTURE
Ride request events → Kafka → Druid ingestion with 30-second rollup: (minute, city, zone, type) → count. Pre-aggregation reduces 1M events/min to ~10K rows/min. Druid real-time nodes answer "requests in zone X last 5 minutes" in <50ms.
QUERY
SELECT SUM(request_count) FROM ride_events WHERE zone='BLR-3' AND time > NOW()-5m — Druid executes this on pre-aggregated data. Result: 2ms. Same query on raw events in PostgreSQL: minutes. This is the entire value proposition of pre-aggregating OLAP.
HISTORICAL
Historical data (>7 days) automatically tiered to deep storage (S3). Druid historical nodes load segments from S3 on demand. Dashboard queries for "surge patterns last 90 days by city" answered from S3-backed segments in <2 seconds.
Shopify — Merchant Analytics Dashboard
BIGQUERY · MULTI-TENANT
SCALE
100K+ merchants. Each merchant has their own analytics (sales by product, conversion rates, geographic breakdown). 50M+ orders/day across all merchants. Each merchant's dashboard must load in <2 seconds.
BIGQUERY
One BigQuery dataset per merchant (logical isolation). Partitioned by order_date, clustered by product_id. Merchant dashboard query: scans only their partitions, <5 seconds for 3 years of data. BigQuery's serverless model: Shopify pays per query scanned bytes, not for reserved cluster capacity.
CACHING
Dashboard common queries (today's revenue, top 10 products this week) pre-computed nightly by a Spark job → results stored in Redis with 1-hour TTL. Dashboard loads from Redis for common views (<50ms). "Custom" queries (arbitrary date range, filter combinations) go to BigQuery (<5 seconds).
ClickHouse
MergeTree
ClickHouse's primary table engine. Data is written in "parts" and merged in the background — like LSM trees but for columnar OLAP.
Insert: data written as a new sorted part (like an SSTable). Background merge: parts are periodically merged and sorted. Query: reads only relevant parts (primary key pruning) + relevant columns. ✓ Extremely fast inserts (sequential writes). Background merge keeps reads fast. Variants: SummingMergeTree (aggregates on merge), ReplacingMergeTree (deduplicates on merge), AggregatingMergeTree (stores pre-aggregated state).
Redshift Spectrum
Query S3 data directly from Redshift without loading it into Redshift storage first.
Create an external table pointing to S3 Parquet files. JOIN it with internal Redshift tables. Spectrum pushes predicates and column selection to the S3 layer — only relevant data is transferred. ✓ Hot data in Redshift (fast). Cold/archive data in S3 (cheap). Query both in one SQL statement. Ideal for: historical analysis where only recent data needs Redshift's full speed.
BigQuery Slots
BigQuery allocates "slots" (units of compute) to each query dynamically from a shared pool.
On-demand pricing: slots allocated dynamically per query, billed per TB (TiB) scanned. Capacity-based Editions pricing: commit to autoscaling slots billed per slot-hour, with steeper discounts for 1- or 3-year commitments — for predictable cost at high, steady query volume. At very large sustained query volume, a capacity commitment is typically far cheaper than on-demand. Slot contention: if your project runs many concurrent queries, they compete for slots. One very large query can starve smaller dashboard queries. Use workload management (reservation assignments) to allocate slots per team or use case.
10 · Advanced OLAP Topics

ClickHouse MergeTree internals and the data lakehouse

01 ClickHouse MergeTree Internals
What it is
ClickHouse's secret: sorted, compressed columnar storage with sparse indexing.

Insert: data written to parts (immutable, sorted by ORDER BY key). Background merge: small parts merged into larger parts. Reads: scan only parts that overlap with the query's WHERE clause (partition pruning + primary key range scan).

Sparse index: ClickHouse doesn't index every row. It keeps one index entry per "granule" (8192 rows by default). To find rows where user_id = 12345: scan the sparse index to find which granule ranges might contain it → decompress those granules → scan within. Index is small enough to fit in RAM; scanned granules are sequential reads.

✓✓ Result: ClickHouse can scan 1 billion rows/second/server. For a query like "count events by country for the last 7 days": partition pruning eliminates all but the last 7 days' partitions → sparse index finds the relevant granules → columnar scan of just the country and timestamp columns. Often 100-1000× faster than row-oriented OLAP.
02 Apache Iceberg & the Data Lakehouse
What it is
Iceberg brings ACID transactions and schema evolution to data lakes stored in S3.

Problem with plain S3 as a data lake: no transactions (concurrent writes → corrupted partitions), no schema evolution (adding a column requires full rewrite), no time travel (can't query "how did the data look last Tuesday?").

Iceberg solves this: maintains a metadata layer (JSON manifests) that tracks all files, their statistics, and versions. ACID writes: create new files, update the manifest atomically. Time travel: each manifest version is immutable — query the manifest from any point in time. Schema evolution: add/remove/rename columns by updating metadata only (no data rewrite).

✓✓ Iceberg is the new standard for lakehouse architecture. Supported by: Snowflake, BigQuery (in preview), Athena, Spark, Flink, Trino. Paired with object storage (S3/GCS), it provides data warehouse semantics without the cost of a managed data warehouse.
📋 · Requirements & Scale

Requirements & Non-Functional Constraints

Functional Requirements

FR1The system must answer analytical queries — GROUP BY, window functions, multi-dimensional aggregations — over billions of rows without the query needing a pre-defined index for every possible filter combination.
FR2The system must serve dashboard queries in well under a second by reading pre-aggregated/rolled-up data instead of scanning raw events on every request, so a business user changing a filter doesn't wait on a full table scan.
FR3The system must ingest streaming data (e.g. via Kafka) directly into the analytical store with only a short delay, so dashboards and alerts reflect events from the last few seconds to minutes, not yesterday's batch load.
FR4The system must compute metrics over sliding and tumbling time windows (per-minute, per-hour rollups) so time-series analysis doesn't require re-scanning raw events for every query.
FR5The system must support interactive, ad-hoc SQL against data whose query shape wasn't known in advance, so a data scientist can explore without a schema or index being pre-built for their specific question.
FR6The system must be able to query columnar files (e.g. Parquet on S3) directly where they sit, without a separate load/ETL step, so a data lake and a data warehouse can share the same underlying storage.

Non-Functional Requirements

NFR1Design target, not a platform guarantee: sub-second p99 is realistic for pre-aggregated dashboard queries (Druid and ClickHouse both publish benchmarks in this range), while multi-second p99 is a more honest target for genuinely ad-hoc scans over billions of raw rows — the achievable number depends heavily on data layout, partitioning, and query shape.
NFR2Order-of-magnitude figures drawn from each engine's own documented/benchmarked ingest capability, not independently re-verified per release: several hundred thousand rows/sec per node is a commonly cited ballpark for both ClickHouse and Druid streaming ingestion — treat as a planning range, and check current benchmarks for your specific hardware and row shape before committing to a number.
NFR3Design target you set and defend: how much lag is acceptable between an event happening and it being reflected in a dashboard. Real-time paths (Kafka → OLAP) commonly target single-digit-seconds to under a minute; batch paths commonly run hourly. Neither is a fact about OLAP engines in general — it's an architecture decision.
NFR4Design expectation grounded in how columnar compression works, not a single fixed number: because same-typed values compress well together, 5-10× compression versus row storage is a commonly cited range across columnar engines, but the actual ratio depends heavily on data cardinality and the specific compression codec — measure it on your own data rather than assuming a fixed multiplier.
NFR5Design target: the concurrency ceiling before dashboard queries start degrading is a function of your cluster size, query complexity, and how much you're relying on pre-aggregation vs raw scans — state the number you're designing for (e.g. "100+ concurrent dashboard queries") and the caching/pre-aggregation strategy that makes it achievable, rather than treating it as inherent to any OLAP engine.
NFR6Verified against Google's current published pricing: BigQuery on-demand queries are billed at $6.25 per TiB scanned (commonly rounded to "~$5-6/TB" in casual discussion) — partition pruning and clustering are essential to controlling this cost. Confirm the current rate against Google's pricing page before quoting an exact figure, since cloud pricing changes over time.
