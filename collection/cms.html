01 — The Problem

Why not just use a counter?

Imagine you're running YouTube. Every second, millions of videos are watched. Your boss asks: "What are the top trending videos right now?"

A naive HashMap of video_id → count works fine for 1,000 videos. But YouTube has 800 million videos. Storing exact counters for all of them = gigabytes of RAM, just for counting.

The insight: For trending, rate-limiting, and frequency analysis, you don't need the exact count. A "slightly-higher-than-truth" estimate is perfectly fine — as long as it's fast and tiny.

Count-Min Sketch gives you ~95%+ accurate frequency estimates in a few kilobytes, with O(1) inserts and queries.

02 — The Key Mechanism

How does a hash function pick a column?

This is the most important thing to understand. A hash function is just a deterministic math machine: same input → always same output. It converts any string into a number, then we use modulo (%) to fit it into our grid width.

// Step-by-step: hashing "video_42" into a 6-column grid

// Hash Function 0: a simple polynomial hash
"video_42" → add up (character codes × prime powers)
= 118×31⁰ + 105×31¹ + 100×31² + ... = big number: 8,472,193
column = 8,472,193 % 6 (grid width) = → Col 3

// Hash Function 1: a different seed / multiplier
"video_42" → same chars, different math → 5,291,847
column = 5,291,847 % 6 = → Col 2

// Hash Function 2: yet another seed
"video_42" → 3,104,522
column = 3,104,522 % 6 = → Col 4

The key insight: the exact number doesn't matter. What matters is that (a) it's always the same for the same input, and (b) different hash functions scatter the same input to different columns.

Real world analogy: Think of 3 bouncers at a party, each with their own arbitrary rule for assigning people to table numbers. If you ask "where does Alice sit?", each bouncer gives a different table — but they'll always give the same table for Alice every time you ask.
03 — The Grid

Count-Min Sketch is just a table of counters

A grid of depth × width. Each row has its own independent hash function. The grid starts at all zeros.

Col 0Col 1Col 2Col 3Col 4Col 5
Row 0 (hash_fn_0) 000302
Row 1 (hash_fn_1) 004010
Row 2 (hash_fn_2) 200150

The highlighted cells are where "video_42" incremented. To query: look up those same cells → values are 3, 4, 5 → take MIN = 3. That's our estimate.

Why is Row2's value (5) higher? Because another video happened to hash to Col 4 in Row 2 — it polluted that counter. The minimum protects us from this pollution.

05 — Key Properties

What to say in your interview

PropertyDetailImplication
Space O(width × depth) — fixed A few KB regardless of traffic volume
Time O(depth) per insert/query Essentially O(1) in practice
Error direction Only overcounts, never undercounts overestimate-only — safe for rate limiting
Accuracy tuning Wider grid → less error per row More rows → lower failure probability
Deletion Not supported by default Counters only go up
The formula: Width = ⌈e/ε⌉ where ε is acceptable error rate. Depth = ⌈ln(1/δ)⌉ where δ is acceptable failure probability.

Plain English: "I want <0.1% error with 99% confidence" → ε=0.001, δ=0.01 → Width ≈ 2719, Depth ≈ 5. That's a ~54KB grid.
06 — Interview Counter Questions

Questions you'll be asked — answered

Why not just use a HashMap? +
A HashMap is exact but memory scales with unique items. 100M unique URLs = gigabytes of RAM just for counters. Count-Min Sketch gives you ~95% accuracy in a few kilobytes. For trending, rate-limiting, and frequency analysis, "close enough" is perfectly fine — and it's orders of magnitude cheaper.
What if two items always hash to the same column? +
That's a collision — their counts bleed into each other. That's exactly why we use multiple rows with independent hash functions. The probability that item A collides with item B in all rows simultaneously drops exponentially with each row added. With 5 rows, it's astronomically unlikely. This is why we take the minimum — it's the least-polluted estimate across all rows.
Can you delete items? +
Standard CMS doesn't support deletion — subtracting could make a count go negative and corrupt the structure. If you need deletion, use Count-Min Sketch with conservative update or switch to a Count Sketch (allows negative values, slightly different statistical guarantees). In practice, most real-world use cases (trending, rate limiting) don't require deletion.
How is this different from a Bloom Filter? +
They're cousins — same probabilistic family, different questions.

When would you NOT use Count-Min Sketch? +
Three cases: (1) When you need exact counts — billing, financial transactions, audit logs. (2) When your key space is small enough to fit exactly in RAM. (3) When you need to enumerate all keys — CMS can tell you the count for a key you ask about, but it can't tell you what keys exist. For that, you need a different structure.
Where is Count-Min Sketch used in production? +
Redis uses it for frequency counting in rate limiting. Twitter/X uses it for trending hashtag detection. Networking equipment uses it to detect high-traffic IPs (DDoS detection). Database query optimizers use it to estimate row frequencies for query planning. CDNs like Akamai use it to identify hot cache objects.
The one line to remember
"Count-Min Sketch is a fixed-size grid of counters. You hash each event across multiple rows, increment that cell in each row, and query by taking the minimum. It trades perfect accuracy for dramatically lower memory — and it only ever overcounts, never undercounts."
