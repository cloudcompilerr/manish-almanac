The Exact Question

You are designing LLM-powered enterprise search for a 10,000-person company. The constraints are:

128k Context window tokens
300 Relevant docs per query
2M Total tokens in those docs
10k Concurrent users
The gap: 2,000,000 tokens of relevant content needs to squeeze through a 128,000 token window. That's a 15× compression problem — without losing the answer.

01 The Problem, Stated Simply

The Librarian Analogy Imagine you ask a librarian a question. There are 300 relevant books in the library. The librarian can only hold 8 books on the desk at once while answering you. Which 8 do they pick? And what happens if the answer is buried in book #247 that they left on the shelf?

That is exactly what happens with LLM-powered search. The LLM is brilliant — but it can only "see" what you put in front of it. You have a context window, which is like the desk. You have a massive document corpus, which is like the library. The art is in deciding what lands on the desk.

The naive answer — "just put everything in" — fails for three reasons:

  • It's impossible. 2M tokens don't fit in 128k. You physically cannot.
  • It's expensive. Even if you had a 2M context model, each query would cost ~$20–60 in API fees at scale.
  • It degrades quality. LLMs lose focus in extremely long contexts — they hallucinate more, and "forget" content in the middle (the "lost-in-the-middle" problem).

02 Why Is This Actually Hard?

You might think: "Just take the top 10 most relevant chunks." The problem is that relevance is not simple.

The Detective Analogy A detective solving a crime doesn't just look at the most "suspicious" clue in isolation. The answer emerges from combining clues: the timeline from document A, the motive from document B, and the alibi hole from document C. Miss any one of them and the conclusion is wrong.

In enterprise search, the "answer" to a query like "What is our data retention policy for EU customers?" might require reading the GDPR policy doc, the engineering SLA doc, and the legal interpretation memo — all together. Any one of them alone gives an incomplete or wrong answer.

The second problem is confident wrongness. An LLM doesn't say "I don't know." It says something plausible-sounding. If you feed it the wrong documents — or the right documents with key paragraphs missing — it will construct a confident answer that is subtly or completely wrong. In an enterprise setting, that is a legal, compliance, and trust problem.

03 The Full Retrieval Pipeline

The industry-standard answer is a multi-stage retrieval funnel. You don't hand 300 documents to the LLM. You intelligently narrow them down through several stages before the final answer generation.

1
Query Understanding & Expansion
NLP · Query Reformulation · HyDE

Before retrieving anything, understand what the user is actually asking. Expand ambiguous terms, detect intent (lookup vs. reasoning vs. summarization), and optionally generate hypothetical answer snippets to improve retrieval direction (a technique called HyDE — Hypothetical Document Embeddings).

Example: User asks "What's our PTO policy?" → Expand to "paid time off", "annual leave", "vacation days", "HR policy".

2
First-Stage Retrieval (Broad Net)
Vector Search · BM25 · Hybrid Search · FAISS / Pinecone / Elasticsearch

Cast a wide net: retrieve the top ~50–100 candidate chunks using a combination of dense vector search (semantic similarity via embeddings) and sparse BM25 search (keyword matching). Hybrid search combining both consistently outperforms either alone.

This stage is optimized for recall — don't miss anything relevant, even if you include some irrelevant chunks.

Why both? Vector search catches "pay raise" when the user said "compensation increase." BM25 catches exact product codes and acronyms like "GDPR Article 17" that embeddings blur over.
3
Second-Stage Re-Ranking (Precision Pass)
Cross-Encoder · Cohere Rerank · ColBERT · BGE Reranker

Take the top 50–100 candidates and re-score them with a heavier, more accurate model. A cross-encoder reads the query AND each document chunk together — it's much more accurate than a bi-encoder similarity score, but too slow to run on all documents upfront.

After re-ranking, you have a precise top 10–20 chunks ordered by true relevance. This is your "shortlist."

4
Context Budget Allocation
MMR · Contextual Compression · Chunk Stitching

From the shortlist, intelligently fill the context window budget (e.g., reserve 120k out of 128k for documents; keep 8k for the query + instructions + answer).

Three key techniques here:

  • MMR (Maximal Marginal Relevance): Don't just pick the top 10 chunks — pick chunks that are relevant AND diverse. If 8 out of 10 top chunks are from the same FAQ page saying the same thing, only include 1–2 of them and use the remaining budget for different sources.
  • Contextual Compression: Instead of inserting a full 1000-token chunk, extract only the 2–3 sentences directly relevant to the query. LLMLingua and similar tools can compress chunks by 3–5× without losing meaning.
  • Chunk Stitching: If adjacent chunks of a document are selected, merge them to preserve coherent context and save tokens on repeated metadata headers.
5
LLM Generation with Citations
Grounded Generation · Self-RAG · Citation Enforcement

The LLM receives: the user query + selected context chunks + a strict system prompt instructing it to only answer from the provided context and to cite the source for every claim.

This is the most important prompt engineering constraint: "Answer only from the documents provided. If the answer is not in these documents, say so explicitly."

04 The 5 Core Strategies, Compared

Strategy What it does When to use Trade-off
Top-K Retrieval Take the K most similar chunks by embedding cosine distance Baseline / simple queries Misses diverse sources; duplicate chunks waste budget
MMR Selection Balance relevance + diversity when picking chunks Multi-document reasoning Slight relevance trade-off for coverage gain
Re-ranking (Cross-Encoder) Re-score top-K with a more accurate model When precision matters more than recall speed Adds 50–200ms latency per query
Contextual Compression Extract only the relevant sentences from each chunk ✓ Always — massive token savings Risk of extracting wrong sentences if compressor is weak
Hierarchical / RAPTOR Cluster docs, summarize clusters, retrieve at right granularity Massive corpora; multi-hop reasoning More complex offline indexing pipeline

In a real system, you combine these. The FAANG-level answer layers them: hybrid first-stage → cross-encoder re-rank → MMR selection → contextual compression → grounded generation.

05 The Hallucination Problem — and How to Beat It

The question specifically says: "without the LLM giving a confidently wrong answer." This deserves its own treatment.

Why LLMs Hallucinate on RAG Queries

There are three root causes in a retrieval setting:

  • The right document wasn't retrieved. The retriever failed. The LLM is asked to answer without the crucial evidence — so it fills the gap from its training data, which may be wrong or outdated.
  • "Lost in the middle" effect. Research shows LLMs have U-shaped attention over long contexts — they pay most attention to the beginning and end of the context window, and lose track of content in the middle. Critical evidence buried in chunk #15 of 20 gets ignored.
  • Conflicting documents. Two sources say different things. The LLM "averages" them and presents a confident synthesis that matches neither.

Mitigation Strategies

A
Strict Grounding Prompts

Instruct the LLM: "Only use information from the provided context. If you cannot find the answer, say 'I could not find this in the available documents.'" This single instruction reduces hallucination significantly.

B
Citation Enforcement

Require the model to cite a specific document + passage for every claim. If it can't cite, it can't state. You can validate citations post-hoc by checking if the claimed text actually appears in the context.

C
Self-RAG / Retrieval Verification

A newer approach: the LLM itself generates a relevance score for each retrieved chunk before writing the answer. Chunks it deems irrelevant are excluded. This reduces "confused by irrelevant context" hallucinations.

D
Confidence Thresholding + Fallback

If the retrieval pipeline confidence score is below a threshold, don't call the LLM at all. Instead, return: "I found some potentially related documents but am not confident I have the right answer — please review these sources directly." This is the honest, safe enterprise default.

06 Doing This at 10,000 Users

The scale constraint adds an engineering dimension. Here is what changes at 10,000 concurrent users:

Component Single-user concern 10k-user concern Solution
Vector Search Accuracy QPS (queries/sec) throughput Pinecone / Weaviate with horizontal sharding; HNSW indexing for sub-10ms recall
Re-ranker Latency (200ms OK) Latency × volume = cost explosion Cache re-ranking for repeated queries; use lighter ColBERT over full cross-encoder
LLM Calls Cost per call (~$0.50) $0.50 × 10k/hr = $5k/hr Semantic query caching (same or similar question → return cached answer); smaller context → cheaper calls
Document Index Static Constantly updated (new docs, edits, deletions) Incremental indexing pipeline; document versioning; ACL-aware retrieval (user can only see docs they have access to)
Critical for enterprise: Access Control. Before any document chunk lands in a context window, verify the querying user has read permission for that document. A mis-retrieval that exposes a confidential HR document to a junior employee is a compliance failure, not just a quality issue.

The Complete System Design Answer

A production-grade LLM search system for a 10,000-person enterprise uses a 5-stage retrieval funnel:

  • Query expansion — understand intent, expand synonyms, use HyDE if needed
  • Hybrid first-stage retrieval — dense (vector) + sparse (BM25) → top 50–100 candidates
  • Cross-encoder re-ranking → shortlist to top 15–25 chunks by true relevance
  • Context budget allocation — apply MMR for diversity + contextual compression to fit within 128k tokens
  • Grounded generation — strict prompts, citation enforcement, confidence thresholding

At scale, add semantic caching, ACL-aware retrieval, and incremental indexing. The goal is not to put all relevant documents in context — it is to put the right 15–25 chunks in context such that the LLM has everything it needs and nothing that confuses it.

07 What to Say in the Interview

Say This — Verbatim if Needed

"The fundamental insight here is that this is a precision-recall tradeoff under a hard budget constraint. I'd design a multi-stage funnel: first cast a wide net with hybrid retrieval — combining dense vector search with BM25 — to maximize recall across the 300 candidate documents. Then apply a cross-encoder re-ranker to promote the most truly relevant chunks. Then I'd use contextual compression and MMR-based selection to fill the 128k context window with the highest signal-density content possible. The key anti-hallucination mechanism is not just what goes in, but how the LLM is instructed — grounding prompts, citation requirements, and a confidence threshold below which we refuse to generate an answer and surface the raw documents instead. At 10,000 users, I'd layer on semantic query caching to reduce redundant LLM calls, and strict ACL enforcement so no document reaches a user who doesn't have access rights to it."

Follow-up Questions They'll Ask — and Your Answers

They'll askYou say
"What if the answer requires reading all 300 documents?" For analytical queries requiring corpus-wide synthesis, use offline MapReduce over LLM: summarize each document cluster independently, then synthesize summaries. Never try to fit it all in one context window in real-time.
"How do you evaluate retrieval quality?" Track MRR (Mean Reciprocal Rank), NDCG for retrieval quality, and answer faithfulness score (RAGAS framework) to catch hallucinations — did the LLM's answer contradict its own context?
"What about documents that update frequently?" Incremental indexing pipeline — on document edit/delete, re-chunk and re-embed only the changed document. Vector store should support soft deletes with version IDs. Stale cache invalidation by document ID.
"How would you handle multi-hop queries?" Use iterative RAG or agentic retrieval: the LLM generates sub-queries, retrieves for each, then synthesizes — rather than one-shot retrieval. IRCoT (Interleaved Retrieval + Chain-of-Thought) is the research formulation.
