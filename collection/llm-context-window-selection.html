01 · Foundations

What Is a Context Window?

A context window is the total number of tokens a language model can "see" in a single forward pass — its effective attention span. Everything outside this window does not exist from the model's perspective. When you send a prompt, the model reads the entire sequence of tokens simultaneously and attends to all of it (within limits) to generate its response.

Tokens are the fundamental unit of text for LLMs. A token is roughly a word piece — common words like "the" are one token, while longer words may be two or three. The tokenizer (BPE, SentencePiece, or tiktoken) converts raw characters into token IDs before any computation happens. The model's context limit is always stated in tokens, not characters or words.

The working memory analogy
Think of a context window like working memory in humans. When reading a long legal contract, you can only hold so many clauses in active attention at once. As you read further, earlier details start to fade — you may still have them in long-term memory but they are not actively influencing your reasoning right now.

An LLM's context window is this "active desk space." Everything on the desk is processed with full attention. Anything that does not fit on the desk must be left out — and the model cannot reason about what it cannot see. Unlike human memory, there is a hard ceiling: exceed the token limit and the model errors out or truncates your input silently.

How Transformers Implement Context Limits

The Transformer architecture (Vaswani et al., 2017) uses self-attention: every token attends to every other token in the sequence. This produces a quadratic O(n²) relationship between sequence length and compute — doubling the context length quadruples the attention computation. Memory (VRAM) scales similarly. This is why context windows were stuck at 4K–8K tokens for years and why extending them beyond a certain point has rapidly diminishing returns on raw throughput.

Modern long-context models use several architectural tricks to tame this: Rotary Position Embeddings (RoPE) with extended base frequencies, Grouped Query Attention (GQA) to reduce KV cache memory, FlashAttention for I/O-efficient attention computation, and sparse attention patterns that skip attending to distant irrelevant tokens. These innovations pushed practical context windows from 4K to 128K, 200K, and even 1M tokens.

Input Tokens
All text sent to the model before it generates a response. Includes the system prompt, conversation history, injected documents, and the user query. Input tokens consume context window space but are cheaper than output tokens — typically 3–10x less expensive per token. Input tokens are processed in a single forward pass; the model reads everything at once before generating a single output token.
Output Tokens
Tokens the model generates, one at a time, via autoregressive decoding. Each new token attends to all previous tokens (input + output so far). Output is significantly more expensive because it requires N sequential forward passes for N output tokens — this is the latency bottleneck, not input processing. Most models are priced 3–15x higher per output token than input token.
KV Cache
The key-value attention cache that stores computed attention states for input tokens. During autoregressive generation, the KV cache means the model does not re-process input tokens for each new output token. This is what makes long-context generation tractable — without KV caching, generating 500 tokens with a 100K input context would require 100K × 500 = 50M token-processing operations instead of 100K + 500. The KV cache lives in GPU VRAM and is why long contexts require more memory.
Prompt Caching
Provider-level caching of repeated input prefixes across API calls. Anthropic (Claude) and Google (Gemini) allow you to designate a portion of your prompt as "cached." If the same prefix is reused within a time window (5 min for Anthropic), the provider serves it from cache at 90% reduced cost and lower latency. Critical for production RAG systems with static system prompts or large repeated document contexts. Not the same as KV cache — this is a billing/infrastructure feature, not a model architecture feature.
Context Utilization
The fraction of the available context window actually filled with meaningful content. A model with a 200K token window does not mean you should always fill it — costs scale linearly with input tokens, latency increases, and quality can degrade (lost-in-the-middle effect). Optimal utilization depends on the task: code analysis benefits from more context, simple Q&A rarely needs more than 8K tokens.

03 · Architecture Decision

Long-Context vs RAG: The Core Architectural Decision

When your application needs to reason over large bodies of text, you face a fundamental architectural choice: shove everything into the context window (long-context approach) or retrieve only the relevant fragments (RAG — Retrieval-Augmented Generation). Neither is universally superior. The right choice depends on your corpus size, update frequency, cost sensitivity, and query patterns.

▶ WHEN TO USE LONG CONTEXT
  • Entire codebase or document set fits within model limits (e.g., <150K tokens)
  • Document relationships matter — reasoning across multiple files simultaneously (e.g., understanding how module A calls module B calls module C)
  • No vector database infrastructure in place and you need a working prototype today
  • One-shot analysis: ingest an entire report, contract, or codebase once, ask many questions
  • The query could match almost anywhere in the document and you cannot predict where
  • Cross-document synthesis: "What are all the places where X is contradicted?"
▶ WHEN TO USE RAG
  • Corpus exceeds model context limits (e.g., 10,000 documents, a whole company wiki)
  • Dynamic data: knowledge base updated frequently — new docs added daily, real-time data
  • Cost-sensitive, high-volume workloads where sending 100K tokens per query is prohibitive
  • Need citations and provenance: RAG naturally returns which source chunks were used
  • Low-latency requirements: small context = faster first-token response
  • Multi-tenant: different users see different document subsets — RAG enforces access control at retrieval time
The Hybrid Pattern — Best of Both Worlds

Hybrid RAG + Long Context: Use RAG to select the top-K most semantically relevant chunks from a large corpus, then pass those chunks to a long-context model for final synthesis. RAG narrows the search space (e.g., 100K docs → top 20 chunks, ~15K tokens). The long-context model reasons holistically over those 20 chunks, preserving relationships within the retrieved set. This pattern captures RAG's scalability and long context's relational reasoning.

This is the production architecture used by most enterprise RAG systems: query → embed → vector search → rerank → long-context LLM → answer.

RAG Architecture Components

Embedding
Model
Converts text chunks into dense vector representations that capture semantic meaning. The embedding model is separate from the generation LLM. Common choices: OpenAI text-embedding-3-large (3072 dimensions), Cohere embed-v3, open-source BAAI/bge-large-en-v1.5. Dimension size trades recall quality against storage/search cost. The embedding model's quality sets an upper bound on retrieval quality — a bad embedder cannot be fixed downstream. Key insight: The embedding model's vocabulary and training distribution must match your domain. A general-purpose embedder works poorly on highly specialized medical or legal text — consider domain-fine-tuned models.
Vector Store
Database optimized for approximate nearest-neighbor (ANN) search over embedding vectors. ANN search finds the K vectors most similar to a query vector using algorithms like HNSW (Hierarchical Navigable Small World graphs) or FAISS (Facebook AI Similarity Search). Common stores: Pinecone (managed), Weaviate (hybrid search), Qdrant (Rust, fast), pgvector (Postgres extension, zero infra overhead), Chroma (local development). Search time is O(log n) to O(n^0.5) — much faster than brute-force O(n) cosine similarity over millions of vectors. For <100K chunks, pgvector on Postgres is often sufficient and eliminates one infrastructure dependency. Only reach for dedicated vector DBs when you need millions of chunks or sub-10ms search at scale.
Reranker
A cross-encoder model that re-scores the top-K retrieved chunks for true relevance to the query. Bi-encoder vector search is fast but imprecise — it uses independent embeddings for query and document. A cross-encoder takes (query, chunk) as a combined input and scores their relevance directly, but at higher compute cost. Typical pipeline: vector search retrieves top-50 candidates in 5ms → reranker scores all 50 against query in 50ms → take top-5 for the LLM. Common rerankers: Cohere Rerank, cross-encoder/ms-marco-MiniLM-L-6-v2. Reranking consistently improves RAG answer quality by 10–30% in benchmarks.
Chunking
Strategy
How you split documents before embedding determines retrieval quality more than almost any other decision. A chunk must be: (1) small enough that the embedding captures a single coherent concept, (2) large enough to contain enough context to be useful when injected into the LLM prompt. The optimal chunk size depends on document type. Fixed-size chunking (512 tokens, 50-token overlap) is the naive baseline. Semantic chunking (split at paragraph/section boundaries) and recursive character splitting (LangChain's default) produce better results. Chunk metadata (document title, section header, page number) should always be stored and injected with retrieved chunks.
04 · Quality Degradation

Quality at Length: The "Lost in the Middle" Problem

In 2023, Stanford researchers (Liu et al.) published a landmark finding: LLMs perform significantly worse on content placed in the middle of long contexts compared to content at the beginning or end. This was demonstrated across GPT-3.5, GPT-4, Claude, and open-source models. The effect worsens as context length increases.

The phenomenon arises from how positional encodings and attention patterns interact at training time. Models see more training data where important information appears near the start (instructions) or end (most recent message). The model's "attention budget" is unevenly distributed — early and late positions get more attention weight than the dense middle of a very long context.

Critical Production Rule

Put the most important instructions and content at the START and END of your context. Never bury critical system instructions, examples, or key facts in the middle of a long prompt. If you are injecting retrieved chunks, order them so the most relevant chunks appear first and second-most-relevant appear last. Filler/supporting context goes in the middle.

Needle-in-a-Haystack Testing

Needle-in-a-haystack (NIAH) is the standard benchmark methodology for evaluating long-context fidelity. The procedure: hide a specific, unique fact (the "needle") at a precise position within a long filler document (the "haystack"), then ask the model to retrieve that fact. Repeat across all position percentages and all context depths (4K, 16K, 64K, etc.) to produce a 2D heat map of recall accuracy.

Most frontier models show near-perfect recall (>98%) at short contexts but degrade meaningfully beyond 50K tokens, especially at positions 30–70% through the context. Gemini 1.5 Pro's original announcement showed exceptionally clean NIAH performance at 1M tokens, but real-world tasks involving reasoning over retrieved facts (rather than pure retrieval) show more typical degradation patterns.

Production Mitigation Strategies

1. Primacy / recency placement: Place critical instructions at position 0 (system prompt start) and key retrieved context at the very end of the user message, just before the question.

2. Reduce context when possible: If you need a model to find a specific answer, RAG to narrow context beats stuffing everything in. A 5K context window has near-perfect recall; a 100K context window has the lost-in-middle problem.

3. Repetition for critical facts: For truly critical instructions (safety rules, formatting requirements), repeat them both at the start of the system prompt and at the end of the user turn. Redundancy is not wasted tokens when the stakes are high.

4. Structured context formatting: Use XML tags, headers, or numbered sections so the model can parse structure. <document id="1" relevance="high">...</document> helps the model allocate attention, especially in models fine-tuned on structured prompts (Claude responds well to XML, GPT-4o to Markdown headers).

How Prompt Caching Transforms Cost Calculus

When a system prompt or large document context is reused across many API calls, provider-level prompt caching can reduce costs dramatically. Anthropic's prompt caching prices cached tokens at 10% of normal input cost ($0.30/1M cached vs $3.00/1M uncached for Claude 3.5 Sonnet). Google's Gemini Context Caching works similarly. The requirement: the cached prefix must be identical (bit-for-bit) across requests and be used within the cache TTL window.

When it works
Prompt caching is most impactful when you have a large, static prefix sent with every request. Classic examples: a 50,000-token system prompt containing company policies + RAG context that rarely changes, or a large codebase context injected for a session of coding assistance. If you send 100K tokens of static context with every request and make 1,000 requests per day, caching reduces that cost by 90% — from $300/day to $30/day (Claude 3.5 Sonnet pricing).
When it does not
Caching does not help when context changes every request. If each user has a unique document context that is never reused, there is no cache hit benefit. Similarly, if you are injecting fresh retrieved RAG chunks that differ per query, those chunks are not cacheable (though the static system prompt above them still is). The key discipline: separate your context into static layers (cacheable) and dynamic layers (not cacheable) and order them with static content first.
Cache TTL
Anthropic's prompt cache has a 5-minute TTL. If the same prefix is not reused within 5 minutes, the cache entry expires and the next request pays full price. For high-traffic applications (many requests per minute), this is fine. For low-frequency workflows, you may need to send a "keep-alive" request to prevent expiry. Gemini's context cache has a configurable TTL (minimum 1 hour, maximum 1 month) — better for batch or overnight workflows.
06 · Engineering Techniques

Context Management Techniques

When raw long-context or basic RAG is insufficient, these techniques allow you to scale, improve quality, or reduce cost. Each involves real engineering tradeoffs — understand when to apply each.

Technique 01
Sliding Window
Move a fixed-size window through a long text sequentially. Overlap by N tokens (typically 10–20%) to preserve continuity at window boundaries. Each window is processed independently. Results are merged. Best for: sequential extraction tasks where each passage is largely self-contained — summarizing chapters, extracting entities from a news feed, processing transcripts. Preserves order-dependent context that RAG loses.
Simple to implement
Technique 02
Chunk & Rerank
Split the document corpus, embed all chunks into a vector space, perform semantic search to retrieve the top-K candidates, then apply a cross-encoder reranker to re-score and select the final N chunks by true relevance. The two-stage pipeline separates recall (vector search, fast) from precision (cross-encoder reranking, slower but more accurate). Industry-standard RAG production pattern. 10–30% quality improvement over retrieval alone.
Medium complexity
Technique 03
Hierarchical Summarization
Summarize each leaf section independently in parallel, then summarize the summaries recursively. Reduces token count from O(n) to O(log n). Preserves the structural outline and key decisions from a large document without fitting everything in the context window. Useful for: meeting transcripts, long reports, book-length text. Tradeoff: information loss at each summarization level — fine details may not survive to the root.
Medium complexity
Technique 04
Dynamic Context
Only include context items that scored above a similarity threshold at query time. Unlike fixed top-K retrieval, threshold-based retrieval adapts to query difficulty: easy queries may include 3 chunks, hard queries may include 20. Prevents injecting low-relevance noise when no good matches exist (which can actively mislead the model). Requires calibrating your similarity threshold on a validation set — too high and you get empty context; too low and you get irrelevant noise.
Requires calibration
Technique 05
Map-Reduce
Process each document chunk independently in parallel (map phase), generating partial answers or extractions. Then merge all partial results in a final synthesis call (reduce phase). Classic distributed systems pattern applied to LLMs. Well-suited for: "What are all the mentions of X across this corpus?" or "Summarize all of these documents." LangChain, LlamaIndex, and DSPy all have built-in map-reduce chains. Latency = depth of reduce tree, not total token count.
Easy with frameworks
Technique 06
Caching Prompt Prefixes
Pin the system prompt and static document context in the provider's prompt cache (Claude's prompt caching API, Gemini's context caching). Repeated requests using the same prefix pay 5–10x less per cached token and get lower latency (no re-processing). Structure your prompts so cacheable content (system prompt, documents) comes first, dynamic content (user query, dynamic RAG chunks) comes last. Single highest-ROI optimization for production LLM systems with repeated context.
High ROI · Low effort

Chunking Strategies in Depth

Chunking is the most underappreciated variable in RAG quality. Poor chunking produces embeddings that mix multiple unrelated concepts, defeating semantic search. Here are the main strategies ranked from naive to sophisticated:

01 Fixed-Size Chunking (Baseline) NAIVE
How it works

Split text every N tokens (typically 256–1024) with an overlap of M tokens (typically 10–20% of N). Simple, fast, requires no understanding of document structure.

Overlap is critical: without overlap, a sentence split across a chunk boundary has half its context in each chunk — the embedding for either half is incomplete and retrieval misses it. Overlap ensures boundary sentences appear in both adjacent chunks.

!Splits sentences and paragraphs arbitrarily. The embedding for a chunk may mix the end of one topic and the start of another. Degrades retrieval quality for complex documents. Only acceptable for homogeneous prose with no section structure.
02 Recursive Character / Structural Splitting STANDARD
How it works

Split on a hierarchy of separators: try to split on \n\n (paragraph breaks) first; if chunks are too large, fall back to \n (line breaks), then ". " (sentence ends), then " " (words), then characters. This is LangChain's RecursiveCharacterTextSplitter and the de facto default for most production RAG systems.

Respects natural text boundaries while staying close to target chunk size. Dramatically better than naive fixed-size splitting for formatted documents.

✓Best balance of quality and implementation simplicity. Use this as your default. Good for: prose documents, articles, reports, conversation transcripts.
03 Semantic Chunking ADVANCED
How it works

Embed consecutive sentences using a fast embedding model. Compute cosine similarity between adjacent sentence embeddings. When similarity drops significantly (topic change), create a chunk boundary. This detects semantic topic transitions rather than syntactic boundaries.

Produces chunks that correspond to coherent topical units regardless of their character length. A short but dense paragraph about one concept is one chunk; a long rambling paragraph spanning three topics is split accordingly.

→Produces the best retrieval quality in benchmarks for long, complex documents (technical manuals, legal contracts, academic papers). Adds ~20ms per document for embedding during ingestion. LlamaIndex's SemanticSplitterNodeParser implements this pattern.
04 Document-Aware / Hierarchical Chunking PRODUCTION BEST PRACTICE
How it works

Parse document structure explicitly: extract headings, subheadings, tables, code blocks, and list items as separate chunk types. Each chunk carries metadata: document title, section path (e.g., "Chapter 3 > 3.2 > Introduction"), page number, and content type. At query time, include the section path in the injected chunk so the LLM understands context.

Code files are split at function/class boundaries (not line count). Markdown splits at heading levels. PDFs use layout detection to separate columns, captions, footnotes.

✓The highest retrieval quality achievable for structured documents. The section metadata alone improves answer quality significantly because the LLM knows where in the document a chunk comes from. Required for codebases — never split source code at fixed character counts.
07 · What Not To Do

Anti-Patterns: Common Mistakes That Hurt Quality & Inflate Cost

Every one of these mistakes is seen regularly in production LLM applications. Understanding why they are wrong is as important as knowing the correct approach.

Anti-pattern 01 · Context Stuffing

Stuffing every available document into the context window regardless of relevance. This is the most common mistake engineers make when first working with long-context models. Reasoning: "the model has 200K tokens, so I should use all of it to give it more information." Reality: irrelevant context actively hurts quality — the model must attend to noise, which dilutes signal. It also increases cost linearly and increases latency. The model's effective reasoning capacity does not scale linearly with context length. More context = higher cost + lower accuracy when content is not curated.

Fix: Always filter context for relevance before injection. Even with long-context models, aim for high signal-to-noise ratio in your context window.

Anti-pattern 02 · Defaulting to Max Context

Always using the model's maximum context window "just in case." Engineers sometimes set their context to the model's maximum (128K, 200K) as a safe default, even when the actual content is 5K tokens. This multiplies cost by 25–40x unnecessarily and significantly increases time-to-first-token. The latency and cost of a 200K-token request is not the same as a 10K-token request — input token processing time scales with context length.

Fix: Measure actual token usage in production. Profile your real p50, p90, p99 context sizes. Set a dynamic context budget based on actual content size, not the model maximum. Implement hard caps with graceful truncation rather than always padding to maximum.

Anti-pattern 03 · Ignoring Lost-in-the-Middle for Critical Instructions

Placing critical instructions, constraints, or safety rules in the middle of a long prompt. This is especially dangerous in production systems that dynamically inject retrieved documents: the system prompt is at position 0, then 20 retrieved chunks are injected (positions 1–20K tokens in), then the critical constraint "do not reveal internal pricing" appears at token 20,001, then the user message follows. The constraint is in the middle. It will be ignored at a much higher rate than if it appeared in the system prompt or at the very end of the user message.

Fix: Put safety constraints and critical formatting instructions in the system prompt (position 0). Repeat them at the end of the user turn. Never rely on instructions buried in the middle of large RAG-injected contexts.

Anti-pattern 04 · Naive Line-Split Chunking for RAG

Splitting documents on newlines or fixed character counts without respecting semantic structure. This produces chunks where a sentence is split mid-way, or where a heading appears at the end of one chunk with its content in the next chunk, or where a code function is sliced in half. The embedding for each malformed chunk is degraded — it does not clearly represent a coherent concept. Retrieval quality collapses. The symptom is "RAG gives irrelevant answers even when the right information is in the corpus."

Fix: Use recursive text splitting as a minimum (LangChain's default). For structured documents, parse structure explicitly. For code, split at function/class boundaries. Always test chunking quality by manually inspecting a sample of 20–30 random chunks from your corpus before going to production.

Anti-pattern 05 · No Token Counting in Production

Not measuring actual token usage per request in production. Without monitoring, you cannot optimize cost, you will not notice when context grows unexpectedly (accumulating conversation history, growing system prompts), and you cannot diagnose quality issues related to context length. Many production bugs manifest as "the model started ignoring instructions" — and the root cause is that conversation history accumulated until the system prompt was being truncated off the front of the context.

Fix: Log token counts for every API request: prompt tokens, completion tokens, total tokens. Set alerts when p95 context size exceeds 50% of model limit. Implement explicit context window management: truncate conversation history oldest-first, summarize old turns when approaching the limit. Never let context grow unboundedly.

Anti-pattern 06 · Treating RAG as a Solved Problem After Prototype

Building a RAG prototype with basic vector search and declaring it production-ready. A basic prototype using OpenAI embeddings + Pinecone + top-3 retrieval will have retrieval precision of 40–60% on real queries — meaning 40–60% of the time, the retrieved chunks are not actually relevant to the question. This gets papered over in demos with cherry-picked queries. In production with real user queries, hallucinations and "I don't have information about that" responses become frequent. Reranking alone can boost precision to 70–80%; semantic chunking, query rewriting, and hybrid (keyword + semantic) search can push it to 85–90%.

Fix: Benchmark retrieval quality separately from generation quality using a held-out evaluation set. Track recall@K and precision@K for your retrieval layer. Treat RAG as a system requiring ongoing evaluation and improvement, not a one-time integration.

08 · FAQ

Frequently Asked Questions

Answers to the questions engineers actually ask when building production LLM systems with long-context and RAG architectures.

When does context window size actually matter?+
Context window size matters in three primary scenarios:

1. Multi-turn conversations at scale: Each message in a chat thread accumulates context. A conversation with 50 back-and-forth exchanges may total 30–50K tokens by the end. If your model has a 4K or 8K context window, the beginning of the conversation gets truncated. The model "forgets" what was said earlier, leading to contradictions and repetition. Long-context models eliminate this problem for typical conversation lengths.

2. Long document analysis: Legal contracts (50–200 pages), financial reports, technical specifications, medical records, or academic papers often exceed the token budgets of short-context models. When you need to ask questions that require reasoning over the entire document — not just extracting a specific paragraph — you need the whole document in context simultaneously. RAG can retrieve relevant sections but misses cross-section reasoning.

3. Multi-file code analysis: Understanding a bug that spans three files, reviewing a pull request that touches 15 files, or generating code that must be consistent with an existing codebase all benefit from having multiple complete files in context simultaneously. A 200K model can hold ~300 average-sized Python files at once. This transforms coding assistance from "here's a snippet" to "here's a change consistent with your full codebase architecture."

When it does NOT matter: Simple Q&A, single-turn instruction following, text classification, short-form generation. Most users interact in bursts of 1–5 messages with short prompts. Over 80% of real API calls use less than 8K tokens — the long-context capabilities are critical for the power users and enterprise use cases, not the median interaction.
Why not just use 1M token context for everything?+
Three converging problems make "always use max context" impractical:

Cost: A 1M-token Gemini 1.5 Pro request costs $1.25 in input tokens alone. If your typical use case only needs 10K tokens of context, you are paying 100x what is necessary. At 10,000 requests/day, that is $12,500/day vs $125/day. For most applications, 90%+ of queries do not need million-token context — sending them through a 1M-token model wastes money on a problem that does not exist.

Latency: Attention computation grows quadratically with context length at the architectural level. Even with FlashAttention and other optimizations, a 1M-token request takes seconds longer to start generating than a 10K-token request. Time-to-first-token (TTFT) — the latency users perceive — increases significantly with context length. For real-time chat interfaces, this is directly noticeable as sluggishness.

Diminishing quality returns: The lost-in-the-middle effect means that beyond a certain context length, adding more content does not improve answer quality — it actively degrades it. If only 5% of a 1M-token context is actually relevant to the query, the model must sift through 950K tokens of noise to find 50K tokens of signal. More targeted context (via RAG or careful filtering) consistently outperforms "inject everything" in quality benchmarks for specific retrieval tasks.

The practical rule: Right-size your context to the task. Use long context when you genuinely need holistic reasoning over large text. Use RAG when you can identify the relevant portions ahead of time. Use cheap small models for tasks that do not need large context. Tiered routing is the production-grade answer.
How does RAG compare to long context in accuracy?+
They excel in different dimensions — this is not a clear-cut winner:

RAG wins on precision: When retrieval works correctly, the LLM only sees the most relevant 5–20 chunks rather than the full corpus. This reduces noise and typically produces more precise, grounded answers. RAG also naturally provides citations (which source chunks were used), which is essential for enterprise applications requiring auditability.

Long context wins on recall and relationship reasoning: RAG can only answer questions about information it retrieves. If the answer requires synthesizing information scattered across 20 different document sections in non-obvious ways, RAG may miss connections. Long-context models can reason over the full document simultaneously, catching cross-references, implicit contradictions, and emergent patterns that are not retrievable in any single chunk.

Key benchmark finding (2023–2024): For simple factual retrieval ("What is the contract's termination clause?"), RAG and long-context perform similarly when retrieval quality is high. For complex multi-hop reasoning ("Do the termination conditions in section 4 conflict with the liability caps in section 12?"), long-context models outperform RAG by 15–30% in accuracy. For very large corpora where the relevant information could be anywhere, RAG is the only practical option regardless of quality differences.

Practical recommendation: Use RAG first for scalability; add long-context models for queries that fail RAG. The hybrid pattern (RAG to select chunks, then long-context model to reason over them) is increasingly the production standard at enterprise scale.
What is prompt caching and how does it save money?+
Prompt caching is a provider-level feature where repeated prompt prefixes are stored and reused across API calls, dramatically reducing cost and latency.

How it works (Anthropic): You mark a portion of your prompt with a cache_control breakpoint. The first request processes those tokens normally and stores the KV cache for that prefix on Anthropic's servers. Subsequent requests that use the identical prefix within 5 minutes are served from cache: you pay only 10% of normal input price ($0.30/1M instead of $3.00/1M for Claude 3.5 Sonnet) and get faster TTFT. Cache writes cost 25% more than normal input ($3.75/1M) — the write cost amortizes after just 3 cache hits.

Break-even analysis: Each cache write costs 1.25x the normal input price. Each cache read costs 0.1x. The formula: savings = (normal_price × N_reads) - (cache_write_cost + cache_read_cost × N_reads). Break-even is at approximately N=3 reads. Any application making the same large prompt prefix 4+ times within the TTL window benefits.

Google Gemini Context Caching: Similar mechanism but with configurable TTL (1 hour to 1 month) and a separate per-hour storage cost for cached content. Better for infrequent but long sessions where the same document context is reused across a work session rather than rapid fire requests.

The structural discipline it requires: To benefit from caching, you must structure prompts with cacheable content (system prompt, static documents, examples) strictly before dynamic content (user query, dynamic RAG chunks). This ordering is often already best practice — caching provides a financial incentive to enforce it rigorously.
How do I handle context limits in production?+
Production context management is a systems engineering problem, not just a prompt engineering problem. It requires explicit measurement, budgeting, and graceful degradation.

Step 1 — Measure actual usage: Instrument every API call to log prompt_tokens, completion_tokens, and total_tokens from the API response metadata. Build a dashboard showing p50/p90/p99 context sizes per endpoint and per user segment. Most teams discover that p99 context size is 3–5x the median — a few power users drive the tail.

Step 2 — Budget allocation: Define a token budget for each "slot" in your context: system prompt (fixed, X tokens), conversation history (sliding window, max Y tokens), RAG chunks (dynamic, max Z tokens), user query (variable, max W tokens). Enforce these budgets in code, not as a hope. Reserve a safety margin — set your hard cap at 80% of the model limit, not 100%.

Step 3 — Conversation history truncation: For conversational applications, truncate oldest messages first when approaching the limit. A more sophisticated approach: summarize the oldest N messages into a paragraph when the history exceeds a threshold, replacing N messages with one summary message. This preserves semantic continuity while reducing token count. Summarization-based compression typically retains 80% of the relevant information at 20% of the token cost.

Step 4 — Semantic chunk selection for docs: Do not include all retrieved RAG chunks — sort by relevance score, include highest-scoring chunks first, and stop when the remaining token budget is exhausted. This ensures the most relevant content always fits, even as context grows.

Step 5 — Graceful degradation: When context limit is hit, fail gracefully. If you cannot fit all context, tell the user which documents were excluded. Do not silently truncate in the middle of an important document — the model getting half a contract is worse than it getting a curated subset.
What is needle-in-a-haystack testing and how do I run it?+
Needle-in-a-haystack (NIAH) is the standard benchmark methodology for evaluating long-context recall fidelity across position and depth dimensions.

The methodology: Take a "haystack" — a long, information-dense document or concatenation of documents (often Paul Graham essays, Wikipedia articles, or synthetic text). Insert a specific, unique fact (the "needle") that does not appear elsewhere in the haystack, at a precisely controlled position (e.g., at the 35% mark of a 64K-token context). Ask the model: "What is the special fact about [topic] mentioned in the documents?" Grade the response as correct (retrieved the needle) or incorrect. Repeat for all combinations of: (a) needle positions from 0% to 100% and (b) context depths from 4K to maximum context length.

What the results show: A 2D grid where X-axis = position in context, Y-axis = total context length. Color each cell green (recalled correctly) or red (failed). Most frontier models show green across the board at short contexts, but red patches appear in the middle columns at longer context depths. Models with strong long-context training (Gemini 1.5 Pro, Claude 3.x) show much cleaner grids than models that merely extended their context window without re-training.

Limitations of NIAH: Needle-in-a-haystack tests pure retrieval of an isolated fact. Real tasks require reasoning — not just finding a fact but synthesizing it with other facts. A model can achieve 100% NIAH recall and still fail at complex multi-hop reasoning over long contexts. NIAH is necessary but not sufficient for evaluating long-context capability. Complement it with RULER (long-context reasoning benchmark) and your own domain-specific evaluations.

Running your own NIAH: Open-source implementations exist in gkamradt/LLMTest_NeedleInAHaystack on GitHub. Point it at any model API, set your context lengths and position grid, and it produces the heatmap automatically. A full run across 10 position points × 8 context depths × 3 trials = 240 API calls — typically $20–100 depending on the model.
