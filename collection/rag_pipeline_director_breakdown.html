01 Ingestion

Building the catalog before anyone asks a question

Doc loader → chunker → embedder → VDB writer
Plain English

Think of building a library's card catalog. You collect the books (doc loader), cut each one into sections short enough that someone can find a fact without reading the whole book (chunker), write a "gist" of each section that captures what it's about rather than just its title (embedder), and file those gist-cards into a catalog organized by meaning, not alphabetically (vector DB writer).

What's actually happening

Documents arrive from sources like S3, Confluence, or internal databases. Each is split into chunks — typically 200–500 tokens. Too large and retrieval becomes imprecise (you fetch a whole page to answer a one-line question); too small and you lose surrounding context. Each chunk is converted into a vector — an array of a few hundred to a few thousand numbers — by an embedding model, and that vector plus metadata (source, position, timestamp) is written to a vector database.

The director's lens — concerns and trade-offs
  • Throughput: embedding APIs are often rate-limited. At 10M+ documents, ingestion becomes a batching and queueing problem, not a "run a script" problem.
  • Idempotency: if ingestion crashes and retries, you must not create duplicate vectors. The fix is chunk_id = hash(source_id + position + content_hash) with upsert semantics, never plain insert.
  • Re-embed on update: when a source document changes, content-hash diffing lets you re-embed only the changed chunks. But if you ever change embedding models, that's a full-corpus re-embed — a capacity-planning event, not a config change.
  • Chunking strategy (fixed-size vs. semantic/section-aware vs. hierarchical parent-child) is decided early and is expensive to change later — it's the single biggest precision/recall lever in this layer.
Interview frame

"I'd treat ingestion as a CDC pipeline, not a batch script — deterministic chunk IDs for idempotent upserts, content-hash diffing so updates only re-embed what changed, and I'd flag any embedding-model upgrade as a capacity-planning exercise, because on a large corpus a full re-embed is a multi-day, real-cost project."

02 Query Processing

Cleaning up the question before you go searching

Query rewriter / expansion → spell check
Plain English

Before the system goes looking for an answer, it tidies up your question — fixing typos, expanding shorthand, and resolving "it" or "that" from earlier in the conversation. Sometimes it rewrites one ambiguous question into two or three versions covering different possible meanings, the way a good reference librarian asks "do you mean X or Y?" before searching.

What's actually happening

A (usually smaller, cheaper) LLM rewrites the raw query: correcting spelling, resolving pronouns and context from chat history, and optionally generating multiple paraphrases or even a hypothetical answer (HyDE) — that hypothetical answer gets embedded instead of the raw question, because an "answer-shaped" vector often matches the corpus better than a "question-shaped" one.

The director's lens — concerns and trade-offs
  • Recall: rewriting catches relevant chunks that wouldn't have matched the raw query's exact wording.
  • Ambiguity handling: a one-word query like "Java" needs disambiguation by conversational context before retrieval even starts.
  • The cost: this step adds an LLM call to the critical path — every query now pays extra latency and token cost. Multi-query expansion fans out retrieval N times, multiplying load on the vector DB.
  • The director's call: make this conditional. Only trigger rewriting/expansion when first-pass retrieval confidence is low, rather than running it unconditionally on every query.
Interview frame

"Query rewriting is a recall lever, but it's also a latency and cost multiplier sitting in the critical path. I'd want it gated — triggered only when initial retrieval scores fall below a threshold — rather than firing on every single query."

03 Retrieval

Two search engines, one referee

Dense ANN → sparse BM25 → RRF fusion
Plain English

Two different search engines run side by side. One searches by meaning — it finds documents conceptually related to your question even if they don't share a single word (dense / ANN). The other searches by exact keyword match, like a classic search engine (sparse / BM25). A referee — Reciprocal Rank Fusion (RRF) — then merges the two ranked lists, favoring anything that ranks highly in either.

What's actually happening

Dense retrieval runs an Approximate Nearest Neighbor search (e.g., HNSW or IVF-style indexes) over the embeddings written during ingestion. BM25 runs a TF-IDF-style search over a classic inverted index. RRF combines the two ranked lists using each item's rank position rather than raw scores — which sidesteps the problem that dense similarity scores and BM25 scores live on completely different, incompatible scales.

The director's lens — concerns and trade-offs
  • Why hybrid (the single most important point): dense embeddings "smear" everything into semantic space and are weak on exact-match needs — product SKUs, error codes, names, version numbers. BM25 is weak on synonyms and paraphrase. Hybrid hedges both blind spots.
  • RRF vs. learned fusion: RRF is parameter-free and robust — a strong production default. The reranker (next layer) does the more sophisticated fusion anyway, so RRF only needs to be "good enough to surface the right candidates into the top 50–100."
  • Latency P99: ANN is fast on average but has tail-latency spikes on large indexes; running both searches in parallel and fusing adds a small, real cost.
  • Index staleness: if the vector index updates asynchronously from ingestion, there's a window where new or edited documents aren't yet retrievable — this is an explicit SLA decision, not an accident.
Interview frame

"I think of retrieval as a recall-maximizing funnel — hybrid dense plus sparse with RRF fusion casts a wide net cheaply, and I accept some noise here because precision is the reranker's job downstream. The architectural question I'd own is index staleness — what's our SLA between a document being ingested and being retrievable, and does that match what the business actually needs?"

04 Reranking

Where retrieval's recall becomes generation's precision

Cross-encoder reranker → top-K selection
Plain English

Of the 50–100 candidates retrieval found, a slower but much smarter model reads each one side-by-side with your actual question and gives it a precise relevance score — like a human expert actually reading each shortlisted resume instead of just scanning for keywords. Only the top few survive.

What's actually happening

A cross-encoder takes (query, chunk) pairs and jointly encodes both to produce a relevance score — far more accurate than comparing two pre-computed vectors (a bi-encoder), but it can't be pre-computed, because the score depends on the specific query. It must run at query time, for every candidate, every time.

The director's lens — concerns and trade-offs
  • This is the classic two-stage funnel in information retrieval: cheap-and-broad (retrieval), then expensive-and-narrow (reranking). It's the only way to get cross-encoder-level precision without running a cross-encoder against the entire corpus on every query.
  • Latency budget: scoring 50–100 pairs at ~100–200ms is usually the single biggest controllable latency cost in the whole pipeline.
  • The dial: candidate-set size into the reranker (top-50 vs. top-100) directly trades latency against precision. Model size (distilled cross-encoders, e.g., MiniLM-class) trades accuracy for speed.
  • Hardware shift: the reranker is often the first GPU-bound component in the pipeline — capacity planning here looks different from the CPU-bound retrieval layer.
Interview frame

"If I had to spend my latency budget in one place, it's here — reranking is where retrieval's recall gets converted into the precision that generation actually needs. I'd tune the candidate-set size as the primary recall/latency dial, and I'd pick a distilled cross-encoder if the latency budget is tight, accepting a small precision hit deliberately rather than by default."

05 Context Building

Packing the briefing document

Chunk assembly → deduplication → token counting
Plain English

We take the winning chunks and pack them into a tidy briefing for the AI — removing anything that repeats itself, and making sure the whole package fits within the AI's "reading limit" so nothing gets cut off mid-sentence.

What's actually happening

The selected top-K chunks — often overlapping, especially when the corpus has near-duplicate documents — get deduplicated and possibly merged if adjacent. A token counter then ensures the total (system prompt + conversation history + retrieved context + query + reserved generation tokens) fits inside the model's context window.

The director's lens — concerns and trade-offs
  • "Lost in the middle": LLMs attend more strongly to information at the start and end of a long context than to the middle. Chunk ordering — not just selection — is a real, measurable lever: put the strongest evidence first and/or last.
  • Deduplication should be semantic, not exact-match — near-duplicate chunks from different document versions silently waste context budget.
  • Token budget is a planning exercise: you decide upfront how many tokens go to system prompt, history, retrieved context, and reserved output — and this directly trades off against per-query cost, since more context tokens means more $.
Interview frame

"This is where I'd push back on 'just add more chunks.' Beyond a point, more context degrades answer quality due to the lost-in-the-middle effect and increases cost linearly. I'd treat the token budget as a fixed allocation across system prompt, history, and retrieved context, and order chunks by relevance rather than retrieval rank — strongest evidence at the edges of the context window."

06 Generation

Where the actual answer gets written

System prompt + context + query → LLM → parser
Plain English

This is where the AI reads everything — its instructions on how to behave, the evidence we gathered, and your question — and writes an answer. A final step then extracts that answer in whatever shape the application needs: plain text, JSON, a form.

What's actually happening

The assembled prompt goes to the LLM. The system prompt typically carries "grounding instructions" — answer only from the provided context, cite sources, decline if the context is insufficient. Output often streams token-by-token for perceived speed, and a parser extracts structured fields when the application needs JSON or a similar format.

The director's lens — concerns and trade-offs
  • This stage is usually the dominant cost line item — both input tokens (the context you built) and output tokens.
  • Model tiering / routing: not every query needs the most expensive model. Route simple factual queries to a cheaper/smaller model, and escalate complex multi-hop queries (flagged by the rewriter or a classifier) to a frontier model — a major lever at scale.
  • Grounding instructions are the first, cheapest hallucination defense — but prompt-only grounding is never sufficient on its own, which is exactly why Layer 7 exists.
  • Output reliability: structured-output / function-calling modes are more reliable than regex-parsing free text, though they can constrain the model's "reasoning space." Malformed-output failure rates compound at scale.
Interview frame

"Generation is usually the dominant cost line item, so I'd design for model routing — a cheap model handles the bulk of straightforward queries, and only queries flagged as complex escalate to a frontier model. On output, I'd push for structured-output modes over regex-parsed free text, because malformed-output failures compound across millions of queries."

07 Validation

The trust layer

Citation check → guardrail → confidence score
Plain English

Before the answer reaches you, the system runs a final check: does this answer actually match what's in the source documents (citation check)? Does it break any safety rule — leaking private data, saying something inappropriate (guardrail)? And how confident should we be that it's correct (confidence score) — should it say "I don't have enough information" instead of guessing?

What's actually happening

Citation checking often uses a smaller NLI (natural language inference) model, or a second LLM call, to verify each claim in the answer is entailed by the retrieved context — flagging unsupported claims as candidate hallucinations. Guardrails are separate classifiers for PII, toxicity, and jailbreak/prompt-injection detection, run on input and output. Confidence scoring combines signals — retrieval similarity, generation log-probabilities, self-consistency across repeated calls — into a single score that gates whether the answer is shown as-is, shown with a caveat, or replaced by a fallback.

The director's lens — concerns and trade-offs
  • This layer is what separates a RAG demo from a production system. At director level, this is where you show you treat trust as an engineered, measured property — not a hope.
  • Cost vs. rigor: a full NLI check on every claim adds latency and cost. Many production systems sample-check, or only run the full check when the confidence score is already borderline.
  • Hallucination rate as an SLA: a director should be able to say "we track hallucination rate via [method] and target X%" — turning a fuzzy quality worry into an owned, monitored metric.
Interview frame

"I think of this as the trust layer — without it, RAG is just plausible-sounding text generation with extra steps. I'd run a lightweight entailment check on every response with a confidence score that gates output: high confidence shows the answer with citations, medium adds a caveat, low falls back to 'I don't have enough information.' And I'd track hallucination rate as a measured SLA, not an afterthought."

08 Observability

The operational backbone

Trace logs → metrics → eval runs → user feedback
Plain English

Everything above is being watched. Every step logs what it did and how long it took (trace logs). Key numbers — speed, accuracy, cost — are tracked over time (metrics). Automated quality tests run regularly to catch regressions (eval runs). Real user feedback — thumbs up/down — feeds back into making the system better.

What's actually happening

Distributed tracing (e.g., OpenTelemetry) instruments each pipeline stage so you can see, per query, how much time and cost each layer consumed and where failures occur. Dashboards track latency percentiles, recall/precision, hallucination rate, and cost-per-query over time. "Golden" eval datasets — curated query/answer pairs with known-correct answers — run against the pipeline before any deploy, as regression tests. User feedback gets converted into new eval cases.

The director's lens — concerns and trade-offs
  • This is the layer that most distinguishes "I built a RAG prototype" from "I operate a RAG system at scale." Directors are evaluated heavily on operational maturity, not architecture diagrams alone.
  • The eval flywheel: production issues → user feedback → new eval cases → regression-gated CI → fewer production issues. Articulating this loop explicitly is a strong senior-level signal.
  • Per-stage cost/latency attribution lets you answer "where do we spend our budget" with data — exactly the question a director should be able to answer about their own systems.
Interview frame

"Observability is what makes the rest of this operable. I'd want per-stage latency and cost attribution so I can say precisely where our P99 and our dollar-per-query go, a golden eval set that gates any change to retrieval, prompts, or models in CI, and a feedback loop that converts user thumbs-down into new eval cases — that loop is what turns a static system into one that measurably improves."

Tying it together

The strongest answer to "walk me through a RAG architecture" isn't a list of eight components — it's the three axes from the top of this page, applied consistently across every layer. Quality, latency, and cost aren't separate concerns; they're the same budget, spent differently at each stage.

"I'd own this system not as eight independent components, but as a budget — a latency budget, a cost budget, and a quality bar — and every architectural choice in each layer is a trade against those three. The director-level job isn't picking the 'best' algorithm at each layer; it's making the trade-offs explicit, measurable, and owned."

Likely follow-up questions
"What happens when retrieval finds nothing relevant?"

The confidence score (Layer 7) should come back low, and the system should answer "I don't have enough information" rather than let generation hallucinate from weak context. It can start even earlier — a similarity threshold below which you don't bother calling generation at all.

"How would you scale this 10x?"

Identify per-stage bottlenecks first (observability tells you this): shard the ANN index, horizontally scale the GPU-bound reranker, lean harder on model routing for generation. Then add caching at multiple layers — embedding cache, retrieval cache, and full-response cache for repeated questions.

"How do you evaluate RAG quality without human labels?"

LLM-as-judge for offline evaluation, synthetic QA pairs generated from the corpus itself for a golden eval set, and implicit signals — re-asks, dwell time, thumbs feedback — for online evaluation.

"How do you handle multi-tenant data isolation?"

Metadata filtering at query time (tenant_id as a hard filter on the vector DB query) for shared-index efficiency, versus separate indexes per tenant for strict isolation at higher operational cost — the choice depends on tenant count, data sensitivity, and compliance requirements.
