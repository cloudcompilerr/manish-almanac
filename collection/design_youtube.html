The TV broadcast analogy
Old TV: one signal broadcast from one tower, everyone watches the same thing at the same time. YouTube: millions of people each watching a different video, pausing, rewinding, choosing quality — and 500 hours of new content added every minute. The magic: every video is sliced into 2-second chunks (HLS segments). When you "stream," your device is actually downloading a sequence of tiny files, each cached at a nearby server (CDN PoP). Seeking to 45:30 = requesting chunk #1350. The CDN probably already has it — so it's instant. The transcoding farm converts each upload into 5 quality levels in parallel, so 360p is ready in 5 minutes while 4K takes 90.
01 · Architecture

Full System — Upload, Transcode, Deliver

01Resumable Upload PipelineGCS Multipart + Pub/Sub
Upload Flow
Client splits video into 8MB chunks. Upload chunks in parallel. Resume on failure.
1. Client: POST /upload/initiate → server creates an upload session (session_id, GCS resumable upload URL). 2. Client splits file: chunk_1.bin, chunk_2.bin, ... with SHA-256 hash per chunk. 3. Upload up to 5 chunks in parallel directly to GCS (pre-signed URLs). Server never handles video bytes. 4. On failure: client queries GET /upload/{session_id}/status → server queries GCS for received bytes → client resumes from the first missing chunk. 5. On completion: GCS triggers Pub/Sub event → transcoding pipeline starts.
✓Pre-signed URL upload: your API servers handle only metadata (kilobytes). GCS handles the gigabytes. 500 simultaneous 8GB uploads = 4TB of traffic that never touches your servers
ℹtus.io is the open standard for resumable uploads. YouTube uses a similar proprietary protocol. The key: each chunk has a checksum; the server verifies before acknowledging
02Transcoding PipelineDistributed Encoder Farm
Encoding Strategy
Source video → parallel encode into 5 quality variants + thumbnails + audio + subtitles.
GCS upload complete → Pub/Sub event → Transcoding Orchestrator creates a job: {source_path, video_id, target_resolutions: [360p, 480p, 720p, 1080p, 4K]}. Job split into parallel tasks: each resolution encoded independently on GPU instances. H.264 for broad compatibility, VP9 for Chrome (20% smaller files). Encoder: FFmpeg on g4dn.xlarge (NVIDIA T4 GPU).
Also generates: 1 thumbnail every 10 seconds (for scrubbing preview), audio track (AAC), auto-captions (speech-to-text → WebVTT).
✓Parallel encoding: 4K encode of 1-hour video takes 90 min on 1 GPU. With 5 resolutions in parallel: total wall time is the slowest (4K) = 90 min. Sequential would be 90+45+20+10+5 = 170 min
→360p available first (fastest to encode): video goes live in ~5 minutes for a 10-minute video. 4K unlocks an hour later. This is exactly YouTube's behaviour
03HLS Adaptive Streaming2-Second Segments + Manifest
Streaming Protocol
Video split into 2-second .ts segments. Client downloads segments sequentially, adapting quality based on bandwidth.
Each quality variant has a manifest file (720p.m3u8) listing all segment URLs: seg_001.ts, seg_002.ts, ... A master manifest lists all variant manifests. Player: download master manifest → choose quality based on measured bandwidth → download segments ahead (2-second buffer).
Bandwidth drops: player switches to lower manifest (360p). Seeks: player calculates which segment contains the target timestamp → fetch that segment directly from CDN. O(1) seek regardless of video length.
✓2-second segments means any seek requires downloading only 2 seconds of video before playback resumes. No server-side seek operations — pure client-side math
ℹDASH (Dynamic Adaptive Streaming over HTTP) is the alternative — used by Netflix. Functionally similar to HLS. YouTube uses HLS for Apple devices, DASH for Android/Chrome
04CDN ArchitectureGoogle's Own Edge Network
Global Delivery
Google CDN co-located in ISPs worldwide. Popular videos pre-pushed to ISP cache servers.
At 1.4 Tbps sustained outbound: no public CDN (Cloudflare, CloudFront) can serve this cost-effectively. Google operates their own edge caching infrastructure inside ISPs (same model as Netflix Open Connect). User in Mumbai watches "Gangnam Style" → served from the Jio edge node in the same building as Jio's own servers → < 5ms latency, zero long-distance transit cost.
Cache strategy: pre-push top 1% of videos (by view count) to all edge nodes. Long-tail (99%) served from regional GCS bucket via CDN on-demand cache.
⚠Cache invalidation: deleted or copyright-struck videos must be purged from all edge nodes. Google CDN propagates purges globally in < 60 seconds via its Anycast infrastructure
→Range requests: HTTP Range header enables seeking into a cached video segment without re-downloading from start. CDN must support byte-range requests (all major CDNs do)
05View CountRedis Write-Behind + BigQuery
Analytics
Redis INCR for live counter. BigQuery for historical analytics. Never hit PostgreSQL per view.
View event: INCR view:count:{video_id}. Return new count to client. Background job every 60s: for each changed key, GETSET view:count:{video_id} 0 → append (video_id, delta, timestamp) to BigQuery streaming insert. BigQuery: analytics queries (views by country, device, cohort).
Display: for hot videos (< 24h old): read from Redis (fresh). For cold videos: read from BigQuery materialized view (updated every 5 min).
ℹYouTube famously froze view counts at exactly 301 views during manual anti-fraud review. This is now automated: ML model flags suspicious view patterns (same IPs, no engagement, bot-like timing).
02 · Deep Dive

Upload to Live — Complete Lifecycle

Video goes from upload to watchable
T+0
Creator uploads a 10-minute 1080p video (2GB). Client initiates upload: POST /upload/initiate → {session_id, upload_url}. Video split into 256 × 8MB chunks.
T+0 to T+180s
5 chunks upload in parallel to GCS. Upload completes in ~3 minutes on 50Mbps connection. GCS confirms all chunks received and assembled.
T+181s
GCS publishes UploadComplete event to Pub/Sub. Transcoding Orchestrator picks it up. Creates 5 encoding jobs (one per resolution).
T+185s
5 GPU instances begin parallel encoding. 360p job is fastest — starts producing .ts segments within 30 seconds.
T+215s
360p encoding complete (30s for a 10-min video at low resolution). Segments uploaded to GCS. Manifest (360p.m3u8) generated. Video marked as "available at 360p."
T+600s
1080p encoding complete (~7 min). Master manifest updated to include 1080p variant. Viewer who started watching at 360p sees quality option appear.
T+5400s
4K variant complete (~90 min for 10-min video). Full quality unlocked. Video now available at all 5 resolutions globally via CDN.

05 · Hard Follow-ups

Every Question Your Interviewer Will Ask

How does video seeking work — how does a player jump to 45:30 in a 2-hour movie instantly?+
HLS segmentation makes seeking O(1). Each segment is an independent file.

The master manifest and each quality manifest contain the start time and URL of every segment. To seek to 45:30: player calculates 45:30 ÷ 2 seconds = segment index 1350. Fetch seg_1350.ts directly from CDN. Player discards its buffer, starts downloading from seg_1350.

The CDN has likely cached this segment (popular videos, popular scrub points). If not: CDN fetches from GCS origin (50ms). Either way: player has 2 seconds of video in < 100ms. Seek appears instantaneous.

Compare to a non-segmented MP4: seek would require HTTP Range request starting at the byte offset for 45:30. CDN cannot cache byte ranges efficiently — every unique seek position is a cache miss. HLS eliminates this problem by making each time slice a discrete cacheable file.
How do you detect copyright infringement — someone uploads a movie they don't own?+
Content ID: generate an audio fingerprint of every video, match against a database of 800M+ copyrighted works.

During transcoding: extract audio track → generate Chromaprint fingerprint (50-byte representation of the audio frequency spectrum over time). Match against the Content ID database using approximate nearest-neighbour search. Also: extract frame hashes for video fingerprinting (handles screen recordings, re-encodings).

Content ID database: 800M works × 50 bytes = 40GB — fits in RAM for brute-force O(1) lookup. Or FAISS index for ANN search.

On match: copyright owner is notified. They choose: block the video, monetise it (ads, revenue share), or allow it. YouTube processes 400M Content ID matches per day. The system is automated — no human review for clear matches.

Timing: Content ID check runs during transcoding. Video goes live only after Content ID clears (< 5 minutes for audio check). This is why there's a processing delay after upload.
How do you handle a video that goes viral — 100M views in the first hour?+
The CDN absorbs the spike. Your origin infrastructure sees at most cache-miss traffic.

A video going viral: first 1M viewers → CDN cache miss → GCS serves the first request per CDN PoP → each PoP caches the segments. 2nd through 100M viewers at the same PoP: CDN cache hit → zero GCS requests.

Global CDN: 200+ PoPs. For a video with 100M views/hour globally: at most 200 cache-miss requests to GCS (one per PoP). GCS: trivially handles 200 requests. CDN handles 100M requests independently.

The failure mode: if a video somehow bypasses CDN (direct GCS URL): 100M requests × 50ms GCS latency = catastrophic. Every video URL must go through CDN — enforced at the URL generation layer.

Pre-warming: for known events (World Cup final, Beyoncé concert drop), pre-push the video to all CDN PoPs before release. CDN cache is warm — first viewer gets the same experience as the millionth.
How does YouTube's recommendation system work at a high level?+
Two-stage: candidate generation → ranking. Billions of videos → hundreds of candidates → top 25 shown.

Stage 1 — Candidate Generation: for each user, generate ~500 candidate videos from: (a) collaborative filtering (users similar to you watched these — matrix factorisation on watch history), (b) content-based (similar to videos you watched — video embedding similarity), (c) freshness injection (recent uploads from subscribed channels). Computed using approximate nearest-neighbour search in embedding space. ~50ms.

Stage 2 — Ranking: deep neural network scores each candidate on: predicted watch time (not clicks — click-bait optimisation caused the "recommendation problem"), satisfaction signals (likes, shares, surveys), freshness, diversity. Top 25 returned. ~100ms on GPU.

The recommendation problem: optimising purely for click-through → click-bait thumbnails win. YouTube shifted to optimising for watch time and satisfaction surveys in 2016. This reduced click-bait but introduced the "rabbit hole" problem (increasingly extreme content maximises watch time). Ongoing tuning.
