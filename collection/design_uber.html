00 · Requirements

Requirements & Scale Assumptions

Functional

FR1A rider must be able to request a ride by specifying a pickup and dropoff location, and receive a fare estimate before committing, so the request itself carries everything needed to find and price a match.
FR2The system must match a requesting rider to a specific nearby available driver quickly enough that the rider doesn't abandon the request, and must guarantee a driver is never double-booked to two riders at once.
FR3Every active driver's location must be tracked in near real time so the matching system always has a current, not stale, picture of where supply actually is.
FR4Once a trip starts, both the rider and driver must be able to see the other's live position on a map for the duration of the trip, independent of the initial matching step.
FR5Prices must rise in areas where ride requests are outpacing available drivers, so supply is incentivized to move toward demand rather than demand simply going unserved.
FR6When a trip ends, the system must compute a final fare (including any surge applied at request time) and charge the rider automatically, without requiring a manual settlement step.

Non-Functional

NFR1Design assumption: 1M concurrent drivers globally — an illustrative sizing input for this exercise, not a figure Uber publishes; state it as your own assumption.
NFR2~38M trips/day ≈ 440 ride requests/sec (Uber's own quarterly filings reported trip volume crossing roughly 3–3.5 billion trips per quarter through 2024–2025, i.e. ~33–38M/day — use this order of magnitude, not the commonly-quoted-but-outdated "100M/day" figure).
NFR3Design assumption: driver location updates at ~250K writes/sec globally, derived from the driver-count assumption above and a 4-second GPS ping interval — arithmetic to defend, not a disclosed Uber metric.
NFR4Design target: match latency under 5 seconds end-to-end — a target you're proposing and should justify from the matching pipeline's own latency budget, not a disclosed SLA.
NFR5Design target: location accuracy within roughly ±50 metres — consistent with typical smartphone GPS accuracy in urban conditions, not an Uber-specific disclosed spec.
NFR6Design goal: high availability such that a rider is never left without a matching attempt — state a concrete SLA target (e.g. 99.9%+) and justify it, rather than leaving "high availability" unquantified.

The radio dispatch analogy
Old-school taxi dispatch: you call the dispatcher, they radio every taxi in the area, first driver to respond gets the fare. Uber does the same thing digitally but with GPS precision. Your phone = the call. The GPS index (Redis GEO) = the dispatcher's map. GEORADIUS = "which taxis are within 3km?" The NX Redis lock = "claim this fare before anyone else does." The surge multiplier = the dispatcher charging more when it's raining and every taxi is busy.
⚠ The interview trap that catches most candidates

"Design Uber" candidates who say "just query the database for drivers near the rider, filtered by lat/lng within a range" are proposing an O(n) scan of every driver row on every match request — it doesn't get better with scale, it gets worse linearly with driver count. The actual hard problem is the geospatial index: some structure that turns "who is near this point?" from a full scan into a lookup over a small number of neighboring cells. The second, subtler trap is stopping at "we'll use a geospatial index" without being able to name which kind, why it fits this problem better than the alternatives (geohash, quadtree, Google's S2, Uber's own H3), and what its specific weaknesses are — that's the difference between a candidate who's memorized the word "Redis GEO" and one who understands why it works.

01 · Architecture

Full System — Every Component Justified

01Driver Location TrackingWebSocket + Redis GEO
Data Flow
Persistent WebSocket connection from each driver app → Location Service → Redis GEO.
Driver app sends GPS every 4 seconds. Location Service receives: GEOADD drivers:bangalore 77.5946 12.9716 driver:123. Also writes to Cassandra for trip replay: (driver_id, timestamp, lat, lng).
Why WebSocket not HTTP polling? 250K drivers × 1 HTTP request/4s = 62,500 HTTP requests/sec with overhead. WebSocket: persistent connection, push updates. 10× less server CPU. Erlang/Go handles 500K WebSocket connections per node.
✓Redis GEO stores 1M drivers in ~80MB. GEORADIUS query for 5km radius runs in < 1ms
⚠WebSocket reconnect: exponential backoff. Buffer updates locally on device, batch-send on reconnect with original timestamps
02Driver MatchingRedis GEO + Atomic Lock
Matching Algorithm
Rider requests ride → find nearest available drivers → notify → first to accept wins.
Step 1: GEORADIUS drivers:bangalore {rider_lat} {rider_lng} 5 km ASC COUNT 10 → 10 nearest. Step 2: check status: HGET driver:status:{id} = "available". Step 3: push notification to all available drivers via WebSocket. Step 4: first driver to accept → SET driver:trip:{id} {trip_id} NX EX 3600 (atomic NX = only if not exists → prevents double-matching). Step 5: reject all other drivers, start trip.
✓NX (set if not exists) is atomic in Redis — impossible for two riders to claim the same driver simultaneously
ℹIf no driver accepts within 30s: expand radius to 8km, retry. After 60s: show "no drivers available"
03Surge PricingKafka + Flink + Redis
Real-time Computation
Demand/supply ratio per geospatial cell determines the surge multiplier.
Kafka streams: ride requests + driver availability events, partitioned by H3 cell ID (Uber's own open-sourced hexagonal hierarchical spatial index — see the geospatial-indexing breakdown below). Flink job: 5-minute tumbling window, count (requests, available_drivers) per cell. Surge = f(demand/supply): ratio < 1.2 → 1.0×, 1.2–2.0 → 1.5×, > 2.0 → 2.0×. Store result: SET surge:bangalore:h3cell:{id} 1.5 EX 300. Pricing Service reads this on every fare estimate.
✓Flink maintains exactly one count per cell window — no double counting even with Kafka redelivery (idempotent state updates)
→H3 resolution 8 hexagons average ~0.74 km² each (per Uber's published H3 cell-area tables); resolution 7 averages ~5.16 km². Either is fine-grained enough for city-level surge without an unmanageable number of cells to track in Flink state
04Trip ManagementRedis + PostgreSQL
State Machine
Active trip state in Redis (fast reads), final state in PostgreSQL (durability).
Trip states: REQUESTED → MATCHED → DRIVER_EN_ROUTE → IN_PROGRESS → COMPLETED → PAID. Each state: HSET trip:{id} status IN_PROGRESS driver_id 123 rider_id 456. TTL = 4 hours (max trip duration). On COMPLETED: write full trip record to PostgreSQL + trigger payment (Stripe API) + Kafka TripCompleted event for driver earnings, analytics, rating requests.
ℹRedis TTL as safety net: if trip state is stuck (crash mid-trip), the key expires and the system can reconcile via Cassandra location history
⚠Payment is synchronous (rider must know charge amount before leaving the car). All other post-trip actions (ratings, analytics, driver earnings) are async via Kafka
05Location HistoryCassandra Time-Series
Persistence
Every driver GPS update stored in Cassandra for trip replay, disputes, and ML training.
Schema: PRIMARY KEY ((driver_id, trip_date), timestamp). Clustering by timestamp gives time-ordered reads within a partition. Query "replay trip 789": SELECT * FROM locations WHERE driver_id = 123 AND trip_date = '2026-03-22' AND timestamp BETWEEN start AND end. At 250K updates/sec × 50 bytes = 12.5 MB/sec = 1 TB/day.
✓Cassandra partition key by (driver_id, date) means each driver's daily data is co-located. 7-year retention with tiered storage: 30 days hot SSD, 7 years cold S3 via TTL + archival job

03 · The Hard Decision

Geospatial Indexing — Geohash, Quadtree, S2, H3

Every "find nearby X" system reduces to the same question: how do you index two-dimensional space so a proximity query touches a handful of cells instead of every row? Four answers show up repeatedly in production systems and interviews.

GEOHASH

Interleave the bits of latitude and longitude into a single string; a shared prefix means physical proximity. Redis GEO commands (GEOADD, GEORADIUS) use a 52-bit geohash-style interleaved encoding internally, stored in a sorted set — this is why Redis GEO is the pragmatic default for a driver-matching prototype: it's a well-tested primitive already built into a data store most teams already run.

Known weakness: boundary discontinuity. Two points a few meters apart can land in cells with completely different prefixes if they straddle a grid boundary — a naive "match on shared prefix length" approach can miss genuinely close points, which is why real implementations query the target cell plus its neighbors, not just an exact prefix match.

QUADTREE

Recursively subdivide space into four quadrants, only splitting further where point density is high. This gives adaptive resolution for free — dense urban cores get small cells, sparse suburbs get large ones — without wasting index entries on empty space.

Known weakness: it's a mutable tree structure. Constantly-moving points (drivers updating location every few seconds) mean constant rebalancing, which is expensive at high update rates compared to a stateless hash-based scheme.

GOOGLE S2

Project the sphere onto a cube (6 faces), then index each face with a Hilbert space-filling curve. Because it models the Earth as a sphere rather than treating lat/lng as a flat grid, S2 avoids the distortion that grows severe near the poles with naive lat/lng-based schemes. Used inside MongoDB's geospatial indexes and multiple Google products.

UBER H3

A hexagonal, hierarchical grid — Uber's own open-source system (released 2018), built specifically for ride-hailing-style workloads. The reason for hexagons over squares: every hexagon has exactly 6 neighbors, all at the same distance from its center. A square has 8 neighbors, but the 4 diagonal ones are ~1.41× farther away than the 4 edge-adjacent ones — for a "how many drivers within 2km" query, that non-uniformity means a square grid systematically over- or under-counts near the boundary. H3 cells are addressable at multiple resolutions (a resolution-8 cell averages ~0.74 km², a resolution-7 cell ~5.16 km², per Uber's published cell-area tables), which is what makes it convenient for both fine-grained matching and coarser aggregation like surge pricing in the same system.

Interview-defensible framing: Redis GEO's built-in geohash is the pragmatic choice for driver-rider matching (it's already inside a data store you're running); H3 is the stronger answer when the interviewer asks specifically about analytics-grade aggregation (surge cells, demand heatmaps) where uniform neighbor distance actually matters.
04 · Interview Decision Framework

Which Index, and How Wide a Search Radius?

🎯Four Questions Before You Commit to a Geospatial Design
1
Is the query "find the K nearest points" (matching) or "aggregate demand/supply over an area" (analytics, surge)?
Nearest-K matching →Redis GEO (geohash-backed) is the pragmatic default. GEORADIUS with ASC + COUNT gives you exactly that primitive with no extra infrastructure.
Area aggregation / heatmaps →A hexagonal grid (H3) is the stronger answer — uniform cell size and uniform neighbor distance make aggregation math (aggregate this bucket's demand vs supply) cleaner than a geohash prefix scheme.
2
How often does the underlying position data change?
Very frequently (driver GPS every few seconds) →Favor a stateless, hash-based scheme (geohash) over a mutable tree (quadtree). Re-hashing a point's cell on every update is cheap; rebalancing a tree on every update is not.
Rarely (static points of interest) →A quadtree's adaptive resolution is worth the rebalancing cost — you pay it once, not on every GPS tick.
3
If no driver accepts within the initial radius, what's the escalation policy?
Expand radius progressively (3km → 5km → 8km) →The defensible default. Bounds worst-case wait time while trying the closest drivers first.
Notify all drivers at once regardless of distance →Minimizes match latency in low-supply areas but risks a poor rider experience (a driver 40 minutes away accepting) — needs a hard distance ceiling even in the "no driver found" fallback path.
4
Does the interviewer push on Earth-curvature accuracy (very large search radii, near the poles, cross-ocean)?
Yes →Name Google S2 — its cube-projection + Hilbert-curve design specifically addresses the distortion that flat lat/lng-grid schemes accumulate near the poles.
No, city-scale radii only →The distortion is negligible at ride-hailing search radii (a few kilometers) — geohash or H3 is sufficient, S2's extra rigor isn't buying you anything at this scale.
⚠ · Failure Modes

What Actually Breaks — Production Failure Patterns

01Stale Driver Positions After a Crash
What it is

A driver's app crashes or loses connectivity without a clean disconnect — their last GPS position stays in the Redis GEO index indefinitely, since nothing ever issued the "remove me" command. Riders keep getting matched to a driver who isn't actually there, and every one of those matches fails after the driver never responds.

✓Fix: treat "no location update for N seconds" as implicitly offline — TTL the presence/status key (not the GEO entry itself, which has no native TTL) and filter matching candidates by a fresh last_seen timestamp, not just GEO membership.
02Double-Dispatch Race Under Redis Failover
What it is

The NX lock's atomicity guarantee holds on a single Redis primary. During a failover — the primary dies mid-write, a replica is promoted, and the write hadn't yet replicated — it's possible for the same driver to be matched twice in the narrow window around the failover, because the new primary doesn't know about the lock the old primary was about to grant.

✓Fix: treat a driver accepting a trip as provisional until a second confirmation step (driver app acknowledges "trip started") completes; reconcile any double-match by cancelling the second one with an apology/credit rather than assuming the lock alone is bulletproof across a failover boundary.
03Surge Feedback Oscillation
What it is

If the surge-computation window is too short relative to how fast drivers can physically relocate, surge can overshoot: a spike attracts a wave of drivers, supply overcorrects, the next window's multiplier crashes to baseline, drivers leave the area, and demand outstrips supply again a few windows later. The system oscillates instead of settling.

✓Fix: smooth the multiplier across windows (e.g. exponential moving average) instead of recomputing from scratch every 5 minutes, and cap how fast the multiplier can rise or fall between consecutive windows.

07 · Hard Follow-ups

Every Question Your Interviewer Will Ask

How do you prevent a driver being matched to two riders simultaneously?+
Redis SET with NX (set if not exists) is the atomic lock.

When rider A's match request claims driver 7: SET driver:trip:7 tripA NX EX 3600. NX means "only set if key doesn't exist." If driver 7 is simultaneously claimed by rider B: Redis processes the two SET NX commands serially (Redis is single-threaded for commands). One succeeds, one fails. The failing request must find a different driver.

Why not application-level locking? Distributed locks (Redlock) across Redis nodes are complex and have failure modes. A single Redis primary processes NX commands atomically — simpler and sufficient for this use case.
How do you handle GPS inaccuracy — a driver appears to be in a building or on the wrong road?+
Kalman filter + road snapping + dead reckoning.

Kalman filter on the driver app: combines GPS reading (noisy, ±50m in cities) with accelerometer + gyroscope data to estimate the most likely position. Reduces GPS noise by 60–70%.

Road snapping: the estimated position is projected onto the nearest road from Uber's internal road graph. A driver "inside a building" snaps to the adjacent road. This requires a map matching service that queries the road graph with the current position estimate.

Dead reckoning during GPS gaps (tunnels, underground): use last known speed + heading to extrapolate position for up to 30 seconds. The driver app buffers location updates during connectivity loss and batch-sends them with original timestamps on reconnect.
How does surge pricing prevent riders from being exploited — what stops surge from going to 10×?+
Surge caps + transparency + pre-trip confirmation.

Technical cap: surge multiplier is capped at 5.0× in the Flink aggregation function. Business logic, not just UX.

Pre-trip price lock: when a rider sees the surge price and taps "Request Ride," the fare is locked at that surge multiplier for 120 seconds. If surge changes during the 2 minutes before a driver accepts, the rider still pays the locked price. This removes the bait-and-switch failure mode.

Surge decay: as drivers enter a high-demand area (attracted by surge), supply increases → demand/supply ratio drops → Flink computes lower multiplier → next 5-minute window has lower surge. This is the negative feedback loop that makes surge self-correcting.
How do you design the system for 10× scale — ~40M trips/day vs ~400M/day?+
The bottleneck shifts at each order of magnitude:

At ~4M trips/day (current ~40M ÷ 10): single Redis instance per city might suffice. PostgreSQL read replicas handle the load.

At ~40M trips/day (roughly today's actual global order of magnitude): city-level Redis sharding (shard by geohash prefix within a city). Cassandra for location history. Kafka for async fan-out of trip events.

At ~400M trips/day (10× today): Redis Cluster per region. Location history in a time-series database (InfluxDB or a custom columnar store). Dedicated matching service per city with no cross-city coordination. Surge pricing becomes a distributed ML model running per-region inference, not a Flink job.
How do you handle driver going offline mid-trip?+
Client-side buffering + server-side timeout + rider notification.

Driver app: buffer all location updates locally (SQLite) when offline. On reconnect: batch-send buffered updates with original timestamps. Location Service accepts out-of-order updates (Cassandra handles this naturally).

Server-side: if no driver location update received for > 30 seconds → mark driver as "connectivity issues." Notify rider ("Your driver has lost connectivity — we're monitoring the situation"). After 120 seconds with no reconnection: trigger escalation (rider support contact, potential trip cancellation).

Trip fare: for connectivity gaps, interpolate between last known and reconnect position using straight-line distance. Apply the same per-km rate. Rider sees the gap acknowledged in the trip receipt.
How does Uber handle payments across dozens of countries with different currencies and regulations?+
A payment processor (illustratively, Stripe) plus local payment method adapters plus a regulatory compliance layer — the general pattern any multi-country marketplace uses, not a confirmed description of Uber's actual internal stack.

A processor like Stripe handles: credit card processing across a large number of currencies (Stripe's own docs state support for 135+ presentment currencies), fraud detection, and PCI-DSS compliance scope reduction (the merchant stores only a tokenized payment_method_id, never raw card numbers) — this pattern, not necessarily Stripe by name, is what keeps Uber's own PCI-DSS scope narrow.

Local payment methods (UPI in India, GoPay in Indonesia, cash in some markets): each implemented as an adapter implementing a PaymentProvider interface. The Trip Completion Service calls paymentProvider.charge(trip_id, amount, currency) — agnostic to which provider handles it.

Regulatory: driver earnings subject to local tax law. Separate Earnings Service calculates driver payout = fare − commission − applicable taxes, stores in an append-only Kafka topic (audit trail). Payout batch runs weekly per country via local banking APIs.
