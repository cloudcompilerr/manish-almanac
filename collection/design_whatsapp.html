00 · Requirements

Requirements & Scale Assumptions

Functional

FR1Two users must be able to exchange messages directly, with the sender able to see whether a message was delivered to the recipient's device and whether the recipient has read it.
FR2A set of users must be able to message as a group (currently capped at 1,024 members, raised from a previous 256-member cap when WhatsApp Communities launched in Nov 2022), with every member receiving every message without the sender addressing each recipient individually.
FR3A user must be able to see whether a contact is currently online or, if not, roughly when they were last active — a presence signal separate from message delivery itself.
FR4Message content must be readable only by the sender and recipient(s) — the server must be structurally unable to decrypt content it routes, not merely policy-restricted from reading it.
FR5Users must be able to send and receive images, video, and voice messages through the same delivery pipeline as text, with the same delivery/read-receipt guarantees.
FR6A message sent to a recipient who is currently offline must still reach them once they reconnect, without the sender needing to resend it manually.

Non-Functional

NFR1~3B users (WhatsApp's last clearly official figure was 2 billion MAU in Feb 2020; Meta's later statements and third-party trackers put it at roughly 3–3.3 billion by 2025), 100B+ messages/day (Meta's last officially disclosed figure was "over 100 billion," Oct 2020; treat as a floor, not a current precise count) — both are sizing inputs to defend with arithmetic, not citations to quote as current fact.
NFR2Design target: sub-500ms delivery latency when both parties are online — justified by the both-online fast path (WebSocket → Redis Pub/Sub → WebSocket) having no disk write on the hot path, not a disclosed WhatsApp SLA.
NFR3Design assumption: ~600M concurrent WebSocket connections, derived from the ~3B user estimate above assuming a fraction are concurrently connected — an illustrative sizing input, not a disclosed figure.
NFR4Design requirement: at-least-once delivery — messages must never be silently dropped, even though that requires clients to de-duplicate on the rare redelivery.
NFR5Design requirement: the server must store and route only ciphertext for message content — the structural guarantee E2EE is meant to provide, not a configurable policy.
NFR6Design target: 99.99% availability — a standard SLA tier to propose and justify, not a disclosed WhatsApp number.

The postal service with vanishing letters analogy
WhatsApp is like a postal service that (a) delivers letters in under a second, (b) burns them after delivery so no one can read them later, and (c) seals them in an envelope that only the recipient can open — not even the post office. Your phone is the mailbox (WebSocket connection). The post office sorting centre (Redis) knows which delivery van (Erlang server) your contact's mailbox is currently on. If your contact is offline, letters go into temporary storage (Cassandra) for up to 30 days — then shredded if uncollected.
⚠ The interview trap that catches most candidates

Candidates who say "we'll encrypt messages with TLS" have described encryption in transit, not end-to-end encryption — and conflating the two is one of the fastest ways to lose credibility in a WhatsApp interview. TLS protects a message between the client and WhatsApp's servers; the server still sees plaintext, decrypts it, and could in principle log or read it. End-to-end encryption (Signal Protocol) means the server routes ciphertext it is structurally unable to decrypt — the key material never leaves the two participants' devices. The follow-up that separates strong candidates from ones reciting a buzzword: if the server never sees plaintext, how do search, spam detection, and content moderation work at all? The honest answer is mostly on-device (local search index) or via metadata/behavioral signals (message frequency, report rates) — not content inspection, because content inspection is exactly what E2EE rules out.

01 · Architecture

Full System — Every Component Justified

01Connection LayerErlang Chat Servers
The 600M Connection Problem
600M concurrent WebSocket connections — solved by Erlang's actor model.
Java thread-per-connection: 600M × 1MB stack = 600TB RAM. Not viable. Erlang lightweight process: ~300 bytes RAM each. 2M connections per Erlang node = 300 nodes for 600M connections. Each WebSocket connection is an independent Erlang process. Messages between processes use Erlang's built-in message passing — no shared state, no locks.
Connection metadata in Redis: HSET user:conn:{user_id} server_id 47 last_seen 1742383200. Any service can look up which server a user is connected to.
✓In a well-documented 2012 talk ("Scaling to Millions of Simultaneous Connections," Erlang Factory SF), WhatsApp engineer Rick Reed described pushing a single server from roughly 200K connections through 1 million and on to 2 million+ concurrent TCP connections by tuning Erlang/OTP and FreeBSD. WhatsApp's company-wide engineering headcount stayed famously small — commonly cited as roughly 50 engineers at the time of its 2014 Facebook acquisition, when it served ~450M monthly users. The actor model was a natural fit: millions of lightweight, isolated, fault-tolerant processes, one per connection
ℹAlternative: Node.js event loop handles 10K–50K connections per process. Would need 60,000 Node processes for 600M connections. Erlang's model is orders of magnitude more efficient
02Message RoutingRedis Pub/Sub + Direct Push
Both-Online Fast Path
Alice → Server A → find Bob's server → Server B → Bob. Under 100ms.
Alice sends message: WebSocket → Chat Server A. Server A: HGET user:conn:bob → server_47. Publish to Server 47's channel: PUBLISH server:47 {message_payload}. Server 47: receives via subscription → finds Bob's Erlang process → delivers to Bob's WebSocket. Return delivery receipt to Alice.
Message ID: Snowflake-style time-sortable ID. Bob's client uses sequence numbers to detect gaps and request retransmission.
✓Redis Pub/Sub message routing: < 1ms. Total round-trip Alice→Bob: < 50ms on same continent
⚠Redis Pub/Sub is fire-and-forget — if Server 47 crashes after publish but before delivery, message is lost. Mitigation: Cassandra persistence before publish (see Offline Flow)
03Offline Message DeliveryCassandra + Push Notifications
Offline Flow
Bob is offline → store in Cassandra → push notification → deliver on reconnect.
Bob offline: HGET user:conn:bob → null. Write to Cassandra: messages(conversation_id, message_id, sender_id, ciphertext, created_at). Send push notification (APNs/FCM) — "You have new messages."
Bob reconnects: Chat Server queries SELECT * FROM messages WHERE conversation_id IN (?) AND message_id > last_seen_id. Deliver all undelivered. Mark as delivered. Delete from Cassandra (messages stored only until delivered). Send delivery receipts to Alice.
ℹWhatsApp deletes messages from server after delivery. Client devices store history locally (encrypted SQLite). If Bob loses his phone: messages in the 30-day offline window are unrecoverable — this is a privacy feature, not a bug
→30-day offline retention: if Bob doesn't reconnect in 30 days, messages deleted. Sender notified with "message expired" status
04End-to-End EncryptionSignal Protocol
E2EE Architecture
Server never sees plaintext. Only the recipient's device can decrypt.
Each user has a public/private key pair generated on device. Public keys stored on WhatsApp servers. When Alice messages Bob: Alice fetches Bob's public key → encrypts message using Signal Protocol (XSalsa20 + Poly1305) → sends ciphertext. Server routes ciphertext. Bob's device decrypts with private key (never left Bob's device).
Key exchange: X3DH (Extended Triple Diffie-Hellman) for initial key agreement. Double Ratchet for forward secrecy — each message uses a fresh ephemeral key derived from the previous one.
✓Even WhatsApp cannot read message content. Government requests: WhatsApp can provide metadata (who messaged whom, when) but not content
⚠Backup weakness: WhatsApp cloud backups (Google Drive, iCloud) were historically NOT E2EE. End-to-end encrypted backup added 2021 — but only if user opts in. Most users don't, exposing backup content
05Group MessagingFan-out on Write
Group Architecture
1,024-member group (WhatsApp's current cap, raised from 256 in Nov 2022): server sends individual encrypted messages to each member.
Alice sends to group: Alice's device uses "Sender Keys" (Signal Protocol optimization) — encrypt once per group session, not once per member. Server receives one ciphertext → creates up to 1,023 delivery tasks → routes to each member's server → delivers. Kafka topic per group for ordered, at-least-once delivery to all members.
At an illustrative scale of 100M group messages/day and an average of ~30 active members per group (most groups are far smaller than the 1,024 cap): ~3B individual deliveries/day ≈ 35K/sec — use your own group-size assumption and show the arithmetic rather than quoting this as a real production number.
ℹSender Keys optimisation: without it, Alice would need to separately encrypt one message per member. With Sender Keys: encrypt once, each member has a pre-shared group key to decrypt — an N× reduction in encryption CPU on the sender's device for an N-member group

03 · The Hard Decisions

The Actor Model and the Signal Protocol — Term by Term

Two independent hard problems make WhatsApp's architecture what it is: holding hundreds of millions of idle connections open cheaply, and guaranteeing a server that routes messages can never read them. Different technologies, same design philosophy — push the hard part to where it's cheapest to solve.

THE ACTOR
MODEL (BEAM)

Every connection is an independent, isolated Erlang process with its own private memory — no shared state, no locks, communication only via asynchronous message passing. This is why one slow or crashing connection can't corrupt or stall another: there's no shared mutable state between them to corrupt in the first place. Contrast with a thread-per-connection model, where an unbounded thread stack (often ~1MB in the JVM) times hundreds of millions of connections is not viable memory-wise, and a shared-heap crash can take down unrelated connections.

"LET IT
CRASH"

Erlang/OTP's supervision-tree philosophy: don't write defensive code to handle every possible error — let a process crash, and let a supervisor process restart it in a known-good state. Applied to a chat server: if one connection's process hits an unexpected error, it dies and restarts cleanly; the other millions of connections on the same node are unaffected. This fault-isolation property is a major reason Erlang was picked for a system where "one bad message shouldn't take down a server" is a hard requirement.

X3DH
KEY AGREEMENT

Extended Triple Diffie-Hellman: how two devices that have never communicated establish a shared secret before the first message is even sent. Each user publishes a bundle of public keys (an identity key, a signed prekey, and a batch of one-time prekeys) to the server ahead of time. A sender can compute a shared secret with a recipient's public key bundle even while the recipient is completely offline — this is what makes "send a message to someone who's never opened the app on this device" possible without an interactive handshake.

DOUBLE
RATCHET

After the initial X3DH handshake, every subsequent message derives a fresh encryption key from the previous one, combined with fresh Diffie-Hellman output exchanged inline with the messages themselves. The practical payoff is forward secrecy and post-compromise security: if an attacker somehow obtains one message's key, they cannot derive past keys (forward secrecy) or, after the ratchet advances a bit further, future keys either (self-healing / post-compromise security). This is the mechanism that makes "we found one key, can we now read the whole conversation history" false by design.

04 · Interview Decision Framework

How Much Concurrency, and How Much Encryption?

🎯Four Questions That Decide the Connection and Crypto Design
1
Does the workload look like "millions of mostly-idle long-lived connections" or "high-throughput short-lived requests"?
Millions of idle connections (chat, presence) →An actor-model / lightweight-process runtime (Erlang/OTP, or Go with goroutines as a more hireable alternative) is the right fit — cost per idle connection has to be near-zero.
Short-lived request/response →A conventional thread-pool or event-loop server (Node.js, a JVM framework) is simpler to hire for and operate, and the C10M-style connection problem doesn't apply.
2
Must the server be structurally unable to read message content, or is "we promise not to look" an acceptable trust model?
Structurally unable (regulated, privacy-first product) →End-to-end encryption (Signal Protocol or equivalent). Accept that server-side search, spam scanning of content, and content moderation are no longer possible — only metadata-based signals remain.
Trust-based is acceptable (enterprise tool with compliance/audit needs) →Server-side encryption at rest + TLS in transit is simpler to operate and enables full-text search, content moderation, and legal e-discovery — the trade-off most enterprise chat tools (Slack, Teams) make deliberately.
3
How large can a group get before "encrypt once per member" collapses?
Hundreds to low thousands (chat groups) →Sender Keys (encrypt once per group session, fan out ciphertext server-side) keeps sender-side crypto cost flat regardless of group size.
Unbounded (broadcast channel, no interactivity needed) →Drop E2EE's per-recipient model entirely — a one-way broadcast (WhatsApp Channels) is a fundamentally different problem (pub-sub, not group chat) and shouldn't be forced through the group-chat crypto path.
4
What happens to a message if the recipient never reconnects?
Bounded retention window, then drop →Sets a hard ceiling on server-side storage and is defensible as a privacy feature, not just a cost optimization — this is WhatsApp's actual approach (30-day offline hold, then deleted).
Indefinite retention until delivered →Simpler guarantee ("nothing is ever lost") but unbounded storage growth for permanently-offline or deleted accounts — needs a separate cleanup policy for abandoned accounts.
⚠ · Failure Modes

What Actually Breaks — Production Failure Patterns

01Node-Level Connection Storm on Restart
What it is

When a chat server node restarts (deploy, crash, capacity rebalance), every one of its ~2M connections drops simultaneously and every one of those clients reconnects at roughly the same moment. If reconnects aren't staggered, the receiving nodes — and the connection-registry service (Redis) that has to process millions of near-simultaneous "I'm now on server X" updates — see a load spike far above steady-state.

✓Fix: client-side reconnect with randomized jitter and exponential backoff (never reconnect instantly); drain connections from a node gradually before taking it down rather than dropping all of them at once.
02Double Ratchet Desync from Out-of-Order Delivery
What it is

The Double Ratchet's key state advances with each message. If messages arrive badly out of order or one is permanently lost (not just delayed), a client can end up unable to derive the correct key for a message it does receive, since ratchet state on each side has to stay reasoned-about-consistently.

✓Fix: the protocol itself carries enough header metadata (message numbers, previous chain length) to tolerate real-world reordering and skip ahead within a bounded window; clients cache a bounded number of skipped message keys so a message that arrives late can still be decrypted, and fall back to re-establishing a session (visible to users as a "security code changed"-style event) only when the gap is unrecoverable.
03Push Notification Silent Failure
What it is

An offline user's push notification token (APNs/FCM) can silently go stale — the OS revoked it, the app was reinstalled, or the token simply expired — and the push provider accepts the send without complaint while the notification never arrives. The message sits correctly in Cassandra, delivery is technically "pending," but the recipient has no idea a message is waiting.

✓Fix: treat push as a best-effort nudge, never as the delivery guarantee itself — the real guarantee comes from the client fetching any undelivered messages on every reconnect regardless of whether a push was received; monitor push-provider delivery receipts and proactively refresh tokens that look stale.

07 · Hard Follow-ups

Every Question Your Interviewer Will Ask

How do you guarantee message ordering in a distributed chat system?+
Per-conversation ordering guaranteed by Cassandra clustering key. Cross-conversation ordering not needed.

Cassandra schema: PRIMARY KEY ((conversation_id), message_id) where message_id is Snowflake (time-sortable). Messages within a conversation are physically sorted on disk by message_id. Queries return in order automatically.

The subtle problem: Alice sends M1, then M2. Network jitter causes M2 to arrive at Server A before M1. Solution: client-side sequence numbers. Alice's device assigns seq=1 to M1, seq=2 to M2. Server stores both. Client detects gap (received seq=2 before seq=1): buffer M2, wait 100ms for M1, then render in order. If M1 doesn't arrive: request retransmission via GET /messages/{conversation_id}?since={last_seen}.
How do you scale to 600M concurrent WebSocket connections — what does the infrastructure look like?+
Roughly 300 Erlang nodes × 2M connections each ≈ 600M, under this exercise's own sizing assumption — not a disclosed WhatsApp node count.

Illustrative node sizing: a large multi-core server with a few hundred GB of RAM comfortably covers this. At roughly 300 bytes per idle Erlang process: 2M connections ≈ 600MB of RAM just for the processes themselves — the real capacity constraint in practice is message buffers, routing tables, and OS socket limits, not per-process memory, which is why the connection count is dominated by tuning (Erlang scheduler and FreeBSD kernel parameters) rather than raw RAM.

Connection routing: Redis Hash user:conn:{user_id} → node_id. Updated on connect/disconnect. Any node can route to any other node via Redis Pub/Sub subscription. Each node subscribes to its own channel: SUBSCRIBE server:{node_id}.

Load balancing: GeoDNS routes users to nearest datacenter. Within a datacenter, L4 load balancer (Nginx/HAProxy) distributes WebSocket connections across Erlang nodes using consistent hashing on user_id — same user always connects to same node (reduces connection lookup overhead).
How do you handle the thundering herd when a user with 10,000 contacts comes online?+
Presence updates are the most expensive part of WhatsApp — send judiciously.

Naive approach: user comes online → notify all 10,000 contacts → 10,000 presence updates → 10,000 × (another user's 10,000 contacts who are online) = O(N²) notifications. At scale: catastrophic.

WhatsApp's approach: presence is opt-in and lazy. User coming online: server marks them online (Redis TTL key, refreshed every 30s by heartbeat). Presence notifications sent only to users whose chat screen is currently open on that conversation. "Last seen" timestamps fetched on-demand (when you open a conversation) not pushed proactively.

Contact sync: done in the background, not at connection time. When you open the app, your contact list presence states load lazily as you scroll.
How does WhatsApp deliver messages when the recipient's device is a different phone (number ported)?+
Messages are addressed to user_id (account), not phone number (device). Phone number is just a login identifier.

When Alice registers: WhatsApp creates a user_id. Phone number is the login credential and verified via SMS OTP. The user_id is stored permanently.

When Bob ports his number to a new phone: new device generates new key pair. Registers the new public key with WhatsApp servers (associated with Bob's user_id, not just his phone number). Alice's device fetches Bob's updated public key before encrypting. Safety number changes (visible in WhatsApp settings) — Alice is notified if Bob's key changed, alerting her to verify with Bob in person.
