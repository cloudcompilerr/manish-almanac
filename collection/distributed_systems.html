00 · CAP Theorem

The constraint every distributed system lives with

CAP theorem: a distributed system can guarantee at most two of Consistency, Availability, and Partition Tolerance. Since network partitions always happen in real distributed systems, the real choice is CP vs AP — not "do we handle partitions."

CAP in plain English
Your bank has two branches. The network between them goes down.

CP (Consistency + Partition Tolerance): Both branches stop accepting deposits until the network is restored. No one gets a wrong balance. But the service is unavailable during the outage.

AP (Availability + Partition Tolerance): Both branches keep accepting deposits and serving customers independently. Service stays up. But when the network restores, one branch might show ₹5,000 and the other ₹7,000 for the same account — they need to reconcile.

The choice is: would you rather return an error, or return potentially stale data?
PACELC Extension
CAP only describes behaviour during a partition. PACELC also describes the trade-off during normal operation:
If Partition → choose Availability or Consistency (the CA in CAP)
Else (normal) → choose Latency or Consistency
Even when no partition exists, you must decide: do you want the lowest latency (return from nearest replica, may be slightly stale) or the strongest consistency (always read from primary, higher latency)?
DynamoDB: PA/EL — available during partition, low latency during normal. HBase: PC/EC — consistent always, higher latency.
Linearisability
The strongest consistency model. Every operation appears to happen at a single point in time, in the order clients observe.
If client A writes X=1 and client B subsequently reads X, B must see 1 — not a previous value.
✓ Operations look as if they happened on a single machine. No surprises. Required for: financial transactions, distributed locks, leader election.
⚠ Requires coordination (consensus) across nodes. High latency. Not scalable to high throughput across geographies.
Eventual Consistency
If no new updates are made, all replicas will eventually converge to the same value.
Reads may return stale data during the convergence window (typically milliseconds to seconds).
✓ Highest availability and lowest latency. Scales globally. Acceptable for: social feeds, product descriptions, DNS, shopping carts.
⚠ Applications must handle stale reads gracefully. Conflicts (two writes to the same key) need resolution strategy (LWW, CRDT, vector clocks).
01 · Consensus

Raft — how distributed systems agree on one truth

Consensus is the problem of getting multiple nodes to agree on a single value even when some nodes crash or messages are delayed. Every distributed database, distributed lock, and leader election uses consensus internally.

Leader Election
Raft elects one leader at a time. All writes go through the leader. Followers only accept writes from the current leader.
If no heartbeat from leader for election timeout (150–300ms), followers start a new election. Candidate requests votes. First to get majority (N/2 + 1) becomes new leader.
✓ Simple mental model: one leader, clear authority. Used by: etcd, CockroachDB, TiKV, Kafka (KRaft mode).
Log Replication
Every write is appended to the leader's log. Leader replicates to followers. Once a majority acknowledges, the write is committed and applied.
Committed = durable even if the leader crashes. Followers will elect a new leader and apply the committed log.
This is exactly how Kafka replication works (ISR — in-sync replicas). Exactly how etcd stores Kubernetes cluster state. Exactly how CockroachDB achieves ACID transactions across nodes.
Why Not Paxos
Paxos is theoretically equivalent to Raft but notoriously difficult to understand and implement correctly.
Raft was explicitly designed to be understandable — the original paper is titled "Raft: In Search of an Understandable Consensus Algorithm."
In interviews: say "I'd use Raft" — it is the modern consensus algorithm of choice and you can explain it. Paxos is largely of historical interest.
02 · Distributed Transactions

2PC and the Saga pattern — when ACID crosses service boundaries

Two-Phase Commit (2PC)
A coordinator asks all participants to prepare (can you commit?), then commits only if all say yes.
Phase 1 (Prepare): Coordinator asks all nodes to lock resources and vote yes/no.
Phase 2 (Commit): If all voted yes → commit. If any voted no → rollback all.
✓ Atomicity guaranteed across nodes. All commit or none do.
⚠ Blocking protocol: if coordinator crashes after Phase 1, participants are locked waiting forever (holding resources). Tight coupling between services. Performance: 2 round trips minimum. Used in: traditional databases (PostgreSQL distributed transactions, XA protocol). Avoid in microservices.
Saga Pattern
Break a distributed transaction into a sequence of local transactions, each with a compensating transaction to undo it on failure.
Example — e-commerce order: (1) Reserve inventory → (2) Charge payment → (3) Create shipment. If step 3 fails: cancel shipment + refund payment (compensation) + release inventory.
✓ No distributed locks. Services remain independent. Failures handled gracefully via compensation. The correct pattern for microservices.
⚠ Eventual consistency only — other services see intermediate states (payment charged before shipment confirmed). Compensation logic must be idempotent. Complex to reason about.
Two implementations: Choreography (events trigger next step) or Orchestration (a saga coordinator directs each step). Orchestration is easier to monitor and debug.
Idempotency
Making the same operation multiple times has the same effect as doing it once.
Critical for: retries (network failures mean requests may be delivered twice), payment processing (charge card once even if confirmed twice).
Implementation: client sends a unique idempotency-key header. Server stores (idempotency_key → result). On duplicate: return stored result without re-executing.
✓ Safe retries. Exactly-once semantics. Used by: Stripe (idempotency keys on all payment APIs), Kafka producers (enable.idempotence=true).
03 · Distributed Locking

Redlock and why distributed locks are hard

Redis SETNX Pattern
Simple distributed lock using Redis SET NX EX.
SET lock:{resource} {unique_id} NX EX 30
NX = only set if not exists (acquire lock). EX 30 = auto-expire in 30 seconds (prevent deadlock if holder crashes).
Release: Lua script to atomically check owner + delete: if GET == unique_id then DEL lock
✓ Works correctly with a single Redis instance. Simple, widely used.
⚠ Single Redis node is a single point of failure. If Redis crashes, lock is lost. Works for most use cases where brief lock loss is acceptable.
Redlock Algorithm
Acquire lock on majority of N independent Redis nodes (N=5 recommended). Lock is held only if majority acquired within timeout.
Steps: (1) Get current time. (2) Try acquiring lock on all 5 nodes in sequence. (3) Lock succeeds if acquired on ≥3 nodes AND total elapsed time < lock TTL. (4) Release all on failure.
✓ Survives failure of minority of Redis nodes. No single point of failure.
⚠ Martin Kleppmann identified a flaw: clock skew and GC pauses can cause two clients to both believe they hold the lock. For truly critical systems (financial), use a CP system like ZooKeeper or etcd for locks.
etcd / ZooKeeper Locks
For strong guarantees: use a CP distributed system built on Raft consensus.
etcd PUT /locks/resource?prevExist=false — atomic compare-and-set. Uses Raft to ensure only one leader can acquire the lock cluster-wide.
✓ Correct under all failure scenarios. Linearisable — no two clients can simultaneously believe they hold the lock. Used by: Kubernetes for leader election, distributed job schedulers.
⚠ Higher latency than Redis (Raft round trip). Operational complexity of running etcd/ZooKeeper cluster.
04 · Clocks & Ordering

Why you cannot trust timestamps in distributed systems

Clock Skew
Different servers have slightly different clocks, even with NTP. Typical skew: 1–100ms. Maximum observed: seconds.
Problem: Server A timestamps event at 14:00:01.000, Server B at 14:00:00.998. B's event appears "before" A's despite happening after.
⚠ Never use wall-clock timestamps for event ordering in distributed systems. "Last Write Wins" based on timestamps will silently discard correct data.
Logical Clocks
(Lamport)
A counter that increments on every event and is included in every message. Receiving a message with counter C → set local counter to max(local, C) + 1.
Guarantees: if event A causally precedes event B, then Lamport(A) < Lamport(B).
✓ Causal ordering without synchronized clocks. Simple to implement.
⚠ Cannot tell if two events are concurrent (no causal relationship between them).
Vector Clocks
One counter per node. Captures causality and detects concurrent events.
Node A: [A:1, B:0, C:0]. Sends to B: B updates to [A:1, B:1, C:0]. If two events have incomparable vector clocks, they are concurrent (conflict).
✓ Detects conflicts precisely. Amazon Dynamo uses vector clocks for conflict detection in shopping carts.
⚠ Vector grows with number of nodes. Conflict resolution still needs application logic.
Google TrueTime
Google Spanner's approach: GPS + atomic clocks provide a bounded uncertainty interval [earliest, latest] for the current time. Spanner waits out this uncertainty before committing.
Uncertainty: ~7ms. Spanner commits with at least 7ms delay to ensure all nodes agree on ordering.
✓ Enables external consistency (linearisability) globally across datacenters. The only system that achieves this at global scale.
You cannot replicate TrueTime without specialized hardware. For most systems: use logical clocks or a single-region Raft-based system.
05 · Follow-ups

Every hard follow-up, answered

How do you handle split-brain in a distributed system?+
Split-brain: a network partition causes two groups of nodes to both believe they are the leader/primary, leading to divergent writes.

Prevention strategies:
1. Quorum writes: a write only succeeds if acknowledged by majority (N/2+1). During partition, the minority partition cannot achieve quorum and stops accepting writes. Only the majority side proceeds. Used by: Raft, Cassandra QUORUM writes.

2. Fencing tokens: every time a new leader is elected, it receives a monotonically increasing token. Storage systems reject writes with older tokens. Even if the old leader thinks it is still active, its writes are rejected.

3. Lease-based leadership: leader holds a lease (timed lock). If it cannot renew before expiry, it steps down voluntarily. Used by: Kubernetes leader election via etcd.
What is the difference between linearisability and serializability?+
These are often confused but refer to different properties at different levels.

Linearisability is about single operations on a single object (key). It means every read-write operation appears to happen atomically at a single point in time. It is a property of a single key's history.

Serializability is about transactions (groups of operations, possibly on multiple keys). It means the result of concurrent transactions is equivalent to some serial (one-at-a-time) execution. It is a property of the database's transaction isolation.

Strict Serializability (Linearisable Serializability) = both: transactions are serialized AND operations appear instantaneous. This is what Spanner and CockroachDB provide. The strongest guarantee, but most expensive.
How does the Saga pattern handle a payment failure mid-order?+
Compensating transactions undo the effects of already-completed steps.

Order saga steps: Reserve Inventory → Charge Payment → Create Shipment → Send Confirmation.

Failure at step 2 (payment declined):
1. Shipment not yet created — skip
2. Compensating transaction for step 1: call Inventory Service with "release reservation for order X." Must be idempotent — if this fails and retries, it should not double-release.
3. Return "payment failed" to user.

Key insight: compensating transactions must be idempotent and durable. Store the saga state in a database so you can resume compensation after a crash. This is what orchestration-based Sagas (e.g., AWS Step Functions, Temporal.io) manage for you automatically.
