System Design Interview Prep

Count-MinSketch

The probabilistic data structure that counts millions of events using just kilobytes of memory — and how hash functions make it work.

↓ SCROLL TO LEARN
01 — The Problem

Why not just use a counter?

Imagine you're running YouTube. Every second, millions of videos are watched. Your boss asks: "What are the top trending videos right now?"

A naive HashMap of video_id → count works fine for 1,000 videos. But YouTube has 800 million videos. Storing exact counters for all of them = gigabytes of RAM, just for counting.

The insight: For trending, rate-limiting, and frequency analysis, you don't need the exact count. A "slightly-higher-than-truth" estimate is perfectly fine — as long as it's fast and tiny.

Count-Min Sketch gives you ~95%+ accurate frequency estimates in a few kilobytes, with O(1) inserts and queries.

02 — The Key Mechanism

How does a hash function pick a column?

This is the most important thing to understand. A hash function is just a deterministic math machine: same input → always same output. It converts any string into a number, then we use modulo (%) to fit it into our grid width.

// Step-by-step: hashing "video_42" into a 6-column grid

// Hash Function 0: a simple polynomial hash "video_42" → add up (character codes × prime powers) = 118×31⁰ + 105×31¹ + 100×31² + ... = big number: 8,472,193 column = 8,472,193 % 6 (grid width) = → Col 3
// Hash Function 1: a different seed / multiplier "video_42" → same chars, different math → 5,291,847 column = 5,291,847 % 6 = → Col 2
// Hash Function 2: yet another seed "video_42" → 3,104,522 column = 3,104,522 % 6 = → Col 4

The key insight: the exact number doesn't matter. What matters is that (a) it's always the same for the same input, and (b) different hash functions scatter the same input to different columns.

Real world analogy: Think of 3 bouncers at a party, each with their own arbitrary rule for assigning people to table numbers. If you ask "where does Alice sit?", each bouncer gives a different table — but they'll always give the same table for Alice every time you ask.
03 — The Grid

Count-Min Sketch is just a table of counters

A grid of depth × width. Each row has its own independent hash function. The grid starts at all zeros.

Col 0Col 1Col 2Col 3Col 4Col 5
Row 0 (hash_fn_0) 000302
Row 1 (hash_fn_1) 004010
Row 2 (hash_fn_2) 200150

The highlighted cells are where "video_42" incremented. To query: look up those same cells → values are 3, 4, 5 → take MIN = 3. That's our estimate.

Why is Row2's value (5) higher? Because another video happened to hash to Col 4 in Row 2 — it polluted that counter. The minimum protects us from this pollution.

05 — Key Properties

What to say in your interview

PropertyDetailImplication
Space O(width × depth) — fixed A few KB regardless of traffic volume
Time O(depth) per insert/query Essentially O(1) in practice
Error direction Only overcounts, never undercounts overestimate-only — safe for rate limiting
Accuracy tuning Wider grid → less error per row More rows → lower failure probability
Deletion Not supported by default Counters only go up
The formula: Width = ⌈e/ε⌉ where ε is acceptable error rate. Depth = ⌈ln(1/δ)⌉ where δ is acceptable failure probability.

Plain English: "I want <0.1% error with 99% confidence" → ε=0.001, δ=0.01 → Width ≈ 2719, Depth ≈ 5. That's a ~54KB grid.
06 — Interview Counter Questions

Questions you'll be asked — answered

Why not just use a HashMap? +
A HashMap is exact but memory scales with unique items. 100M unique URLs = gigabytes of RAM just for counters. Count-Min Sketch gives you ~95% accuracy in a few kilobytes. For trending, rate-limiting, and frequency analysis, "close enough" is perfectly fine — and it's orders of magnitude cheaper.
What if two items always hash to the same column? +
That's a collision — their counts bleed into each other. That's exactly why we use multiple rows with independent hash functions. The probability that item A collides with item B in all rows simultaneously drops exponentially with each row added. With 5 rows, it's astronomically unlikely. This is why we take the minimum — it's the least-polluted estimate across all rows.
Can you delete items? +
Standard CMS doesn't support deletion — subtracting could make a count go negative and corrupt the structure. If you need deletion, use Count-Min Sketch with conservative update or switch to a Count Sketch (allows negative values, slightly different statistical guarantees). In practice, most real-world use cases (trending, rate limiting) don't require deletion.
How is this different from a Bloom Filter? +
They're cousins — same probabilistic family, different questions.

When would you NOT use Count-Min Sketch? +
Three cases: (1) When you need exact counts — billing, financial transactions, audit logs. (2) When your key space is small enough to fit exactly in RAM. (3) When you need to enumerate all keys — CMS can tell you the count for a key you ask about, but it can't tell you what keys exist. For that, you need a different structure.
Where is Count-Min Sketch used in production? +
Redis uses it for frequency counting in rate limiting. Twitter/X uses it for trending hashtag detection. Networking equipment uses it to detect high-traffic IPs (DDoS detection). Database query optimizers use it to estimate row frequencies for query planning. CDNs like Akamai use it to identify hot cache objects.
The one line to remember
"Count-Min Sketch is a fixed-size grid of counters. You hash each event across multiple rows, increment that cell in each row, and query by taking the minimum. It trades perfect accuracy for dramatically lower memory — and it only ever overcounts, never undercounts."
05 · Concepts Quick Reference

Core mechanics in one place

Hash Width
(w)
Number of columns in the CMS table — controls error magnitude.
Guarantee: estimation error ≤ e/w where e is the base of natural log (~2.718). Set w = ⌈e/ε⌉ where ε is your acceptable error rate.
Example: ε=0.01 (1% error) → w = ⌈2.718/0.01⌉ = 272 columns. With total count N=1,000,000: max overcount = 10,000 (1% of N). Wider table = smaller error. Each row is independent — width scales linearly with required accuracy.
Hash Depth
(d)
Number of rows (independent hash functions) — controls error probability.
Guarantee: probability of exceeding the error bound ≤ δ^d. Set d = ⌈ln(1/δ)⌉ where δ is acceptable failure probability.
Example: δ=0.01 (99% confidence) → d = ⌈ln(100)⌉ = 5 rows. With 5 independent hash functions, probability that ALL 5 collide for the same key is (0.01)^5 = 0.0000000001. More rows = higher confidence. Depth grows logarithmically — 5 rows gives 99% confidence, 10 rows gives 99.9999%. Depth has diminishing returns.
Why Minimum?
The CMS query returns the minimum across all d rows — not sum, not average, minimum.
Each row's counter is always ≥ the true count (due to hash collisions adding counts from other keys). The minimum across all rows is the closest to the true count — but still an upper bound. ✓ Mathematically proven: min(rows) ≥ true_count always. And min(rows) − true_count ≤ error_bound with high probability. This is why CMS only over-estimates, never under-estimates.
Space Complexity
O(w × d) — constant space regardless of the number of distinct keys.
A CMS with ε=0.01, δ=0.01: w=272, d=5. Total cells: 272 × 5 = 1,360 integers. At 4 bytes each: 5,440 bytes = 5.3KB.
Compare: tracking 1 billion unique keys in a HashMap = ~24GB. CMS achieves similar functionality in 5.3KB — a 4.5 million times reduction. ✓ This is why CMS is used in production for counting at scale: it fits in L1 CPU cache, enabling billions of updates per second.
CMS vs HyperLogLog
CMS counts frequency of each item. HyperLogLog counts the number of distinct items. Different problems.
CMS answers: "how many times did user X appear?" → frequency/count estimation.
HyperLogLog answers: "how many distinct users appeared?" → cardinality estimation. Both are probabilistic, both use constant space. Use CMS for Top-K (need per-item counts). Use HyperLogLog for DAU / unique visitor counts (need distinct count). Redis supports both natively.
06 · System Design Examples

CMS in production systems

Twitter — Trending Hashtags
BILLIONS OF EVENTS
PROBLEM
500M tweets/day. Count how many times each hashtag appears in the last 1 hour. Millions of distinct hashtags. A HashMap would need gigabytes. Must update in real time as tweets arrive.
CMS SOLUTION
ε=0.01, δ=0.01 ✓ One CMS per 5-minute bucket. Each tweet: extract hashtag → hash into CMS → increment counters. At end of bucket: query CMS for all candidate hashtags to get approximate counts. Top-K selection from CMS estimates using a min-heap.
SIZE
w=272, d=5 → 1,360 cells × 4 bytes = 5.3KB per CMS. 12 buckets/hour = 64KB total for a full hour of sliding window. Compare: tracking all distinct hashtags by count → gigabytes. CMS fits in CPU cache.
ERROR
At 500M events/hour: max error = 500M × 0.01 = 5M per hashtag. A hashtag with 100M appearances is estimated as 95M–105M. For trending (relative ranking), this error is irrelevant — #WorldCup at 100M vs #Olympics at 80M are still correctly ranked.
Redis — Native CMS Implementation
PRODUCTION USE
COMMAND
CMS.INITBYPROB key 0.001 0.01 — create CMS with 0.1% error, 99% confidence.
CMS.INCRBY key hashtag 1 — increment count for hashtag.
CMS.QUERY key hashtag1 hashtag2 — query multiple keys at once.
TOPK INTEGRATION
Redis also has TOPK.ADD which combines a CMS with a min-heap to maintain the Top-K list automatically. Add events one at a time — Redis maintains the top-K internally. No Flink or separate aggregation layer needed for moderate scales (<100K events/sec).
MERGE
CMS.MERGE dest numkeys src1 src2 ... — merge multiple CMS sketches into one. Use for: shard multiple CMS across Redis cluster (one per shard), merge at query time to get global counts. Merge is O(w × d) — constant time regardless of event volume.
07 · Decision Framework

When to use CMS — and when not to

🎯CMS vs Exact Counting — Ask in Order
01
How many distinct keys do you need to count?
Few (<1M distinct) →Exact counting with HashMap is fine. 1M keys × 8 bytes = 8MB — trivially fits in memory. Use Redis HSET or a HashMap. No need for probabilistic structures at this scale.
Many (>10M distinct) →CMS is justified. 100M distinct keys × 8 bytes = 800MB. CMS achieves same Top-K result in 5KB. The accuracy trade-off is worth it.
02
Can you tolerate small over-counting (CMS never under-counts)?
YES →Use CMS. CMS guarantees frequency(item) ≤ estimate ≤ frequency(item) + ε×N. The overcount is bounded and predictable. Perfect for: trending topics, popular product ranking, heavy hitter detection in network traffic.
NO (exact counts required) →Exact counting required. Use a distributed exact counter: Redis INCR per key (limited by memory), or a database COUNT per key (slow at scale), or a streaming aggregation into a database (Flink → Cassandra with exact counts).
03
Do you need to track individual item counts or just find the Top-K?
Just Top-K →CMS + min-heap (or Redis TOPK). Maintain a min-heap of size K. For each new item: query CMS for its estimated count. If estimate > heap minimum, replace minimum with this item. O(log K) per update. K is typically small (top 10, top 100).
All item counts →CMS alone. Query any key in O(d) time — constant regardless of vocabulary size. Cannot enumerate all keys (CMS stores counts, not keys). Combine with a key registry if you need to iterate over all counted items.
