00 · Requirements

Scope first

Functional
1-to-1 messaging. Group chat (up to 256 members). Message delivery receipts (sent, delivered, read). Online/last-seen presence. End-to-end encryption. Media (images, video, voice messages). Push notifications for offline users.
Non-Functional
2B users, 100B messages/day. Message delivery: <500ms when both online. Offline message delivery on reconnect. Order guaranteed per conversation. At-least-once delivery. High availability (messages never lost). E2EE: server never reads message content.
Estimation
100B messages/day ÷ 86,400 = 1.16M messages/sec. Average message: 100 bytes (text). Storage: 1.16M × 100 bytes = 116 MB/sec = ~4PB/year. WhatsApp stores messages only until delivered — not indefinitely. Active connections: 2B users × 30% online = 600M concurrent WebSocket connections.
01 · Architecture

The complete messaging system

Connection Layer
Persistent WebSocket per user → Chat Server. Chat servers stateful for connection management.
Each user maintains one WebSocket connection to a Chat Server. Chat Server knows which users are connected to it. Connection metadata in Redis: user:connection:{user_id} → chat_server_id. This lets any service look up which server a user is on and route messages to them.
600M concurrent connections: Erlang-based chat servers (WhatsApp uses Erlang) handle 2M+ connections per node. 300 Erlang nodes for 600M connections. Erlang's actor model: each connection is a lightweight process (~300 bytes). C10M problem solved.
Message Flow
(Both Online)
Alice → Server A → Route to Server B → Bob. Under 100ms.
Alice sends message: WebSocket → Chat Server A. Server A: look up Bob's server from Redis: HGET user:connection:bob → server_b. Publish message to Server B via internal pub/sub (Redis Pub/Sub or Kafka). Server B: deliver to Bob's WebSocket. Return delivery receipt to Alice: Server A sends "delivered" status back via Alice's WebSocket.
Message ID: monotonically increasing per conversation (Snowflake ID). Used by Bob's client to detect gaps and request missing messages.
Message Flow
(Bob Offline)
Messages stored in Cassandra until Bob reconnects.
Bob is offline → HGET user:connection:bob → null. Store message in Cassandra: messages(conversation_id, message_id, sender_id, content_encrypted, created_at). Send push notification (APNs for iOS, FCM for Android). Bob reconnects → Chat Server checks Cassandra for undelivered messages → batch deliver → delete from Cassandra → return "delivered" receipts to Alice.
Storage TTL: WhatsApp deletes messages from server after delivery. If Bob doesn't reconnect in 30 days, message is deleted. Client devices store message history locally (encrypted).
End-to-End Encryption
Signal Protocol: server never sees plaintext. Only the recipient can decrypt.
Each user has a public/private key pair generated on device. Public keys stored on WhatsApp servers. When Alice messages Bob: Alice fetches Bob's public key → encrypts message with Bob's public key → sends ciphertext to server → server routes to Bob → Bob decrypts with his private key.
Server role: routing and storage of encrypted ciphertext only. Even WhatsApp cannot read the content. Key verification: users can compare "safety numbers" (a hash of both key fingerprints) in person to detect MITM attacks.
Group Messaging
Fan-out on write: server sends one copy per group member.
Group message from Alice (256-member group): Alice's client encrypts message separately for each recipient (Signal Protocol's sender keys optimise this). Server receives one message → creates 255 delivery tasks → routes to each member's server. Kafka topic per group for ordered, reliable delivery to all members.
Scale concern: 100M group messages/day × 256 members avg = 25.6B fan-out writes/day. Handled with: parallel delivery, Kafka for buffering, per-member TTL in Cassandra.
02 · Follow-ups

The questions your interviewer will ask

How do you guarantee message ordering in a distributed chat system?+
Ordering within a conversation is guaranteed by the Cassandra clustering key. Cross-conversation ordering is not needed.

Schema: PRIMARY KEY ((conversation_id), message_id) where message_id is a time-sortable Snowflake ID. Messages within a conversation are stored in order and returned in order. Cassandra clustering key guarantees physical ordering on disk within a partition.

The subtle problem: Alice sends message M1, then M2. Both arrive at the server. Network latency differences cause M2 to be written first. Solution: client-side sequence numbers. Alice's client assigns seq=1 to M1, seq=2 to M2. Server detects out-of-order delivery (seq=2 before seq=1). Options: (1) buffer M2 briefly while waiting for M1, (2) deliver both and let client sort on sequence number.

WhatsApp's actual approach: client-side logical clocks. Each message has a client-assigned sequence number per conversation. Client reorders on receipt. The server provides at-least-once delivery; the client provides exactly-once display via deduplication on message_id.
How do you scale to 600M concurrent WebSocket connections?+
The solution is Erlang's actor model and horizontal scaling of chat servers.

In most languages, a WebSocket connection requires a thread or an event loop callback. Java with thread-per-connection: 1M connections × 1MB stack = 1TB RAM. Not viable. Node.js with async I/O: better, but GC pauses cause latency spikes at scale.

Erlang/Elixir actor model: each connection is an independent lightweight process using ~300 bytes of RAM. Erlang processes are not OS threads — they're scheduled by the Erlang VM. One physical machine can run millions of processes. WhatsApp's chat servers run on Erlang with 2M connections per node. 600M connections ÷ 2M per node = 300 nodes.

The connection routing: when Alice sends a message to Bob, the server must find which node Bob is connected to. Solution: Redis hash: HGET user:connection bob → node_47. Server Alice is on routes the message to node 47 via internal messaging. Node 47 delivers to Bob's process. This lookup happens on every message — must be sub-millisecond. Redis pipelining handles this at 2M+ lookups/sec.
How do you handle the "read receipt" feature at 1M messages/sec?+
Read receipts are high-volume, low-priority writes — batch them asynchronously.

When Bob reads a message: his client sends a read receipt for every unread message (potentially 100 messages if he was offline). That's 100 DB writes per reconnect event. At 1M reconnects/day: 100M read receipt writes/day = 1,157 writes/sec — manageable, but batching makes it better.

Pattern: client buffers read receipts locally (within 1 second or up to 50 receipts). Sends in a batch: POST /receipts {"message_ids": [123, 124, 125, ...], "status": "read"}. Server: one Cassandra batch write per batch. Updates: message_status(message_id) → "read".

Delivering receipts to sender: Alice is connected to Server A. Bob's read receipt arrives → look up Alice's connection: HGET user:connection alice → server_a → route receipt to Server A → Server A delivers to Alice's WebSocket in real time. Alice sees the double blue tick appear. Round trip: <200ms when both online.
