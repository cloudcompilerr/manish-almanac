The newspaper with hundreds of millions of readers analogy
Imagine a newspaper read by hundreds of millions of people every morning, but each person gets a personalised edition showing only stories from people they follow. When you post a tweet, it's like writing an article — copies are instantly distributed to every subscriber's "inbox" (Redis feed list). Celebrities are like wire services (AP, Reuters) — their stories are too widely distributed to pre-deliver, so instead every paper fetches them fresh at print time. The printing press (PostgreSQL) keeps the master copy; the newsstands (Redis cache) keep popular copies nearby for instant pickup.
⚠ The interview trap that catches most candidates

"Design Twitter" candidates who commit to a single fan-out strategy — pure push ("write the tweet to every follower's feed immediately") or pure pull ("compute the feed by querying every followed user's tweets at read time") — are each solving only half the problem. Pure push collapses the moment an account with tens of millions of followers tweets: one write becomes tens of millions of writes, and doing that synchronously in the request path is a guaranteed timeout. Pure pull collapses on ordinary users: someone who follows 2,000 accounts triggers up to 2,000 reads on every feed load. Candidates who score well name the hybrid explicitly — push for the overwhelming majority of accounts with a normal follower count, pull for the small set of "celebrity" accounts — and can explain why the threshold has to be based on follower count (write fan-out cost), not tweet frequency or account age.

01 · Core Architecture

Full System Architecture — Every Component Justified

01Tweet StoragePostgreSQL + S3
Data Model
PostgreSQL sharded by tweet_id (UUIDv7 — time-sortable).
Schema: tweets(id, user_id, content TEXT, media_urls[], created_at, like_count, retweet_count). Index on user_id for profile timeline. 100 shards → each shard ~0.5GB text/year. Why not Cassandra? Tweets are relational (replies, retweets), need ACID for counters, and write QPS (6K/s) fits comfortably on sharded PG.
✓UUIDv7 tweet IDs are time-sortable — range queries for "last N tweets by user" use index scan, not full table scan
⚠Shard by tweet_id not user_id — otherwise celebrity users create hot shards with millions of writes
02Follow GraphRedis + PostgreSQL
Data Model
PostgreSQL follows(follower_id, followee_id, created_at) as source of truth. Index on both columns. 300M users × 200 avg follows = 60B rows — needs partitioning. Redis SET per user: following:user:123 for O(1) "do I follow X?" checks (feed generation uses this heavily). Redis is populated lazily from PG on first access.
ℹA graph DB (Neo4j) seems natural but is overkill — the queries are simple lookups, not multi-hop traversals. PostgreSQL + Redis covers 99% of the follow-graph access patterns
03Feed GenerationHybrid Fan-out
The Hardest Part
Two approaches, each fails alone. Twitter uses a hybrid.
Fan-out on Write (push): when user posts, push tweet_id to every follower's Redis feed list. Feed read = single LRANGE feed:user:X 0 19. Problem: @elonmusk → 200M writes per tweet.
Fan-out on Read (pull): at feed load, fetch last N tweets from each followed user. No write amplification. Problem: user follows 2,000 people → 2,000 DB queries per load, 35K feeds/sec = 70M DB queries/sec.
Hybrid (Twitter's actual solution): Regular users (< 1M followers) → push. Celebrities → pull at read time. Feed assembly merges pre-computed list + fresh celebrity tweets.
✓Push path: feed load = 1 Redis read (< 1ms). Celebrity path: parallel DB reads for each celebrity followed (typically 3–5 queries, 30ms total)
⚠Celebrity threshold matters — set too low and push amplification is huge; set too high and read path is slow
04Cache LayerRedis — Three Tiers
Cache Strategy
Three separate caches, each with different TTLs and purposes:
(1) feed:user:{id} — Redis List of 800 tweet_ids, TTL=24h. Pre-computed by fan-out. Feed read = LRANGE + batch HGET for content.
(2) tweet:{id} — Redis Hash with full tweet JSON, TTL=1h. 99% hit rate for viral tweets.
(3) user:{id} — username, avatar, follower count, TTL=30min. Displayed on every tweet render.
✓At 100:1 read:write ratio, 99% cache hit rate means DB sees only 3,500 read QPS instead of 350,000
→Cache stampede mitigation: jitter on TTL (±10%), stale-while-revalidate for tweet content
05Media StorageS3 + CloudFront
Upload Flow
Never store media in the database. Never proxy through your servers.
Upload: client → POST /media/upload-url → server returns pre-signed S3 URL → client uploads directly to S3 (your server never handles the bytes). On completion: client notifies tweet service with S3 key. Serving: S3 → CloudFront CDN → user. p99 image load: < 20ms globally from CDN edge.
ℹPre-signed URL upload means your API servers never saturate on media bandwidth. 7 image uploads/sec × 200KB = 1.4MB/s — trivial for S3, catastrophic if proxied through your servers
02 · Deep Dive

Feed Assembly — Complete Request Lifecycle

Home Feed Request — T=0 to T=40ms
T+0ms
GET /feed → API Gateway authenticates JWT (verifies RS256 signature against cached public key — no auth service call). Routes to Feed Service.
T+1ms
Feed Service: LRANGE feed:user:123 0 19 → 20 tweet_ids from Redis. If list is empty (cold start or TTL expired) → fall through to fan-out-on-read for this user.
T+3ms
Batch enrich: HGETALL tweet:{id} for each tweet_id. Pipeline all 20 requests in one Redis round trip. ~90% cache hit rate for recent tweets.
T+5ms
For cache misses: SELECT * FROM tweets WHERE id IN (?) on the appropriate PG shard. Populate cache before returning.
T+10ms
Celebrity check: for each followed celebrity user, fetch their last 5 tweets from tweet cache. Typically 3–5 parallel Redis reads.
T+15ms
Merge: combine pre-computed feed + celebrity tweets. Sort by created_at DESC. Deduplicate (user might follow both a celebrity and someone who retweeted them).
T+20ms
Enrich with user profiles: batch HGETALL user:{id} for all unique authors. All in Redis — < 1ms.
T+25ms
Return: 20 tweets with full content, author info, media URLs. Total: ~25ms p50, ~40ms p99.
03 · The Hard Decision

Fan-out on Write vs Fan-out on Read — Term by Term

The entire feed-generation problem reduces to one question: when does the work of "who should see this tweet" happen — at post time, or at read time? Get the vocabulary precise.

FAN-OUT
ON WRITE
(push)

At post time, the tweet_id is written into every follower's pre-computed feed list. A feed read becomes a single cheap lookup (LRANGE feed:user:X 0 19) — all the expensive work happened once, at write time, and is amortized across every future read by every follower.

Cost model: write cost = O(followers). For a normal account with a few hundred followers, that's trivial. For an account with tens of millions of followers, one tweet becomes tens of millions of writes — the "celebrity problem."

FAN-OUT
ON READ
(pull)

At read time, the feed is assembled by querying the latest tweets from every account the reader follows. Write cost is O(1) — a tweet is written once, period, regardless of follower count.

Cost model: read cost = O(followees). A typical user following a few hundred accounts pays a moderate read cost on every feed load; a heavy user following thousands of accounts pays a read cost that fan-out-on-write would have paid once, at write time, and amortized forever.

WHY NEITHER
ALONE WORKS

Fan-out-on-write alone is fine until an account's follower count crosses into the millions — then a single tweet threatens to saturate the fan-out pipeline. Fan-out-on-read alone is fine for celebrities but makes every feed load pay a read-amplification cost that most users don't need, since most accounts followed have normal follower counts and would have been cheap to push.

HYBRID
MERGE

Push for accounts below the celebrity threshold, pull for accounts above it, merge the two result sets at read time and sort by timestamp. This is the answer that's actually defensible in an interview: it isn't a compromise, it's applying the right strategy to each regime of the same underlying cost curve — write-amplification-bounded for the long tail, read-amplification-bounded for the short head of celebrity accounts.

04 · Interview Decision Framework

Push, Pull, or Hybrid? The Questions That Decide It

🎯Four Questions Before You Commit to a Fan-out Strategy
1
Is the follower-count distribution heavy-tailed (a small number of accounts with an enormous following) or roughly uniform?
Heavy-tailed (real social networks) →You need the hybrid. A pure strategy optimizes for one end of the distribution and fails the other.
Roughly uniform, small follower counts →Pure fan-out-on-write is simpler and sufficient — there's no celebrity regime to defend against.
2
What's the read:write ratio?
Read-heavy (100:1 or higher, typical of a feed product) →Bias toward push. Paying the fan-out cost once at write time and serving cheap reads forever wins when reads vastly outnumber writes.
Write-heavy or roughly balanced →Fan-out-on-read's O(1) write cost becomes more attractive relative to push's O(followers) write cost.
3
Can the product tolerate a few seconds of fan-out lag for regular (non-celebrity) accounts?
Yes →Make fan-out asynchronous (publish to a queue, fan out in a background consumer) so the post endpoint returns immediately regardless of follower count.
No, must be synchronous →Push has to happen in the request path — which makes the celebrity threshold even more load-bearing, since a slow synchronous fan-out for a large account blocks the poster's response.
4
Does the feed need to reflect likes/retweets/edits after the fact, not just new posts?
Feed is mostly append-only →A pre-computed feed list of tweet_ids works well — re-fetch the latest tweet content at render time so counters stay fresh without re-running fan-out.
Feed re-ranks based on engagement after posting →Push a candidate set, then re-rank at read time — this is closer to how modern ranked feeds (not strict reverse-chronological) actually work, and it's a stronger answer if the interviewer pushes on ranking.
⚠ · Failure Modes

What Actually Breaks — Production Failure Patterns

01Fan-out Backlog During a Trending Event
What it is

A breaking-news moment causes thousands of mid-size accounts (not quite "celebrity" by threshold, but each with hundreds of thousands of followers) to post and retweet in a short window. The async fan-out queue backs up; regular users' feeds lag behind real-time by minutes instead of seconds, and the lag is invisible until someone notices their feed feels "stale."

✓Fix: autoscale fan-out consumers on queue depth, not just CPU; prioritize fan-out for the most recently-active followers first so the users actually looking at their feed right now catch up quickest.
02Cache Stampede on a Viral Tweet
What it is

A single tweet's cache entry expires (TTL elapsed) at the exact moment it's going viral — thousands of concurrent requests all miss cache simultaneously and hit the database with the identical query for the identical tweet_id, briefly multiplying load on that one row far beyond its normal share.

✓Fix: request coalescing (the first miss triggers a DB fetch, subsequent concurrent misses wait on that in-flight fetch instead of issuing their own); jittered TTLs so popular content doesn't expire in lockstep; stale-while-revalidate so a slightly-stale cached value is served while a refresh happens in the background.
03Hot Shard From a Single Trending Topic
What it is

Trending-topic aggregation (ZINCRBY on a hashtag key) concentrates enormous write volume onto one Redis key during a global event. Even though Redis handles individual operations in sub-millisecond time, a single key on a single shard has a ceiling — and a hot key doesn't spread across a cluster the way a well-distributed workload does.

✓Fix: shard the counter itself (N sub-keys per hashtag, sum them on read) so writes distribute across multiple Redis slots instead of funneling through one key; pre-aggregate at a coarser time bucket during known high-traffic events.

07 · Hard Follow-ups

Every Question Your Interviewer Will Ask

How do you handle the "celebrity problem" — Elon Musk tweets and 200M followers need their feed updated?+
The celebrity problem is solved by NOT updating celebrity follower feeds on write.

When @elonmusk tweets: (1) Write tweet to PostgreSQL. (2) Write tweet_id to celeb_timeline:elon Redis List (not to each follower's feed). Done. Cost: 2 writes, not 200M.

At feed read time: Feed Service checks "which of the users I follow are celebrities?" (maintain a Redis SET of celebrity user_ids). For each celebrity in my following list: fetch their last 5 tweets from celeb_timeline:{id}. Merge with pre-computed feed. Sort by timestamp.

Result: one tweet from Elon → 2 Redis writes (not 200M). 200M users each make 1–5 extra Redis reads when loading their feed. Total cost: 200M × 5 reads = 1B reads spread across feed load time, not a thundering write at tweet time.

Celebrity threshold: a commonly-cited design choice is treating accounts above roughly 1M followers as "celebrities" for fan-out purposes. The exact production threshold and account count aren't publicly disclosed by X/Twitter — pick a defensible number in an interview and justify it by the write-amplification math, not by citing a specific headcount.
How do you implement "read your own writes" — user posts a tweet and immediately sees it in their feed?+
After posting, prepend the new tweet_id to the user's own Redis feed list directly.

POST /tweet → store in PG → fan-out to followers (async) → LPUSH feed:user:{poster_id} {new_tweet_id} (sync, before returning to the poster). The poster's feed is updated immediately. Other users get the tweet through async fan-out within 2 seconds.

This is a classic "read-your-own-writes" consistency pattern. The write propagates eventually to all followers (eventual consistency) but the writer gets immediate consistency. Implementation cost: one extra Redis write in the tweet creation hot path.
How do you scale the like count — at 300K likes/sec on a viral tweet, you can't hit PostgreSQL on every like?+
Redis atomic increment + async batch flush to PostgreSQL.

User likes tweet 789: INCR like:count:tweet:789 in Redis. Return new count to user instantly. Background job runs every 60 seconds: GETSET like:count:tweet:789 0 (atomically read and reset counter) → UPDATE tweets SET like_count = like_count + {delta} WHERE id = 789.

At 300K likes/sec on one viral tweet: Redis handles this trivially (INCR is O(1), Redis does 1M ops/sec). PostgreSQL sees only 1 UPDATE per tweet per 60 seconds regardless of like rate.

Risk: Redis crash between increments = lose up to 60s of likes. Mitigation: Redis AOF persistence + replicas. Acceptable tradeoff for a "like count" feature (vs. unacceptable for financial transactions).
What happens when a user has 200,000 followers and tweets frequently — how do you prevent fan-out storms?+
Rate-limit fan-out per user + process fan-out asynchronously via Kafka.

Synchronous fan-out: POST /tweet → instantly push to 200K Redis Lists → response blocked until 200K writes complete. At 200K × 1ms per write (with pipelining) = 200 seconds. Clearly wrong.

Async fan-out: POST /tweet → write to PG → publish TweetCreated event to Kafka → return 201 to user immediately (< 100ms). Fan-out consumer reads TweetCreated → looks up follower list in batches of 1,000 → LPUSH to each follower's Redis list. Fan-out completes in 2–10 seconds for 200K followers (not in the request path).

The user gets a 201 response immediately. Their tweet appears in followers' feeds within seconds. This is acceptable — Twitter's SLA is "eventually" not "immediately."
How do you implement trending hashtags in real time?+
Redis ZINCRBY on every tweet + sliding window with multiple ZSET buckets.

On every tweet post: parse hashtags from content → for each hashtag: ZINCRBY trending:window:{current_5min_bucket} #{hashtag} 1.

To get "trending in last 1 hour": ZUNIONSTORE across last 12 buckets (12 × 5min = 60min) → ZREVRANGE with top 10. Run this aggregation every 30 seconds and cache the result.

Decay: buckets expire naturally (TTL on each bucket key = 70 minutes). No delete logic needed — old buckets disappear automatically.

At scale (500M tweets/day = 6K/sec): Redis ZINCRBY takes < 1ms. Even at 10 hashtags per tweet average = 60K ZINCRBY operations/sec. Redis handles this comfortably. For extreme scale: shard trending by region (trending:US:..., trending:IN:...).
How does search work — how do you make 500M tweets searchable in < 1 second?+
Elasticsearch as the search index, updated via Kafka CDC pipeline.

Pipeline: Tweet posted → Kafka TweetCreated event → Search Consumer → Elasticsearch index. Delay: tweet searchable within 1–2 seconds of posting (Elasticsearch default refresh interval = 1 second).

Index mapping: tweet_id, user_id, content (analyzed — tokenized, stemmed), created_at (for recency scoring), like_count (for popularity scoring), hashtags[], lang.

Query: BM25 relevance score × recency boost × popularity boost. For "trending" queries: boost documents created in the last 24 hours. For personalized search: boost tweets from accounts the user follows.

Scale: 500M tweets × 300 bytes indexed content = 150GB index. Elasticsearch handles this easily across 10 nodes. Shard by tweet creation time — search queries mostly target recent tweets, enabling time-based pruning.
