01 · Inverted Index

The Inverted Index — Why Databases Can't Do This

How It Works
An inverted index maps each unique term to the list of documents containing it.
Documents: Doc1="Redis is fast", Doc2="Redis scales well", Doc3="Kafka is fast"
Inverted index:
redis → [Doc1, Doc2]
fast → [Doc1, Doc3]
is → [Doc1, Doc3]
scales → [Doc2]
Query "redis fast" → intersection of [Doc1,Doc2] and [Doc1,Doc3] → Doc1 (contains both terms)
Posting List
For each term, the index stores not just document IDs but positions and frequencies.
redis → [(Doc1, freq:1, pos:[0]), (Doc2, freq:1, pos:[0])]
Position enables phrase queries: "redis cluster" requires "redis" and "cluster" to be adjacent.
Frequency enables relevance scoring — a document mentioning "redis" 20 times ranks higher than one mentioning it once.
Text Analysis Pipeline
Before indexing, text passes through an analysis pipeline that normalises it.
1. Tokenization: "Redis is Fast!" → ["Redis", "is", "Fast"]
2. Lowercasing: → ["redis", "is", "fast"]
3. Stop word removal: → ["redis", "fast"] (removes "is")
4. Stemming/Lemmatization: "running" → "run", "faster" → "fast" The same pipeline must run at query time. "Running Redis" → ["run", "redis"] → matches documents containing "run" or "redis" in any form.
TF-IDF / BM25
Relevance scoring: not all matches are equal.

TF (Term Frequency): how often does the term appear in this document? More occurrences = more relevant.

IDF (Inverse Document Frequency): how rare is the term across all documents? "the" appears everywhere — low IDF, low importance. "Kafka" appears rarely — high IDF, high importance.

BM25: modern improvement over TF-IDF used by Elasticsearch. Prevents very long documents from dominating just because they mention a term more times. Elasticsearch uses BM25 by default. You can boost specific fields (title matches worth 3x body matches).

00 · Core Intuition

Why a database cannot do what a search engine does

A SQL database index finds exact values fast: WHERE user_id = 123. But WHERE body LIKE '%distributed systems%' requires a full table scan — every row, every time. At 1 billion documents, that takes minutes. A search engine can answer this in milliseconds because it inverts the problem entirely.

The book index analogy
A database is a book read cover-to-cover to find a word. Slow.

A search engine is a book with an index at the back: "distributed systems → pages 12, 47, 203, 891." You go directly to those pages. That back-of-book index is an inverted index — and it is the entire secret of how search works.
02 · Elasticsearch Architecture

How ES scales to billions of documents

Index → Shards
An Elasticsearch index is split into N primary shards. Each shard is a complete, independent Lucene index.
Index "tweets" with 5 shards: each shard holds ~20% of documents. Queries fan out to all 5 shards in parallel, results merged by the coordinator. ⚠ Shard count is set at creation and cannot be changed (except via reindex). Over-sharding (too many small shards) is as harmful as under-sharding (too few large ones). Rule of thumb: aim for 10–50GB per shard.
Replication
Each primary shard has N replica shards on different nodes.
Writes: go to primary, primary replicates to replicas.
Reads: can be served by primary or any replica — distributes read load.
Node failure: replica promoted to primary automatically. ✓ Replicas both provide HA and increase read throughput. 5 shards × 2 replicas = 15 Lucene indexes total across the cluster.
Near Real-Time
(NRT) Search
Newly indexed documents are searchable within ~1 second, not immediately.
Lucene writes to an in-memory buffer → every 1 second, refreshed to a new segment (searchable) → eventually merged into larger segments. This is why Elasticsearch is "near real-time" not "real-time." To force immediate visibility: ?refresh=true on indexing — forces a refresh but hurts write throughput. Only use for critical flows.
Lucene Segments
Lucene (the underlying library) writes data in immutable segments.
New documents → write buffer → periodic flush → new immutable segment. Background merges combine small segments into larger ones (like Cassandra SSTables, like ClickHouse parts). Deletes are soft-deletes (marked, not removed) until a merge happens. This is why delete-heavy workloads require periodic forced merges to reclaim space.
03 · Typeahead / Autocomplete

Design: search-as-you-type at FAANG scale

Prefix Trie
A tree where each node is a character. Every path from root to leaf is a word. O(L) lookup for a prefix of length L — regardless of vocabulary size.
To find all words starting with "redis": traverse to node 'r'→'e'→'d'→'i'→'s', return all words in subtree. ✓ Fast prefix lookup. Memory-efficient with shared prefixes. Used by: Google Suggest backend, IDE autocomplete. ⚠ Storing popularity scores in a trie and returning top-K results requires augmenting each node with a max-heap — complex. Sharding a trie across machines is non-trivial.
Elasticsearch
Completion Suggester
Built-in completion suggester using an in-memory FST (Finite State Transducer) — more memory-efficient than a trie.
Index time: store completion field with weight (popularity score).
Query: suggest: {prefix: "red", field: "title.completion", size: 5}
Returns top-5 completions by weight instantly. ✓ Easy to implement on top of existing ES infrastructure. Handles millions of suggestions in milliseconds.
Redis ZSET Approach
Store all prefixes as ZSET members scored by popularity. For "redis", store "r", "re", "red", "redi", "redis" all pointing to the suggestion with its popularity score.
ZRANGEBYLEX suggestions "[redis" "[redisÿ" LIMIT 0 5 ✓ Extremely fast (sub-ms). Works well for known vocabulary (hashtags, product names). Easy to update popularity in real time with ZINCRBY. ⚠ Storage: O(L × V) where L is avg word length and V is vocabulary size. For a 10M-word vocabulary, this becomes large.
04 · System Design Examples

Search Architecture in Real Systems

Twitter Search
500M TWEETS/DAY
WRITE PATH
New tweet → Kafka → Indexing Service → Elasticsearch. The Kafka buffer decouples tweet volume from ES indexing rate. ES indexes ~6K tweets/sec sustained. NRT lag: ~1 second before searchable.
SEARCH
Elasticsearch ✓ Full-text BM25 scoring + recency boost + engagement boost. Query rewriting: "from:elonmusk" → field-specific filter. Hashtag search: exact term match on the hashtag field (no tokenization).
TRENDING
Trending hashtags NOT from ES — from a streaming Count-Min Sketch pipeline (Kafka + Flink + Redis ZSET). ES is too slow for trending (requires aggregation queries). The two systems complement each other.
WHY NOT SQL
LIKE '%distributed%' on 500M tweets = full table scan = minutes. Elasticsearch full-text search on same data = milliseconds. Not even close.
05 · More System Design Examples

Search architecture in Uber, LinkedIn, and GitHub

Uber — Driver and Restaurant Search
GEO-SPATIAL · REAL-TIME
GEO INDEX
Uber stores driver locations in a geospatial index. S2 cells (Google's geo library) divide the world into hierarchical cells. Finding drivers within 2km of a rider = find all occupied S2 cells at the appropriate level within radius. Elasticsearch's geo_point field type with geo_distance query handles this natively.
REAL-TIME UPDATE
Driver positions update every 4 seconds via WebSocket. Writes go to a Redis Geo hash (GEOADD) for the hot, live view. Elasticsearch index updated async for the search layer. Two stores: Redis for real-time dispatch, Elasticsearch for search/analytics.
RESTAURANT SEARCH
Uber Eats: full-text BM25 on restaurant name + cuisine tags + menu items. Geo filter applied first (only restaurants within delivery range). Ranked by: rating, estimated delivery time, sponsored placement (business rules layer), and personalisation (user's order history).
LinkedIn — People and Job Search
PERSONALISED · SOCIAL GRAPH
PEOPLE SEARCH
LinkedIn's Galene search engine (Elasticsearch-based): indexes 900M+ member profiles. Query "data scientist in Bangalore" → BM25 retrieval → ML re-ranking using network distance (1st/2nd degree connections ranked higher), engagement prediction, and profile completeness score.
JOB SEARCH
Semantic matching: your profile embedding (skills, title, experience) is compared to job embedding using cosine similarity (vector search). Keyword match + semantic similarity combined (hybrid search). Jobs at companies where you have connections get a boost.
TYPEAHEAD
Job title suggestions: Redis ZSET with ~50K common job titles, scored by global frequency. Prefix query on typed characters returns top 5 suggestions in <5ms. Personalised layer re-ranks suggestions based on user's profile and connections.
04 · Search Ranking

How search results are ordered — beyond BM25

Multi-Stage Ranking
Modern search uses a pipeline: cheap retrieval first, expensive re-ranking after.
Stage 1 — Recall: BM25/inverted index retrieves top 10,000 candidates. Fast, cheap.
Stage 2 — Re-rank: ML model (LambdaMART, BERT-based) scores the top 1,000. Considers personalisation, freshness, engagement signals.
Stage 3 — Business rules: Apply boosts (promoted listings), filters (safety), and diversity rules (not all results from same author). Why multi-stage: running a BERT model on 10M documents per query is too slow. Run it on 1,000 pre-filtered candidates → acceptable latency.
Relevance Signals
Beyond term frequency, production search incorporates:

Query-document signals: BM25 score, field match (title match worth 3x body match), exact phrase match bonus.

Document-level signals: freshness (newer content boosted), authority (PageRank-style link graph), engagement (CTR, dwell time, shares).

Personalisation: user's past clicks, location, language, search history. Elasticsearch Rescore API: retrieve top 10K by BM25, rescore top 500 with a more expensive function. Balances speed and quality.

Faceted Search
Filter and aggregate search results by multiple dimensions simultaneously — the e-commerce standard.
Query: "laptop" → results filtered by brand (Apple/Dell/HP), RAM (8GB/16GB/32GB), price range. Counts shown per facet: "Apple (234), Dell (189)..."
Elasticsearch implementation: use aggregations alongside the query. One request returns both the matched documents AND the facet counts. No separate aggregation query needed. ✓ Helps users narrow results without reformulating queries. Amazon, Flipkart, Zalando — all use faceted search as the primary product discovery interface.
05 · Follow-ups

Every hard follow-up, answered

How do you keep Elasticsearch in sync with your primary database?+
Two patterns, with very different trade-offs:

1. Dual write: Application writes to DB AND ES in the same request. Simple but dangerous — if ES write fails, you have inconsistency with no way to detect it. Acceptable only for non-critical search.

2. Change Data Capture (CDC): Debezium (or similar) reads the PostgreSQL WAL (Write-Ahead Log) and publishes every change to Kafka. An ES indexing consumer reads from Kafka and keeps ES in sync. This is the production approach:
— Source of truth is always the DB
— ES is an eventually consistent read replica
— On ES failure, reindex from DB
— Typical lag: 100ms–2s

Tools: Debezium + Kafka + Elasticsearch Kafka Connector. Used by: LinkedIn, Airbnb, Shopify.
What is vector search and when do you need it?+
Vector search finds documents semantically similar to a query, not just exact keyword matches.

Classic inverted index search for "fast database" would not return a document about "high-performance data store" — different words, even if same meaning. Vector search uses ML embeddings (e.g., OpenAI text-embedding-ada-002) to convert both query and documents to dense vectors in the same semantic space. Documents near the query vector in that space are semantically similar.

Implementation: index document embeddings in a vector database (Pinecone, Weaviate, Milvus, or Elasticsearch with kNN). Query: embed the query text → find K nearest neighbours using approximate nearest neighbour (HNSW algorithm).

When to use: semantic search ("show me articles about making databases fast"), recommendation ("more content like this"), Q&A (RAG — Retrieval Augmented Generation for LLMs).

Hybrid search: combine keyword BM25 + vector KNN scores (Reciprocal Rank Fusion). Best of both worlds — used by production AI search systems.
How do search engines handle spelling mistakes — "gogle" instead of "google"?+
Three techniques, typically combined:

1. Edit distance (Levenshtein): for each query term, find indexed terms within edit distance 2 (2 character insertions/deletions/substitutions). "gogle" is distance 1 from "google." Return results for the nearest match. Elasticsearch has a fuzziness parameter that does this automatically.

2. N-gram index: at index time, break "google" into trigrams: [goo, oog, ogl, gle]. Index each trigram. At query time, break "gogle" into [gog, ogl, gle]. Overlap of 2 trigrams → likely a match. Faster than edit distance for large indexes.

3. Query rewriting with spell checker: maintain a dictionary of correct terms with frequencies. For each query term not in dictionary, suggest the closest term. "Did you mean: google?" Google famously implemented this with a neural spell checker trained on query logs — "what users typed → what they actually meant."

Production approach: use Elasticsearch's built-in fuzzy matching for simple cases. For high-traffic queries, maintain a learned correction model trained on click-through data (if users click the 2nd result for query X, X was likely a misspelling of result 2's title).
How do you keep search results fresh when new content is added every second?+
Elasticsearch's NRT (Near Real-Time) makes documents searchable within ~1 second of indexing — usually sufficient. For truly real-time requirements, different approaches are needed.

Standard NRT path: write to ES → in-memory buffer → refresh every 1s → new segment → searchable. For most use cases (news articles, tweets), 1-second lag is imperceptible.

For sub-second freshness (stock prices, live sports scores): do not use ES for the hot data. Use Redis Sorted Sets or a dedicated real-time index (Druid) for the last few minutes. ES handles historical data. The search UI blends real-time results (from Redis) with historical results (from ES).

Index update strategy: full reindex (expensive, for schema changes), partial update via Update API (efficient for changing specific fields), delete + reindex (for major changes to a document). Avoid full reindexes for high-traffic indexes during peak hours — they consume significant I/O.
09 · Vector Search & ML Ranking

Beyond keyword matching — the AI layer modern search requires

01 Vector Embeddings for Semantic Search
What it is
Convert text to dense vectors. Find semantically similar documents even without keyword overlap.

/p>

Query "cheap flights to goa" → embed with text-embedding-3-small → 1536-dimensional vector [0.23, -0.91, ...]. Documents in the index also embedded at index time. Find documents whose embedding is cosine-closest to the query embedding. Returns results about "affordable airfare Goa" even with zero keyword overlap.

Index: FAISS (Facebook AI Similarity Search), pgvector (PostgreSQL extension), Pinecone, Weaviate, or Elasticsearch's dense_vector field. All support approximate nearest neighbour (ANN) with HNSW index. O(log N) search over billions of vectors.

✓✓ Hybrid search: combine BM25 (keyword) score + vector similarity score with a weighted sum. BM25 wins for exact product codes and names. Vectors win for semantic and intent-based queries. LinkedIn People Search, Notion AI Search, and Google Shopping all use hybrid.
02 Multi-Stage Ranking Pipeline
What it is
Narrow from billions to thousands (retrieval) → score thousands (ranking) → rerank top-100 (re-ranking).

/p>

Stage 1 — Retrieval: BM25 or ANN vector search. Fast, approximate. Returns 1,000 candidates from billions of documents in <50ms.

Stage 2 — Ranking: ML model (gradient boosted trees or a small neural net) scores each candidate on: relevance signals (BM25 score, vector score, freshness), behavioural signals (CTR for this query, dwell time, position bias-corrected), personalisation (user's historical preferences). Scores 1,000 candidates in <100ms.

Stage 3 — Re-ranking: large cross-encoder model (BERT-based) scores top-100 pairs (query, document) together — captures deep semantic interaction. Expensive but only for 100 items. Runs in <200ms on GPU.

Total pipeline: 350ms. Parallelise stages 1+2, run stage 3 on stage 2 top-100.

03 Index Freshness Strategies
What it is
How fast do new documents appear in search results? The answer changes the architecture.

/p>

Batch indexing: rebuild the full index nightly. Freshness: 24h lag. Simple. Right for: product catalogs with daily updates, static content.

Near-real-time (NRT): Elasticsearch refreshes the in-memory index segment every 1 second (index.refresh_interval=1s). New documents visible in 1 second. Default Elasticsearch behaviour. Right for: most applications.

Real-time: Elasticsearch with refresh=true on write (forces immediate segment refresh). Visible immediately. Cost: 10–100× more write overhead. Right for: financial transactions, legal documents where freshness is critical.

Dual-index: a large, rarely-updated "base index" + a small, frequently-updated "delta index." Merge results at query time. Right for: trillion-document indexes where full daily rebuilds take days.

Requirements & Non-Functional Constraints

Functional Requirements

FR1Full-text search with relevance ranking (BM25 + ML signals)
FR2Faceted search: filter by category, price range, date
FR3Autocomplete: type-ahead suggestions in < 100ms
FR4Fuzzy matching: tolerate typos ("gogle" → "google results")
FR5Vector/semantic search: find conceptually similar results
FR6Near-real-time indexing: new content searchable in < 2s

Non-Functional Requirements

NFR1Search latency: p99 < 200ms for full-text queries
NFR2Index size: supports billions of documents
NFR3Write throughput: 10K documents/sec (Elasticsearch NRT)
NFR4Availability: 99.9% (Elasticsearch cluster: 3+ nodes)
NFR5Freshness: Elasticsearch refresh_interval = 1s (NRT)
NFR6Recall: > 95% for navigational queries; precision > 90%
