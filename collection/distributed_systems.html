00 · CAP Theorem

The fundamental constraint every distributed system lives with

CAP theorem states that a distributed system can guarantee at most two of: Consistency, Availability, and Partition Tolerance. Since network partitions are inevitable in any real distributed system, the practical choice is always CP vs AP — you are choosing what to sacrifice during a network partition.

CAP as a bank branch analogy
Two bank branches connected by a telephone line. The line goes down (partition).

CP — Consistency + Partition Tolerance: Both branches close to customers until the line is restored. No one gets incorrect balance info, but service is unavailable during the outage.

AP — Availability + Partition Tolerance: Both branches stay open, serving customers independently. Service stays up. But when the line is restored, one branch shows ₹50,000 and the other ₹72,000 for the same account — they need to reconcile.

The question is: would you rather return an error, or return potentially stale data? Both are wrong — the choice is about which kind of wrong is less harmful to your users.
PACELC Extension
CAP only describes partition behaviour. PACELC adds the normal-operation trade-off.
P → A vs C (partition: choose availability or consistency)
E → L vs C (else: choose latency or consistency)
Even without partitions, you must decide: serve reads from the nearest replica (low latency, possibly stale) or always read from primary (consistent, higher latency). DynamoDB: PA/EL — available during partition, low latency normally (reads from local region).
HBase: PC/EC — consistent during partition (stops accepting writes), consistent normally (always read from primary).
Cassandra: PA/EL by default — configurable per operation via consistency level.
Linearisability
The strongest consistency model. Every operation appears to happen instantaneously at a single point in time, visible to all nodes simultaneously.
If write(X=1) completes before read(X) starts, read must return 1 — not a previous value, even from a stale replica. ✓ System behaves as if running on a single machine. No surprises. Required for: distributed locks, financial transactions, leader election, inventory decrement. ⚠ Requires consensus (Raft/Paxos round trip) on every write. High latency. Cannot scale across geographies without extremely high write latency (speed of light constraints).
Eventual Consistency
If no new updates are made, all replicas will eventually converge to the same value. Reads during convergence may return stale data.
Convergence window: typically milliseconds to seconds in practice (not hours as the name might imply). ✓ Highest availability and lowest latency. Scales globally with no cross-region coordination. Used by: DNS, CDN caches, social feed reads, product descriptions, shopping carts. ⚠ Applications must handle stale reads gracefully. Concurrent writes to the same key create conflicts — need resolution strategy: Last Write Wins (LWW), CRDTs, or application-level merge.
Quorum Reads/Writes
Configurable consistency between linearisable and eventual: require acknowledgement from W of N write replicas, and read from R of N read replicas.
Strong consistency condition: W + R > N (read and write quorums overlap).
Example: N=3, W=2, R=2 → W+R=4 > 3 → any read will see the latest write.
Example: N=3, W=1, R=1 → W+R=2 ≤ 3 → eventual consistency (reads may miss latest write). Cassandra: QUORUM = ceiling(N/2)+1. LOCAL_QUORUM = quorum within one DC only (lower latency). ALL = all N replicas (linearisable but fails if any replica is down).
01 · Consensus — Raft

How distributed systems agree on a single truth without a central coordinator

The Problem
5 nodes must agree on the value of X despite any 2 nodes being down or sending wrong values.
Without consensus: node A believes X=1, node B believes X=2, node C is unreachable. What is the correct answer? Who breaks the tie? How do you ensure a decision made today is honoured after a crash and restart? Consensus is what makes etcd, ZooKeeper, Kafka (KRaft), and CockroachDB reliable — it is the foundation every distributed database is built on.
Raft — Leader Election
Raft elects exactly one leader at a time. All writes go through the leader. Followers only accept log entries from the current leader.
Startup: all nodes start as followers with a random election timeout (150–300ms). First node to time out becomes a candidate, increments term counter, requests votes from all nodes. First to receive majority (N/2+1) becomes leader — sends heartbeats to suppress new elections.
Leader failure: followers stop receiving heartbeats → timeout → new election → new leader. Takes 150–600ms in practice. ✓ At most one leader per term. Clear authority. Simple mental model. Used by: etcd (Kubernetes), CockroachDB, TiKV, Kafka (KRaft), Consul.
Raft — Log Replication
Every write is appended to the leader's log as an entry. Leader replicates to all followers. Entry is committed when a majority acknowledges it.
Flow: client write → leader appends entry → sends AppendEntries RPC to all followers → majority acknowledge → leader commits → applies to state machine → responds to client → followers commit on next AppendEntries.
Committed = durable. Even if the leader immediately crashes, the entry will be present on a majority of nodes and any new leader will have it. ✓ Exactly how Kafka replication works (ISR). How etcd stores Kubernetes cluster state. How CockroachDB achieves ACID transactions across nodes.
Raft vs Paxos
Paxos is theoretically equivalent but notoriously difficult to understand and implement correctly.
Raft was designed explicitly for understandability — the original paper's subtitle is "In Search of an Understandable Consensus Algorithm." Raft makes stronger design choices (single strong leader, log matching) that simplify implementation at the cost of some theoretical flexibility. In interviews: always say Raft. You can explain it end-to-end. Paxos is of historical significance but Raft has replaced it in essentially all new distributed systems. Multi-Paxos (used in Chubby) is even more complex.
02 · Distributed Transactions

2PC, Saga pattern, and when to use each

Two-Phase Commit
(2PC)
A coordinator asks all participants to prepare, then commits only if all vote yes.
Phase 1 (Prepare): Coordinator sends "can you commit?" to all participants. Each participant: locks resources, writes prepare record to WAL, votes yes/no.
Phase 2 (Commit/Abort): If all voted yes → send commit to all. Any voted no → send abort to all. Participants release locks. ✓ True ACID atomicity across multiple databases. All commit or none do. ⚠ Blocking protocol: if coordinator crashes after Phase 1, participants hold locks indefinitely. Tight coupling — all participants must be available. 2 round trips minimum. Used in: PostgreSQL distributed (XA), Oracle, MySQL XA. Never use across microservice boundaries.
Saga Pattern
Decompose a distributed transaction into local transactions, each with a compensating transaction to undo on failure.
Order saga: (1) Reserve inventory → (2) Charge payment → (3) Create shipment → (4) Send confirmation.
If step 3 fails: compensating transactions run in reverse — cancel shipment (no-op) → refund payment → release inventory. ✓ No distributed locks. Services remain autonomous. Failures handled by compensation. The correct pattern for microservices. Eventually consistent — other services may see intermediate states. ⚠ Compensation logic must be idempotent and durable. Other services see partially-committed state during execution. Complex to reason about ordering. Requires careful saga state management.
Choreography vs
Orchestration Saga
Two implementation styles for Saga — fundamentally different operational characteristics.

Choreography: each service publishes an event after completing its step. The next service listens for the event and acts. No central coordinator. Services communicate through events (Kafka).
Problem: hard to debug. "Where is my order?" requires tracing events across multiple services and queues.

Orchestration: a saga orchestrator (Temporal, AWS Step Functions, a dedicated service) explicitly calls each step and decides what to do on failure. ✓ Orchestration is easier to monitor, debug, and reason about. The orchestrator maintains full saga state. Temporal.io is the modern standard for saga orchestration.

Idempotency
An operation that produces the same result whether executed once or many times.
Critical because: network failures cause retries, message queues deliver at-least-once, and saga compensation steps may run multiple times if they fail mid-way.
Implementation: client includes a unique idempotency_key per operation. Server stores (idempotency_key → result) in DB. On duplicate: return stored result without re-executing.
Database pattern: INSERT INTO orders ... ON CONFLICT (idempotency_key) DO NOTHING — atomic, no need for an explicit lookup first. ✓ Safe retries under any failure scenario. Stripe, PayPal, Twilio all require idempotency keys on mutating API calls.
03 · Distributed Locking

Redlock, etcd, and the fencing token pattern

Redis SETNX Lock
Simple distributed lock: SET key value NX EX ttl.
Acquire: SET lock:resource unique_id NX EX 30 — NX = only if not exists, EX 30 = auto-expire in 30s.
Release (atomic via Lua): check owner then delete: if GET(key) == unique_id then DEL(key). ✓ Works correctly with a single Redis instance. Simple, fast (<1ms). Adequate for most use cases where brief lock loss on Redis failure is acceptable. ⚠ Single Redis node = single point of failure. If Redis crashes between SETNX and EXPIRE (in older implementations): lock held forever. Use the atomic SET NX EX single command to avoid this.
Redlock Algorithm
Acquire lock on majority (3 of 5) independent Redis nodes.
Steps: (1) Record start time. (2) Sequentially try to acquire lock on all 5 independent Redis nodes with small timeout (5ms each). (3) Lock acquired if: ≥3 nodes succeeded AND total elapsed time < lock TTL minus clock drift margin. (4) On failure: release lock on all nodes. ✓ Survives failure of 2 of 5 Redis nodes. No single point of failure. ⚠ Martin Kleppmann published a critique: GC pauses and clock skew can cause two clients to both believe they hold the lock. For truly critical systems (financial, coordination): use etcd/ZooKeeper with fencing tokens.
Fencing Tokens
Every time a lock is granted, issue a monotonically increasing fencing token. The protected resource rejects writes with older tokens.
Client A acquires lock, gets token=33. Client A pauses (GC). Lock expires. Client B acquires lock, gets token=34. Client A resumes, sends write with token=33. Storage rejects it: "I've already seen token=34." ✓ Correct under all failure scenarios including GC pauses, clock skew, and slow networks. The only fully safe distributed locking pattern. etcd provides this natively: each lease has a revision number. Store systems like S3 conditionally (ETag + If-Match) and databases with optimistic locking implement the same pattern.
etcd / ZooKeeper
CP systems built on Raft consensus — correct distributed locking under all failure scenarios.
etcd: PUT /locks/resource?prevExist=false with a lease TTL. Raft ensures only one leader can grant the lock cluster-wide. Linearisable reads guarantee no stale state.
ZooKeeper: ephemeral znodes — the lock is an ephemeral node. If the lock holder's session expires (crash), ZooKeeper automatically deletes the ephemeral node, releasing the lock. ✓ Correct under all scenarios. Used by: Kubernetes leader election (etcd), distributed job schedulers, Kafka broker coordination (ZooKeeper historically, now KRaft). ⚠ Higher latency than Redis (Raft round trip = 5–10ms). Operational complexity of running a Raft cluster.
04 · Clocks & Ordering

Why you cannot trust wall-clock timestamps in distributed systems

Clock Skew
Servers in different data centres have different clocks, even with NTP. Typical skew: 1–100ms. Worst case: seconds.
Server A timestamps event at 14:00:01.000. Server B timestamps its event at 14:00:00.998. B appears to have happened first — but it actually happened after A's event. ⚠ Never use wall-clock timestamps for causal ordering. "Last Write Wins" based on timestamps will silently discard correct writes when clocks are skewed. Cassandra's LWW uses this — it works in practice because NTP skew is usually small, but it is theoretically unsound.
Lamport Clocks
Logical clock: a counter that captures "happened-before" relationships without requiring synchronised clocks.
Rules: (1) Increment counter on every local event. (2) When sending a message, include current counter. (3) On receiving a message with counter C: set local counter to max(local, C) + 1.
Guarantee: if event A happened-before event B (causally), then Lamport(A) < Lamport(B). But the converse is not true — two events with comparable Lamport times might not be causally related. Used by: Cassandra timestamps (wall clock + client-side Lamport), logical replication in PostgreSQL.
Vector Clocks
One Lamport counter per node. Captures causality and detects concurrent events precisely.
Node A: [A:2, B:1, C:0]. A sends message to B. B updates to [A:2, B:2, C:0].
Compare two events: if every element of clock1 ≤ clock2 and any element is strictly less, clock1 happened-before clock2. If neither dominates the other: they are concurrent (a conflict). ✓ Detects concurrent writes precisely. Amazon Dynamo original paper used vector clocks for shopping cart conflict detection. Riak database uses them. ⚠ Vector size grows with number of nodes. Conflict resolution still needs application logic (merge, user choice, or CRDT).
CRDTs
Conflict-free Replicated Data Types: data structures that can be merged from any two replicas without conflict, by design.
G-Counter (grow-only): each node has its own counter. Merge = take max of each node's counter. Sum = total across all nodes. Concurrent increments on different nodes are automatically merged correctly.
PN-Counter (positive-negative): two G-counters. Supports increment and decrement. Used for: like counts, view counts, inventory.
OR-Set: add-wins set. Can add and remove elements concurrently — add wins on conflict. ✓ No coordination needed for merging. Perfect for: shared documents (Google Docs uses CRDT-like structures), distributed counters, real-time collaboration. Used by: Riak, Redis (some data types), Apple Notes.
05 · System Design Examples

Distributed systems patterns in real production systems

Kubernetes — etcd as the Brain
CP · RAFT · LINEARISABLE
WHAT etcd STORES
All cluster state: which pods are running on which nodes, service definitions, config maps, secrets, RBAC rules. etcd is a CP system — during a partition, it stops accepting writes rather than risk divergent cluster state.
LEADER ELECTION
Only one API server writes to etcd at a time (via Raft). kube-controller-manager and kube-scheduler use etcd-backed leases for leader election — only the leader instance processes changes. etcd's fencing token (revision number) prevents stale leaders from writing.
WHY NOT AP
If Kubernetes used an AP datastore and two controller-manager replicas disagreed about cluster state during a partition, they'd both try to schedule pods — creating duplicate deployments, split-brain scheduling, or conflicting resource allocation. CP is the only safe choice for infrastructure coordination.
Food Delivery App — Order Saga
SAGA PATTERN · TEMPORAL
SAGA STEPS
(1) Create order record → (2) Reserve restaurant slot → (3) Charge customer → (4) Assign delivery partner → (5) Notify customer. Each step is a local transaction. Each has a compensating transaction.
FAILURE AT STEP 3
Payment fails. Compensating transactions: cancel restaurant reservation (step 2 compensation) → mark order as failed (step 1 compensation). Customer sees "payment failed" immediately. No money was charged. Restaurant slot is freed. Delivery partner was never assigned — no compensation needed.
ORCHESTRATION
Temporal workflow manages the saga state durably. Each step is a Temporal activity. If the Temporal worker crashes mid-saga, it resumes from the last completed step on restart. The saga state is stored in Temporal's backend database. No lost orders, no orphaned state.
EVENTUAL CONSISTENCY
Between step 2 (restaurant reserved) and step 3 (payment charged), the restaurant service sees a reservation that might get cancelled. This intermediate state is visible. The restaurant app must handle "pending" states gracefully — not assume all reservations become confirmed orders.
Google Spanner — Globally Linearisable
CP · TRUETIME · GLOBAL
TRUETIME
GPS + atomic clocks provide bounded time uncertainty: current time is somewhere in interval [earliest, latest]. Uncertainty typically 7ms. Spanner waits out this uncertainty window before committing — ensures all nodes agree on transaction ordering without a Raft round trip per write.
LINEARISABLE GLOBALLY
A transaction committed in Singapore is immediately visible to a read in Frankfurt — even though those data centres are separated by 150ms of latency. Spanner achieves this by assigning commit timestamps from TrueTime and delaying reads until their timestamp is safely in the past.
REPLICATION
WHY UNIQUE
You cannot replicate Spanner without GPS/atomic clock hardware. CockroachDB approximates it with NTP (larger uncertainty window, uses Raft where Spanner uses TrueTime). For your system design: use Spanner for truly global ACID at the cost of 7ms commit latency. Use CockroachDB as an open-source alternative.
06 · Follow-ups

Every hard follow-up, answered

How does split-brain happen and how do you prevent it?+
Split-brain: a network partition causes two groups of nodes to both believe they are the active primary, leading to divergent writes and data corruption.

Example: 6-node cluster, partition splits into group of 4 and group of 2. Both groups try to elect a leader. Both succeed (within their own group). Both accept writes. When partition heals: two divergent histories, conflicting data.

Prevention:
1. Quorum writes: require majority (N/2+1) acknowledgement. The minority partition (2 nodes) cannot achieve quorum and stops accepting writes. Only the majority (4 nodes) proceeds. Raft enforces this automatically.

2. Fencing tokens: new leader gets a higher epoch/term number. Old leader's writes are rejected by storage systems that have seen the higher epoch.

3. Witness nodes: a lightweight tiebreaker node with no data — only votes. 2-node cluster → add a 3rd witness. Split 1+1+witness: majority requires 2 votes. Used by: SQL Server Availability Groups, some Cassandra configurations.
What is the difference between linearisability and serializability?+
They solve different problems at different granularities — commonly confused in interviews.

Linearisability: applies to single operations on individual keys. Every read/write appears to happen atomically at a single point in time, globally visible. "If you write X=1 and then I read X, I must see 1." A property of the key's operation history.

Serializability: applies to transactions (groups of operations across potentially many keys). The result of concurrent transactions is equivalent to some serial execution order. "My multi-step bank transfer looks as if no other transaction interleaved with it." A property of the database's transaction isolation.

Strict Serializability (= Linearisable + Serializable): transactions are both serialised AND appear instantaneous. The gold standard. Spanner and CockroachDB provide this globally. Most expensive guarantee, but the one you want for financial systems.

Common systems: PostgreSQL SERIALIZABLE isolation is serializable but not linearisable (a replica read can be stale). Spanner is strictly serializable. Cassandra with QUORUM is neither (it provides tunable consistency, not transactions).
How do you handle the compensating transaction failing in a Saga?+
Compensating transactions must be idempotent and retried with exponential backoff until they succeed. They should never be allowed to permanently fail.

Make compensating transactions idempotent: "cancel reservation for order X" executed twice should have the same effect as once (the second execution finds the reservation already cancelled — this is success, not an error).

Retry strategy: persistent retry queue (Kafka DLQ or dedicated retry table in DB). Each failed compensation attempt is re-enqueued with exponential backoff (1s, 2s, 4s, 8s...) and a max retry count.

What if compensation is permanently impossible? Example: payment refund fails because customer's card is closed. This is a "business exception" — not a technical failure. Route to a manual operations queue. Ops team handles it (alternative refund method, store credit, etc.). This is expected in production at large scale — Saga frameworks like Temporal provide a UI for exactly this: paused sagas requiring human intervention.

Design principle: compensation must always eventually succeed or escalate to human handling. Never silently drop a failed compensation — that leaves orphaned state in your system.
How does Cassandra handle concurrent writes to the same key?+
Cassandra uses Last Write Wins (LWW) — the write with the highest timestamp wins. This is correct most of the time but has known edge cases.

Two concurrent writes to the same key from different nodes: write A has timestamp 14:00:01.000, write B has timestamp 14:00:00.998 (clock skewed). Write A wins — it has the higher timestamp. Write B is silently discarded, even though B might have been the "correct" or "intended" final value from the application's perspective.

Why Cassandra accepts this tradeoff: NTP clock skew is typically <1ms on modern hardware. The probability of two writes in the same millisecond to the same key is very low for most workloads. And Cassandra is optimised for write-heavy, high-scale workloads where this tradeoff (very rare silent overwrites vs guaranteed write availability) is acceptable.

When it is not acceptable: financial data, counters (use Cassandra counters with conditional updates), any data where silent overwrites are unacceptable. For these: use CAS (Compare-And-Set with Lightweight Transactions) which uses Paxos for coordination — but at 4x the latency cost.

Consistency Model Decision Tree

🎯Which Consistency Model for Your System?
01
Can your users tolerate seeing stale data (even briefly)?
NO — must be fresh →Strong consistency (CP). Every read reflects the latest write. Use: financial balances, inventory counts, seat reservations. Tools: PostgreSQL, CockroachDB, Spanner. Accept higher latency and reduced availability during partitions.
YES — staleness OK →Go to Step 2. Eventual consistency is viable.
02
What is the acceptable staleness window?
Seconds OK →Eventual consistency with read-your-own-writes. Social feeds, product pages, user profiles. DynamoDB (eventually consistent reads), Cassandra (ONE consistency). Add read-your-own-writes: route user's reads to primary for 5s after any write they made.
Minutes OK →Pure eventual consistency. Analytics dashboards, recommendation engines, search indexes. Cassandra ONE, DynamoDB eventuallyConsistent. Maximum availability and lowest latency.
03
Do you need cross-shard / cross-service transactions?
YES — multi-entity atomic →Saga pattern for microservices. Each step is a local transaction with a compensating transaction on failure. Never use 2PC in microservices — it creates distributed locks that block on coordinator failure.
NO — single entity →Single-node transaction or single-shard operation. Design your data model so related data lives on the same shard. Avoid cross-shard operations in the hot path.
07 · Advanced Topics

CRDTs, gossip protocols, and Merkle trees — the mechanisms behind eventual consistency

CRDTs
(Conflict-Free Replicated Data Types)
Data structures that can be updated concurrently on multiple replicas and merged without conflicts.
The key property: merge is commutative, associative, and idempotent. Any order of merging gives the same result. No coordinator needed. No locks. Automatically eventually consistent.

G-Counter (Grow-only Counter): each replica has its own counter. Value = SUM of all replica counters. Increment: only increment your own replica's counter. Merge: take MAX of each replica's counter. Like counts, view counts — never need to decrement. Example: Redis HLL is a CRDT.

LWW-Register (Last-Write-Wins): each write tagged with a timestamp. On merge: keep the value with the larger timestamp. Risk: clock skew can cause causally-earlier writes to win. Used by: Cassandra's default conflict resolution, AWS DynamoDB.

OR-Set (Observed-Remove Set): supports add AND remove without conflicts. Each element tagged with a unique token on add. Remove removes the specific token. Merge: union of all add-tokens, remove any element whose token was removed. Used by: Riak for shopping cart (add/remove items without coordination). ✓ CRDTs power: Redis HyperLogLog (approximate unique count), Riak (distributed key-value), distributed collaborative text editing (Logoot, LSEQ), real-time collaborative applications (Notion uses CRDTs for concurrent editing).

Gossip Protocol
Epidemic information propagation: each node periodically shares state with a few random peers. Information spreads through the cluster without a central coordinator.
Cassandra gossip: every second, each node initiates a gossip round with 1–3 randomly selected peers. Shares: which nodes are alive/dead, ring membership, schema version, load. After N rounds (N ≈ log(cluster_size)): all nodes converge to the same view.
Convergence: with 100 nodes, each gossipping to 3 peers/second → entire cluster has consistent view within ~8 seconds (log₃(100) ≈ 4 rounds, each round ~2 seconds). ✓ Used by: Cassandra (cluster membership), Redis Cluster (node state propagation), Kubernetes (Serf-based gossip for cluster membership in etcd alternatives), AWS DynamoDB (ring membership). Gossip is O(log N) convergence with no single point of failure.
Anti-Entropy &
Merkle Tree Repair
Cassandra detects which data diverged between replicas using Merkle trees, then repairs only the divergent ranges.
Each replica builds a Merkle tree over its token range. The root hash represents the entire data set. Exchange root hashes: if identical → no repair needed. If different → compare child hashes, recursively narrow down the divergent token ranges. Repair only the divergent ranges by reading the correct version from a quorum and writing it back.
Why this matters: comparing two 10TB replicas row-by-row would take hours and saturate the network. Merkle tree comparison requires O(log N) hash exchanges to identify divergent ranges, then targeted repairs. nodetool repair runs this automatically. ⚠ Cassandra without regular repair: over time, deleted data can re-appear (tombstones expire before repair). Run nodetool repair at least every gc_grace_seconds (default 10 days). In production: schedule repair weekly per keyspace.
Raft vs Paxos
Consensus Comparison
Both achieve consensus. Raft was designed to be understandable; Paxos is historically foundational.

Paxos: two phases — Prepare (elect a proposer) + Accept (propose a value). Multi-Paxos optimises by keeping the same leader for multiple rounds. Google Chubby uses Paxos. Complex to implement correctly — even Leslie Lamport acknowledged implementation subtleties.

Raft: designed as Paxos equivalent but more understandable. Three roles: Leader (one per term), Follower (accept entries from leader), Candidate (during election). Leader election, log replication, and safety are explicitly separated concerns. etcd, CockroachDB, TiKV all use Raft. ✓ In FAANG interviews: "I'd use etcd (Raft) for distributed coordination. Raft provides strong consistency (linearisable reads) with understandable failure semantics. For write throughput above what a single Raft group handles, I'd use Multi-Raft (partition data across Raft groups) as CockroachDB does."
