00 · Requirements

Start here — always. What are we actually building?

Interview opening

"Before I start, let me clarify the scope. Are we designing the core tweet + feed experience, or do I need to include DMs, trends, ads? I'll focus on: posting tweets, following users, and reading a personalised feed. Out of scope: search, trends, direct messages, ads."

Functional
Post a tweet (text + optional media). Follow/unfollow users. Read a personalised home feed (tweets from followed users, reverse chronological). Like and retweet. User profiles.
Non-Functional
300M DAU. Read-heavy: 300K reads/sec, 6K writes/sec (50:1 ratio). Feed load <200ms p99. Post tweet <500ms p99. High availability (99.99%). Eventual consistency acceptable for feed (a tweet appearing 1–2s late is OK).
Estimation
Tweets: 300M × 0.02 tweets/day = 6M tweets/day = 70 writes/sec. Feed reads: 300M × 1 feed load/day = 3,500 reads/sec (conservative). Storage: 6M tweets/day × 300 bytes = 1.8GB text/day = 660GB/year. Media: 50% of tweets have images, 200KB avg → 600GB media/day → need S3 + CDN.
01 · Architecture

The complete system — every component justified

Tweet Storage
PostgreSQL sharded by tweet_id (UUIDv7 — time-sortable).
Schema: tweets(id UUID, user_id BIGINT, content TEXT, media_urls TEXT[], created_at TIMESTAMPTZ, like_count INT, retweet_count INT). Index on user_id for "all tweets by user X." Sharded: 100 shards, each shard ≈ 7GB tweet text/year. Why PostgreSQL? Tweets are relational, we need ACID for like_count updates, and the volume is manageable with sharding.
Follow Graph
PostgreSQL table: follows(follower_id, followee_id, created_at).
Index on follower_id (who do I follow?) and followee_id (who follows me?). 300M users × avg 200 follows = 60B rows → needs sharding or a graph DB. Alternative: Redis SET per user (follows:user:123) for O(1) "do I follow X?" checks. DB is source of truth; Redis is read cache.
Feed Generation
The hardest part. Two approaches with different trade-offs:

Fan-out on Write (push): when user A posts, push to the feed of every follower. Store pre-computed feeds in Redis (feed:user:123 as a sorted set scored by timestamp).
✓ Feed read = single Redis lookup. Fast reads.
⚠ Celebrity problem: @elonmusk has 200M followers → 200M Redis writes per tweet. Impractical.

Fan-out on Read (pull): on feed request, fetch the last N tweets from each followed user. Merge and sort.
✓ No fan-out on write. No celebrity problem.
⚠ Feed read requires N DB queries (N = number of following). For users following 1K people: 1K DB queries per feed load. Slow.

Twitter's actual solution: Hybrid. Regular users: fan-out on write. Celebrities (>1M followers): fan-out on read at query time. Feed assembly merges: pre-computed Redis list + fresh celebrity tweets pulled from DB → sorted → returned.

Media Storage
Images/videos → S3. Never store in the DB.
Upload flow: client → pre-signed S3 URL (your server generates it) → client uploads directly to S3 → client notifies tweet service of S3 key → tweet stored with media_urls.
Serving: S3 → CloudFront CDN. Images served from PoP nearest to the user. p99 latency: <20ms for cached images globally.
Cache Layer
Three caches, each serving different purposes:
(1) Feed cache (Redis ZSET): pre-computed feeds for active users. Key: feed:user:123. 1,000 tweet IDs per user. ZREVRANGE returns top-20 tweet IDs in 1ms.
(2) Tweet content cache (Redis Hash): hot tweets (100K+ engagements) cached as JSON. 99% cache hit rate for viral tweets.
(3) User profile cache (Redis String): username, avatar, follower count. TTL=1h. Profile displayed on every tweet — must be fast.
02 · Deep Dive — Feed Generation

The complete feed assembly flow

Home Feed Request — Complete Flow
END-TO-END
STEP 1
GET /feed → API Gateway → Feed Service. Feed Service checks: is user's feed in Redis? ZREVRANGE feed:user:123 0 19. If populated (cache hit): get 20 tweet IDs. Elapsed: 1ms.
STEP 2
Enrich tweet IDs → batch fetch tweet content from Tweet cache (Redis Hash, HGETALL). Cache hit rate: 90% for recent tweets. Misses: fetch from PostgreSQL tweet shard by tweet_id. Elapsed: 5ms.
STEP 3
Fetch celebrity tweets (fan-out on read): check if any followed users are "celebrities" (follower count > 1M). For each celebrity: SELECT * FROM tweets WHERE user_id = X ORDER BY created_at DESC LIMIT 5. Merge with pre-computed feed, sort by timestamp. Elapsed: 30ms (3 celebrity DB queries in parallel).
STEP 4
Enrich with user profiles (avatars, names) from user profile cache. Return final feed JSON. Total elapsed: ~40ms. Well within 200ms SLA.
03 · Follow-ups

The questions your interviewer will ask

How do you handle the "hotkey" problem for Elon Musk's tweets?+
The problem: @elonmusk tweets → 200M followers → 200M simultaneous feed update requests → your Redis and DB cannot handle this write storm.

Solution (hybrid fan-out):
1. Celebrity tweets are NOT pushed to follower feeds on write.
2. Celebrity tweets are written to a "celebrity timeline" in Redis (keyed by user_id).
3. On feed read: fetch pre-computed feed (regular users) + merge with celebrity tweet list (pull from celebrity key). Merging happens at read time, not write time.
4. Celebrity tweet cache has high TTL (30 min) — it's read millions of times, worth caching aggressively.
This way: one write (celebrity tweet) → one Redis write (celebrity timeline). 200M followers read the celebrity tweet lazily at their next feed load — no write storm.
How do you implement the "like count" without race conditions?+
At scale, updating like_count in PostgreSQL on every like would saturate the DB. Use Redis atomic increment with async DB sync.

Pattern: Like event → INCR tweet:likes:tweet_id in Redis → return new count to user immediately. Background job (runs every 30s): flush Redis like counts to PostgreSQL in batch. UPDATE tweets SET like_count = $1 WHERE id = $2 in batches of 1,000.

Race condition protection: Redis INCR is atomic — two simultaneous likes cannot both read 99 and both write 100. Redis guarantees the counter goes to 101.

Durability: if Redis crashes before flush, we lose up to 30 seconds of like counts. Acceptable trade-off — losing some like counts is not a catastrophic failure for this use case. For financial operations (not likes), you'd need stronger guarantees.
How do you make the system highly available — what fails and how do you handle it?+
Design for each component's failure independently:

API servers: stateless, behind a load balancer. Any server can fail. New servers spin up in 2 minutes (auto-scaling). Zero impact on users (ALB stops routing to unhealthy instances).

Redis: Redis Sentinel with 3 sentinels monitors the primary. Failover to replica in <30 seconds on primary failure. During failover: feed reads fall back to PostgreSQL (higher latency but correct). Redis Cluster for horizontal scaling.

PostgreSQL: streaming replication to 2 read replicas. On primary failure: promote a replica in <60 seconds (automatic with Patroni). Writes are unavailable during promotion. Mitigation: route read-heavy endpoints to replicas (already happening), reducing impact on users.

S3: managed by AWS with 99.999999999% durability. Not your problem. Media delivery via CloudFront — CDN absorbs all traffic, S3 is only the origin.
