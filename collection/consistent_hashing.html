00 · The Problem With Naive Hashing

Why key % N destroys your cache on every topology change

You have 3 servers. A request for user:123 maps to hash("user:123") % 3 = 1 → Server 1. Your cache is warm, hit rate 98%. You add a 4th server to handle load. Now hash("user:123") % 4 = 3 → Server 3. Every single key remaps to a different server. Your entire cache is cold simultaneously. Your database receives 100x normal traffic and falls over.

The seating chart analogy — for a complete layman
A wedding has 100 guests and 10 tables. Each guest is assigned hash(name) % 10. The seating works perfectly.

One table collapses mid-event — now 9 tables. Recompute hash(name) % 9 for every guest. Nearly everyone moves to a different table. Chaos.

Consistent hashing arranges all tables in a circle. Remove one table — only that table's guests move to the next table clockwise. Everyone else stays exactly where they were. Only 1/N guests are disrupted.
The interview setup

Interviewers introduce consistent hashing with: "Your caching layer has 10 nodes. Traffic doubles — you need to add 5 more nodes. What happens to your cache?" The wrong answer: "Cache invalidation." The right answer: walk through consistent hashing, virtual nodes, and the fraction of keys that need to migrate.

01 · The Ring — Step by Step

How consistent hashing actually works

The Hash Space
Imagine a circle representing all possible hash values — 0 to 2³² (about 4.3 billion positions). Both servers and keys are placed on this circle by hashing their identifiers with the same function (MurmurHash3 in production).
Servers: hash("server-A") → 120M, hash("server-B") → 1.8B, hash("server-C") → 3.1B
Key assignment rule: walk clockwise from the key's position until you hit a server. That server owns the key.
hash("user:123") → 900M → walk clockwise → hit Server-B at 1.8B → Server-B owns this key.
Adding a Server
New Server-D hashes to position 1.2B — between Server-A (120M) and Server-B (1.8B).
Before D: keys between 120M and 1.8B → Server-B.
After D: keys between 120M and 1.2B → Server-D. Keys between 1.2B and 1.8B → still Server-B.
✓ Only keys previously on Server-B (in that arc) move to Server-D. All keys on Server-A and Server-C are completely unaffected. Exactly 1/N of keys move when adding the Nth server.
Removing a Server
Server-B crashes. Its keys now walk clockwise to Server-C.
Before crash: keys between 1.2B and 1.8B → Server-B.
After crash: keys between 1.2B and 1.8B → Server-C (next clockwise).
✓ Only 1/N of keys experience a cache miss (the ones that were on Server-B). Every other server's keys are completely unaffected. Compare to naive hashing: 100% of keys remapped.
The database only absorbs 1/N of normal traffic from cold cache misses — not a complete collapse.
Virtual Nodes (Vnodes)
Problem: with 3 physical servers, one might own 60% of the ring. Uneven load.
Solution: each physical server gets 100–300 positions on the ring by hashing variations of its ID:
hash("server-A#1"), hash("server-A#2"), ..., hash("server-A#150")
Server-A now has 150 small arcs scattered across the ring instead of one large arc.
✓ Load distributes much more evenly — law of large numbers applies. Larger servers get more vnodes. Cassandra default: 256 vnodes. Redis Cluster: 16,384 fixed slots.
⚠ More vnodes = larger routing table (must store all vnode→server mappings). 1000 servers × 256 vnodes = 256,000 entries. Still small enough to fit in memory easily.
Replication on the Ring
Store each key on the next N servers clockwise — replication factor N gives N-way redundancy.
Replication factor 3: hash("user:123") → 900M → primary Server-B (1.8B) → replica Server-C (3.1B) → replica Server-A (120M + wraparound).
Writes go to all 3. Reads can come from any of 3.
✓ If Server-B crashes, Server-C and Server-A still have the data — zero data loss for RF=3. Used by: Cassandra (RF typically 3), DynamoDB (transparently behind the scenes).
The ring simultaneously handles partitioning (which nodes own which keys) and replication (which N nodes store each key). One data structure, two concerns.

03 · Hot Spots

Consistent hashing distributes keys — not traffic. These are different problems.

⚠ The interview trap that catches most candidates

"I'll use consistent hashing to distribute load evenly." Interviewer: "Beyoncé posts a new album. Her account receives 10 million writes per minute — all hashing to the same server. How does consistent hashing help?" Answer: it doesn't. Consistent hashing distributes the keyspace evenly. A celebrity key is still a single key on a single node — it just happens to be consistently routed to that node.

Key Salting
Distribute one logical key across multiple physical keys with a random or deterministic suffix.
Instead of writing to celebrity:456:post_count, write to one of celebrity:456:post_count#0 through celebrity:456:post_count#15 (16 shards, chosen randomly).
Reads: scatter-gather all 16 shards, sum the counts.
✓ 16x write throughput for that key. Distributes across 16 different servers. Used for: view counters, like counts, follower counts on celebrities.
⚠ Reads require 16 parallel requests + aggregation — adds latency. Tradeoff: write scale vs read complexity.
Fan-Out on Write
Push content to every follower's personal shard at write time — so reads are O(1) per user.
Celebrity posts: instead of one write + 50M lazy reads, pre-write the post to each follower's feed. Each follower's feed is stored on their own shard — reads are local.
✓ Feed reads are sub-millisecond. Twitter uses fan-out on write for most users.
⚠ Celebrity with 50M followers = 50M writes per post. Hybrid approach: fan-out for regular users, fan-out on read (lazy) for celebrities. Twitter's actual system uses this hybrid.
In-Process Local Cache
Cache hot keys on every app server in-memory — zero network hop for reads.
Celebrity profile read 10M times/minute: Caffeine (Java) or dict (Python) on each of 1,000 app servers. Each serves from local RAM. Total: 1M reads/sec per app server absorbed locally.
✓ Eliminates hot spot on the distributed cache entirely for pure reads. Used for: config data, feature flags, celebrity profiles, reference data.
⚠ Each server has its own copy → inconsistency across servers. Short TTL (10–60s) + push invalidation on write. Acceptable for eventually-consistent data only.
Adaptive Routing
Detect hot keys in real time and replicate them to additional nodes dynamically.
DynamoDB's adaptive capacity: automatically provides additional read/write capacity to hot partitions by splitting them. The partition that is hot gets a larger slice of the underlying capacity automatically, with no manual intervention.
✓ Transparent to the application. No manual key salting needed. Used by: DynamoDB (built-in), Google Spanner (automatic split on hot ranges).
04 · Real Implementations

How Cassandra, Redis Cluster, and DynamoDB actually do it

Cassandra — Murmur3 Token Ring
CONSISTENT HASHING · RF=3
TOKEN RING
Murmur3 hash maps partition keys to tokens in range -2⁶³ to +2⁶³. Each node gets 256 vnodes by default, each with a random token. The ring has 256 × N tokens for an N-node cluster.
REPLICATION
RF=3: partition key hashes to a token → first node clockwise is primary → next 2 clockwise nodes are replicas. Data lives on exactly 3 nodes. NetworkTopologyStrategy ensures replicas span different racks/DCs.
COORDINATOR
Any node can be coordinator. Client connects to any node → coordinator hashes the key → identifies the 3 replica nodes → routes request → returns result. No central routing service needed. Gossip protocol keeps topology consistent across all nodes.
ADDING A NODE
New node announces itself via gossip. Cassandra assigns 256 new tokens scattered across the ring. Each existing node streams a portion of its data to the new node for exactly the token ranges the new node now owns. No downtime. No manual resharding.
Redis Cluster — 16,384 Hash Slots
HASH SLOTS · CLUSTER BUS
SLOT ASSIGNMENT
Every key → CRC16(key) % 16384 → slot number 0–16383. Slots are assigned to master nodes: node-A owns 0–5460, node-B owns 5461–10922, node-C owns 10923–16383. Each node stores a 2KB bitmap of its slots, propagated via gossip.
MOVED REDIRECT
Client sends GET to wrong node → node responds MOVED 7892 192.168.1.2:6380 → client redirects to correct node. Smart clients (jedis, redis-py) cache the slot→node map and go direct after first lookup. One extra hop max.
HASH TAGS
Multi-key operations require co-location: {user:123}.profile and {user:123}.sessions — only the content inside {} determines the slot. Both land on same node, enabling MGET, MULTI/EXEC across these keys.
RESHARDING
redis-cli --cluster reshard migrates slots between nodes using MIGRATE command. Each key is migrated atomically. During migration, ASKING redirects handle requests for keys mid-migration. Online resharding with zero downtime.
DynamoDB — Adaptive Capacity + Auto-Sharding
MANAGED · TRANSPARENT
PARTITION KEY DESIGN
DynamoDB uses your partition key as the hash input. Good partition keys have high cardinality and uniform access: user_id (millions of users, random access). Bad: status (3 values, "active" gets 99% of traffic → hot partition).
WRITE SHARDING PATTERN
For hot keys: add a random suffix 1–N to partition key at write time. At read time, scatter-gather N partitions. Example: game:chess#{random(1,10)} distributes writes across 10 partitions. DynamoDB documentation calls this "write sharding."
ADAPTIVE CAPACITY
DynamoDB automatically detects hot partitions and splits them, providing additional throughput capacity. This is transparent — no application changes. Works for read-heavy hot spots; for write-heavy you still need write sharding.
05 · Rendezvous Hashing

The alternative to consistent hashing — and when it wins

HRW Algorithm
Highest Random Weight (HRW): to assign key K, compute hash(K, server_i) for every server. Pick the server with the highest score.
For key "user:123" with 3 servers:
hash("user:123", "server-A") = 0.72 ← winner
hash("user:123", "server-B") = 0.45
hash("user:123", "server-C") = 0.61
→ Server-A owns "user:123". If Server-A is removed, each key independently recomputes and picks the next-highest server.
vs Consistent Hashing
Rendezvous achieves the same minimal disruption property (1/N keys move on server removal) without a ring data structure.
Advantages: No ring, no vnodes, perfect load distribution by default, any client can compute independently without shared state.
Disadvantage: O(N) computation per key (hash against every server). With 1,000 servers and 1M requests/sec, this becomes expensive.
Consistent hashing with a sorted ring: O(log N) lookup.
Used by: Akamai CDN (original design), some load balancers. Not common in databases where consistent hashing dominates.
06 · Interview Decision Framework

How to structure your answer in a sharding conversation

🎯Sharding Strategy — The 5 Questions to Answer
01
What is your access pattern — random key lookups or range scans?
Random lookups →Hash-based partitioning (consistent hashing or hash slots). Distributes load evenly. O(1) point lookups. Used for: cache, user profiles, session data, key-value stores.
Range scans →Range-based partitioning. Time-series data, leaderboards, ordered IDs. All records in a range are co-located on one shard → efficient range reads. Used by: HBase, BigTable, InfluxDB, CockroachDB.
02
Is your data distribution uniform or skewed?
Uniform (user_id, session_id) →Simple consistent hashing works well. Random distribution means no shard will be disproportionately hot.
Skewed (celebrity users, trending events) →Consistent hashing + hot spot mitigation. Key salting, fan-out on write, or in-process caching for the hot keys. Consistent hashing alone is not sufficient.
03
Do you need cross-shard transactions or multi-key operations?
Yes — need ACID across shards →Use co-location strategy. Hash tags (Redis) or entity grouping (DynamoDB: user + all their posts in same partition). Design schema so related data lands on the same shard, eliminating cross-shard ops.
No — operations are single-key →Pure consistent hashing. Each key routes independently. Most cache workloads and many NoSQL workloads fall here.
04
Do you own the infrastructure or use a managed service?
Managed (DynamoDB, Cosmos) →Focus on partition key design. The sharding mechanism is transparent. Your job: choose a partition key with high cardinality and uniform access. Let the service handle sharding.
Self-managed (Cassandra, Redis Cluster) →Choose vnode count, replication factor, and topology strategy upfront. Changing these later requires costly resharding. Plan for 5x current data size minimum.
07 · Follow-ups

Every hard follow-up, answered

Why does Redis Cluster use 16,384 slots specifically — why not 65,536 or 1,024?+
16,384 was chosen as a balance between cluster heartbeat message size and practical flexibility.

Every Redis node sends heartbeat messages to all other nodes containing a bitmap of which slots it owns. 16,384 slots = 16,384 bits = exactly 2KB per bitmap. This fits comfortably in a single network packet and keeps gossip overhead trivial even in large clusters.

Why not more? 65,536 slots would make the bitmap 8KB — 4x larger gossip overhead for no practical benefit. Redis's creator Antirez noted that even with 1,000 nodes, 16 slots per node gives ample granularity for resharding. In practice most clusters have 10–30 nodes, giving 500–1,600 slots per node — plenty of flexibility.

Why not fewer? With 1,024 slots and 100 nodes, you only have 10 slots per node. Resharding granularity becomes coarse — you'd need to move large chunks of data at once.
How does consistent hashing handle data replication across failure domains (racks, AZs)?+
Topology-aware replication strategies ensure replicas land on different failure domains, not just different nodes.

Cassandra's NetworkTopologyStrategy: for each replica beyond the first, skip over nodes in the same rack when walking clockwise. This guarantees that for RF=3 with 3 racks, each rack holds exactly one replica.

Example: key hashes to node-A1 (rack 1 → primary). Walk clockwise for first replica: node-B1 (rack 1, same rack) → skip → node-A2 (rack 2) → first replica. Walk for second replica: node-A2 was just assigned, continue → node-B2 (rack 2, same rack as A2) → skip → node-A3 (rack 3) → second replica.

Result: replicas span 3 different racks. If rack 1 loses power, 2 of 3 replicas are still available. Reads continue at quorum.

AWS DynamoDB does this transparently across AZs — every partition always has 3 replicas across 3 different AZs. You don't configure it; it's the default.
What happens during a network partition — can consistent hashing nodes disagree about who owns what?+
Yes, and this is where the CAP theorem intersects with consistent hashing.

If a network partition separates a 6-node Cassandra cluster into two groups of 3, both groups continue operating — AP choice. Each group believes the other's nodes are down and tries to serve all keys. When the partition heals, Cassandra uses read repair and anti-entropy to reconcile divergent writes using "last write wins" (LWW) based on timestamps, or vector clocks for conflict detection.

Redis Cluster makes a different choice: during a partition, the minority partition (fewer than N/2+1 nodes) stops accepting writes — CP choice. The majority partition continues serving. When the partition heals, the minority replicas catch up from the majority. This prevents split-brain writes but means the minority partition is unavailable during the network outage.

This is a fundamental design decision you must make when designing sharded systems: do you want availability or consistency during partitions?
How would you design a globally distributed sharding scheme across 3 data centres?+
Geo-distributed sharding combines consistent hashing with geo-routing and topology-aware replication.

Approach 1 — Single global ring with DC-aware placement: one ring, vnodes spread across all 3 DCs. NetworkTopologyStrategy ensures each DC holds its share of replicas. Cassandra supports this natively. Write to LOCAL_QUORUM (majority within one DC), replicate asynchronously to other DCs.

Approach 2 — Regional sharding + global routing: each DC is an independent cluster owning its regional data. A global routing layer (DNS geo-routing + application-level user-to-DC affinity) routes each user to their home DC. Cross-DC reads are forwarded to the owning DC. Used by: Shopify (data residency), WhatsApp (region-based data sovereignty).

Approach 3 — Active-active multi-master: data is replicated to all DCs, any DC can serve any user. CRDTs or LWW handle conflicts. Used by: DynamoDB Global Tables, Cassandra multi-DC active-active. Highest availability, most complex conflict handling.
