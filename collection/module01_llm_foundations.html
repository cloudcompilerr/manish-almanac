01 · Mental Model

Tokens, Roles & Temperature

Every Claude API call in this repo, in either stack, is built from the same five ingredients. The definitions below aren't abstract — each one points at the exact line that uses it.

Token
The atomic unit an LLM actually sees — roughly ¾ of a word on average. Every dollar and millisecond logged by this course's services is measured in tokens, not characters.
System Role
Set inside Spring AI's fluent request builder — chatClient.prompt().system("...") in LlmFoundationsService.java. LangChain: a SystemMessage(content="...") prepended to the message list in llm_foundations.py. This is exactly where EngOrgAI's director-facing personality lives — as a class constant in DirectorAssistantService.java.
User Role
The actual ask, chained right after the system role: .user("...") in Spring AI, HumanMessage(content="...") as the second list item in LangChain. Both shown in full in the walkthroughs below.
Temperature
Controls randomness. The Python side pins it explicitly — ChatAnthropic(temperature=0, ...) — for deterministic, repeatable answers, the right call for an engineering-leadership assistant. The Spring side hasn't set a default yet — application.yml only configures the model name, not spring.ai.anthropic.chat.options.temperature, so it currently runs on Anthropic's model default. A real, open gap between the two stacks — not a hidden one.
Usage Metadata
Every response carries back prompt/completion/total token counts. Both services log them on every call, not a sample — log.info("...promptTokens={}...") in Java, logger.info("...promptTokens=%s...") in Python — the foundation for cost tracking before this course reaches RAG and agentic tool calls.

3. The actual LLM call

This is the file the "Mental Model" section above keeps pointing at — system role, user role, the full fluent chain, and token/latency capture from the response metadata.

spring/src/main/java/com/manish/module01/LlmFoundationsService.javaView on GitHub →
package com.manish.module01; import org.slf4j.Logger; import org.slf4j.LoggerFactory; import org.springframework.ai.chat.client.ChatClient; import org.springframework.ai.chat.metadata.Usage; import org.springframework.ai.chat.model.ChatResponse; import org.springframework.stereotype.Service; @Service public class LlmFoundationsService { private static final Logger log = LoggerFactory.getLogger(LlmFoundationsService.class); private final ChatClient chatClient; public LlmFoundationsService(ChatClient chatClient) { this.chatClient = chatClient; } /** * Demonstrates a foundational LLM call: system role, user role, low * temperature for factual answers, and token/latency observability * captured from the response metadata. */ public String askFoundationalQuestion(String userQuestion) { long startTime = System.currentTimeMillis(); try { ChatResponse response = chatClient.prompt() .system("You are a concise technical assistant. Answer in 2-3 sentences.") .user(userQuestion) .call() .chatResponse(); long latencyMs = System.currentTimeMillis() - startTime; Usage usage = response.getMetadata().getUsage(); log.info("LLM call completed - promptTokens={}, completionTokens={}, totalTokens={}, latencyMs={}", usage.getPromptTokens(), usage.getCompletionTokens(), usage.getTotalTokens(), latencyMs); return response.getResult().getOutput().getText(); } catch (Exception e) { log.error("LLM call failed for question: {}", userQuestion, e); throw new LlmCallException("Failed to get response from Claude", e); } } }
Worth noticing

The chain doesn't start with .system() — it starts with .prompt(), which returns a ChatClientRequestSpec that .system(), .user(), and .call() all build on. That single extra step is what makes the test below verbose: every link in the chain needs its own mock.

4. The typed failure path

Six lines, but they matter: a generic exception never reaches the caller. Every failure is wrapped so the controller layer — and anything calling this service later — knows exactly what broke.

5. Testing a fluent builder chain

This is the file that's most worth reading slowly. ChatClient.prompt() returns an interface, which .system() and .user() return again, which .call() turns into a different interface again. Mockito has to be told what each one of those intermediate calls returns before the real assertion at the bottom even runs — there is no shortcut.

Why this is the right amount of mocking

Zero live API calls happen in this suite. ./mvnw test runs it in CI with no ANTHROPIC_API_KEY at all — every collaborator is a mock, so the assertion only proves the service's own logic (extract text, log usage, propagate failure), never the model's behavior.

06 · Real Decisions

Four Decisions That Shaped Module 1

01The CostAwareResponse Hallucination
What happened
A Spring AI response wrapper called CostAwareResponse was suggested for token tracking. It doesn't exist — a fabricated class name that failed at compile time the moment it was tried, so it never made it into a commit.

The real, verified pattern shipped instead — chain .call().chatResponse(), then read response.getMetadata().getUsage() for prompt/completion/total token counts. No custom wrapper needed. See it live in LlmFoundationsService.java, lines 36–40.

✓The lesson: validate against real compiled behavior, not assumed APIs — especially for fast-moving libraries where method signatures change between versions.
02Switching Mid-Build: M2 Milestone → 2.0.0 GA
What happened
The course originally targeted Spring AI 2.0.0-M2, a pre-release milestone. Mid-Module-1, a version check revealed Spring AI 2.0.0 GA shipped June 12, 2026 — built on Spring Boot 4.1 / Spring Framework 7 / Jackson 3 — with Spring Boot 3.5 reaching end-of-life June 30, 2026, just 18 days later.

Verdict: rebuild the project skeleton on Boot 4.1 + Spring AI 2.0 GA before writing further module code. It's still in the repo, in writing — pom.xml, lines 7–25: <!-- Spring AI 2.0.0 GA - released June 12, 2026, on Maven Central --> next to the Boot parent pinned at 4.1.0.

→This is the kind of judgment call a real engineering team makes constantly: a fresh build should target the currently-supported baseline, not whatever was true when the plan was first written.
03One Shared AiConfig, Not One Per Capstone
The decision
EngOrgAI's v0.1 skeleton could have called for its own AiConfig.java. Instead, a single ChatClient bean lives in com.manish.config.AiConfig — built once, injected everywhere.

The proof is in the constructors: LlmFoundationsService(ChatClient chatClient) and DirectorAssistantService(ChatClient chatClient) both take the exact same bean type. No duplicated client construction, one place to add cross-cutting concerns as the course reaches RAG and tool calling.

⚡ · Follow-ups

Hard Follow-ups — What a Staff Engineer Asks Next

The Rosetta Stone and Production-Grade Bar above answer "what did you build." These are the questions that come after the walkthrough — the ones that probe whether the design decisions actually hold up.

Constructor injection for ChatClient — why not a static singleton or field injection?+
Constructor injection makes the dependency explicit and testable: LlmFoundationsService's test mocks ChatClient directly through the constructor — no Spring context, no reflection tricks, no static state to reset between tests. A static singleton would work at runtime but makes every test either share global state or reach for a mocking framework that can stub statics (Mockito's static mocking is possible but noticeably more awkward than a plain constructor mock). Field injection (@Autowired private ChatClient chatClient) hides the dependency from the class's own public contract — you can't tell what a class needs just by reading its constructor. It also makes the field non-final, so nothing stops later code from reassigning it. The one shared AiConfig bean (Decision 03 above) plus constructor injection everywhere is what lets DirectorAssistantService reuse the exact same ChatClient without any of these problems.
Python pins temperature=0 for "deterministic, repeatable answers." Is that actually true?+
Not fully — this is a common oversimplification worth being precise about in an interview. Temperature 0 makes the sampling step deterministic: greedy decoding always picks the highest-probability token instead of sampling from a distribution. But production LLM serving engines continuously rebatch incoming requests for throughput, and GPU reduction kernels (matrix multiply, softmax, attention) tile their floating-point accumulation differently depending on the current batch size. Because floating-point addition is not associative, the exact same prompt can produce logits that differ in the last few bits depending on what else is being processed alongside it that millisecond — occasionally enough to flip a near-tied token choice.

The honest claim for this module is "temperature 0 removes sampling randomness and gets you close to repeatable," not "temperature 0 guarantees identical output every time." For an engineering-leadership assistant giving qualitative recommendations, that's a fine trade. For anything doing exact-match testing against a fixed expected string, it's a trap — assert on structure and key fields (see Module 2's typed schema), not exact prose.
Both services block on .call()/.invoke(). What breaks if a director asks a question that takes 15 seconds to answer?+
Nothing breaks silently, but the request holds a thread (Spring MVC) or blocks the whole process (the Python CLI script) for the full round trip — fine for a single-user CLI demo, a real availability risk for a web-facing assistant under concurrent load. Spring AI's ChatClient exposes a .stream() variant that returns a Flux<ChatResponse> instead of blocking, and LangChain's ChatAnthropic supports .stream() / async invocation the same way. Neither is used yet in this module, deliberately — Module 1's job is the mental model (tokens, roles, temperature), not streaming plumbing. The honest answer in an interview is naming the gap and the fix, not pretending it's already handled: today, a slow model response ties up one request thread per call, and the fix is switching the hot paths to the streaming API before this goes past a single-user demo.
The retry config is 3 attempts, 1000ms→5000ms exponential backoff. Does that actually help against a 529 (overloaded) from Claude?+
Partially, and it's worth knowing the distinction. A 529 means Anthropic's API is at capacity across all callers — it isn't this service's rate limit and doesn't count against its quota, so a bounded exponential backoff (a few seconds, a few attempts) is the correct, polite response: back off, retry once or twice, then surface the failure rather than hammering an already-overloaded endpoint. A 429 (this caller's own rate limit) behaves the same way from the client's perspective but for a different underlying reason. Where backoff-and-retry does not help: a malformed request (400) or an auth failure (401) — retrying those just wastes the retry budget on an error that will never succeed. The framework-native retry here (Spring's spring.ai.retry.*, LangChain's max_retries=3) doesn't distinguish between these cases out of the box, which is exactly the gap called out in the trade-off row below — "no per-error-type control yet (429 vs 5xx)."
Every fluent-chain link is mocked individually in the Java test. Why not a real integration test against a stub server instead?+
Both have a place, and this module deliberately only ships the first one. The Mockito unit test proves the service's own logic — extract text, log usage fields, wrap failures in LlmCallException — in milliseconds, with no network, no API key, and no flakiness from an external dependency. What it can't catch: a real change in Anthropic's response shape, a serialization edge case, or a genuine network timeout. That's what an integration test against a recorded/stubbed HTTP layer (WireMock, or Spring's own @RestClientTest-style slices) is for — record a real response once, replay it in CI without hitting the live API or paying for tokens on every build. Module 1 ships only the unit layer because the fluent chain itself is what's being taught here; a stub-server integration test is the natural next layer to add once the call pattern is stable across more modules.
