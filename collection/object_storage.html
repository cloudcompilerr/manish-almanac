00 · What Is Object Storage

S3 vs Block Storage vs File Storage

Object Storage (S3)
Stores data as flat objects — each object is a file with a key (path), value (bytes), and metadata. No directory hierarchy (though keys can have slashes to simulate it).
Access: HTTP GET/PUT. Each object immutable after write. Unlimited scale. Cheap ($0.023/GB/month).
✓ Unlimited scale. Cheap. HTTP accessible from anywhere. Perfect for: images, videos, logs, backups, data lakes. Used by: Netflix (video), Instagram (photos), Dropbox (files).
⚠ High latency for small random reads (~50–200ms). No in-place updates. No filesystem semantics (no rename, no locking).
Block Storage (EBS)
Raw storage volumes attached to a VM. The OS sees it as a disk — format with any filesystem.
Sub-millisecond latency. Random reads/writes. Required for databases (PostgreSQL, MySQL need a filesystem).
✓ Low latency. Random access. Required for any software that needs a real filesystem (databases, OS volumes).
⚠ Attached to one instance at a time. Fixed capacity (must resize manually). Expensive ($0.10/GB/month vs S3's $0.023).
File Storage (EFS/NFS)
Shared filesystem mounted by multiple instances simultaneously. Files, directories, locking semantics.
Multiple EC2 instances can read/write the same files concurrently.
✓ Shared access across instances. POSIX filesystem. No refactoring of existing code that uses files.
⚠ Higher latency than block storage. More expensive. Rarely needed in modern cloud-native designs (S3 has replaced most file storage use cases).
01 · S3 Internals

How S3 actually works under the hood

Consistency Model
S3 provides strong read-after-write consistency for all operations (since December 2020).
After a successful PUT, subsequent GET will return the new object. After DELETE, subsequent GET returns 404. No more "eventually consistent" surprises.
✓ You can safely read immediately after writing. No need for artificial delays or consistency workarounds.
Multipart Upload
For files >100MB: upload in parallel chunks, then assemble.
1. Initiate: POST /object?uploads → returns uploadId
2. Upload parts: PUT /object?partNumber=1&uploadId=X (each part ≥5MB)
3. Complete: POST /object?uploadId=X with list of part ETags
✓ Parallel uploads (5–10x faster for large files). Resume interrupted uploads. Each part is independently verified with MD5. Required for files >5GB (single PUT limit).
Pre-Signed URLs
Temporarily grant a user direct access to an S3 object without exposing your credentials.
Server generates a signed URL valid for N seconds: aws s3 presign s3://bucket/video.mp4 --expires-in 3600
User uses URL directly to upload or download — bypasses your server entirely.
✓ Client uploads directly to S3 — your server never sees the bytes. Offloads bandwidth and CPU. Standard pattern for all file upload systems (Instagram, Dropbox, Google Drive).
Flow: Client → GET /upload-url → Server → Pre-signed URL → Client PUT directly to S3 → Client notifies Server of completion.
Storage Classes
Different cost/access speed tiers for different data lifecycle stages:
Standard: frequently accessed, ~$0.023/GB/month, <100ms access
Standard-IA: infrequent access, ~$0.0125/GB/month, retrieval fee per GB
Glacier Instant: archive, ~$0.004/GB/month, millisecond retrieval
Glacier Deep Archive: long-term archive, ~$0.00099/GB/month, 12-hour retrieval
Use Lifecycle Policies to automatically transition objects: new uploads → Standard → after 30 days → IA → after 1 year → Glacier. Common for log files and video archives.
02 · System Design Examples

Object storage in real systems

Instagram — Photo Upload Flow
MEDIA UPLOAD
UPLOAD
Client requests pre-signed URL from API server. API server generates URL scoped to that user's bucket path, valid for 5 minutes. Client uploads directly to S3 — API server never receives image bytes. Reduces server bandwidth by 100%.
PROCESSING
S3 PUT triggers a Lambda (or SQS notification → EC2 worker). Worker: resize to 3 resolutions (thumbnail/feed/full), apply filters, extract EXIF metadata, write processed versions back to S3, update DB with S3 keys.
DELIVERY
All S3 objects served through CloudFront CDN. CDN caches at 200+ edge locations. User in Tokyo gets the image from Tokyo edge, not from S3 in us-east-1. ~10ms delivery globally vs ~200ms from origin.
LIFECYCLE
Stories expire after 24h: S3 Object expiry policy automatically deletes after 24h. Old posts after 1 year → transition to S3 Infrequent Access (saves ~45% storage cost). Deleted posts → immediate Object Delete + CDN invalidation.
02 · Data Lake Architecture

S3 as the foundation of every modern data platform

What Is a Data Lake
Store ALL your data in S3 in raw format first. Process later, for different purposes.
Raw events → S3 in Parquet/JSON. Same S3 data is read by: Spark (ML training), Athena (ad-hoc SQL), Redshift Spectrum (BI reports), Flink (stream processing via S3 checkpoints).
✓ Schema-on-read: no predefined schema. Add new data sources without refactoring. Multiple compute engines on same data. Extremely cheap storage ($0.023/GB vs $0.10/GB for block storage).
⚠ No ACID transactions on raw S3. Small file problem: millions of 1KB files are much slower to query than thousands of 100MB files. Use Parquet + Snappy compression + file compaction jobs.
Delta Lake / Iceberg
Table formats that add ACID transactions, schema evolution, and time-travel to S3.
Delta Lake (Databricks) / Apache Iceberg (Netflix, Apple): store metadata files alongside Parquet data in S3 that track which files constitute the current table version.
ACID on S3: each transaction writes new Parquet files + updates metadata atomically. Readers see consistent snapshots.
Time travel: SELECT * FROM events TIMESTAMP AS OF '2026-03-01' — queries the state of the table on March 1st.
✓ Fixes the S3 "no transactions" problem. Schema evolution without rewriting all data. Streaming + batch unified (Flink writes, Spark reads). Used by: Airbnb, Netflix, Apple for petabyte-scale data lakes.
S3 Event Notifications
S3 can trigger Lambda/SQS/SNS automatically when objects are created, deleted, or modified.
New photo uploaded to S3 → S3 event → Lambda triggered → resize image → write variants back to S3.
Log file uploaded → S3 event → SQS message → EC2 worker processes log → writes structured data to Redshift.
✓ Event-driven pipelines with zero polling. S3 becomes the trigger for the entire data processing pipeline. Latency: ~1 second from S3 write to Lambda invocation.
Intelligent Tiering
S3 Intelligent-Tiering automatically moves objects between storage classes based on access patterns.
Objects not accessed for 30 days → moved to Infrequent Access automatically. Objects not accessed for 90 days → moved to Archive Instant. No retrieval fees for objects moved by Intelligent-Tiering.
✓ Optimal cost without manual lifecycle management. Best for: data lakes where access patterns are unpredictable. Small management fee ($0.0025 per 1,000 objects) — worth it for large data lakes.
03 · More System Design Examples

Object storage decisions in real systems

YouTube — Video Storage & Delivery
PETABYTES · ADAPTIVE STREAMING
UPLOAD PATH
Video uploaded directly to Google Cloud Storage (GCS) via resumable upload API (chunked 5MB parts). Upload service returns upload URL → client streams directly to GCS. Server never receives video bytes — saves enormous bandwidth.
TRANSCODING
GCS PUT event triggers transcoding pipeline. Original video → encode at 360p/720p/1080p/4K (H.264 + VP9). HLS/DASH segmentation: split each quality into 10-second segments. All variants stored back in GCS under structured paths: gs://videos/{id}/1080p/seg_{n}.ts.
DELIVERY
GCS → Cloud CDN serves video segments. Highly watched videos cached at 100+ PoPs globally. Long-tail videos served from GCS origin. Adaptive bitrate: player downloads manifest, picks quality based on bandwidth, fetches segments. CDN cache hit rate for popular videos: >99%.
STORAGE COST
500 hours of video uploaded per minute. At 1GB/minute for 720p: 500GB/minute = 720TB/day. GCS Standard ($0.020/GB): ~$14,400/day storage cost. Lifecycle policy: videos with <1000 views/month → GCS Nearline ($0.01/GB) after 30 days. Saves ~50% on long-tail storage.
Airbnb — Listing Photos & Data Lake
MEDIA + ANALYTICS
PHOTO UPLOAD
Pre-signed URL flow: GET /photos/upload-url → presigned S3 URL → client PUT directly to S3 → client notifies API of completion → API queues processing job. Processing: detect faces, apply image enhancement, generate 5 resolutions, extract EXIF. Processed images back to S3, metadata to PostgreSQL.
DATA LAKE
All business events (bookings, searches, clicks, page views) written to S3 in Parquet via Kafka → Flink → S3 sink. S3 is the "source of truth" for analytics. Spark clusters run on the S3 data for pricing ML, fraud detection model training, and business intelligence reports.
ICEBERG
Apache Iceberg used for the booking events table. Enables: schema evolution when new fields are added (new booking metadata), time-travel queries ("what was our booking rate on New Year's Eve 2024?"), and ACID updates (correct a batch of mis-categorised listings without full rewrite).
03 · Follow-ups

Every hard follow-up, answered

How do you handle large file uploads reliably over unreliable mobile connections?+
Multipart upload with client-side resumable upload logic.

1. Client splits file into 5–10MB chunks before starting the upload.
2. Client requests a multipart upload ID from your server. Server calls S3 to initiate and returns the uploadId.
3. Client uploads chunks in parallel (3–5 simultaneous chunks for speed). Each chunk is independent — a failed chunk can be retried without restarting the whole upload.
4. Client tracks which chunks succeeded locally (localStorage or a server-side record).
5. If connection drops mid-upload, client resumes from the last successful chunk on reconnect.
6. When all chunks are confirmed, client notifies your server, which calls S3's CompleteMultipartUpload.

Tools: AWS SDK has built-in multipart upload with retry logic. tus.io is an open protocol for resumable uploads. Used by: Google Drive, Dropbox, YouTube for all video uploads.
How do you design a Dropbox-like file sync system?+
Core challenge: efficiently sync only changed parts of large files across devices.

Chunked storage: files are split into 4–8MB content-addressed chunks. Each chunk is identified by its SHA-256 hash. Only changed chunks need to be uploaded on modification.

Delta sync: if you edit a 1GB file by changing one paragraph, only the 2–3 chunks containing that paragraph change. Only those chunks are uploaded. File metadata (which chunk IDs comprise the file) is updated. Other devices download only the new chunks.

Deduplication: if two users upload identical files, the chunks are deduplicated — stored once, referenced by both. Dropbox saved ~2PB of storage via deduplication.

Conflict handling: if two devices modify the same file while offline, both versions are kept — user sees "conflicted copy" and manually resolves. Alternatively: vector clocks to track causality and auto-merge text files (like Google Docs CRDT).
How do you handle eventual consistency in S3 for applications that require strong consistency?+
Since December 2020, S3 provides strong read-after-write consistency for all operations — this is no longer a problem for new systems.

Historical context: before 2020, S3 had eventual consistency for LIST operations and overwrites of existing objects. This caused real bugs: upload a file, immediately list the bucket, the file might not appear. Developers had to add artificial delays or use DynamoDB to track object existence.

Today: a successful PUT is immediately visible to all subsequent GET and LIST operations. No delays, no workarounds needed.

Where consistency issues remain:
1. Cross-region replication lag: if you enable S3 Cross-Region Replication (CRR), objects are eventually replicated to the destination region. Reads from the destination region might not see the latest version until replication completes (typically 15 minutes, but no SLA). For strong cross-region consistency, do not rely on S3 CRR alone — use a distributed database or accept the replication lag.
2. Concurrent writes to the same key: if two clients simultaneously PUT the same S3 key, the "last writer wins" — but there is no atomic compare-and-swap (no "write only if not modified"). For concurrent update scenarios, use DynamoDB for metadata and version tracking alongside S3 for blob storage.
What is the "small files problem" in data lakes and how do you solve it?+
Millions of small files in S3 make query engines (Spark, Athena, Redshift Spectrum) dramatically slower.

The problem: Flink flushes to S3 every 10 seconds. At 100 partitions × 6 flushes/minute × 60 minutes = 36,000 files/hour, each ~100KB. When Athena queries a day's data, it must open 864,000 files. S3 LIST + OPEN operations are expensive (~10ms each). 864,000 × 10ms = 2.4 hours of overhead before reading a single byte.

Solutions:
1. Compaction jobs: a daily Spark job reads all small files for each partition and rewrites them as a few large Parquet files (100–500MB each). Athena now opens 10 files instead of 864,000. Requires a maintenance window or can run in the background during low-traffic hours.
2. Increase flush interval: instead of flushing every 10 seconds, flush every 10 minutes. Fewer, larger files. Trade-off: longer lag before data is queryable.
3. Delta Lake / Iceberg: these table formats include compaction operations (OPTIMIZE in Delta, REWRITE_DATA_FILES in Iceberg) that compact small files transactionally — no downtime, readers see consistent data throughout.
