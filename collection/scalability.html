00 · Back-of-Envelope Estimation

The skill that separates senior engineers in interviews

Why interviewers ask this
Before designing a system, engineers estimate its scale. A design that works for 1,000 users fails at 1,000,000 — not because the architecture is wrong, but because the numbers change which components you need. Estimation gives you the numbers that drive design decisions.

The goal is not precision — it's an order-of-magnitude answer. "About 10,000 requests/second" is correct. "Exactly 9,847" is wasted effort. 2× wrong is fine. 100× wrong changes the design.
01Numbers to Memorise
What it is
These are the building blocks of every estimation: 1 million seconds ≈ 11.5 days 1 billion seconds ≈ 31 years 1 day = 86,400 seconds ≈ 100K seconds 1 month ≈ 2.5M seconds 1 year ≈ 31M seconds Avg tweet: 140 bytes. Avg photo: 200KB. Avg video min: 10MB. SSD read: 500MB/s. Network: 10Gbps = 1.25GB/s. RAM: 50GB/s.
→You don't need exact numbers. You need the right order of magnitude.
02QPS Estimation Formula
What it is
QPS = Daily Active Users × Actions per day ÷ Seconds per day Twitter example: 300M DAU. Average user reads feed 5× per day + writes 0.1 tweet/day. Read QPS = 300M × 5 ÷ 86,400 = ~17,000 reads/sec Write QPS = 300M × 0.1 ÷ 86,400 = ~350 writes/sec Peak QPS ≈ 3× average = 51,000 reads/sec, 1,050 writes/sec.
→Always calculate peak, not average. Systems fail at peak. Design for peak × 20% headroom.
03Storage Estimation Formula
What it is
Storage per year = QPS_writes × payload_size × seconds_per_year × replication_factor Twitter: 350 writes/sec × 300 bytes/tweet × 31M sec/year × 3 replicas = ~10TB/year Instagram photos: 1M uploads/day × 200KB = 200GB/day = 73TB/year (before CDN caching and compression).
✓✓ Once you have storage/year, you know: if >100TB → object storage (S3), if >10TB → distributed DB (Cassandra), if <1TB → single PostgreSQL might work.
04Bandwidth Estimation
What it is
Bandwidth = QPS × payload size Twitter reads: 17,000 req/sec × 10KB per feed response = 170 MB/sec = 1.4 Gbps. A 10Gbps network link handles this easily. YouTube: 1B views/day × 10MB avg video = 10PB/day = ~1TB/sec outbound bandwidth. This is why YouTube needs a CDN — no single origin could serve 1TB/sec.
→Bandwidth estimation tells you: do you need a CDN? Is a single datacenter connection enough? What's the egress cost?
05Latency Numbers Every Engineer Knows
What it is
These guide architecture decisions — always quote them in interviews: L1 cache: 1ns · L2 cache: 4ns · L3 cache: 10ns RAM read: 100ns · SSD read: 100μs · HDD read: 10ms Same-datacenter network: 0.5ms · Cross-region (US-EU): 150ms Redis GET: 0.1ms · PostgreSQL query (indexed): 1ms DynamoDB: 1ms · S3 GET: 50ms · DNS lookup: 20ms
⚠Key insight: RAM is 1,000× faster than SSD, which is 100× faster than HDD. A cache miss that hits disk is 10,000× slower than a cache hit. This is why caching exists.
01 · Scaling Patterns

The layered approach — how every large system actually scales

01The Scaling Ladder
What it is
Scale problems are solved in layers. Add each layer only when the previous one is insufficient. Level 1: Single server + single DB. Works to ~1K req/sec and ~100GB data. Level 2: Add read replicas. 3–5 replicas handle ~5K read req/sec. Level 3: Add caching (Redis). Offloads 80–90% of read DB traffic. Works to ~50K req/sec. Level 4: Horizontal scale app servers behind a load balancer. Works to ~500K req/sec. Level 5: Database sharding. Handles unlimited write throughput and unlimited data size. Level 6: CDN for static assets + geographic distribution. Handles global scale with low latency.
✓✓ Most systems never need Level 5+. Jumping to sharding before exhausting caching is premature optimisation. In interviews: always state where on this ladder the system sits.
02Vertical vs Horizontal Scaling
What it is
Vertical: bigger machine. Horizontal: more machines.

Vertical (scale-up): upgrade from 16-core to 64-core server. Simple — no code changes. Limit: biggest available machine is fixed (~128 cores, ~24TB RAM). Single point of failure.

Horizontal (scale-out): add more servers of the same size. Unlimited scale in theory. Requires stateless services (session state in Redis, not in-process). Complexity: load balancing, distributed coordination, consistent hashing for data.

→Databases scale vertically first (biggest possible primary), then horizontally (read replicas, then sharding). Stateless app servers scale horizontally trivially. This asymmetry is why the database is always the bottleneck.
03CQRS (Command Query Responsibility Segregation)
What it is
Split your read model and write model into separate services with separate data stores. Commands (writes): go to a normalised write DB (PostgreSQL). Optimised for data integrity and write throughput. Queries (reads): go to a denormalised read DB (Elasticsearch, Redis, Cassandra). Pre-computed views optimised for specific query patterns. Sync: write DB publishes change events → consumer builds and updates read models asynchronously.
✓✓ Each store optimised for its purpose. Read store can be rebuilt from scratch by replaying the event log. Used by: e-commerce (write to OLTP, serve product catalog from Elasticsearch), social feeds (write to PostgreSQL, serve feed from pre-computed Redis list).
⚠⚠ Eventual consistency: reads lag writes by milliseconds to seconds. Complexity: two data stores, sync pipeline. Only justified when read and write patterns are fundamentally different.
04Event Sourcing
What it is
Store every change as an immutable event. Derive current state by replaying events. The event log is the source of truth. Instead of storing "account balance = ₹5,000", store: [AccountOpened(₹0), Deposited(₹3,000), Deposited(₹2,500), Withdrawn(₹500)]. Balance = sum of events.
✓✓ Complete audit log by default. Time-travel: reconstruct state at any point in history. Rebuild any read model from scratch. Events are immutable — no update anomalies. Used by: banking systems, e-commerce order history, git (event sourcing for code changes).
⚠⚠ Query complexity: to get current balance, replay all events (use snapshots for long-lived aggregates). Schema evolution: old events must remain valid when the event schema changes. Steep learning curve for teams accustomed to CRUD.
05Circuit Breaker
What it is
Stop sending requests to a failing dependency. Return a fast fallback instead of waiting for timeouts. States: Closed (normal — requests pass through) → Open (failure threshold exceeded — all requests rejected instantly, return fallback) → Half-Open (after cooldown — send probe requests to test recovery). Example: Recommendation Service is down. Without circuit breaker: every request waits 30 seconds for timeout. With circuit breaker: immediately returns cached/default recommendations. 30s timeout → 5ms fallback.
✓✓ Prevents cascade failures. Fast failure response. Gives downstream service time to recover. Netflix Hystrix (original), Resilience4j (Java), Polly (.NET), Envoy (service mesh — no code changes).
06Bulkhead Pattern
What it is
Isolate failures to a subset of resources, like watertight compartments in a ship. Without bulkhead: one slow downstream service exhausts your entire thread pool → all requests fail. With bulkhead: separate thread pools per dependency. "Payment service pool" has 10 threads. If payments are slow, only payment requests are affected. Feed requests use their own 50-thread pool — unaffected.
✓✓ Failure isolation. One misbehaving tenant/feature cannot starve others. Combined with circuit breaker: bulkhead prevents exhaustion, circuit breaker prevents cascades. Used by: Netflix (separate thread pools per microservice dependency).
02 · Async vs Sync

When to break synchrony — the most consequential architectural decision

01When Sync is Right
What it is
Use synchronous calls when the caller needs the result to proceed. Examples: user login (need auth token immediately), payment processing (need success/failure to show user), inventory check before order placement (need to know if in stock).
→The test: "If the downstream service is slow, should the user wait, or can I proceed without the result?" If the user must wait: synchronous. If you can proceed: asynchronous.
02When Async is Right
What it is
Use asynchronous processing when: (1) the operation takes longer than a user will wait, (2) multiple downstream systems need to be notified, (3) operations can be retried safely. Examples: sending order confirmation email (user doesn't wait for email to send), video transcoding (user uploads and continues — gets email when done), search index update (user doesn't wait for Elasticsearch to index their new post).
✓✓ Decouples producers from consumers. Absorbs traffic spikes (queue buffers). Enables retry on failure. Reduces user-facing latency by doing work in the background.
03Async Patterns: Fire-and-Forget vs Request-Reply
What it is
Two async models with different guarantees:

Fire-and-forget: publish event, don't wait for result. Order placed → publish OrderCreated event → return 200 to user. Fulfillment, email, inventory updates happen in background. Risk: if any step fails, user doesn't know synchronously.

Async Request-Reply: client sends request + callback URL. Server processes async, POSTs result to callback URL when done. OR: client polls a status endpoint. Used for: long-running operations (video export, report generation, ML inference).

03 · System Design Examples

Scaling decisions in real systems

Scaling from 0 to 10M Users — Step by Step
THE FULL JOURNEY
0 → 1K users
Single server: Nginx + Node.js + PostgreSQL on one EC2 instance. $50/month. Works fine. Don't optimise what doesn't hurt yet.
1K → 50K
Separate app server from DB. Add read replica for PostgreSQL. Add Redis for sessions and hot queries. Add S3 + CloudFront for images. Now: 3 servers, ~$300/month. Latency drops 50% from CDN.
50K → 500K
Horizontal scale app servers (2→10) behind ALB. Add Redis cluster (not single node). Add Elasticsearch for search. Async email/notifications via SQS + Lambda. DB is still single primary with 3 read replicas. ~$3,000/month.
500K → 5M
Database starts to be the bottleneck. Shard by user_id across 4 PostgreSQL primaries. Add Cassandra for time-series data (feeds, activity logs). Deploy to 2 AWS regions (US + EU). CDN at edge absorbs 90% of traffic. ~$30,000/month.
5M → 10M+
Full microservices split by domain (user service, feed service, notification service). Each with its own DB. Kafka for inter-service events. Kubernetes for orchestration. Istio for service mesh. Multi-region active-active. ~$300,000/month.
04 · Decision Framework

The interview framework — how to structure a scaling discussion

🎯Scaling Decision Tree — Ask in Order
01
What is the bottleneck? (Always measure before optimising)
CPU-bound →Horizontal scale app servers. Add more cores. Optimise hot code paths. Profile with sampling profiler first — never optimise blind.
DB-bound (reads) →Cache first (Redis cache-aside). Then read replicas. Only shard if cache + replicas are insufficient. 80% of DB read problems are solved by a properly sized cache.
DB-bound (writes) →Async writes (queue + batch). Write-behind cache. Then horizontal sharding. Write throughput is the hardest to scale — minimise synchronous writes in the hot path.
02
Is this a read-heavy or write-heavy system?
Read-heavy (>10:1) →CQRS + pre-computation. Denormalise read models. Pre-compute expensive queries. Cache aggressively. CDN for static/semi-static content. Twitter serves 300K reads/sec but only 6K writes/sec — the ratio drives everything.
Write-heavy →LSM-tree databases (Cassandra, RocksDB). Write-behind caching. Async processing for non-critical writes. Partition writes across shards. Accept eventual consistency on read side.
03
Do you have hot spots (some data accessed much more than others)?
YES (celebrity users, viral content) →Local in-process cache for ultra-hot keys (bypasses Redis network hop). Key salting/sharding for hot write keys. Fan-out on read for celebrity content (don't pre-compute their feed — too many followers). Adaptive replication of hot data.
NO (uniform access) →Standard horizontal scaling. Consistent hashing distributes evenly. Redis cluster handles load. No special treatment needed.
05 · Follow-ups

Every hard follow-up, answered

How do you estimate the number of servers you need?+
Servers needed = Peak QPS × avg response time / target CPU utilisation

Example: 50,000 req/sec peak, each request takes 50ms to process, target 70% CPU utilisation.
One server (32 cores, 4 threads/core = 128 concurrent requests): can handle 128 concurrent × (1000ms/50ms) = 2,560 req/sec per server.
Servers needed = 50,000 / 2,560 / 0.70 = ~28 servers. Round up to 32 for headroom.

Memory: 32 servers × 8GB RAM for app = 256GB total. Does your session store / in-process cache fit? If not, externalise to Redis.

The key insight: servers are cheap and elastic. The bottleneck is almost always the database, not the app servers. Size your DB first, then size app servers to saturate the DB without overwhelming it.
When should you split a monolith into microservices?+
Split on organisational boundaries, not technical ones. The right trigger is team size and deployment independence, not performance.

Stay monolith when: Team is small (<30 engineers). Deployment happens together anyway. Data model is tightly coupled. Latency of network calls between services would hurt performance. Most startups should stay monolith until ~50+ engineers.

Split when: Different parts of the system need to scale independently (payment processing at 100× normal on Black Friday, but user profiles don't). Different teams need to deploy independently without coordination. Different parts need different tech stacks. A failure in one part should not bring down the whole system.

The Strangler Fig pattern: don't rewrite from scratch. Incrementally extract one service at a time. New traffic goes to the new service. Old monolith handles everything else. Over 18 months, the monolith shrinks and the services grow. This is how Shopify, Twitter, and Amazon migrated — never a "big bang rewrite."

The hidden cost: microservices multiply operational complexity by 10×. You need: service discovery, distributed tracing, service mesh, per-service CI/CD, per-service monitoring, distributed transactions. Don't pay this cost before you need it.
How does CQRS handle the read model becoming stale?+
CQRS accepts eventual consistency — the read model lags the write model by the processing time of the async pipeline. The question is: is that acceptable for your use case?

Typical lag: 50ms–2s (Kafka + consumer processing). For most read models (product catalog, user feeds, leaderboards), this is imperceptible.

When staleness is not acceptable: immediately after a user action, they should see their own change (read-your-own-writes). Solutions:
(1) After a write, also update the read model cache synchronously for the writing user's session. Other users get eventual consistency; the writer gets immediate consistency.
(2) Client-side optimistic update: frontend immediately shows the change locally (before server confirms), reconciles when the server eventually confirms.
(3) Version/timestamp in the response: client sends the last-seen version. If the read model hasn't caught up to that version yet, return a loading indicator and poll.

The mental model: CQRS is like a newspaper. The printing press (write DB) prints the paper. Distribution takes time. By the time you read it (read model), it might be hours old. That's fine for news — not fine if you need to know "did my bank transfer arrive yet?"
What is the N+1 query problem and how do you fix it?+
The N+1 problem: fetching N records then making 1 query per record instead of one query for all N records at once.

Example: you fetch 20 posts (1 query). For each post, you fetch the author's profile (20 queries). Total: 21 queries instead of 2.

SQL fix — JOIN or IN clause:
Instead of: for post in posts: author = db.query("SELECT * FROM users WHERE id = ?", post.user_id)
Do: db.query("SELECT posts.*, users.* FROM posts JOIN users ON posts.user_id = users.id WHERE posts.id IN (?)", post_ids)

ORM fix — eager loading:
SQLAlchemy: session.query(Post).options(joinedload(Post.author)).all()
ActiveRecord: Post.includes(:author).all
Prisma: prisma.post.findMany({ include: { author: true } })

GraphQL fix — DataLoader: batches all user ID lookups from a single GraphQL request into one DB query. Returns them in the same tick via Promise.all. Facebook's DataLoader is the standard pattern for N+1 in GraphQL resolvers.

Detection: ORM query logging in development. If you see the same query pattern repeated N times with different IDs — you have an N+1 problem. SQL monitoring tools (pg_stat_statements, DataDog APM) surface this in production.
How do you do a zero-downtime database schema migration on a table with 100M rows?+
Never ALTER TABLE on a large live table. It locks the table for hours. Use an expand-contract (parallel change) pattern instead.

Scenario: you need to rename column user_name to display_name on a 100M row users table.

Step 1 — Expand: Add the new column display_name (with a default). This is a fast metadata operation in PostgreSQL 11+ (no table rewrite for nullable columns). Start writing to BOTH columns in application code. New code writes to display_name; old code still reads user_name.

Step 2 — Backfill: Run a background job that copies user_name → display_name in batches of 1,000 rows (with sleep between batches to avoid overwhelming the DB). This takes hours on 100M rows — that's fine, it runs in the background with zero user impact.

Step 3 — Switch reads: Once backfill is complete and verified, change the application to read from display_name. Deploy. Monitor for errors.

Step 4 — Contract: Stop writing to user_name. After one deploy cycle with no rollback, drop user_name column (fast — metadata only). Migration complete, zero downtime, zero table locks.

Tools: gh-ost (GitHub's online schema migration for MySQL), pgroll (Postgres), Flyway/Liquibase (migration management).

Requirements & Non-Functional Constraints

Functional Requirements

FR1Horizontal scaling: add servers without downtime
FR2Database scaling: read replicas + sharding + caching
FR3Async processing: decouple slow operations from request path
FR4CQRS: separate read and write models for different scale
FR5Circuit breaker: fail fast when dependency is unavailable
FR6Back-of-envelope estimation: size the system before designing

Non-Functional Requirements

NFR1Request latency: p99 < 200ms at 10× expected peak load
NFR2Scalability: system handles 10× load with 10× servers (linear)
NFR3Availability: 99.99% — < 52 min downtime/year
NFR4Cost efficiency: auto-scaling, spot instances, tiered storage
NFR5Observability: CPU, memory, queue depth metrics drive auto-scale
NFR6Recovery: RTO < 15min, RPO < 1min for critical systems
