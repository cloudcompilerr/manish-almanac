00 · The Critical Distinction

Transport vs Processing — they're not the same thing

The biggest mistake candidates make is treating Kafka, Flink, Kinesis, and Spark Streaming as competing alternatives. They're not. They play fundamentally different roles in a streaming architecture.

🚌 Transport / Message Bus
Kafka, Kinesis, Pulsar

Like a highway — vehicles (messages) enter, travel through, and exit. The highway stores vehicles temporarily so producers don't have to wait for consumers to be ready. It decouples producers from consumers.

Key properties: durable storage, ordered delivery within partition, multiple consumers reading the same message independently, replay old messages.
⚙️ Stream Processor
Flink, Spark Streaming, Kafka Streams

Like a factory that processes vehicles as they pass through — counting them, sorting them, combining them with data from other sources, detecting anomalies. The processor does the actual computation.

Key properties: stateful computation, windowing (tumbling, sliding, session), joins across streams, exactly-once semantics, fault tolerance with checkpoints.
The correct mental model for Top-K

Kafka = the highway. Events from users flow in, get durably stored, and multiple consumers can read them independently and at their own pace.

Flink = the factory. Consumes from Kafka, applies the Count-Min Sketch, maintains the local heap, and every 30 seconds flushes the Top-K results to Redis and Cassandra.

You always use a transport layer AND a processing layer together. They're complementary, not competitive.

03 · Processing Layer Deep Dive

Flink vs Spark Streaming — True Streaming vs Micro-Batch

The Core Difference

Apache Flink: True streaming. Processes each event as it arrives. State is maintained in memory/RocksDB between events. Latency: milliseconds. Results are continuously updated.

Spark Streaming (Structured Streaming): Micro-batch. Collects events for X seconds (e.g., 5s), then processes the batch. Latency: minimum is the batch interval. Simpler programming model, reuses Spark's batch optimisations.

True streaming vs micro-batch — the toll booth analogy
True streaming (Flink): Each car approaches the toll booth and is processed individually as it arrives. The attendant collects, processes, and lets through each car without waiting. Immediate, real-time.

Micro-batch (Spark Streaming): Cars are held at a red light for 5 seconds. Then the light turns green, all cars are processed together as a batch, then the light turns red again. Slightly delayed but can be more efficient for high volumes.

Flink's Key Capabilities — What Makes It the FAANG Choice

04 · The Full Stack

How They Combine in a Real Architecture

The standard streaming stack pattern

Layer 1 — Producers: Applications, services, IoT sensors emit events.

Layer 2 — Transport (Kafka / Kinesis): Events are durably stored, decoupling producers from consumers. Multiple downstream consumers read independently.

Layer 3 — Stream Processor (Flink / Spark): Consumes from transport layer, applies business logic (windowing, aggregation, enrichment, filtering), outputs results.

Layer 4 — Sinks: Results written to Redis (hot), Cassandra (warm), ClickHouse (analytics), S3 (cold/archive).

05 · Applied to Real Systems

System Design Examples

Top-K Trending — Complete Stream Stack
500K EVENTS/SEC
TRANSPORT
Kafka ✓ Partitioned by entity_id — all events for video_123 go to the same partition and same Flink worker. No cross-worker coordination needed for local aggregation. 7-day retention enables Flink to replay on crash without data loss.
PROCESSING
Flink ✓ 30-second tumbling windows. Count-Min Sketch per worker (6KB fixed memory). Local min-heap of top-K=1000. Bloom filter for deduplication. Exactly-once via Kafka offset + S3 checkpoint. Flushes ZINCRBY to Redis + rows to Cassandra every 30s.
WHY NOT KINESIS
Kinesis ⚠ Could work in AWS but: 1MB/sec per shard limit means 500K events/sec needs 500 shards minimum. At $0.015/shard-hour × 500 shards × 24h = $180/day just for the shard cost. Kafka on 10 nodes handles same volume for ~$50/day.
WHY NOT SPARK
Spark ⚠ Micro-batch model means Top-K results update every 5–10 seconds minimum (batch interval). Flink's true streaming updates the Count-Min Sketch per-event with millisecond latency. For a trending feature, Flink's freshness is materially better.
Fraud Detection (Payment System)
MILLISECOND DECISIONS
TRANSPORT
Kafka ✓ Payment events partitioned by user_id. Ensures all transactions for a given user go to the same Flink worker — enabling per-user velocity checks without cross-partition joins.
PROCESSING
Flink ✓ Session windows detect: "more than 3 transactions in 60 seconds" or "transaction amount 10x higher than 30-day average." Per-user state (running totals, recent transaction history) stored in RocksDB — survives restarts.
WHY FLINK NOT SPARK
Fraud decisions need sub-100ms latency — the payment is in flight waiting for approval. Spark's 5-second micro-batch interval means a fraudulent transaction would be approved before detection. Flink processes each event in ~10ms.
ETL Pipeline (Data Warehouse Loading)
BATCH-FRIENDLY
CHOICE
Kafka + Spark Streaming ✓ ETL to data warehouse: Kafka → Spark Structured Streaming → Redshift/BigQuery. Spark's micro-batch is fine here — loading data every 5 minutes into a data warehouse is perfectly acceptable. Reuses existing Spark infrastructure. Spark's DataFrame API makes transformations, schema enforcement, and deduplication easy.
AWS VERSION
Kinesis Firehose ✓ Kinesis Data Firehose auto-delivers to S3, Redshift, OpenSearch. Zero-code ETL for simple pipelines. For AWS shops building data lakes, Firehose + Glue is the zero-ops path.
07 · Interview Follow-up Playbook

Every Hard Follow-up, Answered

Kafka guarantees at-most-once, at-least-once, or exactly-once?+
All three — depending on how you configure it.

At-most-once: Consumer reads message, immediately commits offset, then processes. If processing crashes, the message is lost (offset already advanced).

At-least-once: Consumer reads, processes, then commits offset. If processing crashes before commit, message is reprocessed on restart. May be processed twice.

Exactly-once (EOS): Requires both idempotent producers (enable.idempotence=true) AND transactional producers + consumers. Kafka ensures each message is written exactly once even with retries. Combined with Flink's two-phase commit, this gives exactly-once end-to-end. Performance overhead: ~20% throughput reduction.
What happens to in-flight Flink state when a node crashes?+
Flink recovers from its last checkpoint.

Every 60 seconds (configurable), Flink performs a distributed snapshot: all operator states (Count-Min Sketch, local heap, Bloom filter) are saved to S3. The corresponding Kafka offset consumed up to that point is also saved.

On crash: Flink restarts from the last successful checkpoint. It resumes reading Kafka from the saved offset. Events between the checkpoint and the crash are replayed from Kafka (this is why Kafka retention matters). State is restored from S3.

If Flink uses exactly-once mode (two-phase commit), the output (writes to Redis/Cassandra) is also rolled back if the checkpoint was not completed. This prevents double-counting even across crashes.
How do you handle late-arriving events in Flink?+
Watermarks and allowed lateness.

The problem: Events arrive out of order. An event with timestamp t=14:23:45 might arrive at t=14:24:10 (25 seconds late) due to network delays. If the 30-second window for 14:23 already closed and was flushed, what do you do?

Watermarks: Flink maintains a "watermark" — its best guess of the current event time. A watermark of t=14:24:00 means "all events with timestamp < 14:24:00 have probably arrived." Windows only close when the watermark passes the window end time.

Allowed lateness: Even after a window closes, Flink can wait for late events up to X seconds. Late events trigger a window update (re-emit corrected results). Events arriving after the allowed lateness are either dropped or sent to a side output for separate handling.

In Top-K, we use a 5-second watermark lag — accepting that our Top-K results may be 5 seconds stale in exchange for near-complete accuracy.
Why does Kafka partitioning by entity_id matter so much for Top-K?+
It eliminates cross-worker coordination — the fundamental scalability trick.

If all events for video_123 go to the same Kafka partition, they're consumed by the same Flink worker. That worker maintains the local count for video_123 in its own Count-Min Sketch, entirely in local memory. No network calls needed to coordinate with other workers.

If video_123's events were spread across multiple partitions, three things would go wrong: (1) Multiple Flink workers would each have a partial count for video_123. (2) To merge them, every worker would need to communicate with every other worker after each event. (3) At 500K events/sec, this coordination traffic would overwhelm the cluster.

Partitioning by entity_id makes the problem embarrassingly parallel — each worker handles a disjoint subset of entities, does all its computation locally, and the only cross-worker step is the final merge of top-K lists at flush time.
Can you replace Kafka with a database in the streaming pipeline?+
Technically yes, practically no — and interviewers will probe this.

You could write events to a PostgreSQL table and have Flink poll it. This is called "Change Data Capture" (CDC) and it works for low-throughput pipelines. But it fails at 500K events/sec because:

1. Each INSERT is a full row write with WAL logging — massive I/O overhead at scale.
2. Polling introduces latency: Flink polls every X seconds, creating inherent lag.
3. Ordering guarantees are weak: multiple writers can write with slightly different timestamps.
4. Backpressure handling: if Flink falls behind, the database table grows unbounded (no TTL like Kafka retention).
5. Multiple consumers: each consumer needs its own polling mechanism and state tracking.

Kafka is purpose-built for this. Its log-structured storage makes sequential writes extremely fast. Consumers maintain their own offset. Backpressure is handled naturally — consumers just read slower while Kafka buffers the data within retention limits.
07 · Core Concepts Deep Dive

Kafka internals every FAANG interviewer tests

01Consumer Group Rebalancing
What it is
When a consumer joins or leaves a group, Kafka reassigns partition ownership — this is a rebalance. During rebalance: all consumption stops (stop-the-world). Duration: seconds to minutes for large groups. All consumers in the group coordinate via the group coordinator broker.
⚠⚠ Frequent rebalances (pod restarts, rolling deploys) cause processing gaps. Fix: incremental cooperative rebalancing (Kafka 2.4+) — only reassigns affected partitions, others keep processing. Also: set session.timeout.ms appropriately (not too short).
02Exactly-Once Semantics (EOS)
What it is
Kafka guarantees at-least-once by default. Exactly-once requires explicit configuration. Producer side: enable.idempotence=true + transactional.id. Prevents duplicate messages on retries. Consumer side: isolation.level=read_committed. Only reads messages from committed transactions. Flink + Kafka: two-phase commit checkpoint. Flink checkpoints aligned with Kafka offsets — exactly-once end-to-end.
⚠⚠ EOS adds ~10–20% throughput overhead. Use for: financial event streams, inventory updates. Skip for: metrics, logs, analytics where duplicates are tolerable.
03Log Compaction
What it is
Instead of deleting old messages by time, keep only the latest value per key. Compacted topic: Kafka runs a background compaction thread that removes old records for the same key, retaining only the most recent. Result: the topic always contains the current state of every key — like a changelog.
✓✓ Used for: materialising database changelogs (Debezium → Kafka compacted topic = current DB state). New consumers can bootstrap from the compacted topic to get current state without reading the full history. Used by: Kafka Connect, ksqlDB state stores.
04Backpressure in Flink
What it is
Flink propagates backpressure upstream through its credit-based flow control. If a sink (Cassandra write) is slow → output buffer fills → upstream operators slow down → eventually the Kafka consumer slows its poll rate → Kafka consumer lag grows → natural backpressure signal. Monitor: Flink Web UI shows backpressure ratio per operator. High backpressure (red) = that operator is the bottleneck. Fix: increase parallelism for that operator, or optimise the slow operation.
→Flink's backpressure propagation is automatic and zero-copy — no application code needed. It prevents out-of-memory failures when sinks are overwhelmed.
05Watermarks & Late Data
What it is
Event time vs processing time: events arrive out of order. Watermarks tell Flink when a time window is "complete enough" to compute. Watermark = current_event_time - allowed_lateness. When watermark passes window end time, Flink triggers the window computation. Example: 1-minute tumbling window with 5-second allowed lateness. Window closes at 14:01:00. Flink waits until it sees events with timestamps ≥ 14:01:05 before computing. Events up to 5 seconds late are included.
✓✓ Handles network delays and out-of-order mobile events gracefully. Later events (beyond allowed lateness) go to a side output for separate handling.
06Kafka Consumer Lag
What it is
Consumer lag = the difference between the latest offset in a partition and the consumer's current offset. The most important Kafka operational metric. Lag = 0: consumer is keeping up with producers in real time. Lag growing: consumer is falling behind. Causes: slow processing logic, insufficient consumer parallelism, downstream bottleneck (DB writes too slow).
✓Monitor with: Kafka's consumer-groups.sh, Burrow (LinkedIn's open-source lag monitor), or CloudWatch (MSK). Alert when lag > N minutes worth of events — this defines your data staleness SLO.
07Flink State Backends
What it is
Flink's stateful operations (aggregations, joins, windows) store state in a configurable backend.

HashMap (in-memory): fastest, state in JVM heap. Limited by available RAM. Use for: small state (<1GB), latency-sensitive operations.

RocksDB (on-disk): state on local SSD, spills to disk. Handles terabytes of state. Slightly slower than HashMap. Use for: large state (user session data, 30-day aggregations).

→RocksDB is the production default for most Flink jobs. RAM is the bottleneck in streaming systems — RocksDB removes that constraint at the cost of ~2x latency (SSD read vs RAM read).
08Kinesis vs Kafka
What it is
Both are event streaming systems — the choice is almost always cloud commitment and ops budget.

Kinesis: fully managed, AWS-native, limited to 7-day retention, max 1MB/record, shard-based scaling (manual). Simple, zero ops. Best for: AWS-native orgs, moderate throughput (<1GB/sec per stream).

Kafka (MSK or self-managed): configurable retention (unlimited), higher throughput, richer ecosystem (Kafka Connect, Kafka Streams, ksqlDB, Flink). Best for: complex streaming pipelines, multi-cloud, high throughput, need replay.

→At FAANG scale: Kafka. For simple AWS pipelines at moderate scale: Kinesis. For new systems with limited ops capacity: consider Confluent Cloud (managed Kafka without the operational burden).

YES (stateful) →Flink or Spark Structured Streaming. Flink: lower latency (milliseconds), better backpressure, exactly-once. Spark: better for micro-batch (seconds), familiar SQL API, better for ML pipelines. Both handle joins across streams and windows.

<100ms (real-time) →Flink in streaming mode. Processes each event as it arrives. Checkpointing every 30s for fault tolerance. State in RocksDB (on-disk) for large state or JVM heap for small state.
Seconds (near real-time) →Spark Structured Streaming micro-batch or Flink mini-batch. Trigger every 5–30 seconds. More efficient for high-throughput aggregations. Better SQL support.

09 · Kafka Internals Deep Dive

The settings interviewers probe — ISR, acks, min.insync.replicas

ISR (In-Sync Replicas)
& acks Configuration
ISR: the set of replicas that are "caught up" with the leader within replica.lag.time.max.ms.
Producer acks=0: no acknowledgment. Fire and forget. Fastest, no durability. Data loss on broker crash.
Producer acks=1: leader acknowledges immediately after writing to its local log. Fast. Data loss if leader crashes before replicating — followers don't have the message yet.
Producer acks=all (acks=-1): leader waits until ALL ISR replicas have acknowledged. Strongest durability guarantee. Latency: depends on slowest ISR replica.

min.insync.replicas=2: producer with acks=all requires at least 2 ISR replicas to acknowledge. If only 1 replica is in-sync (e.g., one broker is down), producer receives a NotEnoughReplicasException. Better to reject the write than accept it without durability. Production standard: acks=all + min.insync.replicas=2 + replication.factor=3. Tolerates one broker failure without data loss. Use acks=1 only for high-throughput low-criticality data (metrics, logs).

Log Retention &
Log Compaction
Two retention modes with fundamentally different semantics:

Time-based retention: delete segments older than retention.ms (default: 7 days). All events eventually deleted. Right for: event logs, metrics, audit trails.

Log compaction: for each key, keep only the latest value. Old values with the same key are deleted during compaction. Right for: "current state" topics (user profiles, inventory levels, config changes). Kafka acts like a durable, compacted key-value store.
Tombstone: to delete a key, publish a message with the key and a null value. Compaction will eventually remove all messages with that key. ✓ Log compaction powers Kafka Streams' KTable abstraction (current state of each key). Also used by Debezium CDC: the "latest state" of each DB row is compacted into a Kafka topic — new consumers can read the full current state without replaying all history.

Consumer Group
Rebalancing
When a consumer joins or leaves a group, Kafka redistributes partition assignments — this temporarily pauses consumption.
Trigger: consumer joins/leaves, partition count changes, consumer heartbeat timeout (session.timeout.ms, default 10s).
During rebalance: all consumers stop consuming and commit their offsets. The group coordinator assigns partitions to consumers. Consumers resume. Duration: 100ms–30s depending on group size and coordinator load.

Cooperative rebalancing (Kafka 2.4+, incremental rebalance): only partitions that need to move are revoked. Other consumers continue consuming unaffected partitions. Reduces pause from "all stop" to "only affected partitions stop." Use CooperativeStickyAssignor. Production issue: a consumer that processes messages too slowly triggers heartbeat timeout → kicked from group → rebalance → partition reassigned → rebalance again → "rebalance storm." Fix: increase max.poll.interval.ms, reduce processing time, or add more consumers.
