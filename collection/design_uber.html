00 · Requirements

Clarify before designing

Functional
Rider requests a ride (location → destination). Nearby drivers notified. Driver accepts → trip starts. Real-time location tracking. Fare calculation. Payment. Trip history.
Non-Functional
100M rides/day. Driver location update every 4 seconds. Match rider to nearest driver in <5 seconds. Location accuracy: <100m. High availability (no rider stranded). 1M concurrent drivers globally.
Estimation
1M active drivers × 1 location update/4s = 250K location updates/sec. 100M rides/day = 1,157 ride requests/sec. Location data: 250K × 50 bytes = 12.5 MB/sec = 1TB/day (stored in time-series). Geospatial index: 1M drivers × 50 bytes = 50MB in Redis (trivial).
01 · Architecture

The complete system — four core flows

Driver Location
Tracking
WebSocket from driver app → Location Service → Redis GEO.
Persistent WebSocket connection from each driver app. Driver sends GPS every 4 seconds. Location Service receives update → GEOADD drivers:city {lng} {lat} driver:{id} in Redis. Also writes to Cassandra (time-series for trip replay + analytics): (driver_id, timestamp, lat, lng).
Why WebSocket vs HTTP polling? HTTP polling at 4s interval = 250K × 1 HTTP request/4s = 62,500 HTTP requests/sec. WebSocket: one persistent connection per driver, push updates. 10× less server overhead. Uber uses WebSocket for all real-time communication.
Matching Engine
Rider requests ride → find nearest available driver → notify driver → driver accepts → match confirmed.
Rider sends pickup location. Matching Service: GEORADIUS drivers:city {rider_lng} {rider_lat} 5 km ASC COUNT 10 → 10 nearest drivers. Check availability (each driver has a status in Redis: available/on_trip). Notify available drivers via WebSocket (push notification to driver app). First driver to accept: lock the match atomically using Redis SET NX (prevent two riders matching the same driver). Confirm match, start trip.
Surge Pricing
Supply/demand ratio per geospatial cell determines the surge multiplier.
Kafka stream: ride requests + driver availability per S2 cell. Flink aggregation: rolling 5-minute window, count (requests, available_drivers) per cell. Surge multiplier = f(demand/supply). Store in Redis: surge:city:s2cell → multiplier. Pricing Service reads multiplier from Redis on every fare calculation. Druid for historical surge analytics (which zones, which times).
Trip Management
In-progress trips tracked in Redis for real-time access, written to PostgreSQL for persistence.
Active trip: trip:active:{trip_id} → {driver_id, rider_id, status, route} in Redis (TTL=4h). Written to PostgreSQL on completion with full metadata. Payment triggers on completion: ride fare + tip + surge = total → Stripe charge → write payment record to PostgreSQL. Kafka event: TripCompleted → downstream (rating request, analytics, driver earnings).
02 · Deep Dive — Driver Matching

The complete matching flow in detail

Ride Request to Driver Acceptance
<5 SECONDS END-TO-END
T+0ms
Rider taps "Request Ride." App sends: POST /rides {"pickup": {lat,lng}, "dropoff": {lat,lng}}. API Gateway authenticates JWT. Routes to Ride Service.
T+10ms
Ride Service → Matching Service. GEORADIUS drivers:bangalore {pickup_lat} {pickup_lng} 3 km ASC COUNT 5 → [driver:123, driver:456, driver:789]. Check status: HGET driver:status:123 = "available." Found 2 available drivers in 3km.
T+20ms
Push notification via WebSocket to both available drivers: "New ride request nearby — accept?" Driver apps show the request with pickup location, estimated distance.
T+1500ms
Driver:123 taps "Accept." Matching Service: SET driver:trip:123 {trip_id} NX EX 3600 — atomic "claim" of this driver. NX = only set if not exists — prevents two riders matching the same driver. Returns success.
T+1520ms
Notify rider: driver accepted. ETA: 3 minutes. Start trip record in Redis. Update driver status to "on_trip." Notify driver:456 that the request is no longer available.
03 · Follow-ups

The questions your interviewer will ask

What happens if the driver's GPS is inaccurate or they go offline mid-trip?+
GPS inaccuracy: dead reckoning + Kalman filter. Connectivity loss: client-side buffering + reconnect.

GPS inaccuracy: mobile GPS is ±10–50m in cities (building reflection). Uber's driver app applies a Kalman filter — a statistical technique that combines GPS readings with accelerometer/gyroscope data to estimate the most likely position. Road snapping: the estimated position is "snapped" to the nearest road (Uber uses their own road graph). A driver teleporting across a building is corrected to the road they're on.

Driver goes offline during trip: driver app buffers location updates locally (SQLite on device). When connectivity restores, the app batch-sends all buffered updates with original timestamps. Location Service accepts out-of-order updates with timestamps — writes to Cassandra in order. Gap in location data is handled gracefully: straight-line interpolation between last known and first reconnect point.

WebSocket reconnect: exponential backoff. Connection state stored in Redis — on reconnect, driver receives the current trip state and can resume seamlessly.
How do you handle the city-scale sharding of driver location data?+
Shard by city initially, then by geohash within dense cities.

One Redis GEO key per city: drivers:bangalore, drivers:mumbai, drivers:delhi. Bangalore has ~50,000 active drivers during peak — this is a 50K member ZSET in Redis, trivially fast (<1ms queries).

For mega-cities (London, NYC, São Paulo) with 200,000 concurrent drivers: split by 4-character geohash prefix (each cell is ~40km × 40km). NYC becomes ~20 cells covering the metropolitan area. GEORADIUS query: determine which cells overlap with the 5km search radius → query those cells only → merge results.

The lookup function: given a rider's location, determine which geohash cells are within 5km → issue parallel GEORADIUS queries against those Redis keys → merge and sort results. At most 4–5 Redis keys need to be queried for any given pickup location.
How does Uber prevent "ghost rides" — a driver falsely claiming they completed a trip?+
Multiple independent verification systems cross-reference trip legitimacy.

GPS trace verification: the full GPS trace is stored in Cassandra. After trip completion, the route is compared to the claimed start/end points. A trip from MG Road to Indiranagar that has GPS points in Whitefield is flagged as anomalous.

Time-distance consistency: calculate the minimum possible time to travel the claimed distance. If the trip took 2 minutes but the claimed distance requires 30 minutes of driving — fraud signal.

Rider confirmation: rider app must confirm trip end (tap "Arrived"). Rider and driver GPS positions are compared at "trip end" — they should be within 500m of each other.

Machine learning fraud detection: features include: driver's historical trip patterns, rider's complaint history, GPS trace anomalies, payment patterns, device fingerprints. Model flags suspicious trips for manual review before payment is released to driver.
