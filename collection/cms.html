Algorithm · System Design

Count-Min Sketch

The probabilistic data structure that counts millions of events using just kilobytes of memory — and how hash functions make it work.

01 — The Problem

Why not just use a counter?

Imagine you're running YouTube. Every second, millions of videos are watched. Your boss asks: "What are the top trending videos right now?"

A naive HashMap of video_id → count works fine for 1,000 videos. But YouTube has 800 million videos. Storing exact counters for all of them = gigabytes of RAM, just for counting.

The insight: For trending, rate-limiting, and frequency analysis, you don't need the exact count. A "slightly-higher-than-truth" estimate is perfectly fine — as long as it's fast and tiny.

Count-Min Sketch gives you ~95%+ accurate frequency estimates in a few kilobytes, with O(1) inserts and queries.

02 — The Key Mechanism

How does a hash function pick a column?

This is the most important thing to understand. A hash function is just a deterministic math machine: same input → always same output. It converts any string into a number, then we use modulo (%) to fit it into our grid width.

Step-by-step: hashing "video_42" into a 6-column grid

// Hash Function 0: a simple polynomial hash "video_42" → add up (character codes × prime powers) = 118×31⁰ + 105×31¹ + 100×31² + ... = big number: 8,472,193 column = 8,472,193 % 6 (grid width) = → Col 3
// Hash Function 1: a different seed / multiplier "video_42" → same chars, different math → 5,291,847 column = 5,291,847 % 6 = → Col 2
// Hash Function 2: yet another seed "video_42" → 3,104,522 column = 3,104,522 % 6 = → Col 4

The key insight: the exact number doesn't matter. What matters is that (a) it's always the same for the same input, and (b) different hash functions scatter the same input to different columns.

Real world analogy: Think of 3 bouncers at a party, each with their own arbitrary rule for assigning people to table numbers. If you ask "where does Alice sit?", each bouncer gives a different table — but they'll always give the same table for Alice every time you ask.
03 — The Grid

Count-Min Sketch is just a table of counters

A grid of depth × width. Each row has its own independent hash function. The grid starts at all zeros.

Col 0Col 1Col 2Col 3Col 4Col 5
Row 0 (hash_fn_0) 000302
Row 1 (hash_fn_1) 004010
Row 2 (hash_fn_2) 200150

The highlighted cells are where "video_42" incremented. To query: look up those same cells → values are 3, 4, 5 → take MIN = 3. That's our estimate.

Why is Row 2's value (5) higher? Because another video happened to hash to Col 4 in Row 2 — it polluted that counter. The minimum protects us from this pollution.

⚠ The interview trap that catches most candidates "I'll use Count-Min Sketch to find the top trending videos." Said on its own, this is incomplete in a way that a strong interviewer will immediately probe. CMS can only answer "how many times has this specific item occurred?" — for an item you already know to ask about. It has no way to enumerate which items exist in the grid at all; the grid stores counts, not identities. Finding the "top" anything requires a companion structure — almost always a bounded min-heap of candidate items, fed by CMS lookups as events stream in (exactly what Redis's own TOPK.ADD does under the hood by combining a Count-Min Sketch with a heap). Naming that companion structure unprompted is the signal that separates candidates who've memorized "CMS is for trending topics" from candidates who understand what CMS actually computes.

06 — Interview Counter Questions

Questions you'll be asked — answered

Why not just use a HashMap? +
A HashMap is exact but memory scales with unique items. 100M unique URLs = gigabytes of RAM just for counters. Count-Min Sketch gives you ~95% accuracy in a few kilobytes. For trending, rate-limiting, and frequency analysis, "close enough" is perfectly fine — and it's orders of magnitude cheaper.
What if two items always hash to the same column? +
That's a collision — their counts bleed into each other. That's exactly why we use multiple rows with independent hash functions. The probability that item A collides with item B in all rows simultaneously drops exponentially with each row added. With 5 rows, it's astronomically unlikely. This is why we take the minimum — it's the least-polluted estimate across all rows.
Can you delete items? +
Standard CMS doesn't support deletion — subtracting could make a count go negative and corrupt the structure. If you need deletion, use Count-Min Sketch with conservative update or switch to a Count Sketch (allows negative values, slightly different statistical guarantees). In practice, most real-world use cases (trending, rate limiting) don't require deletion.
How is this different from a Bloom Filter? +
They're cousins — same probabilistic family, different questions.

When would you NOT use Count-Min Sketch? +
Three cases: (1) When you need exact counts — billing, financial transactions, audit logs. (2) When your key space is small enough to fit exactly in RAM. (3) When you need to enumerate all keys — CMS can tell you the count for a key you ask about, but it can't tell you what keys exist. For that, you need a different structure.
Where is Count-Min Sketch used in production? +
Redis ships Count-Min Sketch natively via the RedisBloom module (CMS.INITBYPROB, CMS.INCRBY, CMS.QUERY, CMS.MERGE) — a confirmed, documented production use, commonly reached for in frequency-counting and rate-limiting scenarios. Heavy-hitter / high-traffic-flow detection in networking (e.g. spotting which IPs or flows dominate traffic) is a well-established application going back to the original Cormode–Muthukrishnan paper that introduced CMS. Trending-hashtag detection at Twitter-scale is one of the most common system-design interview illustrations of CMS — worth knowing as the textbook answer, but note Twitter's own trending algorithm (as reverse-engineered by outside researchers) actually weighs the acceleration of mentions over time rather than a raw frequency count, so treat "Twitter uses CMS for trending" as the illustrative interview framing rather than a confirmed detail of their real production system. Query optimizers and CDNs are a plausible general fit for the same family of sketches, but if you need a concrete, citable production example in an interview, lead with the RedisBloom case.
The one line to remember
"Count-Min Sketch is a fixed-size grid of counters. You hash each event across multiple rows, increment that cell in each row, and query by taking the minimum. It trades perfect accuracy for dramatically lower memory — and it only ever overcounts, never undercounts."

05 · Concepts Quick Reference

Core mechanics in one place

Hash Width
(w)
Number of columns — controls error magnitude.
Guarantee: estimation error ≤ e/w. Set w = ⌈e/ε⌉ where ε is your acceptable error rate.
Example: ε=0.01 (1% error) → w = ⌈2.718/0.01⌉ = 272 columns. With N=1,000,000: max overcount = 10,000 (1% of N). Wider table = smaller error. Width scales linearly with required accuracy.
Hash Depth
(d)
Number of rows (independent hash functions) — controls error probability.
Set d = ⌈ln(1/δ)⌉ where δ is acceptable failure probability.
Example: δ=0.01 (99% confidence) → d = ⌈ln(100)⌉ = 5 rows. Probability ALL 5 collide simultaneously = (0.01)^5 = 0.0000000001. More rows = higher confidence. Depth grows logarithmically — diminishing returns beyond d=7.
Why Minimum?
CMS query returns the minimum across all d rows — not sum, not average, minimum.
Each row's counter is always ≥ the true count (hash collisions add counts from other keys). The minimum is the closest to the true count — but still an upper bound. ✓ Mathematically proven: min(rows) ≥ true_count always. This is why CMS only over-estimates, never under-estimates.
Space Complexity
O(w × d) — constant space regardless of the number of distinct keys.
ε=0.01, δ=0.01: w=272, d=5. Total: 272 × 5 = 1,360 integers × 4 bytes = 5.3KB.
Compare: 1 billion unique keys in a HashMap = ~24GB. CMS: 5.3KB — a 4.5 million× reduction. ✓ Fits in L1 CPU cache, enabling billions of updates per second.
CMS vs HyperLogLog
CMS counts frequency of each item. HyperLogLog counts distinct items. Different problems.
CMS: "how many times did user X appear?" → frequency/count estimation.
HyperLogLog: "how many distinct users appeared?" → cardinality estimation. Use CMS for Top-K (need per-item counts). Use HLL for DAU / unique visitor counts. Redis supports both natively.

Trending Hashtags at Twitter-Scale — Illustrative Design
HYPOTHETICAL · INTERVIEW EXERCISE
PROBLEM

Count how many times each hashtag appears in the last 1 hour, across millions of distinct hashtags. A HashMap would need gigabytes. Must update in real time.
CMS SOLUTION
ε=0.01, δ=0.01 ✓ One CMS per 5-minute bucket. Each tweet: extract hashtag → hash into CMS → increment. At end of bucket: query CMS for candidate hashtags. Top-K via min-heap.
SIZE

At 500M events/hour: max error = 500M × 0.01 = 5M per hashtag. A hashtag with 100M appearances is estimated as 95M–105M. For trending (relative ranking), this error is irrelevant. 07 · Decision Framework

When to use CMS — and when not to

🎯CMS vs Exact Counting — Ask in Order
01
How many distinct keys do you need to count?
Few (<1M distinct) →Exact counting with HashMap is fine. 1M keys × 8 bytes = 8MB — trivially fits in memory.
Many (>10M distinct) →CMS is justified. 100M distinct keys × 8 bytes = 800MB. CMS achieves same Top-K result in 5KB.
02
Can you tolerate small over-counting (CMS never under-counts)?
YES →Use CMS. CMS guarantees frequency(item) ≤ estimate ≤ frequency(item) + ε×N. Perfect for trending topics, popular product ranking, heavy hitter detection.
NO (exact required) →Exact counting required. Use Redis INCR per key, or streaming aggregation into a database (Flink → Cassandra with exact counts).
03
Do you need to track individual item counts or just find the Top-K?
Just Top-K →CMS + min-heap (or Redis TOPK). Heap bounded at size K. Total memory: O(w×d + K), independent of distinct item count.
All item counts →CMS alone. Query any key in O(d) time — constant regardless of vocabulary size.
📋 · Requirements & Scale

Requirements & Non-Functional Constraints

Functional Requirements

FR1The system must estimate how many times each of a potentially unbounded number of distinct items has occurred, using a fixed memory footprint that does not grow as new distinct items appear — the entire reason to reach for CMS over a HashMap.
FR2Recording an occurrence of an item must be a fast, constant-time operation (hash into each row, increment each cell) so it can sit directly in a high-throughput ingest path without becoming the bottleneck.
FR3Querying the estimated count for any item must also be constant-time and require no scan of the structure — read the same d cells the update path would write to, and return their minimum.
FR4The estimate returned must never be lower than the true count — callers can safely treat the result as "at least this many," which matters for use cases like rate limiting where undercounting would be the dangerous failure direction.
FR5Sketches built independently on different machines (e.g. one per stream partition) must be combinable into a single accurate global sketch by simple element-wise addition, with no need to reprocess the original events.
FR6CMS alone cannot answer "which items are most frequent" since it doesn't store item identities — the system must pair it with a bounded structure (a min-heap of candidate items) to produce a Top-K list without tracking every distinct item ever seen.

Non-Functional Requirements

NFR1Total memory is w×d integer counters — a direct, recomputable consequence of the width and depth you choose for your target error rate and confidence, not a fixed number. Using this document's own running example (ε=0.01, δ=0.01 → w≈272, d≈5): 272×5 = 1,360 counters ≈ 5.4KB. A looser or tighter target changes this proportionally — e.g. a much smaller ε (tighter error bound) or smaller δ (higher confidence) both push memory up.
NFR2The overcount on any query is bounded by ε×N with probability at least 1−δ — this is CMS's core mathematical correctness guarantee (from the Cormode–Muthukrishnan construction), not a vendor-specific claim.
NFR3Width and depth are derived directly from your error targets: w = ⌈e/ε⌉ (ε = acceptable error as a fraction of total events), d = ⌈ln(1/δ)⌉ (δ = acceptable failure probability) — pick your own ε and δ and recompute; these are formulas, not fixed constants.
NFR4Worked example at ε=0.01 (1% error): w = ⌈e/0.01⌉ ≈ 272 columns — shown here as one illustrative operating point, not a universal setting.
NFR5Worked example at δ=0.01 (99% confidence): d = ⌈ln(100)⌉ ≈ 5 rows — again, one illustrative operating point paired with the ε above; scale both together when you change your target.
NFR6Total for this document's running example (ε=0.01, δ=0.01): 5 rows × 272 columns = 1,360 counters × 4 bytes/counter ≈ 5.4KB — small enough to fit comfortably in L1/L2 cache, which is part of why CMS updates are so fast in practice.
⚠ · Failure Modes

What actually breaks when Count-Min Sketch is running in production

01Sizing Drift — Error Silently Exceeds the Design TargetFAILURE MODE
What breaks & how
Width and depth are sized for an assumed total event volume N. If real traffic grows well past that assumption — a launch goes viral, a new product 10x's event volume — the actual error bound (ε×N) grows with it, since ε is a fraction of total events, not a fixed absolute error. A sketch tuned for 1% error at 1B events silently degrades to a much larger absolute error at 10B events, with no crash, no exception, and no log line — counts just get quietly less accurate.
⚠Fix: re-derive width/depth whenever the assumed-N changes materially, and monitor observed error where you can (e.g. spot-check a sample of estimated counts against exact counts on a subset). Building in headroom on N at design time is cheaper than re-provisioning after the fact.
02Predictable Hash Seeds Enable Adversarial CollisionsFAILURE MODE
What breaks & how
If CMS is used for something security-adjacent — rate limiting by IP or API key, for instance — and the hash seeds are fixed/predictable, an attacker who can guess or brute-force which inputs collide with a victim's cells can deliberately inflate the victim's counter and trigger a false rate-limit block (a denial-of-service against a legitimate user), or conversely probe for a set of inputs that never collide with anything to evade rate limiting entirely.
⚠Fix: use randomized/secret hash seeds per deployment (not a fixed public seed), and if CMS is protecting something adversarial, treat it as one signal among several rather than the sole gate — the same caution that applies to any probabilistic structure used in a security-sensitive path.
03Windowed-Sketch Bucket DriftFAILURE MODE
What breaks & how
A common pattern (as in the trending-hashtags example above) keeps one CMS per fixed time bucket and sums the last N buckets to answer "count over the last hour." If bucket retirement logic has an off-by-one, or a bucket fails to roll over on a deploy/restart, the summed window can silently include stale buckets (overcounting, window appears wider than intended) or drop a bucket (undercounting relative to what CMS itself would guarantee for a single sketch). This is an operational bug in the surrounding system, not a flaw in CMS itself — but it's the most common way CMS-based systems misbehave in practice.
⚠Fix: make bucket rollover idempotent and test it explicitly across restarts/deploys; alert if the number of active buckets ever drifts from the expected count.

🃏 · Core Concepts

Every Mechanism — K-Card Deep Dive

01The d × w Counter GridData Structure
What it is
d hash functions × w columns = d × w integer counters. Every item maps to exactly d cells (one per row).
Update: hash the item with each of d hash functions → get d column indices → increment those d cells. Query: hash again → read the d cells → return the MINIMUM. The minimum is always ≥ the true count (overcount only, never undercount).
✓Minimum of d independent estimates: each hash collision inflates one estimate. Taking the minimum means you need ALL d estimates to be simultaneously inflated — probability drops exponentially with d.
02Why Minimum, Not Average?Algorithm
The intuition
Collisions inflate counts. The minimum is the least-inflated estimate.
If item A hashes to the same column as 100 other items in row 1, row 1's counter is inflated. But the probability that A ALSO collides with 100 items in rows 2, 3, 4, and 5 simultaneously is tiny. The minimum across d rows is very likely to be the least-collided estimate.
⚠Average would be wrong: averaging inflated and un-inflated estimates gives a biased high estimate. Minimum gives a bound: true_count ≤ CMS_estimate ≤ true_count + ε×N.
03Parameter TuningConfiguration
How to size it
Two parameters: w (width = columns) and d (depth = rows = hash functions).
w = ⌈e/ε⌉ where ε is the maximum error as a fraction of total events N. For 1% error: w = e/0.01 ≈ 272.
d = ⌈ln(1/δ)⌉ where δ is the failure probability. For 99% confidence: d = ln(100) ≈ 5.
Memory: 5 × 272 = 1,360 counters × 4 bytes = 5.4KB for ANY vocabulary size.
✓Halving the error rate doubles w (544 columns). Adding one more hash function (d+1) multiplies confidence by e — logarithmic improvement.
04CMS + Min-Heap = Top-KTop-K Integration
Why you need both
CMS answers "how often?" — min-heap answers "which K items are most frequent?"
CMS alone cannot enumerate which items are in the top K (it doesn't store item identities).
Min-heap alone would need exact counts for every distinct item — O(N) memory.
Together: each event → CMS.update(item) → CMS.query(item) → if count > heap.min → heap.push(item, count). Total memory: O(w×d + K), independent of distinct item count.
✓At 1B distinct hashtags: exact HashMap = 8GB+. CMS + K=1000 heap = 5.4KB + 8KB = 14KB total.
05Distributed CMS (Merging)Scale
Merging across nodes
CMS sketches built on different nodes with the same parameters can be merged by element-wise addition.
Node A processes partition 1: sketch_A. Node B: sketch_B. Global = sketch_A + sketch_B (add corresponding cells). Same error guarantee as if all events were processed on one node.
Used in: Flink distributed Top-K (each task: local CMS + heap, merge every window), Redis Cluster (each shard: local CMS, coordinator merges periodically).
✓Mergeability is the property that makes CMS work in MapReduce, Flink, and distributed stream processing — unlike exact counting which requires coordination on every event.
