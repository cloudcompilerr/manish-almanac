00 · Why Load Balancing

The first component in every system diagram

A single server handling all traffic is a single point of failure and a performance ceiling. Load balancers distribute traffic across a fleet of servers, enabling horizontal scaling and eliminating single points of failure. In every FAANG system design diagram, the first arrow after "Client" points to a load balancer.

The supermarket checkout analogy
A supermarket has 10 checkout lanes. A greeter (load balancer) at the entrance directs each customer to the shortest queue. Without the greeter, everyone crowds into lane 1 while lanes 2–10 sit empty.

L4 load balancer = greeter who only looks at which lane is least busy (doesn't care what's in your cart).
L7 load balancer = greeter who reads your items and sends produce-only carts to lane 3 (express), bulk items to lane 7 (large cart), etc.
01 · L4 vs L7

The most important distinction in load balancing

L4 (Transport Layer)
Routes based on IP address and TCP/UDP port only. Does not inspect packet contents.
Decision: "This TCP connection from 1.2.3.4 goes to server B."
One TCP connection between client and server — the LB just forwards packets. ✓ Extremely fast — no parsing overhead. Works for any protocol (TCP, UDP, SMTP, MySQL). Lower latency. Used for high-throughput, low-overhead routing. ⚠ Cannot make routing decisions based on URL, headers, cookies, or content. Cannot terminate SSL. Cannot implement application-level health checks. Examples: AWS NLB (Network Load Balancer), HAProxy in TCP mode, Linux IPVS.
L7 (Application Layer)
Inspects HTTP headers, URL paths, cookies, and body to make routing decisions. Terminates the client connection and opens a new one to the backend.
Decision: "This POST /api/payments request goes to the payments service. This GET /images/ request goes to the static content service." ✓ URL-based routing (path-based or host-based). SSL termination (decrypts once at LB, unencrypted to backends). A/B testing and canary deploys. Rate limiting. Request/response transformation. Advanced health checks (HTTP 200 check, not just TCP connect). ⚠ Higher CPU overhead (parses every HTTP request). Slightly higher latency. Cannot handle raw TCP/UDP workloads. Examples: AWS ALB, Nginx, Envoy, Traefik, HAProxy in HTTP mode.
02 · Algorithms

How the LB decides which server gets the request

Round Robin
Distribute requests evenly in rotation: server 1, 2, 3, 1, 2, 3...
Simple and fair for homogeneous servers with similar request costs. ⚠ Fails when servers have different capacities or when request cost varies (a 10ms request and a 5-second request are treated identically).
Weighted Round Robin
Servers get traffic proportional to their weight. Server A (32 cores) gets 2x traffic of Server B (16 cores).
Useful during rolling deploys: new servers start with weight=0, gradually increased. ✓ Handles heterogeneous fleets. Natural fit for canary deployments (weight new version at 5%).
Least Connections
Route to the server with fewest active connections currently.
Ideal for long-lived connections or variable request duration (WebSocket, video streaming, large file uploads). ✓ Naturally load-balances when request durations vary. A slow server accumulates connections and receives fewer new ones. ⚠ Requires the LB to track active connections per server — state overhead.
Consistent Hash
Route requests from the same source (IP or user ID) to the same server consistently.
Required for: WebSocket connections (must reach the same server), stateful sessions without a shared cache, server-side caching (cache warm on one server). ⚠ Can create hot spots if one user generates disproportionate traffic. Server removal disrupts affected users.
03 · Advanced Patterns

Circuit breaker, health checks, and service mesh

Health Checks
LB continuously probes backends. Unhealthy servers are removed from rotation.
Passive: track error rate and latency from real traffic. Remove servers exceeding threshold.
Active: LB sends GET /health every 10s. If 3 consecutive failures → mark unhealthy → remove from pool. ✓ Automatic removal of crashed instances without human intervention. Required for zero-downtime deployments. Return 200 only when truly healthy: DB connected, dependencies up, startup complete. Not just "process is running."
Circuit Breaker
Stop sending requests to a failing service instead of letting failures cascade.
Three states: Closed (normal) → Open (failures exceed threshold, stop sending) → Half-Open (send probe requests to check recovery).
Example: Payment service is down. Without circuit breaker: all requests queue up, threads exhaust, your entire API times out. With circuit breaker: immediately return "payment service unavailable" and redirect to fallback. ✓ Prevents cascade failures. Fast failure response. Used by: Netflix Hystrix, Envoy, Istio, Spring Cloud Circuit Breaker.
API Gateway vs
Reverse Proxy vs
Service Mesh
Three different things that are often confused:

Reverse Proxy: Sits in front of servers, forwards requests. Handles SSL, caching, compression. Example: Nginx.

API Gateway: Smart reverse proxy with auth, rate limiting, request routing by path, API versioning, request/response transformation. Example: Kong, AWS API Gateway.

Service Mesh: Sidecar proxies (Envoy) injected next to every service. Handles service-to-service communication: mTLS, circuit breaking, load balancing, distributed tracing — all without changing application code. Example: Istio, Linkerd. Use API Gateway for external traffic (public API). Use service mesh for internal service-to-service traffic at large scale.

04 · Deployment Strategies

Blue-green, canary, and rolling — how the LB enables zero-downtime deploys

Blue-Green Deploy
Run two identical production environments (blue = current, green = new). Switch traffic instantly by updating the LB.
Blue = v1.0 serving 100% traffic. Deploy v1.1 to green (idle). Run smoke tests on green. Switch LB: 0% → blue, 100% → green. Instant cutover. Rollback: flip LB back to blue in seconds. ✓ Zero downtime. Instant rollback. Full production test on idle environment before cutover. Used for: high-stakes deploys where any version mixing is unacceptable. ⚠ Requires double infrastructure temporarily. DB schema changes must be backwards-compatible (both blue and green must work with same schema during transition).
Canary Deploy
Route a small percentage of real traffic to the new version. Gradually increase if metrics look good.
Week 1: 1% → new version. Week 2: 10%. Week 3: 50%. Week 4: 100%. At each stage, monitor error rates, latency, and business metrics. Automated rollback if anomaly detected. ✓ Real user validation before full rollout. Limits blast radius of bugs to 1% of users initially. Used by: Google, Netflix, Amazon for all feature releases. Implementation: Nginx split_clients, Envoy weighted clusters, AWS ALB weighted target groups. Route by: random (statistical), user ID hash (consistent experience), header flag (beta testers).
Rolling Deploy
Replace instances one at a time. At any point, some instances run old version, some run new.
10 instances: replace 1 → 2 → 3... until all 10 run new version. LB automatically routes to healthy instances (health checks remove in-progress instances from rotation). ✓ No extra infrastructure. Gradual. Works with any LB. ⚠ Both versions run simultaneously — APIs must be backwards-compatible. Rollback requires rolling back all instances (slow). Default strategy for Kubernetes Deployments.
Connection Draining
Before removing a server from rotation, wait for in-flight requests to complete.
1. Mark server as "draining" in LB — no new connections routed to it.
2. Wait for existing connections to finish (or timeout after 30 seconds).
3. Server reports zero active connections → safely terminate/redeploy. ✓ Zero dropped requests. Users in the middle of a long operation (file upload, ML inference) are not interrupted. AWS ALB calls this "deregistration delay" (default 300s).

How Envoy's xDS works — interviewers love this

Traditional proxies require a reload to pick up config changes. During reload, there's a brief pause. With 1000 Envoy sidecars, reloading all of them for every config change is impractical.

xDS (Discovery Service): Envoy maintains a persistent gRPC connection to a control plane (Istio Pilot). The control plane pushes config updates in real time. Envoy applies them instantly with zero connection drops. Adding a new backend node? Control plane updates all Envoy instances in seconds — no reload, no downtime, no deployment needed.

Load balancing in complex real systems

Netflix — Multi-Tier Global LB
GLOBAL · VIDEO STREAMING
DNS / GLOBAL
AWS Route 53 latency-based routing → nearest AWS region. Anycast via CloudFront for video segments. User in Singapore → Singapore edge, never touches US origin for cached video.
EDGE (L7)

Database Proxy — PgBouncer for PostgreSQL
CONNECTION POOLING
THE PROBLEM
PostgreSQL supports ~100–400 concurrent connections before performance degrades (each connection is a process). A web app with 50 servers × 20 threads each = 1,000 connections. Postgres falls over.
PGBOUNCER
PgBouncer sits between app servers and PostgreSQL. App servers open connections to PgBouncer (thousands of connections OK). PgBouncer maintains a pool of 50–100 real connections to PostgreSQL. Transaction-mode pooling: a real connection is only needed during an active transaction — idle app connections share the real connection pool.
LB FOR DB
HAProxy in front of PostgreSQL read replicas: balance leastconn routes read queries to the least-loaded replica. Primary write goes direct. This is an L4 LB — HAProxy does not inspect SQL, just routes TCP connections.
05 · Follow-ups

Every hard follow-up, answered

How do you achieve zero-downtime deployments with a load balancer?+
Rolling deployment with connection draining.

1. Take server-1 out of rotation: set its weight to 0 in the LB. New requests stop going to it.
2. Connection draining: wait for existing connections on server-1 to complete naturally (or timeout after 30s). During this period, server-1 still serves in-flight requests but receives no new ones.
3. Deploy new version to server-1. Wait for health check to pass.
4. Add server-1 back to rotation. Repeat for server-2, etc.

For databases: blue-green deployment — spin up a complete new fleet, promote when ready. Instant cutover with instant rollback. Requires double infrastructure temporarily.
Is the load balancer itself a single point of failure?+
Yes — and the mitigation is to run multiple LBs with automatic failover.

For managed cloud LBs (AWS ALB/NLB): AWS runs them as a managed service across multiple AZs automatically. Not your problem.

For self-managed LBs: run two Nginx/HAProxy instances in active-passive with keepalived. keepalived uses VRRP (Virtual Router Redundancy Protocol) — a virtual IP floats to whichever Nginx is healthy. If primary dies, virtual IP moves to secondary in <1 second. DNS points to the virtual IP, not to either specific host.

At Google/Netflix scale: use anycast routing — the same IP address is announced from multiple data centers. BGP routing automatically sends users to the nearest available one. Individual LB failures are invisible to users.
How does a load balancer handle sticky sessions without storing state?+
Sticky sessions route the same user to the same server, but the LB itself should not store per-user state (that would make the LB stateful and harder to scale).

Cookie-based stickiness (L7): LB injects a cookie (AWSALB, JSESSIONID) containing a hashed identifier for the target server. On subsequent requests, LB reads the cookie and routes to the indicated server. LB is stateless — the routing information lives in the client's cookie.

Consistent hash by IP/User-ID (L4): hash the source IP (or a user ID from headers) to deterministically select the same server. No state stored anywhere. Downside: if server counts change, the hash remaps — consistent hashing mitigates this.

When to avoid sticky sessions: sticky sessions make scaling and rolling deploys harder (you must drain a server of its sticky sessions before removing it). If your application needs stickiness, consider moving the stateful data to a shared store (Redis) instead, so any server can handle any request.
What is the difference between a load balancer and an API gateway?+
All API gateways are load balancers, but not all load balancers are API gateways.

A load balancer distributes traffic across servers. It may be L4 (TCP-level) or L7 (HTTP-level). Its primary concern is traffic distribution and availability.

An API gateway is a superset: it also load balances, but adds: authentication (JWT validation), authorisation (RBAC checks), rate limiting (per-user quotas), request transformation (add/remove headers, transform body), API versioning (route /v1/ and /v2/ to different backend versions), observability (per-endpoint metrics and logging), and developer portal integration.

Rule of thumb for interviews: if the component needs to understand your business logic (who is this user? what plan are they on? is this request authorised?), it is an API gateway. If it just needs to distribute traffic reliably, it is a load balancer. In production, you typically have both: an L4 NLB at the outer edge (raw throughput), an L7 API gateway behind it (business logic), and internal load balancers between services.
07 · Decision Framework

Choosing the right load balancing layer

🎯Load Balancer Selection — Ask in Order
01
Do you need to inspect HTTP headers, URLs, or cookies to route?
YES →L7 (Application Layer) LB. AWS ALB, Nginx, Envoy, HAProxy HTTP mode. Path-based routing (/api/* vs /static/*), host-based routing, header-based A/B testing, SSL termination. Required for any URL-aware routing.
NO (pure TCP/UDP) →L4 (Transport Layer) LB. AWS NLB, HAProxy TCP mode. Raw TCP routing — faster, lower overhead, works for any protocol (MySQL, SMTP, game servers). Use when you don't need HTTP awareness.
02
Are request durations variable (some fast, some very slow)?
YES (variable duration) →Least Connections. Routes to server with fewest active connections. A slow server accumulates connections and receives fewer new ones automatically. Best for: WebSocket, video streaming, large uploads, ML inference endpoints.
NO (uniform fast requests) →Round Robin or Weighted Round Robin. Distributes evenly. Simple, low overhead. Best for: homogeneous stateless API servers with uniform request cost.
03
Do clients need to always reach the same backend (stateful)?
YES (stateful) →Sticky sessions. Cookie-based (LB injects AWSALB cookie) or consistent hash by user ID. Required for: WebSocket connections, legacy session-based apps. Prefer moving state to Redis so any server can handle any request.
NO (stateless) →Any algorithm — no stickiness needed. Stateless is always preferred. Store session state in Redis, not in-process. Enables free horizontal scaling and zero-downtime rolling deploys.
04
Internal microservice traffic or public edge traffic?
Internal (service mesh) →Envoy sidecar proxies + Istio. mTLS between services, circuit breaking, distributed tracing, dynamic config via xDS — all without changing application code. Overkill for small systems; essential at 50+ microservices.
Public edge →API Gateway (Kong/AWS API GW) + L7 LB. Auth, rate limiting, request transformation at the gateway. L7 LB (Nginx/ALB) distributes to backend fleet. Two layers: gateway handles business rules, LB handles distribution.
10 · Global Load Balancing

Beyond the datacenter — routing traffic across regions and continents

01 GeoDNS Latency-Based Routing
What it is
DNS responds with different IP addresses based on the requester's geographic location.

/p>

User in Mumbai queries api.myapp.com → GeoDNS determines their location → returns the IP of the Mumbai regional load balancer. User in London → returns the London LB IP. Same DNS name, different IP, routed to the nearest datacenter.

AWS Route 53 latency-based routing: measures actual latency between the user's DNS resolver and each region (not just geographic distance). Routes to the region with lowest latency, not just the nearest one. Tokyo might actually be faster than Singapore for some Australian users.

→DNS TTL = 60 seconds: if a region goes down, GeoDNS removes it from the response within 60s. But some resolvers cache longer. For fast failover: use Anycast routing instead (or both together).
02 Anycast Routing
What it is
Multiple servers share the same IP address. BGP routing sends traffic to the topologically nearest server.

/p>

Cloudflare uses Anycast for its 200+ PoPs. Every PoP advertises the same IP address (e.g., 1.1.1.1). BGP automatically routes each user to the nearest PoP based on network topology. No DNS magic — happens at the routing layer.

Failover: if a PoP goes down, its BGP advertisement withdraws. Traffic automatically routes to the next-nearest PoP within seconds — faster than DNS TTL-based failover.

✓✓ Used by: Cloudflare, Akamai, AWS Global Accelerator (uses Anycast to route to the nearest AWS edge node). Faster failover than GeoDNS. Used for: DDoS mitigation (absorb attack traffic across many PoPs), low-latency global routing.
03 Active-Active vs Active-Passive Global
What it is
Active-active: multiple regions serve traffic simultaneously. Active-passive: one region serves, the other is standby.

/p>

Active-passive: all traffic goes to US-East. US-West is a warm standby. On US-East failure: DNS/Anycast switches to US-West. Recovery: 30–120 seconds. Simple. RPO/RTO: minutes. Right for: applications where global latency doesn't matter but simplicity does.

Active-active: US-East serves US traffic, EU-West serves European traffic, AP-Southeast serves Asia. Each region is a full stack. DB replication: bidirectional (Cassandra's multi-datacenter replication, or CockroachDB global tables). Right for: globally distributed user bases where latency matters. Hard part: write-write conflicts across regions need careful resolution.

✓✓ Notion runs globally active-active on AWS with CockroachDB. Stripe's payments infrastructure is active-active across 3 AWS regions. Cloudflare serves from 200+ PoPs active-active. Start with active-passive — upgrade to active-active when latency SLA demands it.
