00 · What a CDN Does

Serving content from 200 cities instead of one data centre

The warehouse vs corner shop analogy
Your origin server is a central warehouse in Mumbai. A user in Tokyo requests a video.

Without CDN: request travels Mumbai → Tokyo (~150ms round trip). At 10MB/s, a 1GB video takes 100 seconds to deliver from origin to the user.

With CDN: A CDN edge node in Tokyo has a cached copy. Same video served at ~1ms latency from the nearby PoP (Point of Presence). The origin server is never involved.

The CDN's job: be a corner shop stocking the 100 most popular items, so customers do not have to travel to the warehouse for common requests.
01 · How CDNs Work

PoP architecture, pull vs push, and cache invalidation

PoP & Anycast
CDNs have 200+ Points of Presence (PoPs) worldwide. Anycast routing sends users to the nearest PoP automatically.
Anycast: multiple PoPs announce the same IP address. BGP routing sends the user's packet to the geographically nearest PoP — no DNS lookup delay, no manual geo-routing config. ✓ Cloudflare: 200+ cities. Akamai: 4,000+ PoPs. Fastly: 50+ PoPs but higher bandwidth capacity. User latency: <20ms to nearest PoP anywhere in the world.
Pull CDN (Lazy)
CDN fetches content from origin on the first request (cache miss), then caches it.
First user in Tokyo requests /images/photo.jpg → CDN Tokyo misses → fetches from origin → caches → serves. All subsequent Tokyo users get it from cache. ✓ No management needed. Content is cached on demand. Automatically distributes popular content globally. Suitable for most web assets. ⚠ First user in each region gets origin latency (cache miss penalty). Content that is never requested globally stays uncached.
Push CDN (Eager)
You proactively upload content to all CDN PoPs before any user requests it.
Before a product launch: push all assets to 200+ PoPs. First user in Tokyo gets the asset from cache (zero miss). ✓ Zero cache miss latency. Guaranteed availability. Ideal for: software releases, video premiere events, product launch assets. ⚠ Management overhead. You pay for storage at all PoPs even if content is never requested there. Not suitable for dynamic or user-specific content.
Cache Invalidation
When origin content changes, you need to tell CDN edge nodes to drop their cached copies.

TTL expiry: set a short Cache-Control: max-age=300. Stale for up to 5 minutes.

Cache purge API: Cloudflare/CloudFront have APIs to immediately invalidate specific URLs or patterns. Used when you push a critical fix.

Cache versioning: embed version in filename — app.v2.3.js. Old URL still cached (fine), new URL fetched fresh. Zero-downtime asset updates. ✓ Best practice: use cache versioning for static assets (infinite TTL + version in URL). Use short TTL for semi-dynamic content. Use purge API for emergency fixes.

02 · Video Streaming via CDN

HLS, DASH, and adaptive bitrate — how Netflix/YouTube actually work

Adaptive Bitrate (ABR)
Video is encoded at multiple quality levels. The player automatically switches quality based on network speed.
A 2-hour movie is encoded at: 360p (1Mbps), 720p (4Mbps), 1080p (8Mbps), 4K (25Mbps).
Player measures available bandwidth every few seconds and requests the appropriate quality. ✓ Smooth playback despite varying network conditions. Starts at low quality (immediate playback) and upgrades as bandwidth permits.
HLS Segmentation
Video is split into 2–10 second segments stored as individual files. A manifest file (.m3u8) lists all segments.
Player downloads manifest → fetches segments sequentially → each segment is cached independently by CDN.
index.m3u8 → segment001.ts, segment002.ts ... ✓ CDN caches each segment independently. Popular segments (the first 10 seconds every viewer watches) have extremely high cache hit rates. Seeks jump to the correct segment URL directly.
CDN Role in Video
Video segments are static files → perfect for CDN caching.
Netflix: 3 copies of each segment stored in S3 (origin). CloudFront caches hot segments at 200+ PoPs. Popular shows: 99%+ cache hit rate. Long-tail content: served from origin. ✓ Netflix offloads ~95% of video bytes to CDN. Origin bandwidth savings: enormous. User experience: consistent quality regardless of Netflix's origin capacity.
03 · Edge Compute

Running code at the CDN edge

What Is Edge Compute
Run serverless code at the CDN PoP, close to the user — before the request reaches your origin.
Examples: Cloudflare Workers, AWS Lambda@Edge, Fastly Compute@Edge.
Use for: A/B testing (redirect 10% of users to new version at edge), auth token validation (validate JWT at edge, reject bad tokens before they hit origin), geo-based redirects, request transformation.
CDN for DDoS
CDN absorbs DDoS attacks at the edge — attack traffic never reaches your origin.
A 1Tbps DDoS attack is distributed across 200 PoPs. Each absorbs 5Gbps — trivial for a large PoP. Your 10Gbps origin link never sees the attack. ✓ Cloudflare's network capacity: 100+ Tbps. The largest DDoS attacks ever recorded were absorbed by Cloudflare without origin impact. Used by: every large web property (including FAANG).
04 · Decision Framework

How to talk about CDN in a system design interview

🎯CDN Strategy Selection — Ask in Order
01
Is the content static (same for all users)?
YES (static) →Definitely use CDN. Images, videos, JS/CSS bundles, compiled HTML. Cache at edge with long TTL (1 year for versioned assets). This is the highest-ROI CDN use case — zero origin load for cached content.
NO (dynamic/personalised) →Consider edge caching only for public, cacheable API responses. User-specific content cannot be cached at CDN without per-user cache keys (defeats the purpose). Go to Step 3.
02
For static content: push or pull CDN?
Known ahead of time →Push CDN. Proactively distribute to all PoPs before users request. Zero first-request miss. Use for: software releases, product launch assets, video premieres where you know demand will spike immediately.
Demand unpredictable →Pull CDN (default). First request per PoP hits origin. Subsequent requests served from cache. Automatically distributes popular content globally. Works for 99% of use cases.
03
Do you need logic at the edge (auth, A/B testing, geo-routing)?
YES →Edge Compute (Cloudflare Workers, Lambda@Edge). Validate JWTs at edge (reject invalid tokens before they hit origin), A/B test routing (redirect 10% to new version), geo-based content (show Indian prices to Indian users). Sub-ms overhead, no origin round-trip.
NO →Standard CDN caching. Just set appropriate Cache-Control headers on your origin responses. Cloudflare/CloudFront respects them automatically.
04
What is your cache invalidation strategy?
Versioned filenames →Best approach for static assets. app.v2.3.7.js — old URL stays cached forever, new URL fetched fresh. Zero-downtime deploy. Infinite TTL (Cache-Control: max-age=31536000, immutable).
Purge API →For emergencies. POST api.cloudflare.com/cache/purge with specific URLs. Propagates globally in <150ms (Fastly) to ~30s (CloudFront). Use sparingly — not designed for high-frequency changes.
Short TTL →For semi-dynamic content. Cache-Control: max-age=300. Stale for up to 5 minutes. Acceptable for: news articles, product prices, API responses that change infrequently.
05 · System Design Examples

CDN architecture in real systems

Netflix — Global Video Delivery
PETABYTES · ADAPTIVE STREAMING
OPEN CONNECT
Netflix runs its own CDN called Open Connect. Netflix appliances are co-located in ISP data centers worldwide (1,000+ locations). ISPs host these appliances for free in exchange for reduced peering costs. Result: ~95% of Netflix traffic served from inside the ISP's own network — no internet backbone traversal for the user's last mile.
PROACTIVE CACHING
Netflix pre-loads popular content to Open Connect appliances during off-peak hours (2–4am local time). Trending shows are pushed to all regional appliances before peak viewing. Cache hit rate for popular titles: ~99%. Long-tail content served from S3 origin via CloudFront.
HLS SEGMENTS
Each 2-hour movie = ~720 × 10-second HLS segments per quality level × 5 quality levels = 3,600 cached files. The first 60 seconds (6 segments) of every show is pre-loaded to all major PoPs — zero wait time when users press play. Subsequent segments loaded as user watches.
WHY OWN CDN
At Netflix's scale (~500Tbps peak bandwidth), commercial CDN costs would be $500M+/year. Open Connect amortises over company lifetime and gives Netflix full control over caching policy, health monitoring, and routing decisions.
E-Commerce — Asset Pipeline & API Caching
MIXED STATIC + DYNAMIC
STATIC ASSETS
Product images, CSS, JS bundled with content hash in filename (main.3f2c9a.js). Deployed to S3 → CloudFront. Cache-Control: max-age=31536000, immutable. Images CDN served from nearest PoP in <10ms globally. Origin S3 never receives image requests after initial population.
PRODUCT API
GET /api/products/{id} response: Cache-Control: public, max-age=300, s-maxage=3600. Browser caches 5 minutes, CDN caches 1 hour. Product catalog changes are infrequent — 1-hour CDN TTL is acceptable. CloudFront serves ~80% of product API requests without touching origin.
PERSONALISED
GET /api/cart, GET /api/user: Cache-Control: private, no-store. CDN never caches user-specific data. These requests always reach origin. Keep non-cacheable API calls minimal — design your API to maximise cacheable endpoints.
FLASH SALE
Flash sale landing page pre-pushed to all CDN PoPs 5 minutes before launch. Warm cache ensures zero origin load when 1M users hit the page simultaneously. Origin only handles the purchase API calls — which cannot be cached.
04 · Follow-ups

Every hard follow-up, answered

How do you cache personalised or authenticated content at the CDN?+
The standard CDN model caches public content. Personalised content requires one of three approaches:

1. Edge side includes (ESI): The page has a public frame (cached) with placeholder tags for personalised sections. CDN fetches only the personalised fragment from origin (small request) and assembles the full page. Used by: Akamai ESI, Varnish.

2. Split the response: API returns a public body + a personalised section. Public body cached at CDN (TTL=1h). Personalised section fetched fresh from origin on each request (bypass cache). Combine on the client.

3. Cache by session/user segment: CDN can cache separate copies per cache key, including cookies or auth headers: Vary: Authorization. But this effectively defeats caching for large user populations (one cache entry per user). Only viable for small user pools or role-based segmentation (admin vs regular user).

General rule: use CDN for the parts of your response that are genuinely the same for all users. Fetch personalised parts dynamically. The split between cacheable and dynamic is a key architectural decision.
Cloudflare vs CloudFront vs Fastly — which should you use?+
All three are production-grade. The decision is usually driven by cloud commitment and specific feature needs.

CloudFront (AWS): Best choice if you are already on AWS. Native integration with S3 (origin), ALB, API Gateway, Lambda@Edge. Pricing: per-GB transfer + per-request. Can get expensive at very high volume. Management via AWS Console/IaC (Terraform, CDK).

Cloudflare: Independent of cloud provider. Largest network (200+ PoPs, 100+ Tbps). Best DDoS protection. Workers are the most capable edge compute. Generous free tier. Flat pricing at enterprise scale (often cheaper than CloudFront for high-volume). Best choice for: security-first setups, cloud-agnostic architectures, maximising CDN network size.

Fastly: Fewer PoPs but very high capacity at each. Instant purge API (<150ms globally) — critical for news sites and real-time content. Varnish-based — very developer-friendly cache configuration. Best choice for: media companies, news sites, any use case where sub-second cache invalidation is critical.
How does CDN handle HTTPS — does the CDN see your encrypted traffic?+
Yes — the CDN terminates TLS on your behalf. The CDN can see the decrypted content.

When a user connects to your CDN (Cloudflare, CloudFront), TLS is terminated at the CDN edge. The CDN decrypts the request, makes a routing decision (cache hit or origin fetch), and re-encrypts for the origin if needed.

End-to-end encryption: configure your CDN to also use HTTPS when fetching from origin (origin pull over HTTPS). This means: User → TLS → CDN edge → TLS → Origin. Two separate TLS sessions, both encrypted. The CDN can see the plaintext in the middle — this is a trust question, not a technical limitation.

TLS certificates: CDNs provision and renew TLS certificates automatically (Cloudflare's Universal SSL, CloudFront ACM). You do not need to manage certificate rotation. The CDN's certificate covers your domain (yourdomain.com) via SNI (Server Name Indication) — one IP address serves HTTPS for thousands of domains on shared infrastructure.

For regulated industries (healthcare, finance): check your compliance requirements. Some regulations require end-to-end encryption where only the final recipient can decrypt. In practice, most enterprises use CDNs for HTTPS with contractual data processing agreements (DPAs) with the CDN provider.
What is the difference between a CDN and a reverse proxy — can Cloudflare Workers replace your backend?+
A CDN is a distributed reverse proxy network optimised for caching and delivery. Workers extend it to run arbitrary code at the edge.

CDN without Workers: caches and delivers static/cacheable content. Cannot make database queries, cannot run business logic, cannot access your internal APIs. Acts as a transparent pass-through for uncached requests.

Cloudflare Workers: V8 JavaScript/WASM runtime at every PoP. Can: read/write KV store (Cloudflare KV, Durable Objects), make HTTP requests to external services, modify request/response on the fly, implement rate limiting logic, run ML inference (Workers AI).

What Workers can replace: stateless edge functions (JWT validation, header manipulation, A/B testing, geo-routing, simple redirects), static API responses (config, feature flags), lightweight personalization.

What Workers cannot replace: anything requiring your primary database (Cloudflare KV has ~50ms global read latency but limited querying capabilities), long-running computations (>30ms CPU limit per request), streaming heavy media processing.

The architecture: Workers as edge compute + your origin as the authority for dynamic data. Workers handle 90% of requests at the edge; only complex, personalised, or write requests reach your origin.
07 · Advanced CDN Topics

Range requests, edge functions, and cache invalidation at scale

01 Range Requests for Video Seeking
What it is
HTTP Range header allows a client to request any byte range of a file — enabling video seeking without HLS segmentation.

/p>

HTTP: GET /video.mp4 Range: bytes=45670000-45800000

Server (or CDN): 206 Partial Content Content-Range: bytes 45670000-45800000/1073741824

For a 1GB MP4: seek to 42 minutes → calculate byte offset (bitrate × time) → request only those bytes. CDN serves from cache if that range was previously requested (range is part of the cache key).

Why CDN caches ranges: CDN can cache full files and serve any range from cache. The first range request for a file causes CDN to fetch the full file from origin (or the requested range — implementation-dependent). Subsequent range requests served from CDN cache. This is why YouTube scrubbing is fast — popular video ranges are cached at the CDN edge.

02 Cache Invalidation at Scale
What it is
Purging a URL from 200+ CDN PoPs simultaneously — and why URL versioning is better.

/p>

API-based purge: DELETE https://api.cloudflare.com/zones/{id}/purge_cache. Propagates to all PoPs in ~1 second (Cloudflare claims 150ms). CloudFront purge: ~60 seconds. Fastly: <150ms with instant purge.

The better solution — immutable URLs with versioning: instead of /app.js (must invalidate on deploy), use /app.v3f4a9.js (content hash in URL). Old URL forever cached (TTL=1 year). New deploy: new hash → new URL → automatically served. Zero invalidation needed.

✓✓ This is how Next.js, Vite, and Webpack handle static assets: hash in filename → set Cache-Control: max-age=31536000, immutable → CDN caches forever. Only HTML files with TTL=60s for the version pointers. Zero cache invalidation needed on deploy.
03 CDN vs Reverse Proxy vs API Gateway
What it is
Similar but different layers. Understanding the distinction is a Director-level signal.

/p>

CDN: globally distributed cache for static and cacheable content. Brings content closer to users. Origin sits behind it. Cache hit = CDN never calls origin. Examples: CloudFront, Cloudflare, Akamai.

Reverse Proxy: single-location intermediary for routing, SSL termination, and caching. Sits in front of app servers in your data center. Nginx, HAProxy. Cache hit = doesn't hit app servers but still in your DC.

API Gateway: application-level routing with business logic. Auth, rate limiting, request transformation, API versioning. Kong, AWS API Gateway. Not primarily a cache.

→Cloudflare Workers blurs these lines: it's a CDN with programmable logic at each PoP. Can do auth, routing, transformation at the edge — formerly only possible with origin API gateways.
