00 · Why Microservices

What microservices actually solve — and what they don't

The restaurant analogy
A monolith is a restaurant where one chef does everything: takes orders, cooks, plates, serves, handles billing. When busy, everything slows together. If the chef is sick, the whole restaurant closes.

Microservices is a restaurant with specialists: one takes orders, one cooks, one plates, one serves. Each can work at their own pace. If the dessert chef is sick, you still serve main courses. But now you need a manager (orchestrator), communication protocols between stations, and coordination — way more overhead than one chef.

The lesson: microservices solve organisational and scaling problems, not technical ones. A well-written monolith is almost always simpler and faster than a poorly-designed microservices architecture.
01Service Discovery
What it is
How does Service A find Service B when B's IP changes every time it restarts?

Client-side discovery: each service queries a registry (Consul, Eureka) for the addresses of its dependencies. The client does load balancing.

Server-side discovery: the client sends requests to a load balancer or API gateway. The gateway queries the registry and routes. Client doesn't need to know about other services.

Kubernetes DNS: every Service gets a stable DNS name (payment-service.default.svc.cluster.local). kube-proxy handles routing. Services never hard-code IPs — they use DNS names. This is the de-facto standard in modern architectures.

02Saga: Orchestration vs Choreography
What it is
Two ways to coordinate multi-step distributed transactions:

Choreography: each service publishes events. Other services react to events they care about. No central coordinator. OrderService publishes OrderCreated → InventoryService listens and reserves stock → publishes StockReserved → PaymentService charges → publishes PaymentComplete → ShipmentService ships.

Orchestration: a central saga orchestrator calls each service in sequence. If a step fails, the orchestrator calls compensating transactions. OrderSaga.execute() → call Inventory → if success, call Payment → if fail, call Inventory.rollback().

→Choreography: more decoupled, harder to debug ("why didn't the shipment happen?"). Orchestration: easier to understand and debug, single saga class shows the full flow. Temporal.io is the modern orchestration choice at FAANG.
03Strangler Fig Pattern
What it is
Incrementally extract services from a monolith without a risky big-bang rewrite. Step 1: put a facade/proxy in front of the monolith. All traffic goes through the proxy. Step 2: extract one capability (e.g., user authentication) into a new service. Update the proxy to route auth requests to the new service, everything else to the monolith. Step 3: repeat. One service at a time. The monolith shrinks. The services grow. The monolith eventually handles nothing and is decommissioned.
✓✓ Used by: Amazon (2001–2010), Twitter, Shopify. No downtime. Risk is isolated to each extraction. Easy rollback (just reroute the proxy). Takes 1–3 years for a large monolith — that's fine.
04Sidecar Pattern
What it is
Deploy a helper container alongside each service container to handle cross-cutting concerns without modifying service code. Istio/Envoy: inject an Envoy proxy sidecar next to every service pod. The sidecar handles: mTLS encryption, distributed tracing, circuit breaking, rate limiting, retries — all without changing a single line of application code.
✓✓ Cross-cutting concerns (security, observability, reliability) implemented once in the sidecar, applied uniformly across all services. New service inherits all capabilities automatically. Used by: Lyft (created Envoy), Google (created Istio), Netflix (Zuul as an API gateway sidecar).
05API Gateway Pattern
What it is
Single entry point for all client requests. Routes, transforms, and enforces policies across services. External clients call the API gateway. Gateway handles: routing to the right service, authentication (validate JWT once at gateway, pass user identity downstream), rate limiting (per-user quotas at a single enforcement point), request transformation (translate mobile API format to internal gRPC), response aggregation (call multiple services, combine results for one client response).
✓✓ Clients talk to one address. Backend services can change independently. Cross-cutting policies enforced consistently. Backend For Frontend (BFF) variant: separate gateway per client type (mobile BFF, web BFF, partner BFF) — each optimises responses for its client's needs.
06Outbox Pattern
What it is
Guarantee that a DB write and an event publication happen atomically — or neither happens. Problem: order service writes order to DB → publishes OrderCreated to Kafka → process crashes between the two → order exists but event never published → downstream services never know the order was placed. Solution: in the same DB transaction, write the order AND write an "outbox" record (a pending event). A separate outbox processor reads pending events → publishes to Kafka → marks as sent. If processor crashes: it re-reads unpublished events on restart. Exactly-once publishing via idempotency key in the event.
✓✓ Atomicity between DB write and event publication without 2PC. The pattern powering reliable event-driven microservices. Tools: Debezium (CDC from DB outbox table → Kafka automatically).
01 · System Design Examples

Microservices patterns in real systems

Netflix Microservices Architecture
500+ SERVICES · CHAOS ENGINEERING
DISCOVERY
Netflix uses Eureka for service registration. Each service registers at startup. Client-side load balancing via Ribbon (now Envoy). Every service instance has a health check endpoint. Eureka removes unhealthy instances from the registry within 90 seconds.
RESILIENCE
Hystrix (circuit breaker) on every external call. If Recommendation Service fails, fallback returns a cached/default list — users still see content. Chaos Monkey randomly kills production instances — forces engineers to design for failure. "Anything that can fail will fail" is the operating assumption.
API GATEWAY
Zuul (API gateway) handles: dynamic routing, A/B testing (1% of users get new recommendation algorithm), authentication (JWT validation before any service is called), request fanout (one /home request → calls 10 services in parallel for personalised content sections).
E-Commerce Order Flow — Saga Orchestration
SAGA · TEMPORAL · COMPENSATION
HAPPY PATH
User places order → OrderSaga starts → (1) Reserve inventory [InventoryService] → (2) Charge payment [PaymentService] → (3) Create shipment [ShipmentService] → (4) Send confirmation [NotificationService] → Order complete. All steps orchestrated by Temporal workflow.
FAILURE: PAYMENT FAILS
Step 2 fails → Saga triggers compensations in reverse: (1) Release inventory reservation [InventoryService.release()] → (2) Send "payment failed" notification → Order marked FAILED. User sees: "Payment declined. Your item reservation has been released."
TEMPORAL
Temporal.io persists saga state to a DB. If the orchestrator crashes mid-saga, it resumes exactly where it left off. Each step is idempotent — retried safely. Long-running sagas (payment pending for 24h) handled naturally as Temporal workflows can sleep for days.
02 · Follow-ups

Every hard follow-up, answered

How do you handle distributed transactions in microservices — is 2PC ever appropriate?+
2PC is almost never appropriate for microservices. The Saga pattern is the right tool.

2PC requires a coordinator that holds locks on all participant resources until all confirm. In microservices: the coordinator must hold a DB lock on Service A, B, and C simultaneously. Service B is slow or unavailable → all locks held indefinitely → System A and C are blocked. In a distributed system where services fail independently, 2PC creates a blocking dependency that defeats the purpose of having independent services.

When 2PC IS appropriate: within a single database (PostgreSQL's internal transaction manager), or when using a database with built-in distributed transaction support (Google Spanner's TrueTime-based transactions, CockroachDB). These use optimised distributed commit protocols within a controlled infrastructure — very different from cross-service 2PC.

The Saga alternative: each service has a local transaction + compensating transaction. The saga orchestrates them. Failure at any step triggers compensations for already-completed steps. Eventual consistency is the price — for most business flows (order placement, user registration), this is perfectly acceptable.
How do you test microservices — integration tests are too slow and unit tests don't catch contract breaks?+
The testing pyramid for microservices: unit tests → contract tests → integration tests → E2E tests (minimal).

Contract testing (Consumer-Driven Contracts): Pact framework. Service A (consumer) defines what it expects from Service B's API (a "contract"). Service B's test suite runs against these contracts. If Service B changes its API and breaks Service A's contract, Service B's build fails — immediately, without a full integration environment.
br> Service virtualisation / mocks: in tests, dependencies are replaced with recorded responses (WireMock, Testcontainers). Service A's tests use a mock Service B that returns predefined responses. Fast, isolated, reproducible.

Component tests: deploy one service in isolation with its real database (Testcontainers spins up a real PostgreSQL in Docker) but mock all external services. Tests the full service behaviour without needing a live environment.

E2E tests (minimal): run a subset of critical user journeys in a staging environment after every deploy. Not every code path — just the happy path for the most critical flows. Heavy E2E test suites are slow and brittle; use them sparingly.
What is the Backend for Frontend (BFF) pattern and when do you use it?+
BFF: separate API gateway per client type (mobile, web, third-party), each optimised for its client's needs.

Problem: a general-purpose API must return enough data for all possible clients. Mobile app needs small payloads (limited bandwidth, small screen). Web app needs rich data (multiple sections on screen at once). Each client ends up calling many APIs and assembling data client-side — over-fetching or under-fetching.

BFF solution: Mobile BFF aggregates multiple microservice calls into one endpoint optimised for mobile: small payload, single round trip, mobile-specific fields. Web BFF returns richer payloads with different field sets. Partner API BFF exposes only what partners are permitted to see.

When to use it: when different clients have significantly different data needs. When mobile performance is critical (reduce round trips). When you need to version mobile and web APIs independently without coupling.

When NOT to use it: small teams where maintaining multiple gateways is too expensive. When clients have similar data needs. A single well-designed API with GraphQL (client-specified field selection) can replace multiple BFFs — clients request exactly the fields they need, no BFF required.
How does service mesh differ from an API gateway — why do you need both?+
API gateway handles north-south traffic (external clients to your services). Service mesh handles east-west traffic (service to service).

API Gateway: sits at the edge. Handles: external authentication, rate limiting per external client, request routing to the right microservice, response transformation for external clients, API versioning. Knows about business-level concepts (user tiers, API keys).

Service Mesh (Istio/Envoy): sits between every pair of services. Handles: mTLS (service-to-service encryption and authentication), circuit breaking (stop calling a failing service), distributed tracing (record timing for every hop), load balancing within the cluster, retries with exponential backoff. No business logic — purely infrastructure.

Why both: the API gateway handles external concerns (business-level policies), the service mesh handles internal concerns (infrastructure-level reliability). They operate at different layers and don't overlap. In practice: Kong/AWS API GW at the edge + Istio inside the cluster. Each handles what it's designed for.

Requirements & Non-Functional Constraints

Functional Requirements

FR1Service discovery: find service instances without hardcoded IPs
FR2Saga: coordinate multi-step distributed transactions
FR3API Gateway: single entry point for all external traffic
FR4Service mesh: mTLS, tracing, circuit breaking between services
FR5Outbox pattern: atomic DB write + event publish (no 2PC)
FR6Strangler Fig: migrate monolith to microservices incrementally

Non-Functional Requirements

NFR1Service-to-service latency: < 5ms with mTLS (Istio/Envoy)
NFR2Saga compensation: complete within 30s on failure
NFR3API gateway throughput: 100K req/sec (Kong, AWS API GW)
NFR4Deployment frequency: 50+ deploys/day per team (independent CI/CD)
NFR5Service startup time: < 10s for rolling deploys with no downtime
NFR6Mean time to detect failure: < 2min via health checks + tracing
