The mental model before memorising anything

Most candidates treat REST, WebSocket, gRPC, and GraphQL as competing options. They're not — they solve different communication problems. Before picking any protocol, answer one question:

The single question that matters

Who initiates communication, and how often does data change?

Client asks once, server replies once → Request-Response (REST, gRPC, GraphQL)

Server needs to push data to client without the client asking → Server Push (SSE, WebSocket, Long Polling)

Client and server need to talk simultaneously, continuously → Bidirectional (WebSocket, gRPC streaming)

The restaurant analogy — for a complete layman
REST is a waiter who takes your order, goes to the kitchen, and comes back with exactly what you asked for. Simple, stateless, everyone knows the rules.

gRPC is a waiter using a walkie-talkie with the kitchen using a shared codebook. Faster, more efficient, but both sides need the same codebook (Protobuf schema).

GraphQL is a waiter who lets you design your own plate. "I want 3 items from dish A and 2 from dish B, in one trip." You get exactly what you asked for — nothing more, nothing less.

WebSocket is a phone call — once connected, both sides can speak at any moment without hanging up and redialling.

SSE is a radio broadcast — the server talks continuously to all listeners, but listeners can't transmit back on the same channel.

Long Polling is repeatedly calling the kitchen and asking "is my order ready yet?" — the kitchen keeps you on hold until it is, then hangs up. You immediately call back.
⚠ The interview trap that catches most candidates

"I'd use WebSocket for everything, it's the most powerful" is the answer that gets a candidate cut off fast. Persistent, bidirectional connections are a cost, not a free upgrade — they're stateful (breaking trivial load balancing), they bypass standard HTTP caching and status-code semantics, and they need custom retry/idempotency logic that REST gets for free. The candidates who score well default to the simplest protocol that satisfies the requirement (usually REST) and only reach for WebSocket, SSE, or gRPC streaming when a specific, stated requirement — genuine bidirectional real-time, server push, or internal RPC volume — demands it. Naming the cost of the "powerful" option is exactly what separates a senior answer from a junior one.

The Two Families

Request-Response
Client sends a request, server replies, connection closes. Each interaction is independent. The server has no memory of previous requests unless you send a session token.
Members: REST, gRPC (unary), GraphQL Query/Mutation. HTTP/1.1, HTTP/2, HTTP/3 are the transports.
Persistent / Push
Connection stays open. Server can push data without the client asking. Crucial for real-time features: live feeds, notifications, chat, collaborative editing.
Members: WebSocket (bidirectional), SSE (server→client only), Long Polling (simulated push), gRPC streaming.
01 · Request-Response Family

REST, gRPC, and GraphQL — the three ways to ask

🌐
REST
HTTP · Stateless · Resource-Oriented
The universal default. Every HTTP client speaks it. Resources are nouns (URLs), actions are verbs (GET/POST/PUT/DELETE). No special tooling needed. The right choice until it isn't.
Born 2000 · Roy Fielding's PhD thesis · HTTP/1.1 + HTTP/2
⚡
gRPC
HTTP/2 · Binary · Contract-First
Google's internal RPC framework. Define your API in a .proto file — both sides generate code from it. Binary encoding (Protobuf) is commonly several times smaller and faster than JSON REST (published benchmarks vary widely by payload shape). Built for internal service-to-service calls.
Born 2015 · Google · HTTP/2 + Protobuf
◈
GraphQL
HTTP · Query Language · Client-Driven
Facebook's answer to REST's over-fetching problem. The client describes exactly what data it needs in a typed query. One endpoint, infinite flexibility. Ideal when different clients (mobile/web/partner) need different shapes of the same data.
Born 2015 · Facebook · HTTP/1.1 + HTTP/2

REST — How It Actually Works

Resources & Verbs
REST maps actions to HTTP methods and nouns to URLs.
GET /users/123 → fetch user
POST /users → create user
PUT /users/123 → replace user
PATCH /users/123 → partial update
DELETE /users/123 → delete user The URL is the resource (noun). The HTTP method is the action (verb). This separation is REST's core design principle.
Stateless
Every request must contain everything the server needs to process it. The server stores no session between requests. Identity always comes from a token in the header — never assumed from context.
✓ Statelessness makes REST trivially horizontally scalable — any server can handle any request. No sticky sessions needed.
HTTP Caching
GET requests are cacheable by default — CDNs, browsers, and proxies can cache them. This is one of REST's biggest advantages over gRPC and GraphQL.
Cache-Control: max-age=3600 tells every layer to cache for 1 hour.
✓ A public REST API with GET responses cached at Cloudflare reduces origin traffic by 95%+. gRPC and GraphQL cannot use HTTP caching natively.
Status Codes
HTTP status codes carry semantic meaning every client understands natively:
200 OK · 201 Created · 204 No Content
400 Bad Request · 401 Unauthorised · 403 Forbidden · 404 Not Found
429 Rate Limited · 500 Server Error · 503 Unavailable Every HTTP client, load balancer, and monitoring tool understands these codes. GraphQL always returns 200 — errors are in the response body, invisible to infrastructure.
Over-Fetching
REST's biggest weakness: you get what the endpoint returns, not what you need.
GET /users/123 returns all 40 fields. Your mobile app only needed name and avatar.
⚠️ On mobile with limited bandwidth, over-fetching wastes data and slows rendering. This is exactly why Facebook invented GraphQL.
Under-Fetching
REST's second weakness: one endpoint rarely returns all the data you need.
To show a user's profile with their posts and followers: GET /users/123 + GET /users/123/posts + GET /users/123/followers — 3 round trips.
⚠️ On mobile, each extra round trip adds 50–200ms. Waterfall requests add up fast. GraphQL solves this with a single query.

gRPC — How It Actually Works

Protocol Buffers
gRPC uses Protobuf — a binary serialisation format — instead of JSON. You define your data schema in a .proto file. Both client and server generate code from it automatically.
✓ Binary is commonly cited as ~30–40% smaller than equivalent JSON, with parsing 2–6x faster in published benchmarks (both figures vary by payload shape). At 1M requests/sec, even the conservative end of that range matters enormously.
HTTP/2 Multiplexing
gRPC runs on HTTP/2, which multiplexes multiple requests over a single TCP connection. With HTTP/1.1 REST, each request needs its own connection (or connection pooling). HTTP/2 sends hundreds of requests simultaneously over one connection.
✓ Huge advantage for service-to-service calls where you're making thousands of RPCs per second between the same two services.
Streaming Modes
gRPC supports 4 modes — REST only supports request-response:

Unary — one request, one response (like REST)

Server streaming — one request, stream of responses (like SSE)

Client streaming — stream of requests, one response (uploading chunks)

Bidirectional streaming — both sides stream simultaneously (like WebSocket) Real example: Google Maps sends your location as a client stream, receives route updates as a server stream — all over one gRPC bidirectional connection.

Schema Contract
The .proto file is a strict API contract between client and server. Both sides must use the same schema. Adding a field is backwards-compatible; removing one breaks older clients.
⚠️ gRPC requires code generation on every schema change. REST and GraphQL don't. This is operational overhead — significant for teams with many services.
Browser Support
Browsers cannot call gRPC directly. HTTP/2 trailers (which gRPC uses) are not exposed by browser APIs. You need gRPC-Web (a proxy layer) or gRPC-Gateway (which translates to REST).
⚠️ This is why gRPC is almost exclusively used for internal service-to-service communication, not for public-facing APIs.

GraphQL — How It Actually Works

Single Endpoint
GraphQL has one endpoint: POST /graphql. The query in the request body describes exactly what data to return. No URL routing, no versioning headaches — the schema evolves by adding fields (never removing).
This is how Facebook, GitHub, Shopify, and Twitter serve data to their apps — one endpoint, infinite flexibility.
Query vs Mutation
Query = read (like GET). Mutation = write (like POST/PUT/DELETE). Subscription = real-time push (like WebSocket).
query { user(id:"123") { name, avatar, followerCount } }
mutation { createPost(input:{...}) { id, createdAt } } Subscriptions use WebSocket under the hood — GraphQL is a query language on top of a transport, not a transport itself.
N+1 Problem
GraphQL's biggest pitfall: a single query can trigger hundreds of database calls.
Query for 100 posts, each needing its author → 1 query for posts + 100 queries for authors = 101 DB calls.
⚠️ Fix: DataLoader (batches and deduplicates database calls). Every GraphQL implementation needs it or performance degrades to unusable.
Introspection
GraphQL APIs are self-documenting. Clients can query the schema itself to discover all available types, fields, and operations — no separate Swagger/OpenAPI needed.
✓ Tools like GraphiQL and Apollo Studio give developers interactive playgrounds. New team members explore the API without reading docs.⚠️ Disable introspection in production — it exposes your entire data model to attackers.
Caching Problem
GraphQL uses POST for queries — HTTP caching doesn't work natively. CDNs only cache GET requests. Every GraphQL query hits your origin.
Workarounds: Persisted Queries (assign each query a hash, send hash as GET), Apollo CDN caching, or Cloudflare Workers. More complexity than REST's built-in GET caching.
02 · Real-Time Family

WebSocket, SSE, and Long Polling — the three ways to push

Why REST can't do real-time

REST is pull-only: the client must ask before the server can respond. For a chat app, polling every second means thousands of empty responses. For a live dashboard, you'd poll 60 times/minute per user. At 100K users, that's 6M requests/minute for mostly empty data.

Real-time protocols invert this: the server pushes data the moment it's available. No polling, no wasted requests, no latency from the polling interval.

🔌
WebSocket
Full-Duplex · Persistent · TCP
A persistent bidirectional connection over a single TCP socket. Once the HTTP handshake upgrades to WS, both client and server can send messages at any time, simultaneously. The gold standard for true real-time: chat, multiplayer games, collaborative editing.
Born 2011 · RFC 6455 · HTTP Upgrade handshake
📡
Server-Sent Events
Server→Client Only · HTTP · Auto-Reconnect
A simple HTTP connection that stays open. The server pushes text events whenever it wants. The client cannot send data back on this connection. Simpler than WebSocket, works with HTTP/2 multiplexing, and auto-reconnects on disconnect.
Born 2006 · W3C Standard · HTTP/1.1 + HTTP/2
🔄
Long Polling
Simulated Push · HTTP · Request-Response
Client sends a request. Server holds it open until data is available or a timeout occurs. Client immediately sends a new request. Simulates real-time over plain HTTP — no special protocol needed. The legacy fallback when WebSocket isn't available.
Born ~2000s · No official standard · Plain HTTP

WebSocket — How It Actually Works

The Upgrade Handshake
WebSocket starts as an HTTP request, then upgrades to a persistent TCP connection.
Client sends: GET /ws HTTP/1.1, Upgrade: websocket
Server responds: 101 Switching Protocols
Now: raw TCP frames flow in both directions — no HTTP overhead per message. Why HTTP start? Firewalls and proxies block arbitrary TCP but allow HTTP port 80/443. The upgrade trick bypasses firewall restrictions.
Full-Duplex
Both client and server can send messages at any moment, simultaneously, over the same connection. No waiting for the other side. No request-response cycle.
✓ This is why WebSocket is used for chat (user sends and receives simultaneously), multiplayer games (constant position updates both directions), and collaborative editing (every keystroke sent immediately).
Framing
WebSocket sends data as frames, not HTTP requests. Each frame has a tiny 2–10 byte header (opcode, mask, length) vs HTTP's 200–800 byte headers per request.
✓ A chat message sent via WebSocket costs ~10 bytes overhead. Via HTTP polling: 300–800 bytes of headers per poll even when empty. At 1M active users, this difference is measured in gigabits per second.
State & Scaling
WebSocket connections are stateful and sticky — the connection lives on a specific server. If that server dies, all its connections drop. Clients must reconnect.
⚠️ You cannot load-balance WebSocket with standard round-robin. You need sticky sessions (by user_id) or a pub/sub broker (Redis, Kafka) so any server can push to any user regardless of which server they're connected to.
Heartbeats
Idle WebSocket connections get killed by proxies and NAT gateways after 30–90 seconds. Solution: ping/pong heartbeat every 20–30 seconds. Server sends a ping frame, client echoes a pong. No pong = connection dead, clean up and notify.
Every production WebSocket implementation needs heartbeat logic. Without it, you get ghost connections — the server thinks the client is connected but the client is gone.

SSE — How It Actually Works

The Wire Format
SSE is a plain HTTP response that never ends. Content-Type is text/event-stream. The server sends newline-delimited text events:
data: {"type":"view","count":1247}\n\n
data: {"type":"view","count":1248}\n\n Two consecutive newlines signal the end of one event. The browser's EventSource API parses this automatically and fires events at your JavaScript handler.
Auto-Reconnect
The browser's EventSource automatically reconnects after a disconnect. The server sends an event ID with each event. On reconnect, the browser sends Last-Event-ID header — the server can replay missed events.
✓ This makes SSE dramatically simpler to operate than WebSocket. No custom reconnect logic needed on the client. Works out of the box.
HTTP/2 Multiplexing
Over HTTP/2, multiple SSE streams share one TCP connection. With HTTP/1.1, browsers limit connections per domain (typically 6). If you have 6 SSE streams, you've used all connections. HTTP/2 multiplexes hundreds over one connection.
✓ Use HTTP/2 for SSE at scale. HTTP/1.1 SSE has a hard limit of ~6 concurrent streams per browser per domain.
One Direction Only
SSE is server-to-client only. The client cannot send data back on the same connection. For any client action (user sends a message, acknowledges a notification), you make a separate REST/HTTP POST call.
This is the key difference from WebSocket. In most notification/feed systems this is fine — client-to-server actions are already REST calls.

Long Polling — How It Actually Works

The Mechanism
Step by step:
1. Client sends GET /messages?since=1234
2. Server checks if new messages exist. If yes → respond immediately. If no → hold the connection open
3. When a message arrives, server responds with it
4. Client receives response, immediately sends a new request
5. Repeat forever Timeout: if no data after 30 seconds, server responds with 204 No Content. Client retries. This prevents proxy timeouts.
vs Regular Polling
Regular polling: client asks every N seconds regardless. Empty responses waste bandwidth and add N seconds of latency.
Long polling: client asks once, server responds only when there's data. Near-zero latency, zero empty responses.
✓ Long polling is near-real-time with standard HTTP. No WebSocket, no special protocol. Works everywhere HTTP works.
Scalability Challenge
Long polling holds server threads/connections open while waiting. With 100K concurrent users each holding a long poll connection, you need 100K open connections on your servers — consuming file descriptors and memory even when idle.
⚠️ Mitigate with async event loops (Node.js, Go goroutines, Nginx) that handle thousands of open connections on a single thread. Traditional thread-per-request servers (Java/Rails) cannot scale long polling.
When Still Used
Long polling is the fallback when WebSocket is unavailable (corporate firewalls blocking WS) or for systems where you need guaranteed delivery with replay.
Real usage: Slack originally used long polling before WebSocket. Some mobile apps in restricted networks still use it. XMPP Bosh protocol is long polling. Most modern systems use WebSocket or SSE instead.

04 · Where They Complement Each Other

Protocols that work together — not against each other

The biggest interview insight: real systems use multiple protocols simultaneously. The request-response and real-time families solve different problems and are designed to be combined. Here are the six most common patterns you'll see and need to justify in interviews.

REST + WebSocket
REST for actions · WebSocket for events
REST handles all mutations (send message, create post, update status). WebSocket delivers the real-time events (new message received, presence change, typing indicator). The REST call triggers the server-side change; WebSocket broadcasts the result to affected users.
Used by: Slack, Discord, WhatsApp Web, Notion
REST + SSE
REST for writes · SSE for live updates
User submits actions via REST (POST /start-analysis). Server acknowledges immediately with a job ID. SSE stream delivers progress updates as the job runs. Simpler than WebSocket because the client never needs to send mid-stream. Classic for progress bars, live dashboards, AI streaming responses.
Used by: GitHub Actions, Vercel deployments, OpenAI API (streaming tokens), monitoring dashboards
REST (external) + gRPC (internal)
REST at the edge · gRPC between services
Public API exposed as REST — universal browser support, HTTP caching, familiar to all clients. Internal microservice calls use gRPC — meaningfully smaller payloads, strict typed contracts, HTTP/2 multiplexing. An API Gateway (like Envoy or Kong) translates REST→gRPC at the boundary.
Used by: Google, Uber, Netflix, most FAANG internal architectures
GraphQL + WebSocket
GraphQL Queries/Mutations + GraphQL Subscriptions
GraphQL queries and mutations travel over HTTP for reads and writes. GraphQL Subscriptions use WebSocket under the hood for real-time updates. One unified schema — the client uses the same GraphQL types and vocabulary for both. Apollo Client handles both transports automatically.
Used by: GitHub (GraphQL API + subscriptions), Hasura, Shopify Storefront API
REST + Long Polling (legacy)
REST everywhere · Long polling as fallback
When WebSocket or SSE is blocked by corporate firewalls or unsupported by old clients, long polling bridges the gap. Standard REST for all actions; long polling for the notification channel. Socket.io does exactly this — it tries WebSocket first, falls back to long polling automatically.
Used by: Socket.io fallback, legacy enterprise apps, restricted network environments
gRPC Bidirectional Streaming
One protocol, four modes
For pure service-to-service real-time, gRPC bidirectional streaming replaces both REST and WebSocket. Both sides stream simultaneously over a single HTTP/2 connection. Used for location tracking (client streams GPS, server streams route), audio/video processing, real-time ML inference pipelines.
Used by: Google Maps, real-time ML pipelines, internal FAANG service meshes
The Interview Sound Bite

"In most production systems I would use REST for the request-response layer and pair it with either SSE or WebSocket for the real-time layer — depending on whether the client needs to send data back on the same connection. REST handles mutations; the real-time channel delivers server-initiated events. gRPC replaces REST for internal service-to-service calls where latency and throughput matter."

05 · Applied to Real Systems

Which protocol wins in which system?

Chat App (Slack / WhatsApp)
BIDIRECTIONAL · REAL-TIME
SEND MESSAGE
REST ✓ POST /messages — client sends message, server persists it, returns message ID + timestamp. REST because: idempotency key prevents duplicates on retry, HTTP status codes signal delivery failure clearly, easy to rate-limit with standard middleware.
RECEIVE MESSAGES
WebSocket ✓ Server pushes new messages to all room members the moment they arrive. Bidirectional needed: client also sends typing indicators and read receipts back on the same connection. Sub-10ms delivery vs 1–5 second polling lag.
PRESENCE / TYPING
WebSocket ✓ "Alice is typing…" — client sends typing events over the WebSocket every keystroke. Server fans out to all members via pub/sub (Redis). Low-overhead frames, no HTTP headers per event.
INTERNAL SERVICES
gRPC ✓ Message Service → Notification Service → Presence Service: all internal. Protobuf contracts prevent schema drift. HTTP/2 multiplexing handles thousands of RPCs/sec between services without connection explosion.
WHY NOT ALL WS
Tradeoff ⚠ WebSocket for everything seems elegant but: WS mutations can't use HTTP caching, rate limiting is harder, retry logic needs custom implementation, and load balancing requires sticky sessions. REST for writes + WS for events is the industry standard split.
Top-K Trending Dashboard (YouTube / Twitter)
SERVER PUSH · READ-HEAVY
LIVE RANKINGS
SSE ✓ Dashboard shows top 10 videos updating every 30 seconds. SSE stream pushes updates from Flink flush events. Client never sends data back — perfect SSE fit. Auto-reconnect handles network hiccups transparently. HTTP/2 multiplexes thousands of concurrent dashboard viewers.
INITIAL DATA LOAD
REST ✓ GET /top-k?window=1h®ion=IN loads the initial ranked list. Cacheable at CDN edge (60s TTL). 95% of requests served from cache — SSE stream only delivers delta updates after the initial load.
WHY NOT WEBSOCKET
Overkill ⚠ The dashboard is read-only — users never push data back. WebSocket's bidirectional capability is wasted. SSE is simpler: no handshake upgrade, works through HTTP/2 proxies without special configuration, auto-reconnects, and uses standard HTTP connections that load balancers understand natively.
WHY NOT POLLING
Inefficient ✗ At 30s poll interval and 100K concurrent users: 100K requests every 30s = 3,333 requests/sec, most returning the same data. SSE uses a persistent connection per user — 0 requests until data changes. Orders of magnitude less origin traffic.
Mobile App API (Instagram / Uber)
MULTI-CLIENT · BANDWIDTH-SENSITIVE
WEB APP API
REST ✓ Desktop browser with good connectivity. REST with HTTP/2 is fast, cacheable, and familiar. No over-fetching problem at this scale — one REST response per screen is acceptable.
MOBILE APP API
GraphQL ✓ Mobile on 4G/5G with limited bandwidth. GraphQL lets the app fetch exactly the fields it needs — no wasted data. One query fetches feed + stories + story counts instead of 3 REST calls. Field-level selection commonly cuts mobile payload size meaningfully versus a fixed REST response, though the exact percentage depends heavily on how over-fetched the original REST shape was.
PARTNER API
REST ✓ Third-party developer integrations use REST. Universal support, simple to understand, extensive documentation. GraphQL's flexibility is a liability here — partners need a stable, versioned contract, not an evolving schema.
DRIVER LOCATION (Uber)
WebSocket ✓ Driver app streams GPS location every 2 seconds. Rider app receives driver position updates in real-time. Both directions active simultaneously — classic WebSocket scenario. gRPC bidirectional streaming works equally well for this internal use case.
Notification System (Apple Push / Firebase)
FAN-OUT · MOBILE PUSH
WEB NOTIFICATIONS
SSE ✓ Browser tab receives notifications via SSE stream. User doesn't send acknowledgements in the same connection — REST POST for "mark as read". Simple, reconnects automatically, works with HTTP/2.
MOBILE PUSH
REST ✓ Your server calls APNs (Apple) or FCM (Firebase) REST APIs to push notifications to iOS/Android. The OS maintains its own persistent connection to Apple/Google — you just trigger it via REST. Your app never holds a WebSocket open in the background.
INTERNAL FAN-OUT
gRPC ✓ Notification Service fans out to User Service, Device Service, and APNs Gateway all via gRPC. Hundreds of millions of notifications/day means every millisecond and byte of payload overhead compounds. Protobuf binary encoding + HTTP/2 multiplexing handles the load.
Collaborative Editing (Google Docs / Notion)
CRDT · REAL-TIME · MULTI-USER
EDITS
WebSocket ✓ Every keystroke is an operation (insert/delete + position). Operations are sent over WebSocket immediately. Server applies OT (Operational Transformation) or CRDT to merge concurrent edits from multiple users. The merged result is broadcast back to all connected users via the same WebSocket.
CURSOR POSITIONS
WebSocket ✓ "Alice is editing paragraph 3" — cursor broadcast via WebSocket at ~10 events/sec. Ephemeral — not persisted. WebSocket's low per-frame overhead makes this affordable even for documents with 50 simultaneous editors.
DOCUMENT SAVE
REST ✓ Periodic snapshot of document state sent via REST POST. Idempotent, retryable, separate from the real-time stream. REST for durability; WebSocket for real-time sync.
06 · The Decision Framework

How to pick in an interview — in 60 seconds

🎯Protocol Selection — Ask in Order
01
Does the server need to push data to the client without the client asking?
YES →You need a real-time protocol. Go to Step 2. REST alone cannot solve this.
NO →Request-Response is sufficient. Go to Step 4 to pick between REST, gRPC, and GraphQL.
02
Does the client also need to send data back on the same real-time connection?
YES →WebSocket. Chat messages, cursor positions, game inputs, collaborative edits — bidirectional continuous communication. Pair with REST for mutations that need HTTP semantics (retries, idempotency).
NO →SSE (preferred) or Long Polling (fallback). Live feeds, notifications, progress bars, dashboards — server pushes, client only reads. SSE is simpler and HTTP/2-native. Long Polling if SSE is unavailable.
03
Is this for browser clients or internal service-to-service?
Browser →WebSocket or SSE. Both have native browser APIs (WebSocket API, EventSource API). No proxy needed.
Service-to-Service →gRPC bidirectional streaming — all the benefits of gRPC (binary, typed, multiplexed) plus both sides can stream. Google Maps, real-time ML inference pipelines.
04
Is this a public API, internal service, or multi-client API?
Public API →REST. Universal support, HTTP caching, familiar to all developers, simple to rate limit and monitor. Default until you have a specific reason to deviate.
Internal services →gRPC. Binary Protobuf (meaningfully smaller than equivalent JSON), HTTP/2 multiplexing, strict typed contracts. Ideal for service meshes where latency and throughput compound across hundreds of microservices.
Multi-client (web + mobile + partners) →GraphQL. Different clients need different data shapes. One schema, client-driven queries, no over-fetching on mobile bandwidth. Requires DataLoader to avoid N+1.
05
Do you have strict performance or bandwidth requirements?
Performance critical →gRPC over REST for service-to-service. Binary vs JSON: a meaningful payload reduction (published benchmarks commonly show tens of percent smaller, sometimes more depending on payload shape). At 1M RPC/sec between services, even the conservative end of that range is measurable in infra costs and latency percentiles.
Standard requirements →REST is fine. With HTTP/2 and proper JSON compression (gzip/brotli), REST performance is excellent for the vast majority of systems. Don't optimise prematurely.

The Rules You Must Know

🌐 Always use REST when…
  • Building a public-facing API
  • Need HTTP caching (GET responses)
  • Clients are diverse (browsers, mobile, partners)
  • Team is small, simplicity matters
  • CRUD operations with standard semantics
⚡ Always use gRPC when…
  • Service-to-service internal calls
  • High-throughput, latency-sensitive RPCs
  • Need strong schema contract between teams
  • Polyglot microservices (code gen handles language)
  • Streaming between services (bidirectional)
◈ Always use GraphQL when…
  • Multiple client types with different data needs
  • Mobile bandwidth is constrained
  • Rapidly evolving product with frequent data shape changes
  • BFF (Backend-for-Frontend) pattern
  • Developer experience is a priority
🔌 Always use WebSocket when…
  • Chat or messaging (bidirectional)
  • Multiplayer games or real-time collaboration
  • Both client AND server need to push continuously
  • Sub-100ms latency for every event
  • Persistent session with many small messages
📡 Always use SSE when…
  • Server pushes, client only reads
  • Live dashboards, feeds, notifications
  • AI streaming responses (token-by-token)
  • Progress bars for long-running jobs
  • Simpler alternative to WebSocket
🔄 Long Polling only when…
  • WebSocket and SSE are unavailable (firewalls)
  • Legacy client support required
  • Using Socket.io (handles fallback automatically)
  • Low update frequency (<1/min) where polling gap is fine
07 · Interview Follow-up Playbook

Every hard follow-up, answered

How do you scale WebSocket to millions of concurrent connections?+
The core challenge: WebSocket connections are stateful and live on a specific server. Standard round-robin load balancing breaks — if user A is connected to server 1 and sends a message to user B connected to server 3, server 1 can't directly push to user B.

The solution — pub/sub message bus:
  • Every server subscribes to a Redis Pub/Sub channel or Kafka topic
  • When server 1 needs to push to user B (connected to server 3), it publishes to the shared channel
  • Server 3 is subscribed, receives the message, and pushes it to user B's WebSocket connection
  • Any server can reach any user — no sticky sessions required for message delivery
Connection count: A single server with an async event loop (Node.js, Go, Nginx) can handle 100K–1M concurrent WebSocket connections. C10M is achievable with tuned Linux kernel settings (file descriptor limits, socket buffer sizes).

Load balancing: Use sticky sessions (consistent hash by user_id) so a user's connection always routes to the same server — reduces pub/sub overhead. Failover: client reconnects to any available server on disconnect.
REST vs gRPC — which is faster and by how much?+
Published benchmarks consistently show gRPC/Protobuf beating JSON REST on both size and parsing speed, though the exact multiplier varies a lot by payload shape and tooling — treat any single number (including the ones below) as illustrative, not a figure to quote precisely in an interview.

Why Protobuf is faster than JSON:
  • Size: JSON is human-readable text — a timestamp field like "created_at": "2026-03-20T14:23:45Z" costs dozens of bytes as a quoted string; Protobuf encodes the same field as a compact tagged integer. A single scalar field being several times smaller in Protobuf is a fair illustration, but whole-message size savings are usually more modest (commonly cited in the 30–40% range) once you account for field names being implicit rather than repeated per record.
  • Parsing: JSON parsing is string scanning and Unicode handling. Protobuf parsing is integer-indexed field lookup — commonly 2–6x faster in published benchmarks, with larger gaps on bigger payloads.
  • HTTP/2 multiplexing: gRPC reuses one TCP connection for all RPCs between two services. HTTP/1.1 REST requires a connection per request or connection pooling.
Real-world numbers: published third-party benchmarks vary by payload shape and tooling, but a consistent pattern shows up across them — Protobuf messages typically run 30–40% smaller than equivalent JSON (some report more, some less depending on field types), and Protobuf serialization is commonly 2–6x faster than JSON parsing, with the gap widening for larger payloads. Treat any single multiplier as illustrative, not a number to quote precisely in an interview.

When the difference matters: At 10K RPC/sec between services, the CPU savings from Protobuf are measurable in infra cost. At 100 RPC/sec, use REST — the operational simplicity outweighs any performance gain.
GraphQL solves over-fetching — but doesn't it create its own performance problems?+
Yes — GraphQL solves bandwidth but creates three new challenges:

1. N+1 queries (the biggest one): A query for 100 posts each needing their author resolves by calling getAuthor() 100 times. Without DataLoader, this is 101 database calls instead of 2.
Fix: DataLoader batches all getAuthor() calls that occur in the same tick into one SELECT * FROM users WHERE id IN (1,2,3...100).

2. Query complexity attacks: A malicious client sends a deeply nested query: posts → comments → authors → posts → comments → authors → (∞). Without depth limiting, this triggers exponential resolver calls.
Fix: Query depth limit (max 10 levels), query complexity scoring (each field costs points, reject queries over a budget), query whitelisting in production (only allow known queries).

3. No HTTP caching: GraphQL uses POST — CDNs don't cache POST. Every query hits your origin.
Fix: Persisted Queries — hash each known query, send the hash as a GET parameter. CDN caches the response. Only novel/uncached queries reach the origin.
SSE vs WebSocket — when exactly do you pick SSE?+
Pick SSE when the data flow is one-directional and you want HTTP-native simplicity.

SSE wins over WebSocket when:
  • Client only reads — never sends data on the real-time channel (notifications, feeds, dashboards, AI token streaming)
  • You need automatic reconnection with event replay — SSE's Last-Event-ID mechanism gives you this for free; WebSocket requires custom client logic
  • HTTP/2 is available — SSE over HTTP/2 multiplexes thousands of streams over one TCP connection, solving HTTP/1.1's 6-connection limit
  • Your infrastructure doesn't support WebSocket upgrades (some corporate proxies block it)
  • You want standard HTTP monitoring, logging, and load balancing without special WebSocket-aware tooling
WebSocket wins when:
  • Client sends data frequently on the real-time channel (chat, collaborative editing, games, cursor positions)
  • Sub-frame latency matters — WebSocket frames are slightly lower overhead than SSE's HTTP text envelope
  • You need binary data (WebSocket supports binary frames natively; SSE is text-only)
The practical test: Draw an arrow for your data flow. If the arrow points server→client only, use SSE. If arrows go both directions, use WebSocket.
How does gRPC handle versioning when you change your .proto schema?+
Protobuf has designed-in backwards compatibility rules — but you must follow them religiously.

Safe changes (backwards and forwards compatible):
  • Adding a new field — old clients ignore it, new clients read it
  • Changing a field name — field numbers are what Protobuf uses on the wire, not names
  • Adding a new RPC method — old clients don't call it
Breaking changes (never do these in production):
  • Changing a field's number (field number = wire identity; changing it means old clients misread your data)
  • Changing a field's type (int32 → string will corrupt data in-flight)
  • Removing a required field (old clients still send it; new server rejects it)
  • Removing an RPC method that clients are calling
The strategy for major changes: Create a new package version (package myapi.v2). Run v1 and v2 in parallel. Migrate clients to v2 gradually. Retire v1 only after all clients have migrated. This is identical to REST's /v1/ vs /v2/ URL versioning.
What's the difference between REST idempotency and GraphQL mutation safety?+
Idempotency means: calling the operation multiple times has the same effect as calling it once.

REST's HTTP methods have defined idempotency semantics:
  • GET, HEAD, OPTIONS — safe (no side effects) and idempotent
  • PUT, DELETE — idempotent (doing it twice = same result as once)
  • POST — neither safe nor idempotent (creates a new resource each call)
  • PATCH — not inherently idempotent (depends on implementation)
For POST idempotency: Use an Idempotency-Key header (unique UUID per request). Server stores the key → result mapping. If same key arrives twice, return the stored result instead of executing again. Stripe, Stripe, and most payment APIs require this.

GraphQL mutations: All mutations use POST — no built-in idempotency. You must implement idempotency keys manually in your mutation resolvers if needed (e.g., payment mutations). This is GraphQL's operational weakness vs REST's verb semantics.

Why it matters in interviews: Payment processing, order creation, and any mutation where double-execution has real consequences needs explicit idempotency handling regardless of protocol.
How do you secure WebSocket connections?+
WebSocket has no built-in authentication — you must implement it explicitly.

Step 1 — Use WSS (WebSocket Secure): Always use wss:// (TLS), never ws://. Same as HTTPS vs HTTP. Your certificate covers both.

Step 2 — Authenticate at connection time: The HTTP Upgrade request is a standard HTTP request — you can read headers and cookies. Send a JWT or session token in the Authorization header or as a query parameter on the initial wss:// URL. Validate before accepting the upgrade.

Step 3 — Authorise at message time: Validate that the connected user has permission for every message they send. Don't assume that because they connected legitimately, all their subsequent messages are authorised.

Step 4 — Rate limit messages: Unlike HTTP where rate limiting is standard middleware, WebSocket bypasses your HTTP layer. Implement per-connection message rate limiting at the WebSocket handler level. Without it, one client can flood your server with messages.

Step 5 — Handle token expiry: JWTs expire. If a user's token expires mid-session, the server needs to close the WebSocket and force re-authentication. Implement token refresh via a REST call; send the new token over the WebSocket or reconnect with the new token.
In the Uber system design, why use both REST and WebSocket — why not just WebSocket for everything?+
Using WebSocket for everything seems elegant but creates real problems:

1. HTTP semantics matter: REST gives you status codes (400 bad request, 402 payment required, 409 conflict) that load balancers, monitoring tools, and clients all understand natively. Over WebSocket, you'd invent custom error codes — invisible to your infrastructure.

2. Idempotency and retries: When a user books a ride, you need idempotency guarantees. REST POST with an Idempotency-Key is standardised. WebSocket message delivery is at-most-once by default — you'd need to build your own ack/retry layer.

3. Caching: Fare estimates, driver profiles, and static data are cacheable. REST GET responses are cached at CDN and browser level automatically. WebSocket has no caching layer.

4. Load balancing: REST requests are stateless — any server handles any request. WebSocket connections are stateful — they need sticky sessions or a message bus. Running everything over WebSocket means every service needs WebSocket-aware infrastructure.

5. Operational tooling: HTTP logs, traces, and metrics are supported by every monitoring tool out of the box. WebSocket message-level observability requires custom instrumentation.

The correct split: WebSocket for what genuinely needs real-time bidirectional communication (location, status updates). REST for everything transactional (booking, payment, profile). The complexity-to-benefit ratio is much better.
08 · gRPC Streaming Modes

All four streaming types — with real use cases

01 Unary RPC
What it is
One request → one response. The standard call.

rpc GetUser(GetUserRequest) returns (User);

Use for: any operation where you have one question and need one answer. 90% of RPC calls. Same semantics as REST but with Protocol Buffers and HTTP/2.

02 Server Streaming
What it is
One request → stream of responses. Server sends multiple messages for a single client request.

rpc WatchFeed(WatchRequest) returns (stream FeedEvent);

Use cases: real-time feed subscription (client subscribes once, server pushes new items as they arrive), large data download (server streams chunks), log tailing (client requests logs, server streams them continuously). gRPC keeps the HTTP/2 stream open until the server signals completion. Client reads from the stream in a loop.

03 Client Streaming
What it is
Stream of requests → one response. Client sends multiple messages, server responds once at the end.

rpc UploadFile(stream FileChunk) returns (UploadResult);

Use cases: chunked file upload (client streams 4MB chunks, server assembles), sensor data batch ingestion (IoT device streams 1,000 readings, server processes and returns aggregate), speech-to-text (client streams audio chunks, server returns transcript when done).

04 Bidirectional Streaming
What it is
Stream of requests ↔ stream of responses. Full duplex. Both sides can send at any time.

rpc Chat(stream ChatMessage) returns (stream ChatMessage);

Use cases: real-time chat between services (internal Slack-like communication between microservices), collaborative editing (both sides stream cursor positions and edits), online gaming (client streams player input, server streams game state updates), live translation (client streams audio, server streams translated text in real time).

→Bidirectional streaming is gRPC's most powerful feature — enabling true full-duplex communication over a single HTTP/2 stream. WebSocket achieves similar for browser clients. For server-to-server: bidirectional gRPC is preferred over WebSocket due to Protocol Buffer efficiency and built-in load balancing.
⚠ · Failure Modes

What actually breaks in production — real incident patterns

01WebSocket Connection Storms on Deploy
What breaks & how
A rolling deploy or a load balancer failover drops every WebSocket connection pinned to the recycled instances at once. Every client's reconnect logic fires within the same few seconds, hammering the connection-accept path and the auth/handshake layer simultaneously — a self-inflicted thundering herd triggered by your own deploy, not an attacker.
⚠Fix: jittered client-side reconnect backoff (never reconnect instantly and in lockstep), connection draining during deploys (stop accepting new connections on the old instance before killing it, let existing ones finish naturally), and rolling deploys in small batches rather than all-at-once so the reconnect wave is spread out.
02gRPC Deadline Propagation Gaps
What breaks & how
Service A calls B with a 500ms deadline. B calls C but forgets to propagate the remaining deadline — C keeps working long after A has already given up and returned an error to its caller. The wasted work compounds under load: upstream retries pile more traffic onto a downstream that's still burning CPU on requests nobody is waiting for anymore.
⚠Fix: propagate the remaining deadline (not a fresh one) on every hop — most gRPC client libraries do this automatically if you pass the incoming context through, but it's silently lost the moment a handler constructs a new context instead of deriving one. Alert on "deadline exceeded" rates per service, not just error rates.
03GraphQL Resolver Fan-Out Collapse
What breaks & how
A single, innocent-looking client query with a few nested fields resolves into hundreds of downstream calls once you count every resolver invocation per list item. Under normal load this is invisible; under a traffic spike, or when a malicious client sends a deliberately deep nested query, the downstream services (or the DB) see a multiplicative traffic spike that the edge-level rate limiter — which only sees "1 request" — never catches.
⚠Fix: DataLoader batching to collapse duplicate resolver calls, query complexity/depth limits enforced at the gateway (reject before executing, not after), and per-field or per-resolver rate limiting in addition to per-request rate limiting.
04SSE/Long-Poll Connection Exhaustion Behind a Proxy
What breaks & how
A reverse proxy or corporate firewall silently caps idle HTTP connections per client or buffers the response instead of streaming it. SSE events queue up on the proxy and arrive in a delayed burst instead of in real time, or long-poll connections get killed mid-wait and clients spin in a fast reconnect loop that looks like a self-inflicted DDoS on your own edge.
⚠Fix: explicitly disable response buffering on the reverse proxy for streaming routes (e.g. Nginx's proxy_buffering off), send periodic keep-alive comments/heartbeats over SSE so idle-timeout logic downstream doesn't trigger, and cap long-poll hold time comfortably under any known proxy/firewall timeout in your infra.
📋 · Requirements & Scale

Requirements & Non-Functional Constraints

Functional Requirements

FR1The system must support simple, stateless request/response interactions for standard create/read/update/delete operations, where a client asks once and gets one complete, cacheable answer.
FR2Internal service-to-service calls must be able to use a compact, strongly-typed binary protocol with a compile-time-checked contract, so high-volume internal RPC traffic doesn't pay JSON's parsing and payload-size cost at scale.
FR3The system must support a persistent connection where both client and server can send messages at any time without re-establishing it, for interactions where either side may need to push data unprompted (chat, collaborative editing, live game state).
FR4The system must support server-initiated push to a client that never needs to send data back on the same channel, using a mechanism simpler and more proxy/firewall-friendly than a full bidirectional connection.
FR5Clients with meaningfully different data-shape needs (mobile vs. web vs. partner integrations) must be able to request exactly the fields they need in a single round trip, without the API team building and maintaining a bespoke endpoint per client.
FR6The system must have a real-time fallback that works over plain HTTP for clients or networks that block WebSocket upgrades, even though that fallback has worse latency and efficiency characteristics than a native persistent connection.

Non-Functional Requirements

NFR1REST throughput per server: a capacity target you measure for your own runtime and payload size, not a fixed number — treat any single figure (including ones in this document) as illustrative, and load-test your actual stack before committing to a number in an interview.
NFR2gRPC bandwidth savings vs JSON REST: commonly cited in the 30–40% smaller-payload range with 2–6x faster serialization in published benchmarks, though the multiplier varies significantly by payload shape and benchmark methodology — state the direction (binary wins) with more confidence than any specific multiplier.
NFR3WebSocket concurrent connections per server: an architecture target, not a universal number — a single server with an async event loop (Node.js, Go, tuned Nginx) can commonly handle from tens of thousands up to roughly a million connections depending on message rate, message size, and OS-level tuning (file descriptor limits, socket buffers).
NFR4SSE operational complexity: qualitatively lower than WebSocket (no custom reconnect logic, works over plain HTTP/2) — this is a design trade-off, not a number to cite.
NFR5GraphQL resolver complexity: a real, ongoing operational cost (N+1 risk, query-depth attacks) that must be budgeted for with DataLoader batching and query complexity limits — not a one-time setup cost.
NFR6Latency budget: state one explicitly (e.g. p99 < 200ms for REST, sub-100ms for WebSocket after connect) — the absolute numbers depend entirely on network path and payload, but gRPC's binary encoding and WebSocket's persistent connection both remove per-request overhead that REST pays every time
