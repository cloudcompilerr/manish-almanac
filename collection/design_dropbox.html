00 · Requirements

Requirements & Scale Assumptions

Functional

FR1A user must be able to upload a file from any device (desktop, mobile, or web) and have it become part of the account's single canonical file set — the system owns how it's stored and versioned, not the user.
FR2When a file changes on one device, every other device signed into the same account must learn about the change and be able to fetch it, without the user manually re-uploading or re-downloading anything.
FR3Any device signed into the account must be able to retrieve the current version of any file in the account's file set, not just the device that originally created it.
FR4A user must be able to grant another user access to a specific file or folder, at a chosen permission level (view or edit), without exposing the rest of the account's files.
FR5The system must retain a bounded history of prior versions of each file so a user can recover an earlier version after an unwanted edit or accidental deletion — not just the single most recent state.
FR6A user must be able to open and read previously-synced files while their device has no network connectivity, with any offline edits reconciled once connectivity returns.

Non-Functional

NFR1~700M+ registered users (Dropbox's own current disclosed figure) driving an assumed ~500M file operations/day — the operations/day number is this exercise's own sizing assumption, not a Dropbox-published figure; defend it with arithmetic, don't cite it as fact.
NFR2Design target: files up to 5GB per upload, resumable regardless of where the transfer failed. (Dropbox's real-world limits vary by platform and plan and aren't a single citable number — pick a defensible cap and justify it.)
NFR3Design target: a change should be visible on other devices within 30 seconds — defend this with your notification-pipeline arithmetic (poll interval, fan-out time), not as a disclosed Dropbox SLA.
NFR4The system must correctly handle two devices independently editing the same file while both are offline, without silently discarding either person's edit when they reconnect.
NFR5The system must recognize when multiple users upload byte-identical content and store it exactly once — an outcome of the content-addressing design (see the Hard Decisions section), not a specific disclosed dedup ratio.
NFR6Design target: 99.99% availability (~52 minutes of downtime/year) — a standard SLA tier to propose and justify, not a disclosed Dropbox number.

Key insight
Only changed chunks
The intelligent photocopier analogy
Dropbox is like a photocopier that's smart enough to only copy the pages that changed. You edit slide 3 of a 200-page document: a dumb copier copies all 200 pages (upload entire file). Dropbox copies only the 4MB chunk containing slide 3. The "deduplication" superpower: if 10,000 users upload the same Office installer, Dropbox stores it once and gives everyone a "pointer" to the same copy. Version history is free because unchanged pages are shared — storing 30 versions of a 1GB file costs only 1GB + the size of all changes across versions.
⚠ The interview trap that catches most candidates

"Design Dropbox" candidates who open with "store files in S3, keep a new copy each time one changes" solve file storage but haven't actually designed sync. That model re-uploads the entire file on every edit (no delta sync), stores N full duplicate copies for N users who happen to upload the same file (no deduplication), and multiplies storage by every version retained (no cheap version history). Those aren't three separate features to bolt on — they're the same underlying decision: split every file into content-addressed chunks (hash each chunk, use the hash as its identity) and store or transfer only chunks the server doesn't already have. Naming that one decision — and that it simultaneously buys you dedup, delta sync, and near-free versioning — is the single strongest signal in a Dropbox system design interview.

01 · Architecture

Full System — Every Component Justified

01Chunked Storage & DeduplicationContent-Addressed S3
The Core Insight
Files split into 4MB chunks. Each chunk identified by its SHA-256 hash. Identical chunks stored exactly once.
Upload flow: 1. Client splits file into 4MB chunks. 2. SHA-256 hash each chunk. 3. POST /chunks/check [{hash1, hash2, ...}] → server returns which hashes are missing. 4. Client uploads only missing chunks to S3 (pre-signed URLs). 5. POST /files with {filename, [hash1, hash2, hash3, ...]} → server records file metadata.
Deduplication: two users upload the same 1GB video. Chunk hashes are identical. Server tells User B: "all chunks already exist." User B's upload completes in 1 second (just the metadata write). S3 stores one copy. Both users' file records point to the same chunk hashes.
✓Dropbox hasn't published a specific enterprise-wide petabytes-saved figure for cross-user dedup, so treat any precise number as folklore rather than sourced fact. What is confirmed on Dropbox's own engineering blog: the 4MiB block protocol is real, and a 2020 optimization built on top of it ("Broccoli") measured ~33% average upload-bandwidth savings platform-wide, rising to ~70% for the heaviest editors of large files. Common dedup wins in practice: Office templates, vendor/node_modules directories, OS files, and software installers — thousands of users upload byte-identical copies.
⚠Deduplication only works for unencrypted files. If client-side E2EE is used, identical files encrypt differently → no dedup possible. This is the fundamental E2EE vs dedup tradeoff
02Delta SyncBlock-Level Diff
Bandwidth Savings
Only upload changed chunks — not the entire file. For a 1GB file with a 100KB edit: upload 4MB (one chunk), not 1GB.
On file save: client re-chunks the modified file → compare new hashes to the locally cached chunk list → identify changed chunks (typically 1–2 chunks for a document edit) → upload only those. Server reconstructs the latest version from existing chunks + new chunks.
Example: user edits one slide in a 500MB PowerPoint. Without delta: 500MB upload. With delta: 4MB upload (one chunk containing the changed slide). 125× bandwidth reduction.
✓Delta sync makes Dropbox usable on slow connections (hotel WiFi, train). Without it: every save of a large file would consume minutes of upload time
ℹChunk size selection: 4MB is the sweet spot. Too small (512KB) → too many chunks, too many S3 requests. Too large (16MB) → small edits waste bandwidth re-uploading unchanged data
03Sync EngineLong-Poll + Cursor
Change Notification
Device A uploads a file → notification service → other devices (B, C) are notified → download delta.
Each device maintains a sync cursor (logical position in the change stream). Device registers: "I'm at cursor 12345 for user X." On change: notification service pushes "new events since cursor 12345." Device downloads new chunk hashes → fetches new/changed chunks from S3 → updates local file.
Notification delivery: long-poll connection per device. Device sends GET /changes?cursor=12345 → server holds connection open until new events arrive (up to 60s) → response with events → device immediately makes next long-poll request. This gives near-real-time sync without WebSocket complexity.
✓Cursor-based sync: device offline for 1 week → reconnects → fetches all events since its cursor → fully caught up. No missed events, no full resync needed
→Notification service backed by Redis Pub/Sub: file change → publish to user:{user_id} channel → all devices subscribed receive immediately
04Conflict ResolutionConflicted Copy
Two Devices, Same File
Detect conflicts via vector clocks / edit counter. Resolution: keep both versions.
Detection: each file version has an edit_counter. If Device A and Device B both modify a file while offline (both starting from edit_counter=5): when they reconnect, server detects two conflicting versions of edit_counter=6. Neither can be discarded — both contain real edits.
Resolution: Dropbox's simple but safe strategy: keep BOTH versions. "report.docx" becomes "report.docx" (winner, usually later timestamp) and "report (Alice's conflicted copy 2026-03-22).docx." User sees both files, manually merges.
Why not auto-merge? Dropbox handles arbitrary binary files. Only text files have mergeable diffs. A conflicted .docx or .psd cannot be auto-merged without understanding the file format.
ℹGoogle Docs avoids this entirely using operational transforms (OT) / CRDT — each character insertion is a discrete operation that can be merged. This only works for text/structured documents, not arbitrary binary files
→Version history: Dropbox keeps the last 30 versions. Rolling back to a pre-conflict version is always possible.
05Version HistoryContent-Addressed, Zero Extra Storage
How it's Free
Each version is stored as a list of chunk hashes. No data duplication for unchanged chunks.
File V1: [chunkA, chunkB, chunkC]. File V2 (one slide edited): [chunkA, chunkB_new, chunkC]. Storage cost of V2: only chunkB_new is new (4MB). chunkA and chunkC are shared references — stored once, referenced from both versions.
Maintaining 30 versions of a 1GB file with small edits: stores the original 1GB + 30 × 4MB (one changed chunk per version) = ~1.1GB total. Not 30GB. The content-addressed model makes versioning nearly free.
✓This is why Dropbox can offer 30-version history without charging extra for storage. The actual storage cost is proportional to the amount of data changed, not the number of versions
02 · Deep Dive

File Change to Sync — Complete Flow

Alice edits report.docx on her laptop — Bob sees the change on his phone
T+0s
Alice saves report.docx (200MB, one section edited). Dropbox desktop client detects file change via OS filesystem watcher (FSEvents on macOS, inotify on Linux).
T+0.5s
Client re-chunks the file into 50 × 4MB chunks. Computes SHA-256 for each chunk. Compares against locally cached chunk hashes. Detects 2 chunks changed.
T+1s
POST /chunks/check [{new_hash_1, new_hash_2}] → server: "hash_1 not found, hash_2 exists." Client uploads only chunk_1 to S3 via pre-signed URL (4MB upload).
T+3s
Upload complete. PUT /files/report.docx {version: 6, chunks: [hash_1, hash_2, ..., hash_50]}. Server stores new version metadata. Publishes ChangeEvent to Redis.
T+3.1s
Notification service receives ChangeEvent. Finds all of Alice's devices with open long-poll connections. Sends response to Bob's phone long-poll: "cursor 12345: report.docx updated, new chunk hashes: [...]"
T+3.5s
Bob's phone: receives notification. Checks local cache: has chunk_2 (unchanged) and chunk_3..50. Missing: chunk_1 (new). Downloads chunk_1 from S3.
T+5s
Bob's phone reconstructs report.docx from chunk_1 (new) + all cached chunks. File updated. Total sync time: ~5 seconds on a 50Mbps connection.
03 · The Hard Decisions

Chunking, Content-Addressing, and Conflict Detection — Term by Term

Three technical decisions do the real work in any sync system. Get the vocabulary precise — interviewers are listening for it.

FIXED-SIZE
CHUNKING

Splitting a file into equal-sized blocks (Dropbox uses 4MiB, per its own Magic Pocket engineering blog) so only the blocks that actually changed need to be re-hashed and re-uploaded.

The known weakness: fixed-size chunking is byte-offset sensitive. Insert a single byte at the start of a file and every chunk boundary after it shifts — every subsequent chunk hashes differently even though almost none of the underlying bytes changed, and dedup/delta sync silently stop helping for that file.

CONTENT-DEFINED
CHUNKING (CDC)

The fix for the boundary-shift problem: pick chunk boundaries based on the file's own content (a rolling hash, e.g. Rabin fingerprinting) instead of fixed byte offsets. A local edit only ever changes the 1–2 chunks around it — everything before and after it re-derives the same boundaries and the same hashes. rsync's rolling checksum and backup tools like Borg and restic use this technique for exactly this reason.

Interview-defensible answer: name fixed-size chunking as the simple baseline, then name content-defined chunking as the refinement you'd reach for the moment you're asked "what if I insert one byte at the top of the file?"
CONTENT-
ADDRESSING

A chunk's identity is the cryptographic hash of its bytes (SHA-256), not an arbitrary ID assigned by the server. Two users who upload byte-identical content always produce the same hash — dedup falls out for free, with no need to compare file contents directly. This is the same underlying idea as Git's object store and IPFS content identifiers: identical content is structurally indistinguishable, so it can only ever be stored once.

CONFLICT
DETECTION

An edit counter (or vector clock) per file version detects — but does not resolve — concurrent offline edits. Detection is the easy half: both devices agree edit_counter=5 was the common ancestor, and both independently produced a conflicting edit_counter=6. Resolution is the hard half, and it's why Dropbox keeps both copies rather than attempting an automatic merge — correctly merging arbitrary binary files is, in general, impossible without file-format-specific knowledge.

04 · Interview Decision Framework

How Aggressively Should You Chunk, Sync, and Resolve Conflicts?

🎯Four Questions That Decide the Sync Design
1
Does the product need end-to-end encryption?
No →Server-side (Dropbox-managed) encryption at rest. Dedup and delta sync both work normally, because the server can see — and hash — plaintext chunks.
Yes, non-negotiable (legal/medical, Tresorit-style) →Client-side E2EE. Accept that cross-user dedup is gone — ciphertext of identical files differs per key — and size storage estimates accordingly.
2
Are most files large binaries edited in small increments (video, slide decks, CAD) or small text files (code, config)?
Large binaries, small edits →Delta sync pays for itself immediately — a 500MB file with a 100KB edit uploads one 4MB chunk, not 500MB.
Small files, whole-file rewrites →Chunking overhead (the hash-check round trip) can cost more than it saves. A simpler whole-file upload-if-changed model is defensible for something like a codebase-sync tool.
3
Can two devices plausibly edit the same file while both offline?
Yes (consumer sync product) →You need conflict detection and a "keep both, never silently discard" resolution policy.
No (single-writer, e.g. a backup agent) →Skip conflict resolution entirely — last-writer-wins is safe when there's structurally only one writer.
4
Is near-real-time push notification worth the connection-management cost, or is polling acceptable?
30–60s sync latency is fine →Long-poll. Simpler, works behind restrictive corporate firewalls, no persistent-connection fleet to operate.
Sub-second latency matters (live collaboration) →WebSocket or a dedicated push channel — accept the connection-management operational cost (see WhatsApp's Erlang connection layer for what that looks like at extreme scale).
⚠ · Failure Modes

What Actually Breaks — Production Failure Patterns

01Chunk Reference Leaks (Orphaned Blocks)
What it is

Content-addressed storage means a chunk is only safe to delete once zero files reference its hash. A race between "file deleted" and "chunk refcount decremented" either leaks chunks forever (storage cost creeps up silently) or deletes a chunk while a live file still references it (that file corrupts).

✓Fix: garbage-collect via a mark-and-sweep pass that snapshots live references before deleting, not a live decrement-on-delete counter; keep a grace-period window before physical deletion so a wrongly-decremented chunk is still recoverable.
02Sync Loop / Phantom Re-upload
What it is

A metadata field that changes on every read (a "last accessed" timestamp some other tool writes into the file, or an editor that rewrites the whole file on every autosave) makes the client detect a "change" every sync cycle and re-chunk, re-hash, and re-upload — even though the meaningful content is identical. At scale this looks like one account silently consuming a disproportionate share of sync capacity.

✓Fix: compare content hashes before uploading, not just an mtime check; flag accounts whose upload volume is anomalous relative to their file count for investigation.
03Conflicted-Copy Storms
What it is

A shared folder with several active editors and a flaky connection can produce a cascade of conflicted-copy files — every reconnect after a dropped connection can look like a fresh offline edit. Users end up with a folder full of "report (Alice's conflicted copy 1).docx," "(2)," "(3)"...

✓Fix: collapse a new conflict into an existing conflicted copy if the bytes are identical instead of creating another file; surface one merged conflict-resolution UI rather than N separate files once N crosses a small threshold.

07 · Hard Follow-ups

Every Question Your Interviewer Will Ask

How does Dropbox Smart Sync work — files appear local but aren't downloaded until you open them?+
Virtual filesystem driver intercepts file system calls at the OS level.

Dropbox installs a kernel extension (macOS: DropboxFS via FUSE; Windows: Cloud Files API built into Windows 10+; Linux: FUSE). This driver registers as a file system with the OS.

How it works: file "report.docx" appears in Finder with a cloud icon. Metadata exists (name, size, dates) but no local bytes. User double-clicks: OS sends open("report.docx") syscall → intercepted by Dropbox driver → driver downloads file from S3 → buffers to local disk → returns file handle to OS → application opens it. To the application: the file was always there.

Eviction: when local disk is full, LRU policy removes "online-only" files from disk. The file still appears in Finder (metadata stays). Next open triggers re-download. "Pinned" files (user marks as always-available) are never evicted.
How do you handle a user uploading 1,000 files simultaneously from a new device?+
Rate limiting + parallel chunk uploads + efficient check-before-upload.

Scenario: user installs Dropbox on new computer, 1TB of files needs syncing. Naive approach: upload all files simultaneously → saturate network → everything is slow for everyone on the same ISP.

Rate limiting: the Dropbox desktop client caps itself to a small, bounded number of parallel chunk uploads rather than firing off every chunk at once (the exact concurrency limit isn't a number Dropbox publishes — treat "N parallel uploads" as a design parameter you'd tune and justify, not a cited constant).

Check-before-upload optimisation: before uploading any chunk, check if the server has it (dedup check). For a user reinstalling Dropbox on a new device: many files haven't changed — their chunk hashes already exist on the server. POST /chunks/check returns "all 12,500 hashes already exist" → zero bytes uploaded. File metadata synced immediately. This is why reinstalling Dropbox on a new computer syncs in minutes, not weeks.
How do you design the sharing system — one user shares a folder with another?+
Shared folders create a "namespace mount" — the folder appears in both users' Dropbox.

Database model: Folder is a first-class entity. folder_members(folder_id, user_id, permission: viewer|editor|admin). When Alice shares /projects/website with Bob: add (folder_id, bob_user_id, editor) to folder_members.

Bob's sync client: on next sync, receives "new shared folder mounted at /projects/website." Downloads all files in the folder (or Smart Sync: just metadata). Bob's edits propagate to Alice's devices (and all other members) through the same sync pipeline.

Permission enforcement: every file operation checks folder_members. GET /files/{path} → server verifies requesting user is a member of the parent folder with at least viewer permission. Revoke access: delete the folder_members row → immediate effect (next API call is denied). Dropbox does NOT invalidate already-downloaded local copies — revoked user still has local copies until their client syncs and detects the access revocation.
How does Dropbox handle file encryption — can Dropbox employees read your files?+
Standard Dropbox: files encrypted at rest with AES-256. Dropbox manages the keys. Employees with sufficient privilege CAN access files.

Encryption at rest: each file's chunks are encrypted in S3 using AES-256. Dropbox's Key Management Service (KMS) manages per-file encryption keys. This protects against S3 data theft (someone steals physical drives) but not against Dropbox employees with KMS access.

Client-side E2EE (Dropbox Vault / extended access): user generates a key on their device. Files encrypted before upload. Server stores only ciphertext. Dropbox cannot decrypt. Trade-off: no deduplication (ciphertext of identical files differs), no server-side search, no web preview. If user forgets password: data is permanently unrecoverable.

The real-world position: most business users accept Dropbox-managed encryption (same as trusting Google Drive). Highly sensitive data (legal, financial, medical) requires client-side E2EE or a zero-knowledge service (Tresorit, ProtonDrive). Dropbox is working toward broader E2EE support but hasn't deployed it by default due to the dedup and collaboration trade-offs.
