00 · The Problem

Why naive hashing breaks when you add or remove servers

You have 3 servers and use hash(key) % 3 to route requests. Server 2 goes down. Now you have 2 servers. hash(key) % 2 gives completely different results — every key maps to a different server. 100% of your cached data is now on the wrong server. Your entire cache is invalidated simultaneously. Your database collapses.

The seating chart analogy
A restaurant has 10 tables. Each guest is assigned hash(name) % 10. Works perfectly. Then one table is removed — now 9 tables, and nearly every guest is now "assigned" to a different table. Total chaos.

Consistent hashing is like arranging all tables in a circle and assigning each guest to the nearest table clockwise. Remove one table — only that table's guests need to move to the next table. Everyone else stays exactly where they were.
01 · How It Works

The ring — step by step

The Hash Ring
Imagine a circle with positions 0 to 2³² (about 4 billion). Both servers and keys are hashed onto this circle using the same hash function.
Servers: hash("server-A") → position 12M, hash("server-B") → position 1.8B, hash("server-C") → position 3.1B
Keys: hash("user:123") → position 900M
To find which server owns a key: start at the key's position and walk clockwise until you hit a server. user:123 at 900M → nearest server clockwise is server-B at 1.8B.
Adding a Server
New server-D hashes to position 1.2B. It sits between server-A (12M) and server-B (1.8B).
Only keys between 12M and 1.2B (previously owned by server-B) now move to server-D.
✓ Only ~1/N of keys need to move when adding the Nth server. All other keys stay on their current server.
Removing a Server
Server-B (position 1.8B) goes down. Its keys now walk clockwise to server-C (3.1B).
Only server-B's keys need to be fetched from DB (cache miss). All other servers' keys are unaffected.
✓ Only ~1/N of keys are disrupted on server failure, vs 100% with naive hashing.
Virtual Nodes
The problem with basic consistent hashing: non-uniform distribution. With only 3 real servers, one server might own 60% of the ring and another only 10%.
Solution: virtual nodes (vnodes). Each physical server gets 100–1000 positions on the ring:
hash("server-A#1") → 12M, hash("server-A#2") → 890M, hash("server-A#3") → 2.1B ...
✓ Load is distributed much more evenly. Larger servers can have more vnodes. Used by: Cassandra (default 256 vnodes), DynamoDB, Redis Cluster.

03 · The Hot Spot Problem

Consistent hashing does not solve hot keys — here is what does

⚠ The interview trap

Candidates often say "I'll use consistent hashing to distribute load evenly." Interviewers immediately ask: "What about a celebrity user with 50M followers? All their post writes hash to one node." Consistent hashing distributes keys evenly — it does not help when one key receives disproportionate traffic.

Key Salting
Append a random suffix to distribute one hot key across multiple nodes.
Instead of writing to celebrity:123, write to celebrity:123#0 through celebrity:123#7 (8 shards).
Reads: scatter-gather across all 8 shards, sum/merge results.
✓ Distributes write load 8x. Used for: hot counters (view counts), celebrity post writes.
⚠ Read complexity — must query all shards and aggregate. Adds latency for reads.
Write Fan-Out
Pre-compute and write results to each consumer's own shard.
Celebrity posts to 50M followers: instead of one write + 50M reads, write the post to each follower's feed shard at write time.
✓ Reads are trivially cheap — each user's feed is pre-computed on their own node. Twitter uses fan-out on write for most users.
⚠ Expensive for celebrities (50M writes per post). Hybrid: fan-out for regular users, lazy load for celebrities (fan-out on read).
Local Caching
Cache hot keys in-process on every app server.
Celebrity user profile read millions of times/minute → cache in Caffeine/Guava on each app server. Zero network hops for reads.
✓ Eliminates hot spot entirely for read-only data. Used for: configuration, feature flags, reference data that rarely changes.
⚠ Inconsistency across servers — each has its own copy. Use short TTL + push invalidation.
04 · Real Implementations

How Cassandra, Redis Cluster, and DynamoDB actually do it

Cassandra — Token Ring with Vnodes
CONSISTENT HASHING
MECHANISM
Cassandra uses Murmur3 hash to place both nodes and keys on a token ring (range: -2⁶³ to 2⁶³). Each node is assigned 256 virtual tokens by default, giving it 256 positions on the ring. Data is replicated to the next N nodes clockwise (N = replication factor).
ADDING A NODE
New node joins the ring with 256 vnodes. Cassandra automatically streams data from existing nodes to the new node for only the token ranges it now owns. Other nodes are unaffected. No downtime, no manual resharding.
COORDINATOR
Any node can be the coordinator for any request. The coordinator hashes the key, identifies which nodes own it (via the ring), and routes the request — then returns the result to the client. Clients can connect to any node.
Redis Cluster — Hash Slot Assignment
HASH SLOTS
16,384 SLOTS
Redis Cluster uses 16,384 fixed hash slots (not a ring). Key → CRC16(key) % 16384 → slot number. Each master node owns a range of slots (e.g., node A: 0–5460, node B: 5461–10922, node C: 10923–16383). Adding a node = reassigning some slots to it.
HASH TAGS
Multi-key operations (MGET, transactions) require all keys to be on the same slot. Use hash tags: {user:123}.profile and {user:123}.settings — the {...} part determines the slot. Both keys land on the same node, enabling multi-key ops.
MOVED REDIRECT
Client sends GET to wrong node → node responds with MOVED 7892 node-B:6380 → client redirects to correct node. Smart clients cache the slot→node mapping and go direct after first lookup.
05 · Follow-ups

Every hard follow-up, answered

Why 16,384 slots in Redis Cluster — why not more or fewer?+
16,384 was chosen as a practical balance between cluster message size and flexibility.

Each Redis node sends heartbeat messages to all other nodes containing a bitmap of which slots it owns. 16,384 slots = 16,384 bits = 2KB bitmap. This fits comfortably in a small network packet. Redis's creator Antirez noted that with 1,000 nodes (an extremely large cluster), 16 slots per node is still enough granularity. More slots would increase heartbeat message size unnecessarily.
What is rendezvous hashing and when is it better than consistent hashing?+
Rendezvous hashing (HRW — Highest Random Weight) is an alternative that achieves the same minimal disruption property without requiring a ring data structure.

Algorithm: to assign key K to a server, compute hash(K, server_i) for every server, pick the server with the highest hash value. On server removal, only that server's keys are reassigned — they each independently recompute and pick the next-highest server.

Advantages over consistent hashing: No ring data structure needed. No virtual nodes complexity. Perfect load distribution by default. Any client can independently compute the assignment without shared state.

Disadvantage: O(N) computation to assign one key (must compute hash for every server). With 1,000 servers and millions of keys per second, this becomes expensive. Consistent hashing with a sorted ring is O(log N).

Used by: CDNs (Akamai's original), some load balancers. Less common in distributed databases where ring-based approaches dominate.
How does consistent hashing handle data replication across nodes?+
In systems using consistent hashing with replication (like Cassandra), a key is stored on not just the nearest node but the next N nodes clockwise.

Example with replication factor 3: key hashes to position 900M. Server-B is at 1.8B (primary). Server-C at 3.1B (first replica). Server-A at 12M + 4B wraparound (second replica). All three nodes store a copy.

Writes go to all 3 (with configurable consistency: ONE/QUORUM/ALL). Reads can come from any of the 3. This means the ring simultaneously handles both partitioning (which set of nodes owns this key) and replication (which specific N nodes in that set).

Node failure: the ring automatically re-routes to the surviving replicas. Once a new node is added, it receives a copy of the data it should own via a streaming repair process (Cassandra's repair mechanism).
