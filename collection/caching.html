00 · Why Caching Exists

The single reason every system needs a cache

A database read on a cold system takes 1–10ms. A cache hit takes 0.1–1ms. At 100K requests/sec, that difference is the line between a system that works and one that collapses. But caching is not just about speed — it is about protecting your database from traffic it was never designed to handle.

The library analogy — for a complete layman
A library (database) has every book ever written. But fetching any book takes a librarian 10 minutes. So you keep the 100 most popular books on a desk beside you (cache). When someone asks for a book, you check your desk first. 99% of the time it's there — instant. Only 1% of requests require the 10-minute librarian trip.

The cache hit rate is everything. A 99% hit rate means your database handles 1% of original traffic. A 90% hit rate means 10% — still 10x less. A 50% hit rate barely helps at all.
The interview framing

Never say "I'll add a cache" without answering: (1) What exactly gets cached? (2) What is the cache key? (3) When does it get invalidated? (4) What is the consistency trade-off? Interviewers give no credit for "add Redis" — they want the strategy.

⚠ The interview trap that catches most candidates

"I'll cache the database query results" sounds right and is dangerously incomplete. The trap is treating the cache as a passive speed-up instead of designing for the moment it fails. Three questions a strong candidate answers unprompted, that a weak candidate never reaches: What happens when the cache is completely empty (cold start after a deploy or a Redis failover)? If nothing protects the DB, a cold cache means 100% of traffic hits a database sized for 1–5% of it — this is a self-inflicted outage, not a hypothetical. What happens when a single key gets far more traffic than the rest (a viral post, a celebrity profile, a flash-sale SKU)? A cache with a uniform hashing scheme still puts that one key on one shard — the fix is application-level (local caching of just that key, key splitting, or request coalescing), not "add more Redis nodes." Is the cache ever allowed to become the source of truth, even briefly? It should never be — if the DB write fails after the cache write succeeds (or vice versa), you need a defined recovery path, not an assumption that both always succeed together.

02 · Write Strategies

The four write patterns — this is what interviewers test

Cache-Aside
(Lazy Loading)
Application manages the cache explicitly. Most common pattern.
Read: check cache → if miss, read DB → write result to cache → return.
Write: write to DB → invalidate or update cache entry. ✓ Only caches data that is actually requested. Cache can survive a restart (just misses until warmed). Resilient — cache failure doesn't break reads. ⚠ Cache miss penalty: 3 operations instead of 1. Race condition: two threads can miss simultaneously, both read DB, both write cache (use distributed lock or short TTL). Used by: most read-heavy systems — social feeds, product pages, user profiles.
Write-Through
Every write goes to cache AND database synchronously before returning.
Write: write cache → write DB → return success.
Read: always hits cache (always fresh). ✓ Cache is always consistent with DB. No stale reads. No cache miss on subsequent reads. ⚠ Write latency = cache write + DB write (two hops). Caches data that may never be read (write-heavy systems waste cache space). Used by: systems where reads must be fresh — financial dashboards, inventory systems.
Write-Behind
(Write-Back)
Write to cache immediately, persist to DB asynchronously in the background.
Write: write cache → return success → background job flushes to DB. ✓ Fastest write latency — single cache write. Batches DB writes (10x fewer DB operations). Great for high-write-frequency data (view counters, like counts). ⚠ Data loss risk: if cache crashes before flush, writes are lost. Not safe for financial data. Complex recovery logic needed. Used by: counters, analytics, non-critical state. Redis itself uses write-back for AOF persistence.
Refresh-Ahead
(Read-Through)
Cache automatically refreshes hot entries before they expire, predicting future reads.
Cache layer intercepts reads. On miss: fetches from DB, caches, returns. Proactively re-fetches keys nearing expiry if they were recently accessed. ✓ No cache miss latency for hot data. Application code never touches DB directly — clean separation. ⚠ May cache stale data if prediction is wrong. Requires a separate refresh thread/process. Used by: read-through cache libraries (Ehcache, Spring Cache), Redis with background refresh logic.

Cache Invalidation — The Hardest Problem in Caching

TTL (Time-to-Live)
Every cache entry expires after N seconds. Simplest approach. After expiry, next read re-fetches from DB.
SET user:123 {json} EX 3600 — expires in 1 hour. ✓ No invalidation logic needed. Self-healing — stale data auto-purges. ⚠ Data is stale for up to TTL seconds after an update. TTL too short = many misses. TTL too long = stale data shown to users.
Event-Driven
Invalidation
When data changes, explicitly delete or update the cache entry.
User updates profile → DEL user:123 in Redis → next read re-fetches fresh data. ✓ Immediately consistent. No stale window. ⚠ Cache and DB writes must be atomic — if cache delete succeeds but DB write fails (or vice versa), you have inconsistency. Use transactional outbox pattern or delete-after-DB-commit.
Cache Stampede
(Thundering Herd)
A popular key expires → thousands of simultaneous requests all miss → all hit the DB simultaneously → DB falls over.
Scenario: trending video cached with 10-minute TTL. At expiry, 50K requests/sec all miss simultaneously. ⚠ The cache that was protecting your DB is now the reason your DB dies.

Fixes:
• Mutex lock: first thread to miss acquires a lock, fetches DB, populates cache. Others wait, then read from cache.
• Probabilistic early expiry: slightly before TTL, a fraction of requests proactively refresh.
• Jitter: randomise TTL (±10%) so not all keys expire simultaneously.
• Stale-while-revalidate: return stale value immediately, refresh in background.
03 · Eviction Policies

What gets removed when the cache is full

LRU
(Least Recently Used)
Evict the entry that was accessed longest ago. Implemented as a doubly-linked list + hashmap. O(1) get and put. Most common default.
✓ Works well when recency correlates with future access. A user just viewed their profile — it should stay cached.⚠ A single large sequential scan (backup job reading all users) pollutes the cache with one-time data, evicting actually-hot entries.Redis default policy: allkeys-lru. Used by: most web application caches.
LFU
(Least Frequently Used)
Evict the entry accessed fewest times total. Tracks a frequency counter per key. O(1) with a min-heap + frequency buckets (complex implementation).
✓ Better for workloads with stable hot keys (celebrity user profiles, popular products). Resists cache pollution from one-time scans.⚠ New keys start with frequency=1 — they get evicted immediately even if they'll be accessed 1M times tomorrow. Requires frequency decay to handle shifting popularity.
TTL-Based
Evict entries whose TTL has expired. Passive expiry (evict on access if expired) + active expiry (background sweep). Redis uses both.
✓ Natural fit for session caches, API response caches where staleness has a defined bound.
Redis Policies
Redis has 8 eviction policies. The most important:
noeviction — return error when full (safest, but breaks writes)
allkeys-lru — LRU across all keys (most common)
volatile-lru — LRU only among keys with TTL set
allkeys-lfu — LFU across all keys (Redis 4+)
allkeys-random — random eviction (surprisingly effective for uniform workloads) Set via maxmemory-policy config. Always set maxmemory or Redis will consume all available RAM.
04 · Redis Deep Dive

Redis data structures — the right tool for each problem

String
Binary-safe value up to 512MB. The catch-all type.
Use for: JSON blobs, HTML fragments, counters, session tokens.
SET user:123 "{name:Alice}" EX 3600
INCR pageview:home — atomic counter, no race condition. INCR/DECR are atomic — the only safe way to do distributed counters without locks.
Hash
Field-value map within one key. Ideal for objects.
HSET user:123 name Alice age 30 city Bangalore
HGET user:123 name — fetch one field without deserializing the whole object. ✓ More memory-efficient than separate string keys per field. Update one field without reading/writing the entire object. Used by: user profiles, shopping carts.
Sorted Set (ZSET)
Set of unique members, each with a float score. Ordered by score. O(log N) operations.
ZADD leaderboard 9241038 user:alice
ZREVRANGE leaderboard 0 9 WITHSCORES — top 10 with scores.
ZINCRBY leaderboard 847 vid:abc — atomic increment. ✓ The backbone of Top-K, leaderboards, rate limiting windows, priority queues. Used by: Top-K system, gaming leaderboards, Twitter trending.
Set
Unordered collection of unique strings. O(1) add/remove/lookup.
SADD online:users user:123 user:456
SISMEMBER online:users user:123 — is user online?
SUNION followers:alice followers:bob — union of sets. Used for: online presence, unique visitors per day, tag systems, friend intersections (SINTER).
List
Doubly-linked list. O(1) push/pop from both ends.
LPUSH feed:user:123 post:789 — prepend to feed.
LRANGE feed:user:123 0 19 — fetch first 20 items.
BRPOP queue:emails 30 — blocking pop (simple message queue). Used for: activity feeds, simple task queues, recent items lists. BRPOP pattern = lightweight job queue without Kafka overhead.
HyperLogLog
Probabilistic cardinality estimator. Counts unique items using ~12KB regardless of cardinality.
PFADD unique:visitors:2026-03-21 user:123 user:456
PFCOUNT unique:visitors:2026-03-21 — returns ~100M unique visitors using 12KB RAM. Error rate: ±0.81%. ✓ Count 1 billion unique visitors using 12KB. A HashSet for the same would need ~8GB. Used by: DAU metrics, unique video views, distinct IP counting.
Pub/Sub & Streams
Pub/Sub: fire-and-forget broadcasting. Streams: persistent, replayable event log (mini Kafka).
PUBLISH notifications:user:123 "New message from Alice"
XADD events * type view entity_id vid_abc — append to stream.
XREAD COUNT 100 STREAMS events 0 — read from stream. Pub/Sub: real-time notifications between app servers. Streams: durable event log for small-scale streaming (not a Kafka replacement at scale).

05 · System Design Examples

Caching decisions in real systems

Twitter / X — Social Feed
READ-HEAVY · FAN-OUT
FEED CACHE
Redis List ✓ Each user's pre-computed feed stored as a Redis List (LPUSH on new tweet, LRANGE for reads). Cache-aside with TTL=24h. 99% of feed reads are cache hits — the DB never sees them. Key: feed:user:{id}.
TWEET CONTENT
Redis String ✓ Individual tweet JSON cached as a String with TTL=1h. Celebrity tweets get longer TTL (>24h) because they're read millions of times. Key: tweet:{id}.
TRENDING
Redis ZSET ✓ Hashtag counts in a sorted set. ZINCRBY trending:1h #WorldCup 1 per event. ZREVRANGE trending:1h 0 9 returns top 10. Sub-millisecond at any scale.
INVALIDATION
User deletes a tweet → DEL tweet:{id} + rebuild affected feeds. TTL as safety net for stale data. Eventual consistency is acceptable — seeing a deleted tweet for 1 minute is tolerable for Twitter's use case.
E-Commerce — Product Catalog
WRITE-RARE · READ-HEAVY
PRODUCT PAGE
CDN + Redis ✓ Static product HTML cached at CDN edge (TTL=10min). Inventory count cached in Redis String with TTL=30s. CDN handles 95% of product page traffic. Redis handles inventory checks without hitting DB.
INVENTORY
Redis DECR ✓ DECRBY inventory:{sku} {qty} — atomic decrement. If result < 0, rollback: INCRBY inventory:{sku} {qty} and reject order. No DB needed for inventory check during purchase flow.
FLASH SALE
During a flash sale (10K requests/sec for one SKU), cache stampede risk is extreme. Solution: Redis lock (SET lock:{sku} 1 NX EX 5) + pre-warm cache 5 minutes before sale. Only the lock-holder refreshes the cache; others read stale value briefly.
06 · Decision Framework

Interview Framework — Scale & Strategy

🎯Caching Strategy — Answer These in Order
01
What is the read-to-write ratio?
Read-heavy (>10:1) →Cache aggressively. Cache-aside or read-through. High cache hit rate justifies complexity. Most social, e-commerce, and media systems fall here.
Write-heavy →Cache carefully. Write-behind for non-critical counters. Cache invalidation complexity may outweigh benefit. Consider whether caching actually helps.
02
Can you tolerate stale data? For how long?
Yes (seconds/minutes OK) →TTL-based invalidation. Simple, no code coupling. Social feed, product descriptions, user profiles — all tolerate seconds of staleness.
No (must be fresh) →Event-driven invalidation + write-through. Financial balances, inventory counts, seat availability — must be consistent. Use shorter TTL as safety net too.
03
What is your data structure need?
Simple key-value →Memcached (simpler, multi-threaded, pure LRU) or Redis String. Memcached is faster for simple string caching with multiple CPU cores.
Rich structures (sorted sets, counters, lists) →Redis. No contest. Sorted sets for leaderboards, atomic INCR for counters, Lists for queues, HyperLogLog for cardinality.
Persistence needed →Redis with AOF/RDB. Memcached is pure in-memory — no persistence. Redis can persist to disk and survive restarts.
04
What is the data size and access pattern?
Small hot dataset (<100GB) →Redis Sentinel. All data fits on one primary. Simple HA with automatic failover. No sharding complexity.
Large dataset or high write throughput →Redis Cluster. Horizontal sharding across multiple primaries. Scale both data size and write throughput. More operational complexity.
📋 · Requirements & Scale

Requirements & Non-Functional Constraints

Functional Requirements

FR1On every read, the system must check the cache before querying the database, and on a miss populate the cache with the fetched result so repeat reads for the same key stop paying the database round trip.
FR2The system must support write-through, write-behind, and refresh-ahead write strategies as interchangeable options, so a team can pick the consistency/latency trade-off that matches each specific data type's freshness requirement rather than using one strategy everywhere.
FR3The system must invalidate stale entries either via TTL expiry or by explicitly deleting/updating the affected key the moment the underlying data changes, so a read never surfaces indefinitely stale data after a write.
FR4The system must use the Redis data structure suited to each access pattern — Strings for simple values, Hashes for partial-field reads/writes, Sorted Sets for ranked/leaderboard data, Lists for ordered queues, HyperLogLog for approximate cardinality — instead of forcing every use case through a single generic key-value shape.
FR5The system must prevent a single popular key's expiry from triggering a coordinated flood of simultaneous database reads (cache stampede), typically via a mutex lock, request coalescing, or probabilistic early refresh.
FR6The system must support a two-tier cache — an in-process local cache for the hottest handful of keys in front of a shared distributed Redis tier — so the very busiest reads never leave the app server while the rest of the traffic still benefits from a shared cache.

Non-Functional Requirements

NFR1Design target: sustain a cache hit rate above roughly 95% for the hottest keys. The right bar depends entirely on your traffic's skew and cache size — state your own number and the reasoning behind it rather than quoting this as a platform guarantee.
NFR2Design target, consistent with independent Redis benchmarks: GET operations typically show p50 latency around 0.1ms and p99 under 1ms when Redis and the caller sit in the same datacenter/AZ — real end-to-end latency also depends on network hops and client-side overhead, so treat this as achievable, not guaranteed.
NFR3Design target you set and defend, not a vendor-given number: how long a freshly restarted or newly deployed cache is allowed to run at a degraded hit rate before pre-warming or a gradual traffic ramp brings it back to steady state.
NFR4Cache size is bounded by available RAM and the configured eviction policy (e.g. Redis maxmemory + maxmemory-policy) — this is a hard resource constraint, not a number to tune around.
NFR5Consistency is eventual by design: a stale-read window bounded by the TTL (or by however long an invalidation event takes to propagate) is an accepted trade-off, not a bug.
NFR6Design target, and one to tune deliberately rather than assume: Redis Sentinel's out-of-the-box defaults are considerably more conservative than "fast" — down-after-milliseconds defaults to 30s before a primary is even declared down, and failover-timeout defaults to 180s (3 minutes) as the outer bound for completing a failover. Sub-30-second failover is achievable but requires deliberately lowering both settings, not assuming the defaults deliver it.
07 · Interview Follow-ups

Every hard follow-up, answered

Redis is single-threaded — how does it handle 1M requests/sec?+
Redis's event loop is single-threaded for command processing, but that is actually its strength, not its weakness.

Since commands execute serially, there are no lock contention or deadlock issues. Redis commands are in-memory operations taking microseconds — the bottleneck is never CPU, it is always network I/O. Redis 6.0 added optional multithreaded I/O for reading and writing the network buffers (disabled by default, opt in with io-threads), while command execution itself stays single-threaded. Result: Redis's own published benchmarks show over a million SET/GET ops/sec on a single instance with pipelining on commodity hardware, and 100K+ ops/sec unpipelined is typical for simple GET/SET — the real number depends heavily on pipelining, payload size, and command mix, so don't quote a single figure without those caveats.

When you need more throughput than one instance gives you: Redis Cluster shards load across multiple independent single-threaded instances, so aggregate throughput scales roughly linearly with node count for well-distributed key access.
How do you handle cache consistency in a microservices architecture?+
This is one of the hardest distributed systems problems. Three patterns, in order of complexity:

1. TTL + eventual consistency: Each service caches with a short TTL (30s–5min). Stale data is guaranteed to expire. Simple, no coordination. Works for most social/media use cases where slight staleness is acceptable.

2. Event-driven invalidation: When Service A updates user data, it publishes a UserUpdated event to Kafka. Service B consumes the event and deletes/updates its cache. Consistent eventually. Risk: if the event is lost, cache stays stale indefinitely — mitigate with TTL as backup.

3. Cache ownership: Each data domain is owned by one service. Other services must call that service's API to read data — they cannot cache it themselves. Eliminates invalidation problem entirely at the cost of added latency on every cross-service read.
What is the difference between Redis and Memcached? When do you pick each?+
Memcached is a simpler, faster, multi-threaded string cache. Redis is a full data structure server.

Pick Memcached when: You need pure key-value string caching, you have a multi-core server and want to saturate all cores (Memcached is truly multi-threaded), you do not need persistence or replication, and you want the absolute simplest operational footprint.

Pick Redis when: You need any data structure beyond strings (sorted sets, lists, hashes), you need atomic operations (INCR, LPUSH), you need persistence (AOF/RDB for crash recovery), you need Pub/Sub or Streams, or you need built-in replication and cluster mode.

In practice at FAANG: Redis has won. The operational overhead of maintaining two different cache systems (Redis for rich structures, Memcached for simple caching) is rarely worth the marginal performance difference. Most teams standardize on Redis for everything.
How does Redis persistence work — RDB vs AOF?+
Redis has two persistence mechanisms that can be used independently or together.

RDB (Redis Database Backup): Point-in-time snapshot written to disk periodically (every N seconds if M keys changed). Fast to restore — single compact binary file. Risk: data since last snapshot is lost on crash. Used for: disaster recovery, backups, cache warm-up after restart.

AOF (Append-Only File): Every write command is appended to a log file. On restart, Redis replays the log. Three fsync options: always (safest, slowest), every second (good balance — max 1 second data loss), never (OS decides, fastest). AOF rewrite periodically compacts the log. Used for: when you cannot afford data loss.

Recommendation: Use both for critical data — RDB for fast restarts + AOF for durability. For pure cache use cases where data can be reconstructed from the DB, disable persistence entirely for maximum performance.
08 · Advanced Patterns

Cache stampede, thundering herd, and warming — the failure modes interviewers test

The newspaper analogy
Imagine a newspaper stand where 1,000 people want the morning paper. The stand runs out at 8am. Now all 1,000 people simultaneously go to the printing press to get copies — overwhelming the press that was only designed for one delivery truck.

Cache stampede: your cache entry expires → 1,000 concurrent requests all miss the cache → all hit the database simultaneously → database collapses under load. The cache was protecting the DB; when it expires, that protection evaporates instantly.
01 Cache Stampede Prevention
What it is
Four strategies, in order of complexity:

1. Mutex/Lock (simplest): when cache miss detected, acquire a Redis distributed lock for that key. Only one request rebuilds the cache; others wait. On rebuild complete, release lock. Others get the freshly cached value.

result = cache.get(key)

if not result:

  if redis.set(f"lock:{key}", 1, nx=True, ex=30):

    result = db.query(); cache.set(key, result)

  else: time.sleep(0.1); result = cache.get(key)

2. Probabilistic early expiry: before TTL expires, each request has a small probability of refreshing early. At TTL-30s: 1% chance of refresh. At TTL-5s: 50% chance. Refresh happens without blocking other requests. The first probabilistic refresh populates the cache before expiry.

3. Background refresh: a background thread monitors keys approaching expiry. At 80% of TTL, asynchronously refresh. Cache never actually expires for live traffic. Serves stale data for milliseconds during the async refresh — acceptable for most use cases.

4. Stale-while-revalidate: return the expired value immediately (stale), trigger async refresh in the background. HTTP Cache-Control header: max-age=60, stale-while-revalidate=30. Zero latency impact on the user.

02 Thundering Herd — Facebook's "Leases" Mechanism
What it is
The industry-standard fix for thundering herds, documented in Facebook's 2013 NSDI paper "Scaling Memcache at Facebook."

The general pattern: a hot key undergoes heavy concurrent read and write activity, or expires while under heavy read load, and every client that misses goes to the backing store (MySQL) at once. Facebook's published fix — leases: when memcached serves a cache miss, it also hands the requesting client a lease token, and rate-limits how often it hands out a new token for the same key — the paper describes a default of once every 10 seconds per key. Any other client that misses on that key within the window gets told to wait a short time instead of being allowed to query the DB; the lease holder is expected to populate the value within milliseconds. The same mechanism doubles as a fix for "stale sets": a lease token is invalidated if a delete arrives for that key while the lease is outstanding, so a slow writer can't clobber a fresher value.

The paper reports this mechanism, together with a related "stale value" strategy, cutting peak database load from roughly 17,000 queries/sec to about 1,300 queries/sec during a stress test of a real thundering-herd scenario at Facebook's scale — a concrete, published number worth citing directly instead of inventing your own.

✓✓ The lesson: cache stampede is a systemic failure mode, not a code bug. It requires architectural solutions (leases, background refresh, mutex) — not faster code. Redis doesn't ship leases natively, but the same idea is implementable with SET key val NX EX ttl as a coarse-grained lock.
03 Cache Warming (Cold Start Problem)
What it is
A freshly deployed cache has 0% hit rate. All traffic hits the DB until the cache warms up.

Scenarios: new deployment, Redis restart after failure, new Redis cluster added for scaling.

Warming strategies:

(1) Pre-warm from DB: before cutover, run a job that reads the top-1000 most-accessed keys from DB analytics → populates cache. Used when you know the hot set.

(2) Shadow traffic: replay production traffic against the new cache instance before switching. Cache warms from real traffic patterns without affecting users.

(3) Gradual ramp: route 1% of traffic to the new cache → 5% → 25% → 100%. Cache gradually warms. DB handles the slightly elevated load at each step. Never a cold-start cliff.

(4) Dual-write: write to both old and new cache for 1 hour before switching reads to new cache. New cache is warm before any reads are sent to it.

04 Local Cache + Distributed Cache Hybrid
What it is
Two-tier caching: L1 in-process cache (nanoseconds) + L2 Redis (milliseconds).

In-process cache: a Guava LoadingCache or Caffeine cache on each application server. Stores ~1,000 ultra-hot entries. Access time: 100ns (no network). Limited to what fits in one server's RAM.

Redis: distributed, shared across all app servers. Stores millions of entries. Access time: 0.5–1ms (network round trip).

Pattern: request → check L1 (Caffeine) → hit: return (100ns). L1 miss → check L2 (Redis) → hit: populate L1, return (1ms). L2 miss → query DB → populate L2 + L1, return (10ms).

✓✓ Used by: Uber (two-tier caching for driver surge multipliers), Netflix (local cache for frequently-accessed config), Facebook (mcrouter handles two-tier Memcached). The key: L1 is per-server and inconsistent across servers — only safe for data where staleness within a few seconds is acceptable.
05 Redis Cluster vs Redis Sentinel
What it is
Sentinel: HA for a single Redis instance. Cluster: horizontal scaling across multiple Redis nodes.

Redis Sentinel: 3+ sentinel processes monitor 1 Redis primary + N replicas. If primary fails, sentinels elect a new primary in ~30 seconds. No data sharding — all data on one primary. Right for: high availability on a single dataset that fits in one machine's RAM.

Redis Cluster: data sharded across 3+ primaries using 16,384 hash slots. Each primary has replicas. If a primary fails, its replica is promoted. Right for: datasets too large for one machine, or write throughput too high for one primary.

→Common mistake: using Redis Sentinel when you actually need Redis Cluster (dataset is 500GB, single primary is the bottleneck). And vice versa: using Redis Cluster for a 2GB dataset that one primary handles fine — added operational complexity for no benefit.
06 Hot Key / Hot Partition
What it is
One key gets far more traffic than the sharding scheme was designed for, and consistent hashing can't fix it — it only decides which single shard absorbs the whole spike.

A celebrity's profile, a viral post, a single flash-sale SKU, or a globally-shared config key can drive orders of magnitude more requests per second than any other key. Redis Cluster and Memcached both shard by key, so all of that traffic lands on one node no matter how evenly the rest of the keyspace is distributed — the node saturates its CPU or network link while every other shard sits idle. This is a fundamentally different failure from cache stampede: the cache is still serving hits, but one physical node can't keep up with the request rate for a single logical key.

Detection: per-key or per-shard traffic monitoring (Redis MONITOR in short bursts, or slot-level metrics in Redis Cluster / Enterprise) showing one node's CPU or ops/sec far above its siblings while aggregate cluster load looks unremarkable — the classic false signal is "the cluster looks healthy on average" while one node is pegged.

✓✓ Fixes, roughly in order of how often they're used: (1) local/L1 caching of just the hot keys on each app server, so the shard only sees a fraction of the traffic (the two-tier pattern above); (2) key splitting — replicate the hot value under N suffixed keys (product:sku123:0..:9) and pick one at random on read, trading a little staleness risk for spreading load across N shards; (3) client-side or proxy-side (mcrouter, Twemproxy) request coalescing so concurrent reads for the same key collapse into one backend call.
