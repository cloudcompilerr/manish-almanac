The general contractor analogy
Shipping a GenAI feature is like building a custom house. The architecture firm (orchestration layer) draws the plan and coordinates every trade. Subcontractors (foundation models) do the specialized work — framing, electrical, plumbing — but none of them knows what the house next door looks like, and swapping the electrician shouldn't require re-pouring the foundation. The materials supplier (the RAG/data layer) has to deliver the right lumber and wiring on schedule, or the crew stands around with nothing to build. A universal permit and inspection standard (protocols like MCP) means any subcontractor can plug into any job site without a bespoke contract negotiated from scratch each time. And a building inspector (LLMOps, guardrails, and evaluation) signs off at every stage — foundation, framing, final walkthrough — because nobody wants to discover the wiring was unsafe after the family has moved in. Skip the inspector to ship faster, and the failures don't disappear — they just show up later, as fires instead of punch-list items.
⚠ The interview trap

Candidates who open a system design answer by reciting all ten layers regardless of what's actually being asked get cut off fast. A two-person startup shipping an MVP support chatbot doesn't provision a low-code automation layer, a dedicated protocol layer, and a full LLMOps firewall on day one — those are layers you add as team size, traffic, or compliance surface grows, not layers you default to. The strong answer names the one or two layers that are actually load-bearing for the specific ask, and explicitly defers the rest with a stated trigger for when they'd get added — e.g., "I'd skip a dedicated protocol layer until we have more than one team building tools independently; hand-wired integration is fine below that." Listing the full stack for every question signals template memorization, not judgment.

01 Application & Presentation Layer

The Edge

Angular, React, Vercel AI SDK, Streamlit, Gradio, Chainlit.
What It Means

The frontend user experience and API gateway topology that manages user sessions, downstream system state, and asynchronous streaming connections (Server-Sent Events).

Why It's Needed

Raw LLM token outputs have high time-to-first-token (TTFT) latency. This layer streams responses character-by-character to reduce perceived latency, handles WebSocket channels for real-time human-in-the-loop interventions, and dynamically renders AI-generated artifacts (like structured JSON converted into UI charts or components).

02 Orchestration & Agentic Logic

The Brain

LangChain, LlamaIndex, DSPy, CrewAI, AutoGen, LangGraph, Spring AI, LangChain4j.
What It Means

The execution middleware that chains prompts, contextual memory, tool bindings, and stateful multi-step LLM calls into a programmatic workflow.

Why It's Needed

Foundation models are stateless text predictors. Orchestration frameworks give them memory, handle state machines for multi-agent collaboration (e.g., planner, actor, critic), translate native code execution or system APIs into "function calling," and manage complex retry/fallback logic when an upstream API model fails.

03 Low-Code Automation & Workflows

The Democratization Layer

n8n, Flowise, LangFlow, Make.com AI, Dify.
What It Means

Visual drag-and-drop nodes and event-driven automation interfaces that wrap around code blocks, external webhooks, and AI prompts.

Why It's Needed

It bridges the gap between software engineers and product/data operations teams. Instead of hardcoding simple prompt schedules, routing logic, or third-party CRM syncs inside the core codebase, this layer allows rapid pipeline prototyping and business-logic adjustments without triggering full deployment cycles.

04 Data, Memory & RAG Engine

The Context Window

pgvector, Pinecone, Qdrant, Milvus, Unstructured.io, LlamaParse, GraphRAG (Neo4j), Docling.
What It Means

The indexing, document chunking, and semantic vector retrieval infrastructure that matches user queries against a private corporate knowledge base.

Why It's Needed

General-purpose LLMs lack access to private data and hallucinate when their pre-training context fails. This layer chunks complex, multi-modal documents (PDFs, DB tables), passes them through embedding models, and surfaces the exact semantic context inside a vector search, allowing the LLM to provide verified, grounded answers.

05 Model Access & Gateways

The Router

LiteLLM, OpenRouter, Portkey, Hugging Face Hub.
What It Means

Hubs for discovering open-weight models, and unified API gateways for routing across different commercial providers.

Why It's Needed

Hard-coding an application to a single vendor API is a massive liability as pricing shifts and stronger models ship monthly. This layer abstracts the provider into a configuration value, preventing codebase rewrites.

06 Protocols

The Connective Tissue

Model Context Protocol (MCP), A2A.
What It Means

Open standards defining how an agent reaches an external tool, and how two agents reach each other.

Why It's Needed

Before protocols, every framework required hand-written integration for every tool and every other agent — an M-tools × N-frameworks problem. Protocols like MCP standardize these connections, including across the Python/Java boundary itself.

07 Model Serving & MaaS

Model-as-a-Service

AWS Bedrock, Azure OpenAI, GCP Vertex AI, Groq, vLLM, Hugging Face TGI, Ollama.
What It Means

The infrastructure abstraction layer where foundation models are hosted, whether accessed via fully-managed multi-tenant cloud endpoints or self-hosted on private hardware.

Why It's Needed

Running deep learning models requires massive compute optimization. MaaS (e.g., AWS Bedrock, Groq) abstracts away raw GPU node management, eliminates cold starts, and provides instant scalability via pay-per-token consumption. For custom or fine-tuned weights where data cannot leave the firewall, self-hosted serving engines (like vLLM) perform tensor parallelism, continuous request batching, and high-throughput token compression instead.

08 Foundation Models

The Cognitive Core

GPT-5.x, Claude Opus/Sonnet, Gemini 3.x, Llama 4, Mistral, DeepSeek V3/V4.
What It Means

The base neural networks trained on internet-scale corpora, separated into proprietary APIs and open weights.

Why It's Needed

This is the primary engine for reasoning, translation, and structured output formatting. Selecting a model is a permanent balancing act: proprietary models (GPT-5.x, Claude Opus/Sonnet) offer state-of-the-art coding and math reasoning, while open weights (DeepSeek V3/V4, Llama 4) allow for zero-licensing overhead, infinite fine-tuning control, and local deployment. Worth tracking: as of mid-2026, Meta's own actively-developed flagship (Muse Spark, announced April 2026 via its new Meta Superintelligence Labs group) is closed, not open-weight — a real strategic reversal from the Llama era. Llama 3/4 weights remain available and deployable, but they're now a legacy open-weight snapshot rather than Meta's current frontier; DeepSeek is the more actively-updated open-weight option for this layer as of this writing.

09 LLMOps, Telemetry & Guardrails

The Production Firewall

LangSmith, Arize Phoenix, NeMo Guardrails, PromptLayer, Datadog LLMOps, Promptfoo.
What It Means

Runtime monitoring, system observability, prompt filtering, and policy enforcement tools sitting between application code and the LLM API endpoints.

Why It's Needed

You cannot manage what you do not measure. This layer tracks token consumption costs, monitors request/response latencies, logs full execution traces (so you can see why an agent went loop-crazy), and acts as an inline firewall to dynamically intercept and strip out PII, malicious prompt injections, or toxic generations before they reach an end user.

10 Automated Model Evaluation

The Quality Assurance Layer

Ragas, DeepEval, TruLens, G-Eval, Spring AI Evaluator.
What It Means

Frameworks dedicated to programmatically scoring the quality, accuracy, toxicity, and retrieval relevance of an AI system using automated "LLM-as-a-judge" paradigms.

Why It's Needed

Traditional unit testing fails in non-deterministic AI systems. If you tweak a system prompt or change a RAG chunk size, you risk breaking downstream behaviors. This layer runs synthetic data test suites to calculate exact metrics like faithfulness (did the LLM invent facts?), answer relevance (did it answer the prompt?), and context precision (did the search pull the right data?), guaranteeing regressions are caught before production deployment.

🏗 Production Reference Architectures

Three topologies, three driving forces

The same ten layers, assembled three different ways — each assembly driven by a different non-negotiable constraint.
Topology 1 — The High-Throughput Enterprise Engine
E2E Stack

Angular UI → Apache Kafka → Spring AI & Spring Batch → MCP (@McpTool) → pgvector (PostgreSQL) → Claude Opus/Sonnet via AWS Bedrock → Datadog LLMOps.

Use Case

Processing 500,000+ daily asynchronous order transactions, inventory tracking, and streaming data intelligence.

Driving Selection Forces
  • Type-safety & resiliency: the existing backend microservices architecture demands compilation-time verification. Spring AI integrates directly into existing corporate security configurations without adding separate Python infra complexity.
  • Asynchronous scalability: Kafka functions as the heavy buffer. Spring Batch reads order streams from high-partition Kafka clusters, processing heavy analytical payloads concurrently using Java 21 virtual threads (or Spring WebFlux) for non-blocking LLM API calls.
  • Data consolidation: pgvector lets the team keep operational transactional data and vector search indexes in the same PostgreSQL engine (ACID-compliant), avoiding the CAP-theorem overhead of a separate standalone vector store.
  • MaaS (AWS Bedrock): chosen for enterprise SLA compliance, strict ISO/SOC data privacy boundaries, and predictable pay-per-token pricing that eliminates hardware operational expense.
Topology 2 — The Agentic Research & Prototyping Loop
E2E Stack

Streamlit UI → HTTP/REST sync → LangGraph & CrewAI → MCP → Pinecone & LlamaParse → GPT-5.x native API → LangSmith evaluation.

Use Case

A multi-agent network where independent AI personas (Researcher, Writer, Compliance Critic) execute complex cyclic loops to plan, retrieve, match, and self-correct financial compliance reports.

Driving Selection Forces
  • Graph-based state management: multi-agent collaboration is inherently non-deterministic and cyclic. LangGraph treats the workflow as a stateful directed graph, using a checkpointer to save state at every node, enabling fine-grained agent rollbacks and human-in-the-loop approvals.
  • Bleeding-edge parsing depth: standard flat RAG fails on tables. LlamaParse is selected because the system must extract intricate tabular schemas from complex PDF financial statements, then route them to specialized sub-agents that can reason over rows and columns.
  • Deep execution traceability & tool precision: multi-agent loops can spiral into infinite API call chains. GPT-5.x is chosen for its strict JSON-mode tool-binding reliability, while LangSmith is mandated to give developers clear, granular visual traces of every step in the prompt chain — to debug loops and control cost.
Topology 3 — The Sovereign On-Premises Fortress
E2E Stack

React UI → RabbitMQ → Haystack / LlamaIndex → MCP (local) → self-hosted Milvus → vLLM serving an open-weight model (DeepSeek V4 or legacy Llama 4 — Meta's own current flagship, Muse Spark, is closed-weight as of April 2026) → Arize Phoenix & NeMo Guardrails.

Use Case

High-security defense, healthcare, or air-gapped banking applications handling sensitive data that requires zero external API calls.

Driving Selection Forces
  • Data sovereignty: zero tolerance for third-party API exposure. All weights, parsers, and vector stores are hosted entirely within local corporate data centers via Kubernetes, ensuring no SaaS telemetry leaks.
  • High-throughput local serving performance: vLLM is selected over simple local runtimes because it uses PagedAttention. By paging the key-value (KV) cache, it drastically minimizes GPU memory fragmentation and pushes throughput well above naive Hugging Face Transformers on local server racks.
  • Sovereign guardrails: because open models lack the built-in ethical/safety filtering of commercial counterparts, NeMo Guardrails is implemented as a hard policy intercept layer directly on top of the model endpoints, applying rule-based and vector-similarity checks to hard-stop generation if PII or disallowed topics are detected.

⚠ Failure Modes

What actually breaks in production

Real incident patterns across this stack — not a specific fabricated outage, but the shape production failures in each of these layers actually takes.
Silent gateway drift

The whole point of Layer 5 (model gateways like LiteLLM/Portkey) is that swapping providers is a config change. The failure mode is the same abstraction cutting the other way: a provider silently changes a model's default sampling behavior, deprecates an endpoint, or degrades under load, and because every call routes through one shared gateway config, the blast radius is every feature at once — not one team's isolated incident.

Fix: pin exact model versions (not floating aliases) in the gateway config, run a small canary eval suite against the pinned version on every gateway config change, and alert on latency/error-rate/output-shape drift per model id, not just per endpoint.

Orchestration loops that don't terminate

Layer 2's planner/actor/critic pattern and Layer 6's tool-calling protocols make it easy for an agent to call the same tool repeatedly with slightly different parameters, never converging — burning tokens and API budget with nothing to show for it. This is especially common when a tool's description is ambiguous enough that the model can't tell whether its last call actually succeeded.

Fix: hard step-count and wall-clock limits per agent run, loop detection on repeated tool calls with near-identical arguments, and mandatory spend caps tied to the calling identity — not just the account.

Embedding-index mismatch after a silent redeploy

Layer 4's RAG engine depends entirely on every vector in the index coming from the same embedding model. If a deploy bumps the embedding model version without a full re-embed of the corpus, the index now holds vectors from two incompatible semantic spaces — retrieval doesn't error, it just quietly returns worse and worse results, which is far harder to catch than a hard failure.

Fix: version-tag every vector with the embedding model id that produced it, and make the deploy pipeline refuse to serve a mixed-version index — either block the deploy until re-embedding finishes, or route queries only to the fully-migrated shard.

Guardrail false-positive cascades

Layer 9's PII/content filters are a hard stop by design — that's the point. But an overly aggressive filter tuned for one use case (say, blocking anything that looks like a SSN) can silently truncate or reject legitimate output in an adjacent use case (a support agent quoting a case number in the same numeric format), and because the block happens post-generation, the user just sees a degraded or empty response with no visible error.

Fix: log every guardrail intervention with the rule that fired, track false-positive rate as its own monitored metric (not just "did we block something"), and route borderline blocks to a caveat instead of a silent hard stop.

Tying it together

None of the ten layers exist in isolation, and none of the three topologies are "more correct" than the others — each is the same stack reshaped around one non-negotiable constraint: throughput and type-safety for the enterprise engine, traceable agentic reasoning for the research loop, and data sovereignty for the air-gapped fortress. The job isn't picking the single best tool at each layer; it's naming the constraint first, then letting it pick the stack.

The Rosetta Stone exists for the same reason: Python and Spring/Java aren't competing answers to "how do you build GenAI systems" — they're the same ten-layer architecture, expressed in whichever ecosystem your organization's existing engineering investment already lives in.
