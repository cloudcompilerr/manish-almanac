01 · Mental Model

Tokens, Roles & Temperature

Every Claude API call, in either stack, is built from the same five ingredients.

Token
The atomic unit an LLM actually sees — roughly ¾ of a word on average. Every dollar and millisecond in this course is measured in tokens, not characters.
System Role
Sent once per conversation, defines persona and constraints. Spring AI: .system("..."). LangChain: SystemMessage(content="..."). This is where EngOrgAI's "concise, director-facing" personality lives.
User Role
The actual ask. Spring AI: .user("..."). LangChain: HumanMessage(content="...").
Temperature
Controls randomness. 0 = deterministic, repeatable, factual — what an engineering-leadership assistant needs. Higher values trade consistency for creativity.
Usage Metadata
Every response carries back prompt/completion/total token counts — the foundation for cost tracking, latency monitoring, and, as this module proved, catching API hallucinations through compilation rather than assumption.

04 · Real Decisions

Four Decisions That Shaped Module 1

01The CostAwareResponse Hallucination
What happened
A Spring AI response wrapper called CostAwareResponse was suggested for token tracking. It doesn't exist — a fabricated class name that failed at compile time the moment it was tried.

The real, verified pattern: chain .call().chatResponse(), then read response.getMetadata().getUsage() for prompt/completion/total token counts. No custom wrapper needed.

✓The lesson: validate against real compiled behavior, not assumed APIs — especially for fast-moving libraries where method signatures change between versions.
02Switching Mid-Build: M2 Milestone → 2.0.0 GA
What happened
The course originally targeted Spring AI 2.0.0-M2, a pre-release milestone. Mid-Module-1, a version check revealed Spring AI 2.0.0 GA shipped June 12, 2026 — built on Spring Boot 4.1 / Spring Framework 7 / Jackson 3 — with Spring Boot 3.5 reaching end-of-life June 30, 2026, just 18 days later.

Verdict: rebuild the project skeleton on Boot 4.1 + Spring AI 2.0 GA before writing further module code, rather than build fresh on a stack with zero forward runway.

→This is the kind of judgment call a real engineering team makes constantly: a fresh build should target the currently-supported baseline, not whatever was true when the plan was first written.
03One Shared AiConfig, Not One Per Capstone
The decision
EngOrgAI's original v0.1 skeleton called for its own AiConfig.java. Instead, a single ChatClient bean lives in com.manish.config.AiConfig — built once, injected everywhere.

Every module and capstone service receives a ready-made ChatClient via constructor injection — no duplicated client construction, one place to add cross-cutting concerns as the course reaches RAG and tool calling.

04Python Syntax Notes: A Companion File, Not Comments
The decision
New to Python, strong in Java. Rather than clutter production-grade Python files with beginner-syntax comments, every code block gets a short syntax-notes table — decorators, dict literals, type hints — anchored to the Java equivalent, written to a separate companion file: python/PYTHON_SYNTAX_NOTES.md.
✓The codebase stays interview/portfolio-clean; the learning trail stays fully intact, just in its own file.
