00 · Why Rate Limiting

What breaks without it

Without rate limiting: one bad actor (or a bug in a client) sends 100K requests/second to your API. Your database collapses. Every other user is impacted. Rate limiting is the first line of defence — it protects your system from both malicious abuse and accidental overload.

Real examples of why this matters

Stripe: Charges per API call. A bug in customer code loops 10K calls/sec. Without rate limiting: customer pays $10K/sec unexpectedly AND Stripe's infra is impacted.

Twitter API: 300 requests per 15-minute window per user. Prevents scrapers from harvesting all tweets while ensuring legitimate app developers can build.

Payment APIs: Max 10 login attempts per minute per IP. Prevents brute-force credential stuffing attacks.

01 · The Four Algorithms

Token bucket, leaky bucket, fixed window, sliding window log

Token Bucket
A bucket holds up to N tokens. Tokens refill at rate R per second. Each request consumes 1 token. No tokens = rejected.
Example: bucket capacity=100, refill rate=10/sec. A burst of 100 requests is allowed immediately (uses all tokens). Then max 10/sec until refilled.
✓ Allows bursts up to bucket size. Smooth average rate enforcement. Memory: O(1) per user (just store token count + last refill time).
⚠ Allows requests at exactly the boundary — two full bursts are possible at the start and end of a window.
Used by: AWS API Gateway, Stripe, most REST API rate limiters. The industry standard algorithm.
Leaky Bucket
Requests enter a queue (the bucket). They are processed at a fixed rate (the leak). If the queue is full, requests are dropped.
Example: process 10 requests/sec regardless of how many arrive. Smooths out bursts entirely.
✓ Perfectly smooth outbound rate. No bursts. Protects downstream services from traffic spikes.
⚠ Bursts are queued, not served fast — legitimate spikes experience latency, not rejection. If queue fills, recent requests are dropped even if earlier ones were slow.
Used by: traffic shaping in networking, protecting database connection pools.
Fixed Window
Count requests per fixed time window (e.g., per minute). Reset counter at window boundary.
Example: 100 requests/minute. Counter at 14:03:00 resets at 14:04:00.
✓ Simplest to implement. INCR counter:user:minute:1403 in Redis.
⚠ Boundary attack: 100 requests at 14:03:59 + 100 requests at 14:04:01 = 200 requests in 2 seconds (both within their respective windows). Actual rate is 2x the limit at the window boundary.
Sliding Window Log
Store a timestamp log of every request. For each new request, count logs in the last N seconds. Reject if count exceeds limit.
Redis: ZADD log:user:123 {timestamp} {timestamp}. ZREMRANGEBYSCORE log 0 (now-window). ZCARD log = request count.
✓ Perfectly accurate. No boundary attack. Truly enforces the rolling window.
⚠ Memory: O(requests) per user. At 1000 req/min and 1M users, that is 1 billion log entries. Only practical for low-rate, critical endpoints (login, payment).
Sliding Window Counter
Hybrid: fixed window counters with interpolation to approximate sliding window. Best of both.
Store counter for current window and previous window. Weighted estimate:
count = prev_window * (1 - elapsed/window_size) + curr_window
✓ O(1) memory. Accurate enough (Cloudflare uses this — they found <0.003% of requests are incorrectly rate-limited). The practical production choice.
Used by: Cloudflare, most high-scale rate limiting systems.
02 · Distributed Rate Limiting

How to rate limit across 100 app servers

The core challenge

Each app server sees only its fraction of total traffic. If you rate-limit locally (100 req/min per server × 100 servers = 10,000 req/min global), your rate limit means nothing. You need a shared counter that all servers update atomically.

Redis INCR Pattern
The standard approach: shared Redis counter with atomic increment.
MULTI
INCR ratelimit:{user_id}:{window}
EXPIRE ratelimit:{user_id}:{window} 60
EXEC
If result > limit → reject with 429. Redis's single-threaded INCR is atomic — no race conditions.
✓ Simple, correct, fast (<1ms). Works for token bucket too: Lua script atomically checks and decrements token count.
Redis Lua Script
For token bucket — atomically check and decrement in one round trip.
local tokens = redis.call('GET', KEYS[1])
if tokens and tonumber(tokens) > 0 then
redis.call('DECR', KEYS[1]); return 1
else return 0 end
✓ Lua scripts execute atomically in Redis — no race between check and decrement. Libraries like redis-rate-limiter use exactly this.
Local Approximate
+ Sync
Each server maintains a local counter, periodically syncing to Redis.
Each server allows up to limit/N requests locally (N = server count). Every 100ms, sync actual count to Redis and refresh local quota.
✓ Reduces Redis calls by 100x. Much more scalable for high-throughput APIs.
⚠ Up to 100ms window where slightly over-limit requests are allowed. Acceptable for most use cases.
03 · System Design Examples

Rate limiting in real systems

API Gateway Rate Limiting
MULTI-DIMENSIONAL
PER USER
Token Bucket ✓ 1000 req/min per authenticated user. Key: ratelimit:user:{id}:minute. Allows legitimate burst traffic (developer hitting API in a loop) while preventing abuse.
PER IP
Sliding Window ✓ 100 req/min per IP for unauthenticated requests. Stops credential stuffing (many login attempts from same IP). Key: ratelimit:ip:{hash(ip)}:minute. Hash the IP to avoid storing raw IPs (privacy).
PER ENDPOINT
Different limits per endpoint: POST /login = 5/min, GET /feed = 300/min, POST /payment = 10/min. The sensitivity of the endpoint determines the limit.
RESPONSE HEADERS
Always return: X-RateLimit-Limit: 1000, X-RateLimit-Remaining: 743, X-RateLimit-Reset: 1742383200. Clients use these to back off gracefully before hitting 429.
Notification System
SPAM PREVENTION
PER USER/CHANNEL
Max 2 SMS per user per 10 minutes. Max 5 emails per user per hour. Max 10 push notifications per user per day. Multi-dimensional limits using separate Redis counters per dimension: ratelimit:sms:{user}:10min.
GLOBAL SEND RATE
Email provider (SendGrid) limits to 100K emails/hour. Token bucket at the sender level: fill 100K tokens/hour, each email consumes 1. If empty → queue for next hour window rather than dropping.
04 · Decision Tree

Which algorithm to pick

🎯Rate Limiting Algorithm Selection
01
Do you need to allow bursts?
YES (burst OK) →Token Bucket. Accumulates tokens when idle, releases in bursts. Standard for REST APIs. Stripe, AWS, Twilio all use token bucket.
NO (strict smooth rate) →Leaky Bucket. Enforces exactly R requests/second with no bursting. Use for protecting downstream services that can only handle a fixed rate.
02
How important is precision vs simplicity?
Precision critical →Sliding Window Log. Perfectly accurate but O(req) memory per user. Only use for high-value low-rate endpoints (login, payment, account creation).
Balanced →Sliding Window Counter. 0.003% inaccuracy, O(1) memory. Production choice for most high-scale systems. Cloudflare's approach.
Simplicity first →Fixed Window. Single Redis INCR. Boundary attack is acceptable if limits are conservative (set limit 2x lower to account for the boundary doubling).
03
What is the enforcement layer?
API Gateway →Rate limit at the gateway (Kong, AWS API Gateway, Envoy). Centralized, language-agnostic, enforced before traffic hits your services.
Application level →Redis-backed middleware in your service. More granular (can access business logic for tiered limits). Used for per-feature or per-plan limits.
Service mesh →Istio/Envoy sidecar proxies enforce rate limits between services. Used for internal service-to-service rate limiting in microservice architectures.
05 · Follow-ups

Every hard follow-up, answered

How do you handle rate limiting for distributed clients — e.g., a user calling from multiple devices?+
Rate limit on the authenticated user identity (user_id from JWT), not on the device or IP.

The user_id is consistent across all their devices. The Redis key ratelimit:user:{user_id}:{window} is incremented by every request regardless of which device or IP it comes from. This means a user signing in on phone + laptop + tablet all share the same quota — preventing circumvention by using multiple devices.

IP-based limiting is additive and separate — it is used for unauthenticated endpoints (login page, signup) to prevent automated attacks before authentication.
What happens if the rate limit store (Redis) goes down?+
You have two choices and you must pick one explicitly — there is no "right answer," only a trade-off.

Fail open (allow all traffic): If Redis is unavailable, do not rate limit. 100% of requests are served. Risk: abuse during the outage window. Appropriate when: availability is more important than abuse prevention (most consumer APIs).

Fail closed (reject all traffic): If Redis is unavailable, reject with 429 or 503. No abuse during outage. Risk: legitimate users are blocked. Appropriate when: abuse has high cost (payment APIs, authentication endpoints).

In practice: Use local fallback counters. Each app server tracks its own count. If Redis is down, enforce limit/N per server (N = server count). Slightly inaccurate but functional. Redis sentinel/cluster with automatic failover ensures outages are rare and brief.
How do you implement tiered rate limits (free vs pro vs enterprise)?+
Store the user's tier in their JWT or a fast lookup cache, then apply tier-specific limits.

Approach:
1. JWT contains "tier": "pro" — decoded at the rate limit middleware with zero extra lookups.
2. Tier → limit mapping stored in config: {"free": 100, "pro": 1000, "enterprise": 100000}
3. Rate limit key includes tier for isolation: ratelimit:{tier}:{user_id}:{window}

Why include tier in the key: so upgrading from free to pro immediately gives the new limit without needing to reset the counter. The free counter is simply no longer checked.

For enterprise customers with custom limits: store their limit in Redis itself: ratelimit:config:{user_id} = their custom limit. Fallback to tier default if not set.
